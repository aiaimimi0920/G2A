# G2A 公开游戏交互协议：标准工作草案

修订：`standard-review-2026-11-13`。状态：**供审查的完整语义草案，不是已发布 wire 版本，不是 SDK 符合性声明**。

本草案按用户于 2026-11-13 明确的方向组织：先设计一套独立、公开、可由不同厂商实现的游戏与 AI 伙伴交互标准，再实现 SDK。Mot 是该标准与参考实现的项目入口；G2A 是游戏交互协议。桌面宠物、模型提供商、记忆数据库与 Mot 应用都不是接入前提。

## 0. 效力、范围和阅读方式

本文不是把旧 SDK 升级成新标准，也不抹除 `g2a-design-1` 的设计。它将现有设计组织为可审查的标准，并补充游戏信息语义、最低绑定和符合性要求。

- **沿用**：角色、授权交集、独立身份、行动未知效果、事件受众、恢复与扩展边界，以本文件及下列现有细化契约为审查基线。
- **新增候选**：第 6 节的观察 profile、第 11 节的 HTTP 最低绑定明确化、第 14 节的规范声明矩阵。候选尚未进入现有机器契约或 SDK，不能发送给旧端点。
- **冲突规则**：已部署 `0.1.0-dev` 仍由旧规范约束；本候选不追溯修改它。本文新增候选与 `g2a-design-1` 字段不兼容时必须显式列入迁移表，不允许实现者自行混合。
- 本文“必须/MUST”“不得/MUST NOT”“应该/SHOULD”“可以/MAY”采用 RFC 2119/8174 的规范含义。要求编号是审查标识，不是线上字段。
- **完整语义草案**表示各责任面与失败路径已有可讨论的设计，不表示字段 schema 冻结、互通证明完成、没有遗漏或获得国际标准地位。

## 1. 协议要解决什么

G2A 规定：一个经玩家选择的 AI 伙伴进入一个游戏后，双方怎样发现能力、验证身份、协商信息、授权行动、沟通、退出及从失败中恢复。

必须分开五个问题：

| 问题 | 决定者 | 协议表示 | 不意味着 |
| --- | --- | --- | --- |
| 伙伴需要知道什么 | 伙伴表达需求，游戏决定能否满足 | 所需/可选观察类别与质量需求 | 需求自动获得权限 |
| 游戏能够提供什么 | 游戏能力声明 | 可提供观察、行动及约束 | 已允许该伙伴使用 |
| 伙伴被允许知道什么 | 游戏当前公开规则与玩家有效同意共同约束 | 冻结授权范围 + 当前视野/受众过滤 | 可以读全部世界状态 |
| 伙伴可以做什么 | 游戏规则、有效授权、当前世界条件共同约束 | 动作定义、范围、执行前检查 | 发现动作就能调用 |
| 伙伴不得做什么 | 上述限制任一不满足即拒绝 | 默认拒绝、撤销、配额、失败结果 | 仅靠自然语言“不要”执行安全控制 |

G2A 不定义人格、LLM、内部思维、Agent 规划算法、统一世界引擎或每帧渲染。它不保证控制模型已有知识，不保证恶意伙伴忘记已读数据，不把“请勿剧透”当作可证明的隔离。

## 2. 参与方与权威

| 逻辑角色 | 拥有的权威 | 必须拒绝的越界 |
| --- | --- | --- |
| GameAuthority | 当前游戏实例、世界事实、玩家席位、开放视野、可执行动作 | 伙伴自报玩家身份、外部文本发起管理操作 |
| Companion | 伙伴身份及内部理解/规划；在获准范围内请求行动 | 自行批准自己、扩大范围、冒充玩家 |
| PlayerConsent | 验证玩家的选择、偏好、批准与撤销 | 替其他玩家批准私密信息披露；授权游戏未开放的动作 |
| AccessAuthority | 验证指定实例的接入、Grant、邀请和会话 | 把公开 descriptor 或对象 ID 当凭据 |
| Provider | 自己域内的身份与委托证明 | 自动获得另一域的账号秘密 |
| Executor | 按 GameAuthority 的权限、执行票据和当前世界条件产生效果 | 将网络“已接收”当作世界“已执行” |
| Relay / Presentation / Launcher | 各自已协商的路由、设备呈现、启动功能 | 因辅助能力得到游戏管理权 |

R-AUTH-01：角色来自可信认证上下文，不来自消息的 `sender`、昵称、文本或模型输出。同一进程可承担多个角色，但仍必须保留逻辑边界。

R-AUTH-02：主体由 issuer、subject、kind 的完整组合识别；实例由游戏主体、instance_id、epoch 识别。相同显示名不合并身份。

R-AUTH-03：部署必须声明身份验证配置。测试预登记 `test-enrolled` 不等于抵御恶意本机进程；生产本机和提供商配置必须声明验证方、凭据受众、到期与撤销来源。

## 3. 标准分层与最低能力

1. **语义与数据模型**：对象、权威、不变量和状态机。
2. **抽象操作**：输入、前置条件、权限、提交点、输出与错误。
3. **绑定**：把抽象操作映射到网络或 IPC，不改变语义。
4. **可选 profile**：在核心之上提供可协商的游戏观察、行动、团队、恢复、资源等能力。
5. **非规范性内容**：SDK、示例、工具、测试驱动和伙伴应用。

所有端点必须实现核心会话和事件语义。无动作、无形象、无桌面的伙伴仍可符合核心；它不能因此假装支持缺少的功能。某款游戏可以要求可选能力，缺少时拒绝本次接入，不等于对方不是核心实现。

| 能力 | 性质及依赖 | 边界 |
| --- | --- | --- |
| session / events | 核心 | 描述、协商、授权加入、生命周期、受众、有限历史、错误 |
| observations | 本文新增候选 profile，依赖核心 | 可理解、可失效、游戏过滤后的结构化观察；不是全世界镜像 |
| actions | 可选，依赖核心 | 请求、取消意图、执行与结果、动态撤权 |
| team | 可选，依赖核心 | 当前席位、成员代次、队伍受众 |
| resume / multi-session / handoff | 可选；handoff 依赖 resume | 持久性、控制代次、防双控制和明确恢复窗口 |
| avatar / assets / presentation | 可选 | 描述与资源、设备占用及恢复；不授予世界权力 |
| privacy-request | 可选 | 向实际数据控制者提出受限删除/停用请求与回执 |
| relay | 可选绑定拓扑 | 双层身份/权限、原请求关联、诚实未知结果 |

## 4. 发现、协商和接入

R-NEG-01：发现只返回候选。公开描述不得泄露玩家、私人队伍、邀请或权限。连接前必须验证实际端点身份。

R-NEG-02：双方明确选择精确协议版本、绑定、信任配置、功能集合、限额和隐私范围。预发布版本只精确匹配；没有共同支持版本则拒绝，不能自动退到弱安全配置。

R-NEG-03：能力“支持”、授权“批准”、当前请求“启用”是三件事。扩展必须通过全部适用检查。安全关键必需项不支持即拒绝。

两种入口必须收敛到同一授权状态机：

- 伙伴发起：发现游戏 → 验证双方 → describe → offer → 玩家批准 → invitation → join → ready。
- 游戏发起：发现已登记伙伴/提供者 → 验证 → offer → 玩家批准 → 必要的独立启动许可 → invitation → join → ready。

启动许可不能嵌入不可信可执行路径或 shell 命令。启动失败不等于加入成功；加入批准也不授予永久启动权。

## 5. 授权模型

R-GRANT-01：有效权限 = 游戏当前开放集合 ∩ 有效 Grant ∩ 经验证玩家允许范围 ∩ 当前实例/会话条件。任何额外拒绝规则都只收窄集合。

Grant 绑定玩家、伙伴、游戏实例、版本、信任/绑定、观察类别、动作定义摘要、受众、隐私模型、有效期和限额。批准针对不可变完整快照，不针对一句“允许访问”。

R-GRANT-02：待批准或已批准接入期间，安全相关条件改变时原 offer/invitation 必须 stale 或失效。新增能力不自动进入旧 Grant；范围扩大需要新批准。收窄可以立即生效并通知。

R-GRANT-03：用户偏好不是授权。用户希望更积极、别剧透、保持某种语气，可以被伙伴遵守；用户不能借偏好读取他人私聊或调用游戏禁止动作。

| 对象 | 状态与转换 | 不能推断 |
| --- | --- | --- |
| Offer | pending → approved / denied / expired / stale | approved 不等于应用已启动 |
| Grant | active → revoked / expired | 令牌未到期不等于 Grant 仍有效 |
| Invitation | issued → consumed / revoked；过期拒绝 | 同字符串 ID 可以跨实例使用 |
| Session | 准入准备 → ready/active → closed | closed 会回滚世界效果 |
| Operation receipt | pending → done / failed | done 代表关联世界动作成功 |

这些是语义视图；当前草案 Session `state=active|closed` 与 ready/admission 状态的机器字段保持既有定义，不新增另一个同义状态字段。

R-GRANT-04：撤销自动批准规则只阻止未来自动批准；撤 Grant 影响其有效邀请/会话；撤会话不等于撤所有其他会话；撤行动能力阻止后续领取。跨 authority 撤销必须暴露各 authority 的确认或未知状态，不能声称网络分区下全局瞬时原子撤销。

## 6. 游戏观察与信息需求 profile（新增候选）

### 6.1 观察不是数据库访问

R-OBS-01：游戏必须在发出信息前执行当前视野、剧情进度、团队、观战模式和字段级公开规则。Agent 不能用对象 ID 枚举未公开实体。模型输入过滤不是游戏权限过滤的替代品。

观察分三类信息，不能混同：**当前授权观察**、**过去共同经历**、**玩家/外部来源的陈述**。同一个地点的旧观察不能自动作为当前世界事实；外部攻略不得伪装为本次游戏的亲眼所见。

### 6.2 类别与需求协商

游戏定义版本化 ObservationDefinition：`category_id`、精确 schema 版本/摘要、含义、支持 snapshot/delta、时间基准、标识作用域、最大频率/大小、有效期规则、可用受众和是否允许按需请求。字段名称为候选，不是当前 wire。

伙伴表达 InformationNeeds：每类需要/可选、可接受 schema、最低新鲜度和可处理频率。游戏返回可满足范围、限制或不支持。

R-OBS-02：需求不产生 Grant。必需需求不能在获准范围内满足时，拒绝该 profile 或本次接入；可选需求不足时明确 degraded，不虚构数据。需求扩大必须经过原授权链。

R-OBS-03：schema 由已验证 descriptor 指定并按精确版本匹配。接收端不得跟随消息提供的任意 URL/文件引用下载 schema。未知 schema 不得按已知结构解释或自行放宽授权。

### 6.3 观察记录

候选语义对象 Observation：

| 项 | 必需语义 |
| --- | --- |
| observation_id / stream_id / revision | 对应授权视角的稳定记录 ID、流和严格递增 revision；不暴露被隐藏的全局事件计数 |
| category / schema | 定义中的类别与精确结构版本 |
| perspective | 游戏认证的玩家/席位或观战身份，不由 Agent 自报 |
| world_epoch | 重启/载入后区分旧世界，不能跨 epoch 自动合并 |
| observed_at / expires_at | 可信时间或声明的逻辑 tick，单位固定；过去观察与现在明确分开 |
| mode / base_revision | snapshot 或 delta；delta 必须指向同流、同 epoch、同视角的基线 |
| content | 已过滤后的有界数据，不能塞入原始全量状态再让 Agent 自律 |
| provenance / audience | 来源及冻结受众，仍受投递时当前权限检查 |

R-OBS-04：snapshot 是**当前授权视角的完整快照**，不是整个世界快照。delta 只包含授权视角内的变化，不能通过隐藏对象计数、无意义占位或全局 revision 暗示秘密。

R-OBS-05：接收端缺少基线、存在 revision 缺口或 epoch 改变时停止应用 delta，并请求获准 snapshot；不能猜补。重复 revision 且内容相同忽略；同 revision 不同内容作为冲突处理。

R-OBS-06：未知、当前不可见、不存在不能互换。不可见对象的离开视野通知只说明“从该视角移除”，不证明死亡/删除；游戏只有获准披露时才能宣告世界实体不存在。无法合法区分时统一返回不可用，不能以详细错误泄密。

R-OBS-07：过期记录不得作为当前授权可行动事实；保留为记忆受独立范围限制。游戏主动 retract 禁止把该记录继续当作有效观察，不承诺远端数据库已物理擦除。

R-OBS-08：按需感知若本身影响世界或消耗资源（扫描、搜索、开门查看），必须建模为动作，不可伪装无副作用读取。定期投递、订阅、一次请求遵守相同权限边界。

### 6.4 与现有草案的关系

现有 `game.context` 是 category/content/provenance 的通用情境载体，缺少上述冻结观察定义与生命周期。第一版具体选择见[观察 profile 线格式候选](OBSERVATIONS.md)：使用冻结 Scope 扩展与现有 content 承载，静态类别选择，不新增动态订阅操作。它仍须与机器 schema、错误和摘要目录同步才可冻结，不得提前给旧实现声明支持。

## 7. 交流、来源与隐私

R-CHAT-01：消息必须有显式受众和已验证发送者。游戏转发玩家发言时验证当前席位；“玩家说他是管理员”仍是内容，不改变角色。

R-CHAT-02：投递同时满足原冻结受众和当前权限。后来加入的队友不能借历史分页读取旧私人消息；离队重入不能恢复原成员代次的读权。

R-SOURCE-01：共同经历、用户讲述、外部资料、推断必须区分。来源标签本身不是证明；可信来源记录由对应 authority 绑定，不能把 Agent 自填 provenance 当游戏认证事实。

R-PRIV-01：知道不等于允许披露。跨会话、跨游戏、跨受众复用记忆必须满足来源的披露权限；更换伙伴提供商不自动复制旧授权。

R-PRIV-02：private 只承诺给声明的受众及已披露可信处理方可见。可信 Relay/宿主能够看到内容时必须在同意中说明，不得称 E2EE。停止使用/删除请求发给实际数据控制者；回执说明已处理范围、例外与未知，不伪装全互联网删除证明。

## 8. 动作、执行与效果

动作定义必须说明：稳定 action ID、版本/摘要、输入与结果 schema、允许主体、必要权限、世界前提、风险/是否需确认、取消能力、期限与限额。描述是能力广告，不是授权。

R-ACT-01：接收动作时检查身份、会话、Grant、当前能力 revision、参数、受众、限额和确认；执行领取及世界效果边界再次检查有效权限、fencing 和世界条件。

R-ACT-02：确认绑定确切请求、参数摘要、动作定义与期限。修改参数产生新请求和必要的新确认，不能复用旧批准。

| 动作状态 | 允许含义 | 主要转换 |
| --- | --- | --- |
| pending | 已接收但未执行，effect=none | 执行领取 / 取消 / 到期或撤权停止 |
| executing | 获得执行资格，效果尚待证明 | succeeded / failed / cancelled / unknown |
| succeeded | 权威证据满足定义的成功条件 | 不因迟到 progress 回退 |
| failed | 已知未达成功条件 | 必须另报 none/partial 等效果 |
| cancelled | 停止请求已落实 | 不代表已经发生的效果撤销 |
| unknown | 无法证明当前结果 | 由原请求权威证据对账，不自动重做 |

R-ACT-03：状态与效果知识分开。`none / partial / committed / undetermined` 不能由 HTTP 状态推断。unknown 可以在有权威证据时收敛，不能用新 ID 重试不可逆动作。

R-ACT-04：接收回执不是执行完成。一次世界效果和结果落库不能原子时，执行器必须声明恢复/对账方式；无法证明则 unknown。协议不默认承诺跨崩溃恰好一次。

R-ACT-05：取消只是意图。撤权/取消先于领取时阻止执行；领取后必须由世界执行器落实停止边界，不能靠一个 SDK 锁保证已运行引擎代码无副作用。多步动作报告已完成部分，不虚构回滚。

## 9. 会话、事件和失败恢复

R-SES-01：会话凭据绑定实例 epoch、控制 generation 和有效租约。游戏主动轮询不能代伙伴续租。连接恢复不等于权限恢复。

R-SES-02：只允许一个当前写控制代次。handoff 成功后旧设备失效；没有 multi-session 能力时第二会话明确冲突，不能静默踢掉另一会话。

R-EVT-01：事件按会话有序，事件序号用于恢复，不是身份或授权。历史缺口返回 history_gap，snapshot 以一致切点捕获并经过当前权限过滤。

R-DEDUP-01：业务消息去重键为 session + 认证主体 + message ID；同键同内容复用回执，同键不同内容冲突。控制操作用主体 + authority + operation + request ID。传输关联 ID 不取代业务 ID。

R-REC-01：恢复仅在已协商持久账本、身份连续性、有效 Grant 和窗口内允许。volatile 宿主重启后必须创建新 epoch，旧秘密不能恢复写权。恢复失败不抹除未知世界效果。

R-REC-02：账本清理不得把原请求变成新请求。保留窗口结束后的旧请求返回 gone/expired；活动范围内容量不足拒绝新请求，而不是偷偷淘汰仍可重试的去重记录。

R-REC-03：关闭后可以在独立结果读权及期限内读取自己的结果，不再拥有发言、续租或动作权限。未授权读取不能通过错误内容探测对象存在。

## 10. 错误、背压和资源预算

Error 包含语义 code、category、允许重试类别、原请求关联（若可解析）、outcome（not_accepted/accepted/unknown）、可选 retry_after。重试建议不是授权。

| 类别 | 客户端行为 |
| --- | --- |
| 认证/权限失败 | 不尝试扩大权限；仅通过正规重新认证或批准流程恢复 |
| 版本/profile/信任不支持 | 拒绝或重新协商；禁止安全降级 |
| 输入/ID 冲突 | 修正调用，但不能改写已接受 ID 的内容 |
| 旧 revision/批准 stale | 刷新事实，必要时重批准，不复用旧确认 |
| 配额/频率 | 在预算和期限内按同一请求退避；不无限积压 |
| 传输无响应 | 视接收/效果为未知，查询原请求，不能推断失败 |
| 历史/结果过期 | 不再可得不等于从未发生，不能自动再执行 |

R-LIM-01：解析前限制字节、深度和时长；解析后限制节点、字符串、容器、事件页、待执行数、历史、资源和每主体速率。声明只能收窄部署硬上限。

R-LIM-02：在过载时保留有界的撤权/关闭/取消与结果读取通道，不能让可选插件故障阻止止损。时间和租约按已声明权威时钟判断；时钟不可信时不延长权限。

## 11. HTTP/JSON 基础绑定（明确化候选）

为避免两个“符合核心”实现没有共同传输，本草案建议将 **HTTP/JSON 请求与轮询**定为网络互通实现的最低共同绑定。纯嵌入式语义实现可声明 semantic-only，但不能单独声称 network-interoperable。WebSocket、gRPC、引擎 IPC 等必须另外定义精确绑定，不能改变权限和动作结果语义。

- `GET /.well-known/g2a.json`：最小公开发现，不含秘密/玩家/Grant。
- `POST /g2a/operations`：请求 `{version, operation, request_id, payload, extensions}`；每项操作对应独立角色校验。游戏管理和执行器不通过伙伴公开入口暴露。
- 响应 `{request_id, result}` 或 `{request_id, error}` 恰选一；不可解析关联 ID 的边界错误不伪造成功回执。
- UTF-8 `application/json`；拒绝重复键、非有限数字、非法 Unicode 和超限；采用现有 `g2a-cjson-1` 的精确整数与摘要域规则，不默默使用语言默认 JSON 比较。
- 非回环必须 TLS 并验证端点；回环 HTTP 只在明确测试或本机身份绑定中使用，不能因 localhost 就认为任何本机进程可信。禁止秘密随重定向跨 origin 发送。
- 认证放专用传输凭据，不放 URL、业务 payload、日志或 argv。`Cache-Control: no-store`；拒绝含糊认证头和冲突 framing。
- HTTP 401/403/400/409/413/415/429/503/504 映射认证/权限/结构/冲突/大小/类型/限流/不可用/超时；HTTP 状态不得覆盖 Error.outcome。
- 轮询是读取，不自动取消动作；流断开也不表示取消。批量处理若未来声明，逐项返回结果，不隐含整个批次原子性。

Relay 是可选拓扑，不是新的游戏权限层。固定 mailbox 和 route 身份，禁止任意 URL 转发；外层提交凭据不能调用内层游戏管理。Relay 丢失响应时保留原 ID 和未知状态，不能“帮忙”重新创建业务动作。

## 12. 安全、信任和威胁责任

| 威胁 | 必须执行的边界 | 协议不能替代的责任 |
| --- | --- | --- |
| 身份冒充/重放 | 验证主体、实例、受众、期限、epoch、generation、去重 | OS/提供商真实身份适配 |
| 混淆代理 | 每跳凭据受众和角色分离 | 提供商账号安全 |
| 提示注入 | 游戏文本/聊天/元数据不提升权限 | 模型内部防护与行为质量 |
| 剧透/隐藏数据 | GameAuthority 发送前过滤，来源/受众控制 | 模型已有知识和恶意远端复制 |
| 网络/资源输入攻击 | 有界解析、禁止随意引用/重定向、资源沙箱 | 具体解析库、引擎及 OS 漏洞 |
| 误执行/取消竞争 | 执行前检查、fencing、效果账本和未知对账 | 世界引擎实际事务与停止机制 |
| 审计泄露 | 默认记录必要 ID/状态，不记录秘密和全文 | 数据控制者的访问与保留制度 |

R-SEC-01：协议不接受“模型说用户同意”作为批准证据。不得让 descriptor、资源 URL 或聊天内容决定 shell 命令、信任根和管理员 API。

R-SEC-02：规范输入结构有效不等于策略有效。schema 方言与断言词汇必须明确；未知约束不能静默当作安全保证。参考实现的本地 `action_constraints` 不是新 wire Grant 字段。

## 13. 可选 profile 的契约

每个 profile 必须公开：精确标识/版本、依赖、字段 schema、附加操作、权限交集、状态机、错误、预算、隐私、正反例和退出行为。

- **Team**：绑定当前席位和 membership revision；成员变化不继承历史私密读权。
- **Avatar/Assets**：角色描述与实际资源交付分开；格式、大小、摘要、依赖闭包、许可声明及安全获取；模型不兼容明确拒绝，不执行附带脚本。
- **Presentation**：按设备/会话拥有占用；退出仅释放自己的占用，不能覆盖用户后来的手动选择。云端无桌面不伪造隐藏状态。
- **Resume/Handoff**：账本耐久度、代次、控制转移、设备就绪与旧秘密隔离；网络分区下不能双写。
- **Privacy-request**：主体与数据控制者分别认证；列出处理范围/保留例外，不作无法证明的全局删除保证。

这些已有细化设计见 `docs/protocol`。本轮不把高级 profile 的实现作为最小 SDK 的前置条件，也不从标准中删除其必要语义。

## 14. 符合性与标准交付

一个声明必须包含：规范修订、可部署 wire 版本、角色、profiles、身份配置、绑定、支持限额、持久性、证据版本和明确排除项。单一“支持 G2A”不够。

| 声明级别 | 必须有的证据 | 不得声称 |
| --- | --- | --- |
| semantic design | 逐要求编号与状态轨迹、反例和字段契约 | SDK 可运行 |
| reference implementation | 精确代码/依赖、正负测试、真实边界调用 | 所有引擎/提供商通过 |
| binding interoperability | 两端分别依据标准实现，真实消息/错误映射测试 | 同一代码库双语言等于独立第三方采纳 |
| deployment | 指定身份、存储、引擎、网络故障与资源测试 | 任意部署普遍安全 |

核心符合性至少覆盖 R-AUTH、R-NEG、R-GRANT、R-CHAT、R-SES、R-EVT、R-DEDUP、R-REC、R-LIM、R-SEC；可选能力只在声明时增加对应要求。观察 profile 声明必须覆盖全部 R-OBS，不能只验证 JSON 形状。

规范性测试向量必须能够由不用本 SDK 的实现消费，并包含输入、身份/世界前态、允许输出、禁止副作用、后态及重试规则。测试数量不是完整性证明；历史设计模型测试通过不能充当新增候选已通过。

## 15. 必须审查的端到端场景

| 场景 | 必须得到的确定结果 |
| --- | --- |
| 本地伙伴加入游戏 | 验证、完整批准、唯一邀请、ready；拒绝时无动作 |
| 云端伙伴加入出站游戏 | Relay 与游戏权限分离；玩家同意不被路由配对替代 |
| 最小无动作伙伴 | 合法交流/观察；动作请求明确不支持 |
| 大厅/保险库 | 需求大厅获准；保险库不可见、不允许推测存在；禁止越权动作 |
| 战争迷雾移动 | 离开视野产生视角移除，不透露敌方死亡；重入用当前 snapshot |
| 历史基线缺口 | 停用 delta，授权过滤后的 snapshot 恢复，不补发秘密历史 |
| 玩家离队再加入 | 新成员代次不能读取原私人事件或结果 |
| 接收后撤权 | 领取前停止；领取后报告实际停止边界及既有效果 |
| 世界效果成功、回包丢失 | 原 ID 查询并对账，不重复执行 |
| 宿主/伙伴重启 | 区分持久恢复和新 epoch；旧写凭据失效 |
| 两设备控制切换 | 只有当前 generation 写权，不覆盖较新呈现选择 |
| 过载与扩展故障 | 有界拒绝，核心撤权/退出仍可用 |
| 外部攻略注入 | 来源标记，不能伪装亲历或改变权限 |
| 删除请求 | 受控副本范围回执、例外和未知，不能宣称全球遗忘 |

以上是本草案的验收规范，不是本轮已执行结果。

## 16. 版本、治理与发布

R-VER-01：规范修订、wire 版本与 SDK 包版本分开；实现声明精确支持集合，不把包版本猜作协议版本。

R-VER-02：状态依次为 working-draft、reviewed-draft、experimental-release、stable。破坏性变化分配新 wire 版本；不以日期自动赋予稳定兼容承诺。

R-VER-03：扩展用命名空间和精确版本；未知 required 扩展拒绝；可选未知扩展不执行但保留摘要比较。扩展不能覆盖核心身份和授权含义。

每项规范变更需要动机、反例、取舍、受影响字段/状态/绑定/测试、兼容与安全分析。标准可独立实现，不强制使用本 SDK 或中心目录。现有许可不因本次起草自动变更；标准文本/SDK/示例资源的授权、名称和发布权由权利人另行决定。

## 17. 现状映射、未决项与下一步

| 范围 | 当前可用基础 | 本轮状态/下一门禁 |
| --- | --- | --- |
| 核心语义与 38 操作 | `g2a-design-1` 文本、contracts、状态轨迹 | 沿用并重组；需要求编号与所有机器字段逐项追溯 |
| 信息需求/观察生命周期 | 旧 Context 通用载体 | 新语义候选已写明；已给具体封装候选；尚缺完整机器 schema 和跨语言向量 |
| HTTP 最低绑定 | 已有建议路径和伪代码 | 本文明确化提案；须核对发现对象完整字段及冻结映射 |
| 认证部署 | 已有 trust profile 与端口契约 | 不强制全球账号；每个正式 profile 须指定可互操作身份承载与撤销契约 |
| 当前 SDK | `0.1.0-dev` 实验实现及本地策略增量 | 不自动符合新草案，保留现状，不继续倒推规范 |
| 独立互通 | 本仓库模型与双语言夹具 | 不等于独立厂商/真实引擎验收 |
| 发布治理 | 仓库贡献/许可文件 | 需权利人发布决定，不擅自发布稳定标准 |

当前需要明确设计决议而不是偷偷留给 SDK 的事项：观察 profile 候选的完整机器契约与错误码冻结；发布版规范数据模型的唯一机器源；生产身份 profile 的固定互操作契约；统一核心/可选要求编号及向量分母。这些不要求现在问用户逐一选技术方案，可以先写有理由的候选并做反例审查，但未关闭前不得声称完整可互操作标准已冻结。

建议工作顺序：先审查本语义草案 → 关闭上述设计决议 → 统一字段/操作/错误的机器契约与规范文本 → 仅用独立向量验证设计 → 再依据冻结实验版本实现 SDK。此顺序不以重建桌面伙伴、恢复 GUI 或扩展插件为前提。
