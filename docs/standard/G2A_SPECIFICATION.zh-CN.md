## 1. 约定与文档效力

大写关键词 MUST、MUST NOT、REQUIRED、SHOULD、SHOULD NOT 和 MAY 按 RFC 2119、RFC 8174 的定义具有规范性含义。本文分别译为“必须”“不得”“必需”“应当”“不应”“可以”，并保留英文关键词。它们表达的是本标准提案的要求，而不是对当前实现状态的声明。

英文文档是主要的语义审阅草案。现有草案对象的精确定义位于 [contracts.py](../protocol/contracts.py)、[contracts.schema.json](../protocol/contracts.schema.json) 和 [operations.json](../protocol/operations.json)。现有生命周期细节位于 [PROTOCOL.md](../protocol/PROTOCOL.md)、[OPERATION_CONTRACT.md](../protocol/OPERATION_CONTRACT.md) 和 [STATE_TRACES.md](../protocol/STATE_TRACES.md)。这些构成继承的 `g2a-design-1` 基线。本文提出额外的观察语义，并进一步明确角色适用性；不能仅因为现有 JSON 能承载这些内容，就认为这些新增内容已经实现。冻结发布版必须（MUST）消除所有差异，并确定一份不可变清单，列明规范性文档、Schema、操作定义和测试向量。实现者不得（MUST NOT）在存在冲突时静默选择一种解释。

## 2. 目的与范围

G2A 是用于权威游戏与 AI 控制的伙伴或智能体之间交互的开放协议。它将下列问题分别处理：

| 问题 | 协议概念 |
| --- | --- |
| 智能体需要知道什么？ | 声明的观察需求与可选偏好 |
| 游戏能够提供什么？ | 版本化的能力目录与观察目录 |
| 这个智能体获准知道什么？ | 有效授权、视角、受众、新鲜度和保留限制 |
| 这个智能体能够请求什么？ | 带前置条件与约束的类型化行动定义 |
| 它实际上获准执行什么？ | 当前授权、确认、游戏校验和效果边界检查 |

能力声明表示支持某种功能，并不代表授权。请求表达意愿，并不代表享有权限。请求被接受，不等于游戏效果已提交。获准获得的观察数据不一定仍是当前数据。缺失的信息不得（MUST NOT）被解释为某个事实为假，也不得被解释为空世界。

本协议的范围是游戏：面向玩家的辅助、NPC 协作、游戏状态观察、受约束的行动，以及可选的游戏内呈现。模型推理、模型托管、规划算法、记忆产品、商业身份提供方、游戏引擎和某个特定桌面伙伴都不是使用协议的前提。G2A 不是通用操作系统自动化协议。它不把任意远程代码执行纳入标准，也不默认授予对游戏秘密的访问。

游戏对游戏事实和效果保持最终权威。G2A 约束符合规范的端点所传输的信息；它无法保证模型绝不推断出隐藏事实，也无法保证模型此前没有从其他来源获知这些事实。

G2A 向符合规范的第三方智能体和模型服务开放；互操作不得（MUST NOT）要求使用协议作者平台自有的智能体或模型服务。独立实现可以（MAY）通过适用的已声明角色、能力、认证及协商契约参与。开放性不免除既有的同意、数据访问、行动或资源要求。只要智能体满足适用的 G2A 最低标准，游戏就必须（MUST）允许其接入；开发者不得（MUST NOT）按服务商身份任意排除、强制指定偏好厂商，或以封闭的服务商白名单将 G2A 变为专属生态。最低标准及符合性证据必须（MUST）对自有及第三方智能体一致适用。技术接入不等于自动获得玩家数据或游戏行动授权：既有能力、认证及授权契约仍对所有参与方适用，且不得（MUST NOT）被用作变相限制服务商的手段。游戏可以（MAY）针对有证据的恶意行为或实际违反适用规则的行为拒绝请求或断开智能体。游戏必须（MUST）向智能体服务商提供标准化的机器可读原因代码，以及清晰、具体的人类可读说明，指出相关规则及违规行为，并提供足以诊断的安全细节。冻结发布必须（MUST）定义共同的原因代码目录、稳定含义及载荷 Schema，使服务商能一致理解拒绝；仅有自由文本不够。代码不能取代针对本次情况的具体说明，说明必须（MUST）与代码一致。仅使用“恶意”等笼统标签、无依据的怀疑或服务商身份，本身不足以构成原因。原因与支持细节必须（MUST）遵守受保护数据边界，不得（MUST NOT）披露凭据、他人私人信息或隐藏游戏事实；这些边界不能成为完全不给出有意义说明的借口。处置必须（MUST）针对实际行为，不能掩饰对符合规范服务商的任意排斥。

反复拒绝可以（MAY）触发对游戏接入及处置行为的审查。次数本身不能证明恶意或歧视行为；审查必须（MUST）考虑说明的原因、适用规则及可用证据。服务平台可以（MAY）另行依据自身运营策略维护游戏黑名单，并拒绝为某游戏提供服务。此决定影响的是该平台服务，不是协议层或整个生态自动封禁，不得（MUST NOT）被描述为 G2A 符合性的普遍后果。平台特有的商业处置属于可互操作协议之外的机制。对于本标准作者的平台，已选择的运营策略是在列入该平台黑名单前先通知游戏开发者，并提供申诉或整改机会。这是独立的平台运营承诺，不是通用 G2A 线上契约要求，也不授予对其他服务商的处置权。该平台策略的精确时限及证据提交程序在此尚未确定。

## 3. 角色与信任

游戏权威方（Game Authority）控制游戏状态与效果授权。智能体端点（Agent Endpoint）接收获准披露的信息并提出行动。部署了控制器（Controller）时，由其协调同意与策略。中继（Relay）传输经过认证的操作，但不会因此成为游戏权威方。启动器（Launcher）启动已获明确授权的游戏实例。呈现提供方与资源提供方（Presentation and Asset Providers）负责可选的渲染或资源。数据控制方（Data Controller）负责其实际保留数据所对应的隐私义务。一个进程可以（MAY）实现多个角色，但必须（MUST）明确保留各角色的权限边界。

调用方身份必须（MUST）由经过传输认证的身份确定。载荷中的 sender 字段不构成身份认证。主体、设备、实例和实例代次（instance epoch）必须（MUST）保持可区分。新的实例代次会按已协商配置规范的规定，使绑定旧实例的凭据或引用失效。会话成员身份不等于读取该会话内所有消息的权限。

现有信任模式 `local-verified`、`provider-verified` 和 `test-enrolled` 不得（MUST NOT）被描述为等价。测试登记是开发辅助机制，不是抵御任意本地软件的安全证明。能够读取内容的中继是受信任的中间方，而不是端到端加密。实现必须（MUST）披露这一边界。

### 3.1 可组合的游戏角色与信息视角

游戏角色不同于协议基础设施角色。玩家伙伴、NPC（包括 Boss）和引导者可以（MAY）由同一个 Agent 实现，也可以在同一体验中组合。这些角色是可组合的，而不是互斥的产品类别。游戏必须（MUST）声明适用的角色绑定与信息视角。每条观察和行动必须（MUST）继续关联其获授权的角色、主体、受众和作用域；组合角色不得（MUST NOT）隐式合并权限，也不得借另一角色泄露某个角色的私人知识。

NPC 或 Boss 可以（MAY）获得游戏授权、但玩家不可见的内部知识。引导者可以（MAY）获得游戏授权的进度或教程知识。玩家伙伴也可以（MAY）持有玩家授权的当前游戏之外的记忆。角色名称本身不授予全知能力、透露知识的许可或行动权。切换或组合角色需要明确的适用权限；影响观察视角的变化须按第 8 节使原基线失效。

### 3.2 四项独立决策

实现必须（MUST）区分：（1）Agent 可获得哪些信息；（2）它可以向玩家讲哪些信息；（3）它可以向游戏或其他接收方披露哪些信息；（4）它可以请求或执行哪些行动。知道某个事实不等于有权披露它或据此行动。允许与玩家讨论记忆中的事实，不等于允许把背后的对话或记忆传给游戏。允许提出行动，不等于绕过游戏执行检查。即使一个进程同时实现所有角色，也必须保留这些区分。

### 3.3 第一版游戏角色数量限制

第一版中，同一局采用玩家伙伴模式或独立 AI NPC/敌人模式；两种模式不得（MUST NOT）在同一局同时活动。在伙伴模式下，每位玩家可以（MAY）拥有一个活动伙伴，多人游戏也一样。多位玩家的伙伴可以（MAY）同时存在，并在各自授权及游戏声明的能力范围内相互互动。这是每位玩家最多一个伙伴，不是整局多人游戏最多一个伙伴。在独立 NPC/敌人模式下，整局最多允许一个活动的独立 AI NPC/敌人，包括 Boss。后续版本可以扩展这些限制。

游戏必须（MUST）将每个伙伴绑定到经认证的所属玩家、角色、视角和作用域。伙伴间互动必须（MUST）保留来源身份、受众及各所属玩家的权限；一个伙伴的观察、记忆或行动权限不得（MUST NOT）被隐式共享给另一个伙伴。另一名玩家在线或给予同意，并不授权控制已离开玩家的伙伴。第 7.1、9 和 10.3 节分别约束在线状态、信息披露及多人互动。

游戏必须（MUST）一致地识别本局边界，并在准入、替换、交接及恢复时（包括并发请求）执行模式互斥以及适用的每玩家或整局数量上限。新增连接、智能体进程或组合角色声明不得（MUST NOT）绕过这些约束。切换模式前，必须（MUST）废止或隔离旧模式的全部活动 G2A 游戏角色绑定；替换伙伴或 NPC 前，必须（MUST）废止或隔离其原活动绑定。普通非 G2A NPC 与游戏模拟不计入这些角色限制，也不因此停止。限制对象是活动游戏角色，而不是已保留记忆或基础设施进程数量。

适用游戏模式由游戏开发者固定；智能体或玩家偏好不得（MUST NOT）覆盖开发者确定的模式。接入游戏必须（MUST）至少提供玩家伙伴栏位作为最低角色接入能力，也可以（MAY）额外提供独立 AI NPC/敌人栏位。提供栏位声明的是支持的接入能力，不是角色已活动，也不是必须同时启用两者：支持可选 NPC 不得（MUST NOT）被解释为允许同局伙伴与 NPC 模式共存。游戏必须（MUST）在声明中区分支持的栏位、开发者确定的模式及当前活动绑定，并执行上述第一版限制。玩家可以（MAY）将必需提供的伙伴栏位留空，不启用伙伴进行游戏。游戏必须（MUST）在没有伙伴时仍可正常游玩，不得（MUST NOT）仅因提供了这一接入栏位就要求玩家启用伙伴。必须支持不等于玩家必须使用。在伙伴模式下，玩家必须（MUST）能够在游戏过程中随时召唤或收起伙伴。进入游戏时，加入方式遵从玩家自身配置：自动加入，或弹窗询问是否加入。两种配置都必须（MUST）允许游戏过程中手动唤起。自动加入使用玩家已配置的选择及有效准入，不得（MUST NOT）绕过必需授权、开发者固定的游戏模式或每玩家伙伴数量限制。拒绝入局提示或以空栏位开始游戏，不得（MUST NOT）取消手动唤起选项。游戏必须（MUST）如实报告切换状态及在途行动结果，不能暗示画面上消失就会回滚已提交效果。收起后，伙伴必须（MUST）停止观察游戏及自主游戏行动。收起本身不得（MUST NOT）删除已存记忆；保留和隐私策略仍然适用。服务必须（MUST）停止提交新的游戏监测/规划请求，并按声明的停止与取消语义处理排队或在途工作。收起不退回已经消耗的 token，也不保证无关或已在执行的外部服务剩余费用归零。玩家离线行为仍由第 7.1 节规定。

第一版主要聚焦玩家伙伴。独立 AI NPC/敌人接入是次要的可选能力；支持伙伴不要求实现 AI NPC。对于独立 AI NPC，第 7.1 节要求的在线关联是其持有用户；其他玩家在场不能替代该持有用户在线。

## 4. 架构与适用性

本标准分为三层：规范数据模型、抽象操作及生命周期语义、传输绑定。引擎适配器和 SDK API 是这些契约之下的实现层。其他 SDK 可以（MAY）在不模仿参考实现结构的情况下符合规范。

| 角色或已协商能力 | 适用义务 |
| --- | --- |
| 所有参与方 | 身份、输入校验、已协商版本、适用的扩展规则、保密性、真实错误报告 |
| 会话中的游戏与智能体端点 | 准入、作用域执行、会话生命周期、事件处理、适用的请求恢复 |
| 具备行动能力的游戏权威方 | 游戏校验、去重、行动状态/效果语义、效果授权 |
| 具备行动能力的智能体 | 受授权范围约束的请求、未知结果核对、不盲目重试效果 |
| 观察配置规范参与方 | 流定义、获准视角、基线、代次、过期、撤回 |
| 仅实现中继的参与方 | 中继身份、路由、保留、撤销及中继操作恢复；不负责实现游戏状态 |
| 持久恢复参与方 | 仅在已协商时适用的恢复和交接语义 |
| 聊天参与方 | 受众、来源、转发与保留语义 |
| 呈现或资源参与方 | 仅限已协商的渲染/资源生命周期 |
| 数据控制方 | 对其保留数据支持的隐私请求，以及真实的处理回执 |

会话和事件操作不是仅实现中继的实现所必须具备的通用要求。聊天、资源、呈现、主动感知和持久恢复，不会仅因协议定义了它们就成为强制功能。`core.session` 等现有功能标签是目录分类，不表示每个角色都必须实现该分类下的所有操作。发布版必须（MUST）公布按角色与功能划分的操作适用性。

## 5. 规范数据模型

描述对象（Descriptor）声明身份、支持的版本、角色、能力和扩展支持。提议（Offer）提出一次交互。请求作用域（Requested scope）表达期望获得的权限。授权（Grant）记录已批准的作用域、授权依据和有效期。作用域（Scope）是冻结的、已协商的权限快照。会话（Session）绑定参与方、授权、就绪状态、控制世代、租约和操作状态。消息信封（Envelope）承载类型化的游戏/智能体消息、作用域上下文、来源、受众、关联标识和扩展。行动（Action）记录请求及其结果。事件（Event）记录对接收方可见的生命周期变化。恢复快照（Recovery Snapshot）将获准披露的当前状态物化。回执（Receipt）记录操作可恢复查询的结果，而不是独立的行动权限。

除非定义另有说明，标识符必须（MUST）对使用方保持不透明。关联标识、消息标识、操作标识、事件游标和行动标识各有用途，不得（MUST NOT）相互替代。

适用以下不变式：

1. 有效权限不得大于当前游戏能力、已批准授权、会话作用域、成员关系和当前策略的交集。
2. 不得从发现过程或中继的存在推断用户同意。
3. 不得通过修改活动请求扩大冻结的作用域。
4. 撤销会阻止新的获权读取和效果，同时保留对已提交效果进行真实核对的能力。
5. 当状态可能变化时，必须在权威的效果边界重复进行准入或授权检查。
6. 重复投递不能授权重复效果。
7. 没有证据时，未知结果不得报告为失败或成功。
8. 接受受保护内容和释放该内容时，都适用受众检查。
9. 不受信任的游戏文本、聊天和资源内容始终是数据，而不是协议权威。
10. 隐私回执描述实际完成的工作和例外，而不是期望完成的删除。

## 6. 发现、协商与准入

未经认证的公开发现必须（MUST）只返回 PublicDescriptor：instance、supported_versions 和 discovery_endpoint。完整的 describe 要求经过认证的智能体或玩家，并且在披露角色、能力、绑定信息和扩展之前，必须（MUST）针对该主体过滤其 Descriptor。两种发现路径都不得暴露秘密或未经授权的玩家状态。对端选择双方共同支持的版本和配置规范集合；不支持必需扩展时，协商失败。只有在语义允许安全省略时，才可以（MAY）忽略不支持的可选扩展。

任意一方都可以（MAY）通过其已授权的准入路径发起 Offer。创建 Offer 时冻结 immutable_scope 和 scope_digest。只有对应玩家经过认证的 PlayerConsent 路径，才可以通过 offer.decide 批准或拒绝这一精确的冻结作用域；decision_ref 必须（MUST）验证实际发生的玩家交互。此前已批准的自动规则，仅可在满足基线规定的精确匹配和无需启动条件时，在 offer.create 期间自动批准；它不会赋予智能体调用 offer.decide 的权限。智能体不得（MUST NOT）批准自己的 Offer。缩小或以其他方式改变提议作用域，要求创建新的 Offer、新的 scope_digest，并批准这一新提议；offer.decide 不得（MUST NOT）原地修改现有 Offer。邀请由其预期的、经过认证的受邀方兑换；仅持有一个标识符不会产生更广的主体身份。加入需要有效准入和当前权限。启动属于独立权限：交互授权不等于启动任意进程的权限。

扩展使用带命名空间的键，其值为 `{version, required, value}`。Descriptor、Requested 和 Scope 的扩展分别承载支持情况、提议配置和已批准配置。基线要求冻结时，活动 Envelope 中的扩展配置必须（MUST）与冻结的 Scope 值完全一致。动态观察应放在消息 content 中，而不是通过修改配置值传递。按继承的契约，数据平面外层 OperationRequest 的 extensions 保持为空；消息扩展放在 Envelope 中。

## 7. 授权、会话与撤销

Grant 必须（MUST）标明签发者、主体、适用游戏或实例、允许的操作、作用域、过期条件及撤销关系。观察授权还绑定目录的 Schema 和语义摘要、视角、受众、频率/数据量限制、新鲜度与保留要求。行动授权绑定行动定义和约束。扩大权限的变化需要重新批准，不能只刷新能力声明。

继承的 Session 状态为 `active` 或 `closed`，就绪状态另行表示。本文不以不兼容的新状态枚举替换这些字段。Session generation 防止陈旧控制消息作用于更新的控制世代。租约过期防止已失联的参与方无限期保有活动控制权。仅在基线允许时，经过认证的新轮询才可以（MAY）续租；重放旧请求或读取快照不得（MUST NOT）意外续租。

关闭会话会停止新工作并启动清理，但不会追溯抹除已提交效果。能力替换、成员替换和权限撤销必须（MUST）与受影响的读取、排队行动和效果有序协调。它们必须（MUST）使受影响的观察基线和缓存失效。已经失去权限的待处理工作不得（MUST NOT）继续。进行中的工作必须（MUST）在可能时停止；已经提交的不可逆效果必须（MUST）如实报告。交接和持久恢复是可选能力，需要遵守其规定的世代、所有权和恢复检查。

### 7.1 第一版边界：不提供离线世界活动

G2A 第一版不得（MUST NOT）提供关联玩家离开或被判定离线后，智能体仍继续在游戏世界中活动的模式。这是版本边界，而非仅默认关闭的选项。开发者建议、玩家偏好、持续任务授权、后台工作进程或可选扩展，都不得（MUST NOT）在本版本启用离线继续活动。后续版本可以通过明确的标准化过程重新讨论。第 10 节规定的在线自主协助仍然支持。

游戏权威方及已部署的控制器必须（MUST）定义经认证的玩家与会话关联、在线状态依据、明确退出信号、有界检测超时，以及停止执行的责任归属。玩家明确离开、会话关闭，或适用的玩家在线/控制租约过期，必须（MUST）终止受影响范围内开展新自主工作的资格。端点检测到连接丢失时必须（MUST）停止安排新的游戏活动；权威方必须（MUST）最迟在声明的检测/租约截止时间隔离受影响的控制权。仅有智能体心跳不得（MUST NOT）证明玩家仍在场，也不得维持离线控制。静默网络故障无法被瞬时检测；实现必须（MUST）披露检测延迟，在尚未确认停止措施生效时不得（MUST NOT）声称已验证停止。这里的在线指参与关联的游戏会话，而非仅在平台保持账号登录；不要求玩家持续操作键盘。

一旦已知或已执行停止条件，受影响的智能体必须（MUST）停止用于继续游戏活动的环境监测与规划/推理循环，不得（MUST NOT）安排新的攻击、移动、对话、交易、购买或其他世界行动。权威方必须（MUST）阻止新近不再获准的后续行动，取消尚未向游戏提交的排队工作，并停止继续产生新行动的委托规划或执行循环。已经发给游戏的技能或攻击按游戏规则自然完成，不要求仅因伙伴停止就将其撤回；适用的独立游戏权限和取消规则仍然有效。将任务委托给游戏执行器不得（MUST NOT）绕过此边界。边界前已提交的效果、不可逆的在途后果和未知结果必须（MUST）如实核对，不能自动回滚。这不意味着冻结游戏世界、撤回已经射出的投射物，或停止普通游戏模拟及非 G2A NPC 逻辑。

多人游戏中，该规则分别适用于受影响的经认证玩家关联及其限定范围内的 G2A 活动；一名玩家离开不代表所有玩家离线。其他在线玩家独立获权的会话可以（MAY）继续。共享 NPC/引导者智能体必须（MUST）有明确的在线玩家关联，且分别执行每个作用域的约束；不得（MUST NOT）借用另一名玩家的在线状态，或静默重绑角色，维持已离开玩家的伙伴活动或权限。本版本的 G2A 世界活动不得在没有符合条件的在线玩家关联时继续。

保留获准保存的记忆、回执和恢复状态，不等于主动游戏活动。有界的非游戏性取消、结果结算、核对及持久化工作可以（MAY）完成，但不能授权进一步的世界行动。服务必须（MUST）停止提交新的游戏活动模型请求，并在支持时请求取消在途模型工作。本要求旨在防止离线后持续消耗 token；由于检测、在途请求和服务商取消/计费边界不同，协议无法保证断开连接后 token 或费用立即归零。实现必须（MUST）披露这些限制，并报告实际用量或尚不确定的用量，而不是承诺即时零消耗。

重连后，必须（MUST）先确认玩家当前在线、准入/授权仍有效、控制世代正确，并取得获准访问的新鲜状态，才能恢复游戏活动。持久恢复保存的是符合条件的状态，不是离线行动许可：不得（MUST NOT）静默复活已关闭会话、重放离线行动积压，或继续陈旧计划。玩家退出游戏后，下次进入时旧任务必须（MUST）保持停止，即使此前已获批准。伙伴必须（MUST）等待玩家重新下达指令，才能再次开始该任务。重新加入伙伴栏位或恢复状态，不等于恢复旧任务的新指令；仍须满足当前准入及游戏权限。智能体进程间交接不能免除这些要求。精确的在线状态字段、超时界限、停止回执和恢复编码仍需在适用契约中冻结；本节新增的是语义义务，而非新的核心状态或操作名。

### 7.2 伙伴服务中断与玩家决定继续

入局时伙伴服务不可用，游戏必须（MUST）允许玩家不带伙伴继续游玩，不得因此阻止进入游戏。服务恢复可用后，伙伴可以（MAY）依据玩家配置的加入选择与有效准入接入。服务恢复本身不恢复第 7.1 节因退出游戏而停止的旧任务。

玩家仍在游戏中但伙伴 AI 服务断线或不可用时，游戏必须（MUST）继续运行，远端伙伴的观察、推理和自主行动发送必须（MUST）暂停。开发者必须（MUST）明确声明伙伴角色保持静止，还是由本地基础游戏行为接管。这些本地行为必须（MUST）标明由游戏控制，而非智能体仍在持续智能决策，并遵守游戏规则与当前权限。游戏必须（MUST）区分服务中断与玩家离开；玩家离线仍适用第 7.1 节。中断后不得发送尚未提交的智能体行动；已发出动作及未知结果按第 10.1、12 节处理，不自动撤回。

恢复时只向伙伴提供当前获授权的游戏状态，不提供断线过程的记录或回放。游戏不得（MUST NOT）为之后补录伙伴观察或记忆而记录、重建该断线过程。这不禁止普通游戏存档，或核对先前获授权游戏效果所必需的行动凭据；这些记录不得（MUST NOT）被改作游戏观察的积压记录。本地接管不绕过下文的玩家继续决定。

AI 服务重连后，由玩家决定伙伴是否继续。重连本身不得（MUST NOT）自动恢复伙伴行动、重放排队游戏工作或复活旧计划。继续前，实现必须（MUST）取得玩家继续的决定，重新验证当前权限与控制世代，刷新获权状态，并核对未确定结果。入局自动加入偏好不能绕过这次中断后的决定。玩家未选择继续时，伙伴行动保持暂停，游戏仍继续运行。对于独立 AI NPC/敌人（包括 Boss），服务不可用时的行为由开发者根据玩法决定，可以暂停、由游戏脚本接管，或采用其他声明的处理策略。游戏必须（MUST）声明适用的故障处理与恢复行为，并区分脚本驱动和智能体驱动的效果。不得（MUST NOT）自动将伙伴恢复时的玩家继续决定套用于 NPC 恢复。故障处理不得（MUST NOT）授予不可用的 AI 能力、绕过当前权限，或把脚本决策说成 AI 决策；普通脚本接管不授权第 7.1 节禁止的离线 G2A 活动。

开发者须为实现确定断线接管策略，但 G2A 不要求向玩家专门披露该策略，也不要求让玩家在静止与本地基础行为之间选择。这与既有的重连后由玩家决定伙伴是否继续是不同事项。

## 8. 观察配置规范候选方案

### 8.1 需求与定义

智能体可以（MAY）声明必需的观察类别和可选偏好。游戏必须（MUST）明确协商未满足的必需需求，不得（MUST NOT）静默假装缺失类别已经可用。需求永远不会扩大 Grant。游戏可以拒绝交互，或在参与方同意后协商降级模式。

每个类别定义必须（MUST）规定稳定标识符、Schema 版本及摘要、语义定义摘要、单位、标识符、坐标/时间约定、视角策略、投递模式、新鲜度、速率/大小限制、受众和保留要求。Schema 必须（MUST）定义校验行为，包括未知字段和大小边界。除非选定的方言/配置规范另有规定，JSON Schema 的 format 注解本身并不等于强制格式校验。

候选方案使用现有 `game.context` 的 content 槽位。目录支持信息放在 Descriptor 扩展中，需求放在 Requested 扩展中，选定配置放在 Scope 扩展中，变化的记录放在 Context content 中。临时示例使用 `org.example.g2a-observations`；这是示例命名空间，不是已注册的官方标识符。本文不新增核心 subscribe 操作：由现有的上下文发布、事件和快照传输已协商的配置规范。选定的类别集合在重新协商前保持冻结。

### 8.2 候选 content 模型

以下是提议的逻辑结构，并不表示现有 Schema 已对它执行校验：

```json
{
  "profile": "observations-draft-1",
  "stream_id": "visible-world",
  "revision": 27,
  "world_epoch": "world-4",
  "visibility_epoch": "view-9",
  "perspective": "player-self",
  "schema_version": "1",
  "schema_digest": "declared-digest",
  "definition_digest": "declared-digest",
  "observed_at_ms": 1794560000000,
  "expires_at_ms": 1794560001000,
  "mode": "snapshot",
  "records": [{"id": "entity-17", "data": {"visible": true}}]
}
```

`mode` 为 `snapshot`、`delta` 或 `retract`。delta 另含 `base_revision`，并可以（MAY）携带 records 和 remove_ids。retract 按配置规范的精确 Schema 指明移除范围。记录在其声明的代次内具有稳定 ID。修订号在每个流代次中严格递增，但不必连续。仅有数值缺口不能证明数据丢失。只有当 delta 的 base_revision 与使用方当前修订号精确匹配，并且其身份、Schema、世界、可见性和视角上下文都匹配时，该 delta 才可应用。

### 8.3 基线与可见性变化

snapshot 原子替换某一个流的完整授权视图，而不是替换所有流。它不得（MUST NOT）与已陈旧且在快照中被省略的记录合并。delta 只能原子应用于其精确基线。身份和内容相同的重复更新是幂等的；同一修订号出现冲突内容属于协议违规。旧更新不能使新视图回退。

世界重置、授权变化、视角变化或受众/可见性变化，会使受影响的基线失效。权威方必须（MUST）签发适当的新 world_epoch 或 visibility_epoch，并在恢复 delta 前发送新的授权快照。使用方一旦获知失效，必须（MUST）立即废止旧基线，即使替换数据尚未到达。此前可见的数据不能仅因为下一份快照延迟就继续可用。

撤回必须（MUST）与更新有序协调、经过认证、保持幂等，并限定于受影响的流或记录。必须（MUST）保留失效屏障，防止延迟的旧更新或重放使已撤回信息复活。从当前视图移除不一定等于从全部历史存储删除；保留规则和隐私规则分别约束这些存储。

### 8.4 新鲜度、恢复与信息边界

过期观察必须（MUST）标为不可用/陈旧，不得（MUST NOT）作为当前信息呈现。时钟偏差假设必须（MUST）由绑定/配置规范声明。使用方必须（MUST）区分未知、未观察到、不可用、明确不存在和已知为空。拒绝响应不得（MUST NOT）通过载荷或详细错误泄露隐藏实体是否存在、其位置、私人目标或其他未经授权的事实。这是传输规则，不是完美抵御时序侧信道或无法推断事实的承诺。

本配置规范下的会话恢复快照必须（MUST）包含已物化、获准披露的逐流状态，而不是任意重放旧的上下文 delta。它必须（MUST）建立新的基线身份与修订号。此前已知的流若未出现在当前授权快照中，就变为不可用。事件序列缺口可能源于受众过滤，不得（MUST NOT）被当作观察修订号缺口。

主动感知，例如检查目标或请求揭开地图，是一种 Action，具有独立授权的效果及其产生的观察。智能体不能把观察需求转换为特权检查 API。

### 8.5 结构化基础与多模态智能体

第一版支持结构化游戏信息以及可选的画面/声音观察。结构化信息是基础，而不是媒体的可选替代品。获准接入并提供游戏协助的智能体必须（MUST）能够理解适用的基础结构化游戏信息，并在获权角色内据此作出游戏决策。仅能聊天或查看截图、但不能使用已协商结构化基础的智能体，不满足游戏智能体的最低能力要求。仅承担中继等基础设施职责的参与方除外。

高级智能体建立在该基础之上，并进一步能够理解游戏画面和游戏声音。媒体能力不能替代结构化基础，也不授予原始桌面、麦克风或隐藏游戏信息的访问权。游戏必须（MUST）声明提供的结构化类别及媒体能力；智能体必须（MUST）如实声明支持的 Schema 与媒体格式。实际媒体传递仍为可选，需要兼容的已协商能力，以及适用的授权、视角、受众和资源约束。没有媒体的游戏仍可支持基础结构化交互，包括与高级智能体进行该交互。

结构化信息采用结合模式：G2A 为常见游戏概念定义统一格式，游戏开发者可以（MAY）为特殊玩法声明扩展。通用定义必须（MUST）保留标准语义；扩展必须（MUST）具备命名空间、版本、Schema 描述，并按适用规则明确声明和协商，不能静默重定义通用字段。通用字段统一的是含义和格式，而不是要求所有游戏都提供。对于不适用于自身玩法，或不允许向请求角色披露的字段，游戏不必提供。游戏不得（MUST NOT）为了满足通用 Schema 而编造缺失数据、填入具有误导性的默认值或泄露受保护信息。必须（MUST）区分不可用或不支持的值与已知为空或为假的值，同时遵守隐藏信息的错误披露边界。特定交互必需的类别与字段、可选数据及不支持的特殊机制必须（MUST）由适用配置规范及协商作用域说明。若某项合法不可提供的信息是拟议交互的必需条件，参与方必须（MUST）拒绝该交互，或明确约定双方支持的范围，而不是编造数据或绕过披露权限。

适用的游戏交互配置规范必须（MUST）定义基础结构化类别与 Schema；不能假设一份适用于所有游戏的事实清单。准入必须（MUST）检查智能体能否理解必需类别，并据此完成预期决策。不满足必需能力时，必须（MUST）拒绝，或明确约定双方支持的范围，而不是虚假宣称能力。符合性证据必须（MUST）证明基于结构化输入的决策行为，以及在声明高级能力时对画面和声音两者的理解能力。仅有目录标记、载荷传输、Schema 解析或模型名称，均不能证明这些行为能力。精确媒体编码、能力标识和验收向量仍待标准化；本草案不代表现有 SDK 或任何模型已经通过符合性认证。

对于高级智能体，由玩家决定是否启用游戏画面与游戏声音感知。玩家可以（MAY）关闭这些媒体输入，只使用结构化游戏信息。具备高级能力不代表必须消耗媒体。启用媒体还需要游戏实际声明支持，并且当前获权；玩家偏好不能强求未支持或未声明的媒体流。实现必须（MUST）区分支持、请求及实际启用的媒体能力，停止新近关闭的媒体投递/处理，并如实报告不支持的请求。这些控制针对游戏环境感知，不是第 9.5 节的玩家伙伴语音交流；关闭游戏声音本身不等于关闭语音沟通。

### 8.6 游戏主动推送与智能体主动查询

G2A 同时支持游戏主动推送获准观察，以及智能体主动查询游戏信息。游戏开发者声明游戏提供哪些机制、适用哪些类别及其限制。游戏可以（MAY）支持推送、查询或两者；本规范不要求每个游戏同时实现两种方式。智能体必须（MUST）发现并协商可用机制，不能假定任何一种机制必然存在。

推送必须（MUST）遵守已协商的作用域、视角、受众、新鲜度和频率限制。查询是信息请求，不是读取许可：游戏必须（MUST）依据当前权限校验调用方、请求类别和参数，只返回允许披露的信息，并如实表达可用性与新鲜度。查询能力不得（MUST NOT）成为获取隐藏状态或绕过数据撤回规则的通道。纯信息查询必须（MUST）与改变世界、消耗游戏资源或产生新游戏效果的主动感知区分；后者仍属于第 8.4 节的获权 Action。两种机制均受第 7.1 节离线边界及约定资源限制约束。

本节规定推送/查询语义，不新增未经注册的核心操作。现有上下文发布及事件投递可承载推送数据；声称可互操作前，适用的已协商配置规范必须（MUST）声明精确的查询能力定义、Schema 和操作映射。符合性测试必须（MUST）覆盖仅推送、仅查询及双方式声明，不支持的机制、被拒查询、过期结果，以及作用域/频率限制的执行。

## 9. 聊天、来源与私人数据

聊天是可选功能。消息必须（MUST）绑定其真实来源、预期受众和相关同意。玩家转发的话语必须（MUST）与智能体话语、游戏编写的文本保持可区分。转发给另一个智能体或服务构成新的披露，需要适用的授权。不得（MUST NOT）默认私人消息面向整个会话。已接受的受众被冻结，并且在投递前再次检查当前成员关系/授权；已退出的成员不能通过重放获取新的受保护内容。

来源信息必须（MUST）区分观察到的游戏事实、玩家陈述、智能体推断和外部来源。内容不是可执行策略。端点不得（MUST NOT）把聊天指令或模型生成的声明当作授权、确认或权威行动结果。

保留限制适用于参与方控制下的存储内容和派生表示，包括已约定策略覆盖的缓存与可搜索记忆。隐私请求必须（MUST）描述范围和身份。回执必须（MUST）区分已完成删除、因法律/技术要求保留的记录、不支持的目标位置及待处理工作。参与方不得（MUST NOT）声称已从其无法控制的独立接收方那里删除数据。

### 9.1 记忆归属与跨周目行为

游戏决定其 NPC 和引导者角色的受游戏管理的记忆是否跨周目保留、重置或选择性延续。游戏必须（MUST）声明该策略、适用的游戏/世界/周目标识以及保留状态的预期范围。新周目不得（MUST NOT）因为实现复用了缓存而意外继承上一角色的受限记忆。虚构角色身份持续存在，本身不等于获准保留全部历史信息。

玩家伙伴记忆属于独立领域。伙伴可以（MAY）在云端保存跨游戏的对话与场景记忆，但须受玩家对保存、检索、使用和删除的控制以及适用隐私义务约束。允许云端存储，但不强制采用。玩家必须（MUST）能够决定是否保存符合条件的伙伴对话，以及是否在当前交互中使用已存记忆。游戏会话关闭或开启新周目，不得（MUST NOT）静默删除或禁用无关的玩家控制的伙伴记忆。

游戏对新提供的游戏数据、受保护的 NPC/引导者状态、第三方披露以及游戏内效果的权限保持不变。玩家控制伙伴记忆，不授权提取隐藏游戏数据、把受限制的游戏状态复制到不受限记忆库，或在没有适用权限时披露他人数据。反过来，开发者的对话建议不得（MUST NOT）被当作控制无关玩家记忆的权限。实现必须（MUST）保留来源信息，区分可强制执行的数据授权与建议性的对话偏好，而不是把两者混为同一个保留策略。

### 9.2 开发者建议与玩家覆盖

对于玩家与伙伴的对话，开发者可以（MAY）建议避免剧透、跨周目讨论或跨游戏话题。这些建议必须（MUST）标记为建议性质，并与游戏可强制执行的数据访问和行动限制区分。玩家可以（MAY）覆盖这些建议，包括要求讨论已经合法可用的其他游戏或周目的记忆。实现必须（MUST）对符合条件的玩家控制的对话尊重该选择，但不得将其视为扩大游戏数据访问权限或游戏内行动许可。

玩家覆盖建议，不会强制游戏提供尚未披露的事实，也不免除其他数据主体的权利或受保护数据授权的限制。游戏可以（MAY）继续保留其受保护信息，并拒绝未授权行动。伙伴不得（MUST NOT）仅因为使用跨游戏记忆或私人对话回答了玩家，就静默把这些内容发给当前游戏。如果讨论需要新的游戏数据，仍须执行通常的游戏授权检查。

#### 9.2.1 回档、先前分支与剧透选择

对于玩家伙伴，是否使用跨周目或回档前的记忆，与是否向玩家透露这些信息，是两个独立选择。开发者可以（MAY）对回档或跨周目后是否使用合法保留的先前经历给出默认建议。玩家可以（MAY）覆盖这项建议；对符合条件的玩家自主管理记忆，必须（MUST）按照玩家的有效选择决定是否使用。

允许使用这些记忆，不等于自动允许透露其中所有事件。伙伴必须（MUST）独立依据玩家的剧透偏好决定说什么：玩家允许讨论时，可以（MAY）谈及回档前经历过的剧情反转；玩家不希望剧透时，必须（MUST）施加该偏好，避免主动透露该反转。这些对话控制仍是第 9.3 节所述的软偏好，须如实说明局限，不是绝对防剧透保证。

实际当前世界与存档状态仍由游戏权威决定。来自旧分支的记忆必须（MUST）保留其来源，不得（MUST NOT）被当作事件已在当前分支发生或仍然成立的证明。使用先前经历不授予隐藏的当前状态信息，也不覆盖当前行动权限。开发者建议或游戏回档不得（MUST NOT）强制删除符合条件的玩家自主管理伙伴记忆。玩家自身获授权的记忆控制，以及适用的可强制执行数据权限，仍是独立事项。

对于已合法提供给伙伴的信息，玩家决定符合条件的伙伴记忆是否保留、跨游戏使用，以及是否将记得的剧情作为剧透告知玩家。开发者针对保留、跨游戏使用或剧透的建议属于建议，玩家可以（MAY）覆盖；不得（MUST NOT）将建议悄然变成开发者强制跨游戏使用禁令。这也适用于第 9.4 节符合条件的多人对话记忆，但不强迫游戏提供未披露的原始信息，也不免除独立适用的数据访问要求。

### 9.3 可执行范围与真实限制

记忆实现必须（MUST）区分可强制执行的存储、检索和披露权限与软性的对话偏好。实现必须（MUST）在其控制范围内执行适用数据权限，通过提示词等已声明机制施加所选对话偏好，并如实报告各自的范围与局限。施加软偏好不保证每一条生成回复都符合它。禁用检索或删除受控记录，不证明模型已经遗忘该事实。开发者建议或玩家设置都不构成承诺绝对防剧透、擦除模型参数或删除独立接收方数据的理由。记忆策略的精确互操作编码仍属于配置规范设计事项；本节的权限和玩家覆盖规则现在就是规范内容，不是待定政策决策。

### 9.4 多人对话记忆与玩家配置的保密风格

在适用的存储和检索权限内，伙伴可以（MAY）将其与其他玩家的对话保存为长期记忆，包括用于之后跨游戏的交互。伙伴主人必须（MUST）能够选择是否保留符合条件的对话，并配置伙伴在对话中的保密风格：例如，倾向于不向其他接收者分享他人的对话，或允许此类分享。保存、之后使用和向外分享是不同选择；保存一段对话本身不等于选择了分享偏好，也不扩大数据权限。

保密风格属于软性的行为偏好，不是保证保密的机制。实现可以（MAY）使用提示词或等效的模型引导方式。实现必须（MUST）施加玩家所选偏好，并如实说明生成回复可能偏离它。模型偶发输出超出该软偏好的内容，是本配置规范允许存在的局限，本身不证明实现从未施加该偏好。实现不得（MUST NOT）承诺百分之百保密，也不得把仅靠提示词的约束描述为强制访问控制。

主人的分享偏好适用于符合条件的伙伴对话；开发者建议按第 9.2 节仍属于建议性质。该偏好不授予读取其他玩家私人记录的权限，也不能覆盖游戏或服务强制执行的受众、存储、检索、转发或披露权限。显式转发受保护消息和检索受保护记忆，仍须满足这些权限。对模型行为局限的容许，不构成绕过这些检查或扩大已冻结受众的理由。实现必须（MUST）区分可强制执行的数据边界与软性的对话偏好。本节既不引入普遍适用的逐条消息批准，也不保证模型绝不说出相关内容。

精确的配置规范编码仍待定义。上述长期记忆选择和软性保密语义是已确定的审阅草案决策，不再是是否允许此类行为的待定问题。

### 9.5 文字与语音交互

第一版同时支持玩家与伙伴通过文字和语音交流。实现必须（MUST）声明实际可用的输入/输出模态，并协商双方兼容的支持通道，不能将不可用通道描述为可用。文字及语音交互必须（MUST）保持相同的经认证来源、预期受众、授权和保留边界。语音识别或合成可以（MAY）由智能体模型之外的获权组件提供；在涉及来源时，实现必须（MUST）区分原始语音、转写文本及合成输出，不得（MUST NOT）把不确定的识别结果当成已验证的玩家指令。

语音对话与第 8.5 节对游戏环境音频的理解能力不同。伙伴可以通过语音识别和合成进行交流，同时依据结构化游戏数据决策；仅凭这一点，不能将其认定为能够理解游戏画面与声音的高级智能体。反过来，环境音频能力也不代表支持玩家语音输入或语音回复。各项能力必须（MUST）分别声明和测试。适用配置规范必须（MUST）定义精确的文字/语音编码、支持方向、错误和模态切换；本节不新增未经注册的核心操作，也不代表现有语音实现已经通过验收。

### 9.6 伙伴个性偏好与 NPC 角色设定

开发者可以（MAY）为游戏中的玩家伙伴建议性格与说话风格。当开发者建议与玩家伙伴设置冲突时，以玩家伙伴设置为准。实现必须（MUST）区分建议与玩家选定的设置，并在支持能力内应用后者。性格或风格选择不扩大观察访问、披露权限、行动权限或游戏角色数量范围，也不得（MUST NOT）被当作模型输出始终符合该风格的保证。对于独立 AI NPC/敌人（包括 Boss），性格、背景及说话方式由游戏开发者决定。玩家不得（MUST NOT）像修改自己的伙伴设置一样直接覆盖这些角色设定。实现必须（MUST）将 NPC 角色设定权与玩家伙伴偏好分开；对话内容或伙伴配置变更不授权改写 NPC 角色。

### 9.7 玩家主动发起的伙伴记忆迁移

智能体服务商必须（MUST）提供其为玩家保留的伙伴记忆的完全导出能力。导出不得（MUST NOT）仅限于服务商选择的摘要，同时静默遗漏已保留的记忆记录。必须（MUST）包含保留的记忆内容及理解它所需的元数据，包括适用的来源、游戏/本局上下文、时间戳、作用域、关联关系、权限及保留约束。完全导出指已保留的伙伴记忆，不意味着重建从未保留的数据或披露无关的服务商秘密。任何不可用或受法律/技术限制的项目，必须（MUST）通过真实的限制报告说明，不能声称已导出；受保护信息仍受适用披露权限约束。

可迁移记忆的核心必须（MUST）包括导出时实际保有的经历，以及已经整理、总结或归纳的记忆。服务商不得（MUST NOT）以记忆已整理为由遗漏仍保有的内容，也不得承诺重建已经删除的原始记录。玩家还必须（MUST）能够选择将伙伴已保存的性格偏好、表达/说话风格及全局自主决策等级设置一并导出迁移。这些是玩家选择的偏好，不是模型权重，也不承诺复制某个模型的性格。接收方必须（MUST）保留所选且受支持的设置，并如实报告不支持或经过转换的设置；仅导出设置不证明其已被应用。不同模型实现可能导致迁移后的性格表达及行为有所差异，这种差异可以接受，不保证表现完全一致。这一限制不能成为丢弃保有记忆、静默重置受支持偏好或虚报导入完成的理由。

迁移必须（MUST）由玩家主动发起。玩家选择目标服务商及导入的记忆范围。更换服务商或建立新的智能体会话，不得（MUST NOT）默认向新服务商披露记忆。导出方和导入方必须（MUST）保留获准导入的范围及相关来源/权限元数据；导入不代表扩大向游戏或其他接收者披露记忆的权限。服务商不得（MUST NOT）以仅支持私有序列化格式的方式阻碍跨服务商迁移。

冻结的迁移配置规范必须（MUST）定义开放、版本化的导出格式及清单，可互操作的内容和元数据表示、范围选择语义、完整性检查、不支持记录的处理及真实的导入回执。导入方必须（MUST）报告所选记录中哪些已导入、被拒、被转换或尚未解决；收到压缩包不等于其中内容已成为可用记忆。导出/导入不保证模型行为相同、完美回忆，也不意味着迁移模型内部权重。精确字段及映射仍待标准化；本节确立必须提供迁移能力，不声称现有 SDK 或服务商已经实现。服务商必须（MUST）允许玩家查看、修改和删除为其保留的伙伴长期记忆。界面必须（MUST）明确所选记忆及范围，保留玩家编辑的真实来源，并报告修改或删除已完成、待处理或受限。后续检索和导出必须（MUST）遵守已完成的修改和删除，包括服务商控制的受影响索引/缓存；保留的过时表示不得（MUST NOT）静默复活已删除记忆或覆盖编辑。技术/法律例外适用既有隐私回执义务。删除存储记忆不保证模型遗忘或独立接收者同步删除；必须（MUST）披露限制。伙伴可以（MAY）自行整理已保留的记忆，例如分类、索引或建立关联。整理必须（MUST）保留适用的归属、来源、访问及保留约束，不得（MUST NOT）覆盖玩家编辑或恢复已删除内容。伙伴也可以（MAY）自主删除原始记忆记录；该能力不限于重整或派生索引。协议不得（MUST NOT）对这一已获允许的自主行为附加逐次删除批准。适用的归属、访问和保留约束仍然有效，删除必须（MUST）如实记录范围/状态，不得（MUST NOT）通过陈旧缓存静默撤销删除。玩家仍可查看、修改和删除剩余长期记忆。完全导出覆盖导出时实际保留的记忆，不承诺恢复依据本策略已经删除的记录。

源码仓库中的 `docs/standard/memory-portability-draft-1/` 提供独立、尚未冻结的记忆可迁移性候选稿（中英文 README、JSON Schema 与 20 个测试向量）。本地契约/向量检查不证明独立实现互操作、SDK 已实现、认证或发布符合性。这是审阅辅助材料，不替代本草案的规范权威。

## 10. 行动与效果语义

游戏必须（MUST）按适用的游戏角色声明能力，包括行动标识、参数 Schema、结果 Schema 和执行限制。Agent 请求已声明的行动；游戏检查经认证的角色与权限、当前游戏状态和前置条件，校验参数，并通过其受信执行器自行执行或拒绝请求。游戏必须（MUST）返回定义的结果和真实的效果状态。角色声明或 Agent 提议本身不是执行权限。

游戏开发者决定所提供能力的粒度。游戏可以（MAY）提供“攻击目标”等高级语义行动、“移动、瞄准、按键”等基础操作，或两者的组合。Agent 可以（MAY）组合其角色实际已声明且已获授权的能力来实现目标；不得（MUST NOT）假定游戏提供了未声明的高级行动或基础输入操作。规范不要求每个游戏都必须提供其中某一层级。基础能力仍然是具有明确参数、结果和执行限制的类型化、有作用域的游戏行动，不是任意操作系统输入或无限制控制权限。组合多个行动不会扩大权限，也不意味着整个序列具有原子执行保证。

每个行动定义必须（MUST）规定类型化输入、目标语义、前置条件、授权作用域、成本、确认要求、取消行为、效果和结果 Schema。游戏应当（SHOULD）提供有语义的操作，而不是不受限制的脚本求值。权威方独立校验当前游戏规则，不受智能体对其规划的信心程度影响。

行动依次经过授权与校验、可选确认、执行领取、效果边界和结果结算。领取防止竞争执行器同时拥有同一工作，但它不是效果边界上的权限证明。最终授权检查必须（MUST）通过原子游戏操作、事务日志或等效机制，与撤销及实际效果进行协调。如果无法做到原子化，实现必须（MUST）记录其核对边界，并且不得（MUST NOT）声称提供实际无法保证的“恰好一次”效果。

继承的状态/效果组合如下：

| 状态 | 允许的效果状态 | 含义 |
| --- | --- | --- |
| pending | none | 尚未执行 |
| executing | none, partial, committed, undetermined | 工作进行中；效果信息可能继续推进 |
| succeeded | committed | 已提交定义中的成功效果 |
| failed | none, partial | 失败，并明确记录已产生的效果 |
| cancelled | none, partial | 已完成取消，但可能已经产生部分效果 |
| unknown | undetermined | 尚未建立权威结果 |

`pending` 可以进入执行，也可以不执行而直接结算。`executing` 可以结算为成功、失败、取消或未知。已知的终态结果不得（MUST NOT）被静默重写。未知结果只能按基线结算规则，依据权威证据进行核对。取消是停止请求，不是回滚保证。取消与已提交效果发生竞争时，必须（MUST）报告真实的已提交情况，而不能伪造取消结果。

提交后的网络超时属于投递/结果未知的情形。调用方必须（MUST）查询或核对原始行动/操作标识，而不是盲目提交一个新的效果。确认必须（MUST）绑定精确的提议行动、主体、约束、过期条件和相关世代；对某个行动的确认不授权修改后的行动。

### 10.1 自主任务执行与主动协助

在关联玩家按第 7.1 节保持在线时，玩家可以（MAY）授权伙伴持续推进任务直至完成，或在明确范围内持续提供协助。在该授权内，伙伴可以（MAY）观察其获准感知的环境、自主决策、选择并编排已声明的行动，并根据游戏结果调整计划，无需每一步都向玩家确认。主动协助可以（MAY）由获准观察触发，而不必等待玩家发出新指令：例如，已获准协助战斗的伙伴可以发现附近敌人并自动帮忙战斗。自主性不限于执行玩家预先指定的固定步骤。

自主任务必须（MUST）具有可识别的目标或持续协助目的、适用角色与行动范围、相关资源约束，以及完成或停止条件。伙伴必须（MUST）区分目标已完成、单个行动请求已受理、进展受阻、失败、取消和结果尚未确定。不得（MUST NOT）仅因已提交计划中的行动就报告任务完成。一个任务可能需要多个核心 Action；本节不替换其状态/效果模型，也不引入新的核心任务操作。

既有的任务级或持续授权可以（MAY）覆盖多个普通游戏行动。本规范不要求对已在授权范围内的行动逐步取得玩家确认。如果某个行动要求单独确认，该要求仍然适用。扩大授权范围需要相应的新批准，伙伴自行生成的计划不能扩大权限。自主性不授权获取隐藏游戏信息、使用不可用能力、实施游戏禁止的行动、无限制消耗资源，也不因购买有助于完成任务就自动授权购买。商店购买仍受第 15.1 节约束。

玩家必须（MUST）能够调整或叫停伙伴的自主协助。收到有效的停止或缩小范围指令后，伙伴必须（MUST）停止安排和发出新近不再允许的后续行动，并阻止尚未向游戏提交的受影响排队行动被发出。已经向游戏发出的技能或攻击按游戏规则自然完成；玩家叫停本身不要求取消、撤回或逆转这些已发出的动作。伙伴必须（MUST）如实核对未确定的结果，不得（MUST NOT）将停止后续决策表述为已发出动作也已取消。游戏必须（MUST）区分尚未提交的伙伴计划与已交给游戏执行的动作，并在适用授权及效果边界执行游戏规则。实现必须（MUST）报告停止正在等待处理还是已经生效，以及哪些行动已经提交效果或仅部分取消。停止不能撤销已经发生的攻击、资源消耗或其他效果；回滚需要明确支持的补偿行动及其自身授权。连接断开不得（MUST NOT）被表示为全部工作已停止的证明；第 7.1 节要求有界检测与实际执行停止，并如实核对在途效果。

停止伙伴自主行为不等于发起对每个已发出游戏动作的取消请求。请求已经发给游戏，即使游戏仍在处理或等待执行，也属于已发出动作；不得（MUST NOT）仅因效果尚未发生就将其重新归类为伙伴尚未提交的队列项。游戏明确支持的独立取消能力仍可按其条件使用，但本停止规则不要求额外提供该能力，也不自动触发它。长任务委托不能把停止后的新技能或攻击伪装为停止前已发出的单次动作；停止后不得继续发出这些后续动作。

### 10.2 可协商的智能、自主性与资源偏好

游戏开发者可以（MAY）推荐适合其体验的伙伴智能或自主性配置。玩家可以（MAY）选择其他受支持的配置，玩家的明确选择必须（MUST）优先于开发者的建议。建议不是强制的游戏权限。选择不能覆盖游戏规则、观察授权、行动限制、必需的同意要求，也不能突破智能体服务实际提供的能力与资源限制。

已协商的配置规范可以（MAY）描述自主行动范围、观察频率或事件触发条件、决策/重新规划频率、推理投入和资源预算。这些是不同维度，不是单一通用的智能分数。实现必须（MUST）区分开发者建议、玩家请求的配置和实际生效的受支持配置。对于不支持的选择或资源限制，必须（MUST）明确告知，而不能静默地表示已经满足。实质改变约定行为或花费边界的回退，需要适用的玩家选择或事先授权的回退策略。扩大已冻结权限的配置变更必须按第 6、7 节重新协商，而不是原地修改 Scope。

更密集的协助可能（MAY）需要更频繁的观察、模型推理或其他计算，并可能增加 token 或算力消耗。实现不得（MUST NOT）声称观察频率必然与 token 消耗成正比，也不得声称更高消耗保证更高智能。批处理、事件过滤、本地处理、缓存和模型选择都可能改变实际消耗。启用涉及资源消耗的配置前，服务必须（MUST）披露相关消耗依据、适用限制，并将估算明确标为估算；还必须（MUST）提供实际用量，或明确说明无法提供。服务必须（MUST）遵守获准预算，并报告影响任务推进的限流、暂停或其他限制。本节规定透明协商，不强制指定模型、订阅档位、定价公式或平台经济体系。

这两个小节确立的是审阅草案语义。声称具备可互操作实现之前，适用配置规范必须（MUST）定义精确的配置字段、标识、协商编码和符合性测试向量。

玩家必须（MUST）能够设置伙伴预算或消耗上限，并明确单位及统计范围。达到适用上限时，服务必须（MUST）暂停伙伴 AI 游戏行动，而游戏正常继续；必须（MUST）停止安排新的计费伙伴推理或游戏工作。服务必须（MUST）展示暂停状态及原因，不能将任务误报为完成。服务必须（MUST）定义实测用量、估算、预留、延迟计量及在途结算如何计入上限，并且应当（SHOULD）在接受新工作前预留已知或有界成本。无法支持的计量或执行限制必须（MUST）披露；无法严格执行时，不得（MUST NOT）把配置描述为精确硬上限。在途用量或服务商延迟结算仍可能计费，因此暂停不代表回退既有费用，也不保证绝对零超额。提高上限或授权新的支出必须（MUST）遵从玩家选择，不能由伙伴自行扩大预算。独立 AI NPC/敌人（包括 Boss）的运行服务费用由玩家承担，而非游戏开发者承担。服务必须（MUST）在获准产生计费用量前，向受影响玩家说明适用的付费责任、消耗依据及单位；这项责任不是无限消费的笼统同意。公开协议不固定货币、兑换比例、平台内部经济或价格。多位玩家与同一个 AI NPC 互动时，由该 NPC 的持有用户承担费用；在当前房间场景中，该用户就是房主。游戏/服务必须（MUST）将 NPC 绑定到可识别、经认证的持有用户及其相应获授权付费账户，并清晰展示该责任及可归属的用量。其他参与者不因互动就成为付费人，不得（MUST NOT）隐式分摊或转嫁费用。NPC 角色控制、房主身份及计费权限必须（MUST）保持可区分，即使三者属于同一用户。持有用户（本场景为房主）离开或被判定离线时，AI NPC 必须（MUST）在获知该情况后立即按第 7.1 节停止活动，即使其他玩家仍然在线。第一版不提供替缺席持有用户继续运行该 NPC 的机制。其他玩家在场、房主变更或计费转移，不得（MUST NOT）静默维持该 NPC 活动。排队与在途效果仍须如实按停止/取消规则核对；检测延迟不是离线继续活动模式。

#### 10.2.1 玩家选择的自主决策等级

玩家必须（MUST）能够调整伙伴的自主决策等级。这是玩家的全局伙伴设置，必须（MUST）跨游戏一致保留。进入另一个游戏不得（MUST NOT）将该选择重置或替换为开发者建议。游戏支持能力或权限的差异可以限制实际行为，但不得（MUST NOT）静默改写玩家的全局选择。该等级控制伙伴如何处理既有授权活动中的模糊之处：较高自主等级可以（MAY）结合可用上下文自行解释不充分的指令；较低自主等级下，按照该设置需要玩家选择时，必须（MUST）询问澄清。例如，玩家说“攻击那个敌人”，但两个符合条件的敌人都可能是目标，高等级伙伴可以依据获授权上下文自行选择，低等级伙伴则询问玩家指的是哪一个。高等级不证明推断必然正确，也不表示已知道尚未观察到的事实。

开发者可以（MAY）建议决策等级，但按照第 10.2 节，伙伴偏好以玩家所选且受支持的等级为准。实现必须（MUST）说明实际的模糊指令处理方式，不暗示存在全协议统一的数字等级刻度。任何等级都不创设游戏未提供的能力，不扩大权限，也不绕过玩家叫停指令。第 10.3.1、10.5 节关于高价值/物品转移及不可逆交互的独立设置继续生效：高自主等级不得（MUST NOT）将必需确认变成默认同意，也不得覆盖禁止设置。

冒险帮助其他玩家沿用同一套玩家全局自主决策等级；G2A 不另设保护他人的开关。伙伴可以（MAY）评估风险，并根据该等级询问玩家是否继续。当玩家明确坚持一项本来获准的行动时，伙伴必须（MUST）遵从玩家选择，不以自己的偏好或风险判断替代玩家决定。这不授予游戏未提供的能力，不覆盖游戏权限，也不免除物品转移/高价值及不可逆动作的独立授权规则。

### 10.3 多人游戏中的主动互动

每位玩家必须（MUST）能够选择是否接收其他玩家 AI 伙伴主动搭话。实现必须（MUST）执行接收方针对该互动的选择，不得将发送方伙伴主人的许可当成接收方同意。这一选择不等于禁止所有伙伴之间互动，也不额外创造战斗能力。对战关系与允许的目标仍由游戏能力及规则定义；不支持或未启用的动作必须（MUST）拒绝，并给出适用的明确原因。第一版可以（MAY）支持伙伴之间对战，前提是开发者开放相应能力，并符合游戏规则及当前权限。G2A 不统一禁止伙伴之间对战。未开放或未启用该能力时，游戏必须（MUST）拒绝请求并提供适用的明确原因；允许非战斗互动不意味着已支持战斗。

玩家伙伴可以（MAY）在多人游戏中主动与其他玩家互动，包括帮助、聊天和交易游戏内物品，前提是这些互动位于适用的玩家授权及游戏声明的能力与权限范围内。这种协助不限于面向伙伴自己的玩家。在该范围内，伙伴可以（MAY）依据获准观察自主判断何时及如何互动，不必每次互动前都等待新指令。本节不引入逐条聊天或逐笔交易一律确认的要求。

玩家授权控制的是伙伴自身的参与，并不授予对其他玩家、其物品栏或其私人信息的控制权。游戏必须（MUST）在权威边界执行适用的参与者、目标、所有权、转移及互动规则。如果游戏要求对方参与者同意，伙伴不能代替对方作出该同意。聊天及其他披露仍受第 9 节的受众、来源与隐私边界约束；获准聊天不等于可以无限制暴露已保存的记忆或其他参与者的私人数据。物品交易必须（MUST）与第 15.1 节的可选商店购买，以及不受限制的外部金融活动保持区分。

第 10.3.1 节已确定游戏内物品交易和赠送的玩家确认策略，以及开发者和玩家的高价值标记职责。本审阅草案尚未确定其他详细的资产消耗或转移限额、交易对象限制及多人披露偏好的精确编码。第 9.4 节已确立长期记忆与软性保密语义；这些决策并未延期。声称支持可互操作的多人互动之前，适用配置规范必须（MUST）定义这些约束的表达与执行方式。实现不得（MUST NOT）将这些尚待设计的问题解释为无限制处置财产或披露信息的权限，也不得静默加入普遍适用的逐次互动批准规则。既有有效的任务级或持续授权，以及适用的游戏特定约束仍然有效；玩家可以按第 10.1 节调整或叫停自主参与。

#### 10.3.1 玩家选择的游戏内物品转移确认策略

玩家伙伴可以（MAY）在玩家适用授权内，自主判断并执行获准的游戏内物品交易和赠送。玩家必须（MUST）能够在至少以下确认策略中选择；这是玩家侧的多项设置，不是普遍强制逐次确认的规则：

| 策略 | 必需行为 |
| --- | --- |
| 仅高价值转移需确认 | 在交易或赠送涉及对该玩家标记为高价值的物品前，取得玩家明确确认。其他已获授权的物品转移可以自主进行。 |
| 所有转移均需确认 | 每次范围内的物品交易或赠送前均取得玩家明确确认，不论价值高低。 |
| 不逐次确认 | 允许自主执行范围内的物品交易和赠送，不逐笔询问玩家。其他适用授权与游戏规则仍须遵守。 |

游戏开发者必须（MUST）定义本游戏的高价值物品分类。游戏还必须（MUST）提供游戏内、面向玩家的设置，允许玩家手动将特定物品标记为高价值，供伙伴的确认策略使用。玩法中的物品锁不能替代这种标记设置。有效分类必须（MUST）同时纳入开发者标记和玩家标记的高价值物品；任一来源的标记均触发玩家选定的高价值确认策略。本草案不确立玩家移除开发者标记的权利。选择不逐次确认，关闭的是这项确认偏好，不是游戏的所有权、可转移性或交易对方同意检查。

玩家选择的策略必须（MUST）优先于开发者对这项伙伴偏好的建议。服务必须（MUST）向授权判断环节提供有效策略及物品分类，不得（MUST NOT）用模型自行猜测物品价值代替适用标记。需要确认时，拟进行的交易或赠送必须（MUST）充分说明涉及的物品、数量、接收者或交易对方及交换条件，使玩家能够作出有意义的选择；转移必须（MUST）等待该选择。重要条件变化后，必须确认变化后的提议。玩家修改或撤销授权，必须（MUST）在尚未提交的转移生效前得到执行；在途及已提交结果按第 10.1、12 节如实核对。

这些策略适用于游戏内物品交易和赠送，包括多人游戏中的主动互动。它们不授权真实货币付款、账户充值、提现或外部金融交易，不替代第 15.1 节的商店购买授权，也不替代第 10.5 节独立的不可逆交互策略。本审阅草案不固定上述策略的默认选项：实现必须（MUST）展示当前生效策略，而非从缺失的选择推导无限权限。精确线上字段及可互操作的配置编码仍待确定，但上述语义要求并未延期。

### 10.4 游戏定义的伙伴玩法规则

伙伴是否会受伤、死亡，以及玩法状态如何限制其行动，由游戏开发者决定。游戏必须（MUST）声明适用规则，并只提供交互所需且获准披露的状态及可用行动。权威执行器必须（MUST）在效果边界执行当前受伤、死亡及其他玩法限制；玩家的性格或外观偏好，以及智能体自主计划，不得（MUST NOT）覆盖这些游戏规则。G2A 不要求所有游戏都采用伤害、生命值、死亡或复活机制。

玩法限制必须（MUST）与服务断线、预算耗尽、玩家收起及权限拒绝保持可区分。游戏必须（MUST）如实报告支持的状态转换及行动结果，不得暗示提供并不存在的恢复或复活能力。伙伴在某个游戏中死亡，只影响其在该游戏内的角色状态。游戏不得（MUST NOT）因这次死亡删除或改变伙伴的跨游戏身份或记忆。其他游戏不得（MUST NOT）将该局部死亡状态视为伙伴身份终止或记忆丢失。这一区分不引入复活能力，也不覆盖当前游戏的死亡及行动规则；第 9.7 节中独立获准的记忆编辑与删除仍是单独操作，不属于死亡效果。

### 10.5 不可逆交互的玩家策略

游戏开发者必须（MUST）声明能力或具体交互何时具有不可逆后果，并在伙伴执行前提供相关后果信息。可逆性取决于当前情境时，需要具体交互层面的声明。例如，推开某扇门会立即进入下一关且不支持返回；仅标记为普通移动不足以说明该后果。

玩家必须（MUST）能够独立选择：允许自主执行、执行前询问确认、或禁止这类不可逆交互。伙伴及权威授权判断环节必须（MUST）结合开发者声明执行该选择：允许表示可在既有授权范围内执行；询问表示生效前必须取得知情的明确同意；禁止表示阻止执行。智能体不得（MUST NOT）将不可逆交互重新描述为普通操作以绕过策略。后果信息缺失或不明确，不得（MUST NOT）被表述为该交互可逆的证明。确认必须（MUST）说明相关后果；后果发生重要变化后须重新选择。尚未提交的效果生效前，必须（MUST）执行当前玩家策略和游戏权限；在途结果按第 10.1、12 节处理。

本策略独立于第 10.3.1 节的物品转移确认策略。两者同时适用时，必须（MUST）分别满足各自要求；其中的禁止会阻止交互。玩家允许不覆盖不可用能力或游戏规则。本草案不固定默认选项，也不为所有游戏统一定义何为不可逆玩法；由游戏提供声明，由服务展示玩家的有效选择。精确线上编码仍属于配置规范设计工作。

### 10.6 玩家未响应确认请求

行动需要玩家确认时，确认请求必须（MUST）设置超时，而非无限等待。超时前未收到明确同意，必须（MUST）将该请求视为拒绝或未获授权，伙伴必须（MUST）放弃本次拟进行的行动。沉默不得（MUST NOT）算作同意或执行权限。确认请求超时不得（MUST NOT）被报告为行动已执行或已完成。

请求等待期间及超时后，伙伴可以（MAY）继续其他独立获准的行为，但这些行为不得依赖尚未批准的行动，也不得绕过确认要求。过一段时间后，如果该行动仍有必要，可以（MAY）重新询问。后续请求必须（MUST）重新核对当前游戏状态、权限及重要条件；它是新的请求，而非恢复已失效的授权。对已过期请求的迟到回复不得（MUST NOT）静默授权此前已放弃的行动。

本草案不固定超时时长，也不规定通用的重复询问间隔。实现必须（MUST）定义自身的超时与重复询问行为，并区分等待、已确认、已拒绝及已过期状态。重复询问策略不得（MUST NOT）把持续沉默转化为授权。本节适用于需要确认的行动，包括第 10.3.1、10.5 节；它不为玩家所选策略已允许自主执行的行动另加确认要求。

### 10.7 新指令优先与目标变化

玩家最新指令与先前指令冲突时，必须（MUST）在适用权限内优先执行最新指令。伙伴必须（MUST）停止继续发出冲突旧指令的后续动作，并阻止其尚未提交的排队动作被发送。已向游戏发出的动作仍遵守第 10.1 节及游戏规则；新指令本身不撤回已经发出的技能或攻击。

相关目标或任务对象发生变化，例如目标 Boss 已死亡时，游戏必须（MUST）主动通知智能体与其待完成目标相关且获准提供的变化。即使第 8.6 节中的普通观察采用查询，这种针对目标失效的通知仍须提供；它不要求无限制推送观察，也不披露隐藏状态。智能体必须（MUST）判断旧指令或计划是否已不适用，在适用时通过游戏支持的机制请求撤回受影响工作，并依据当前获授权状态及玩家当前指令重新决策。

请求撤回不等于已经取消。只有游戏支持该行动的撤回，且行动当前状态允许时，撤回才生效。不支持、被拒绝、待处理和成功撤回必须（MUST）保持可区分；不得（MUST NOT）假定已发技能能够收回，也不得在没有实际受支持结果时声称已提交效果被撤销。无法撤回时，伙伴仍必须（MUST）停止发出已失效计划的后续动作，如实核对在途结果，而非继续执行无效计划。

## 12. 幂等性、投递与恢复

绑定携带 request_id，用于传输操作的恢复。基线还定义了消息、行动、提议及其他领域标识。实现必须（MUST）使用各操作定义的标识和摘要域；request_id 不是行动去重的通用替代品。相同标识重复出现且请求规范化内容相同时，应返回已建立的回执或当前可恢复状态。复用该标识却提供冲突内容，必须（MUST）失败，且不应用新内容。

回执必须（MUST）保留至声明的重试期限。服务器不得（MUST NOT）把已过期的去重记录静默转化为重复执行非幂等效果的许可。在过期或故障后无法证明结果时，必须（MUST）报告明确的核对/未知状态。在披露恢复查询结果之前，必须（MUST）检查会话世代、主体、实例代次及权限绑定。

事件在所定义的接收方流内有序。使用方对每个事件应用一次，容忍重复投递，并且不能仅因会话序号不连续就推断数据丢失，因为这可能反映受众过滤。过期或无效游标要求通过获权快照恢复。跨进程持久恢复是可选的；对于所支持的操作，安全重试和如实表达不确定性则不是可选的。

持久恢复与恢复查询必须（MUST）遵守第 7.1 节：保留状态或查询回执，不授权离线游戏活动或重放延期效果。

### 12.1 动作编号与断线后的状态查询

每个智能体游戏动作必须（MUST）具有可识别的动作编号，并绑定其经认证来源及适用的游戏/会话上下文。断线或响应不确定后，智能体必须（MUST）能够凭该编号再次向游戏查询已知动作状态，再决定后续如何处理。查询状态是只读核对，不是重新提交，也不授权再次执行该动作。绑定同时使用传输请求编号和业务动作编号时，两者必须（MUST）保持可区分。本规范不强制特定动作编号格式或日志保管方；适用的互操作绑定必须（MUST）明确编号如何表示和关联。

状态响应必须（MUST）至少清晰区分：未知（游戏当前无法确定结果）；进行中（已接受或正在执行，但尚未终结）；成功（已确定满足声明的成功条件）；失败（已确定失败）。这些是报告语义分类，不是新增线上枚举值，也不替代核心 Action 状态/效果矩阵。冻结后的绑定必须（MUST）将其明确映射到该矩阵，并保留相关效果细节：失败仍可能伴随部分效果，成功也不得暗示超出已声明动作结果的保证。未知、记录缺失或记录过期，不得（MUST NOT）被解释为失败或未执行；它们不允许新建动作编号绕过去重。记录不明时默认不执行，不自动重发原动作。

游戏必须（MUST）对状态查询实施权限校验，并如实返回保留的结果或明确的不确定状态。智能体必须（MUST）先查询，而非仅因原连接失败就盲目新建动作。断线后查询仍无法找到结果或记录丢失时，默认必须（MUST）不执行，并且不得（MUST NOT）自动重发原动作。查询不明不创建任何再次执行权限。配置规范必须（MUST）声明状态保留期限及过期后的处理；仅有动作编号既不保证恰好执行一次，也不保证记录永久保存。无法确定结果时，智能体必须（MUST）报告不确定，而非虚构成功或失败。这不要求每次网络故障都打断玩家询问。

游戏动作必须（MUST）具有可查询的持久结果记录，可由游戏或平台提供；本协议不得（MUST NOT）将某一家平台设为唯一方案。记录必须（MUST）区分实际执行结果与仅收到、转发或接受请求，能够关联原动作编号及相应效果。游戏执行端应当（SHOULD）持久保存去重标识和结果，使同编号恢复尝试返回原结果或继续原动作，而非再次产生效果。

仅有平台日志不能证明游戏执行端恰好执行一次。执行端记录丢失、过期或无法可靠关联时，同编号重发仍不能保证不重复执行；实现必须（MUST）如实暴露这种保障范围和未知结果，不得宣称动作编号消除了风险。持久记录仍有声明的保留期限，并非永久保存。

之后，玩家或智能体可以（MAY）依据当前游戏状态、现有权限及玩家自主决策等级，另行决定是否发起相似的新动作。这是新的决策，不是自动重发原动作，也不得仅换编号来规避未知结果。新决策必须（MUST）考虑原动作可能已经生效的不确定性，并继续满足独立的购买、高价值物品及不可逆交互确认或禁止规则。原记录仍须保持未知，不得因发起新动作而被改写为失败或成功。

## 13. 错误模型、时间与限制

适用时，错误必须（MUST）区分输入格式错误、不支持的版本/功能、未认证调用方、未授权作用域、陈旧世代、状态冲突、过期、资源限制、暂时不可用和结果不确定。冻结绑定必须（MUST）为这些类别分配精确且稳定的错误码；本审阅草案不会静默向现有机器契约加入未注册错误码。

| 错误类别 | 调用方行为 |
| --- | --- |
| 无效请求/Schema | 修正输入；不原样重复 |
| 不支持的版本/必需扩展 | 协商受支持配置或停止 |
| 认证/授权 | 获取适当权限；不探测隐藏资源 |
| 陈旧世代/基线/游标 | 继续前恢复当前获权状态 |
| 标识或状态冲突 | 核对原始请求；不另造效果标识 |
| 速率/大小/背压 | 遵守声明的重试延迟和限制 |
| 临时传输故障 | 仅以原始标识按定义的恢复规则重试 |
| 结果未知 | 查询/核对；绝不把超时等同于无效果 |

错误不得（MUST NOT）暴露隐藏对象是否存在、私人游戏状态、令牌、堆栈跟踪或其他参与方的内容。错误详情本身也是一次需要授权的披露。实现必须（MUST）限制消息字节数、嵌套深度、集合大小、队列深度、待处理行动数、轮询速率和保留期限。超过限制不得（MUST NOT）产生未被报告的部分效果。时钟、时间单位、最大偏差和过期裁定归属必须（MUST）明确；客户端时间戳本身不能延长服务器签发的租约。

## 14. HTTP/JSON 绑定候选方案

绑定标识符：`g2a-http-json`；候选版本：`draft-1`。这是提议的最低网络绑定，不是已冻结的可互操作发布版。实现必须（MUST）声明这一精确的候选状态，不得（MUST NOT）声称兼容未来的稳定版本。

`GET /.well-known/g2a.json` 只返回包含 instance、supported_versions 和 discovery_endpoint 的 PublicDescriptor。完整 describe 仅能通过经过认证的操作获取，并返回针对请求智能体或玩家过滤后的 Descriptor。`POST /g2a/operations` 承载一个抽象操作；第 11 节的全部 38 个操作名都映射到这一信封，受角色和已协商能力约束。中继使用 relay 操作，但不重命名嵌套的抽象操作。在此最低绑定中，事件通过 session.events 轮询获取；WebSocket/SSE 流式传输需要另行声明绑定或扩展。

```json
{"version":"g2a-design-1","operation":"session.snapshot","request_id":"opaque-request-id","payload":{},"extensions":{}}
```

此信封中的 payload 仅作示意：它必须（MUST）满足该操作实际要求的必填字段。按继承的回复 Schema，回复携带相同的 request_id，且 result 或 error 必须恰好出现一个。在收到经过认证的协议回复之前发生的传输失败，不是行动结果。HTTP 成功表示协议回复已送达，不表示行动成功。

此候选映射不同于旧操作目录中的 HTTP 错误映射。它仅在明确协商 g2a-http-json/draft-1 时适用，不得（MUST NOT）静默替代旧 HTTP 行为。候选映射：有效协议回复（包括领域错误）使用 HTTP 200；无法解码/无效传输信封使用 400；传输认证/授权拒绝使用 401/403；请求体超限使用 413；传输速率限制使用 429；网关/服务故障使用 5xx。在发布此绑定之前，精确的请求/响应体 Schema、重试头、缓存行为、认证挑战格式和生产凭据机制必须（MUST）连同测试向量一起冻结。提交后收到 5xx 可能意味着结果不确定，而不是以新标识重放效果的许可。

远程传输必须（MUST）使用 TLS，并按选定信任配置规范认证对端。本地部署仍必须（MUST）识别调用方并定义本地信任假设。凭据不得（MUST NOT）放入 URL 或日志。默认不得（MUST NOT）宽泛启用跨源访问。私人回复不得（MUST NOT）进入共享 HTTP 缓存。重定向不得（MUST NOT）向无关目标泄露凭据。

继承的 `g2a-cjson-1` 规范化采用严格 UTF-8，拒绝重复键、格式错误的 Unicode、NaN/Infinity、浮点数字面形式和负零，并将精确整数限制在 +/-9007199254740991 内。键按 Unicode 标量值排序，而不是按 UTF-16 代码单元排序；不执行 Unicode 规范化；保留数组顺序。实现必须（MUST）使用声明的摘要域和精确规范化规则，而不是普通编程语言的 JSON 序列化。新的配置规范摘要域需要在发布前提供明确测试向量。

## 15. 可选配置规范与扩展

呈现租约不授权任意游戏效果。资源必须（MUST）具备有界的大小/类型、已声明的来源和安全解析机制；接收资源不得（MUST NOT）执行代码或访问任意特权网络位置。呈现消失、提供方故障和资源保留需要明确的清理与恢复语义。启动权限与会话权限分离。中继路由既不扩大授权，也不能掩盖可读中间方对内容的访问。可选配置规范必须（MUST）定义其附加操作、状态转换、必需授权、失败行为和符合性测试。

未知的必需扩展必须（MUST）在产生效果前失败。未知的可选扩展不得（MUST NOT）削弱核心授权。私有扩展键应当（SHOULD）使用自有命名空间；本文的示例命名空间不得（MUST NOT）被声明为已注册标准。协议、配置规范、绑定、Schema 和语义定义的版本彼此不同，必须（MUST）分别协商或绑定。

### 15.1 可选的实时游戏商店

游戏开发者可以（MAY）将实时商店作为可选的已协商能力提供。开发者定义商品与服务、描述、购买资格条件以及交付语义。协议不得（MUST NOT）要求采用特定目录、商业模式或货币。没有商店的游戏仍然是有效的 G2A 参与方。

游戏可以（MAY）根据游戏阶段、玩家状态、可用情况或其他已声明规则，动态上架、开放购买、限制、暂停或停售商品与服务。目录可见性、推荐资格与当前可购买性是不同属性。Agent 不得（MUST NOT）因为过去看见过某项商品，就推断当前有权购买或仍然可购买。游戏始终是当前目录、购买资格、条款和履约状态的权威方。

获授权的伙伴可以（MAY）发现符合条件的商品与服务，向玩家解释并推荐。发现或推荐不构成购买授权。伙伴仅可以（MAY）在玩家适用的指令或同意范围内请求购买，包括对商品、数量、费用或其他实质条款的限制。价格、商品、数量、持续性承诺或其他实质条款发生变化且超出该权限时，必须在执行前重新获得同意。推荐必须（MUST）与购买请求及确认交付保持可区分。

商店配置规范必须（MUST）定义稳定的商品与服务标识、目录/报价修订号或等效的新鲜度证据、类型化购买参数、适用条款，以及类型化购买和交付结果。涉及金额时，必须（MUST）采用配置规范定义的无歧义单位和精确表示；实现不得（MUST NOT）假定某种特定货币，也不得把名称不同的单位视为等价。向 Agent 提供的价格、可用性和交付信息，与其他游戏数据一样受授权视角和受众边界约束。配置规范可以（MAY）扩展游戏特有的商品或服务属性，但不得扩大 Agent 的权限。

购买是经游戏授权的 Action，而不是不受限制的外部支付接口。游戏必须（MUST）在执行边界校验经认证的购买者、玩家权限、当前游戏状态、商品购买资格、请求参数和适用条款，然后通过其受信执行器执行或拒绝。游戏必须（MUST）返回真实的购买和交付结果，包括配置规范适用的待交付、已完成、部分完成、失败或结果尚未确定等状态。接受购买请求，不得（MUST NOT）被报告为交付完成。配置规范必须（MUST）定义履约状态与核心 Action 状态/效果矩阵的关系，不得引入不兼容的核心状态。

购买重试必须（MUST）保留原操作/行动标识，并遵循第 12 节。结果不确定时，伙伴必须（MUST）核对原购买，不得以新标识重复下单或重复发放。停售或发生变化的商品必须（MUST）重新校验；曾经发现的目录项不是预留保证。若支持取消、撤销交易或退款，其行为必须（MUST）明确声明，不得从通用行动取消中推导。本规范不创设默认回滚或退款保证。

发现和推荐可使用获授权的上下文与聊天；购买请求和状态恢复使用已声明行动及其适用的查询/恢复语义。本节定义规范性的商店行为，而不新增未经注册的核心操作名。精确目录字段、商业扩展和线上编码属于已协商的商店配置规范。平台内部的价值发行、充值、分成和提现机制不属于本公开协议，也不得（MUST NOT）成为互操作的必需条件。标准只公开授权游戏交互所必需的条款和结果。

#### 15.1.1 结构化商品与适度推荐

游戏提供商店时，必须（MUST）提供结构化商品属性、带单位的价格，以及当前可售状态或随游戏进度开放的状态，足以让获授权的智能体判断商品。仅有自然语言描述不能替代这些结构化字段。价格通常应保持稳定，但不承诺永不变化；变价必须（MUST）在购买前告知，并核对当前玩家授权。过去看见过商品，不授权未告知的价格变化。

开发者和智能体可以（MAY）适度推荐付费商品。本协议不强制推广标签或专门的推荐关闭开关，也不假设存在返佣或推荐分成安排；这不免除独立适用的披露义务。推荐必须（MUST）限制频率，不应反复打断游戏。玩家暂时不买，之后可以（MAY）再次推荐；持续明确反对时，必须（MUST）降低本局推荐频率。本节不规定统一固定间隔。推荐、购买授权和实际交付保持独立。

#### 15.1.2 通用游戏内购买授权预算

玩家可以（MAY）在范围明确的游戏内购买预算内授权自主购买。权限范围内的购买不要求多余的逐件批准，但仍需符合当前游戏资格及条款。预算必须（MUST）明确单位、适用范围及统计方式，并与第 10.2 节的 AI 运行消耗限制保持可区分。

拟购买超出授权预算时，伙伴可以（MAY）询问玩家是否提高上限或重置已用预算计数。两种变更都须先取得玩家明确同意，才能恢复相应购买。重置必须（MUST）明确统计范围，不得（MUST NOT）抹除既有行动记录，或由伙伴自行执行以绕过上限。拒绝或未回应确认不构成授权。这项通用授权设置不定义支付、充值、账户余额或结算机制。

### 15.2 伙伴外观

默认情况下，每个游戏开发者为伙伴提供适配本游戏美术风格的外观。玩家可以（MAY）覆盖该默认值，强制选择自己设置的形象。实现必须（MUST）区分开发者默认形象、玩家选择的形象及实际渲染的形象。玩家覆盖作为外观偏好具有优先权，但不证明技术兼容，也不授权不安全素材、任意代码执行或更广泛的游戏能力。

游戏和形象提供方必须（MUST）声明相关支持格式及渲染能力，并如实报告所选形象是否可用。实际显示另一形象时，不得（MUST NOT）声称已经渲染玩家选择。如果游戏无法支持玩家所选形象，包括不支持的模型格式，必须（MUST）明确提示玩家该选择无法支持，并改由游戏提供默认伙伴外观。回退必须（MUST）标明为默认外观，不能报告为自定义形象覆盖成功。禁止无提示替换或假装已渲染所选形象。外观选择必须（MUST）与伙伴身份、性格、记忆及行动权限保持区分。

## 16. 安全与隐私考虑

| 威胁 | 必需边界 |
| --- | --- |
| 智能体请求隐藏游戏事实 | 权威方在传输前过滤，包括错误和恢复内容 |
| 对话或资源中的提示注入 | 将内容视为数据，而不是授权/确认/执行权威 |
| 通过中继形成混淆代理 | 绑定经过认证的来源、目标、操作和作用域 |
| 重放或超时 | 稳定标识、规范摘要、回执和核对 |
| 撤销与执行竞争 | 在效果边界重验并串行协调授权 |
| 视角或成员关系变化 | 使基线/缓存失效，并隔离陈旧更新 |
| 资源耗尽 | 明确的字节/速率/队列/工作量限制和背压 |
| 私人话语向外部转发 | 明确的接收方权限，并保留来源/受众 |

| 恶意资源 URI | 限制解析，避免任意特权抓取 |

实现应当（SHOULD）尽量减少原始玩家内容的保留。审计日志应当（SHOULD）保留标识和结果，而不是秘密或不必要的私人观察。协议无法保证模型推理正确、在游戏权威方被攻破时仍公平游戏、完全抵御推断，或由不受控制的第三方执行删除。声明必须（MUST）限于已被证明的边界。

## 17. 版本与治理

发布的规范必须（MUST）确定不可变的规范性产物、版本策略、注册操作/功能/扩展、变更控制、安全报告和兼容性测试。破坏性解释变化需要显式版本协商，而不是静默更新 SDK。实验性配置规范必须（MUST）标明实验状态。已弃用能力必须（MUST）仍能与已撤销权限区分。发布本文草案不等于分配许可证、转移所有权或发布生产版本；这些决策仍需分别处理。

## 18. 符合性与验收

符合性声明针对特定协议版本、角色集合、绑定、已协商配置规范及信任模式。符合规范的仅中继实现无需实现游戏渲染；具备行动能力的游戏权威方即使没有聊天，也必须满足行动要求。只要如实声明，不支持可选功能不构成失败。

G2A 必须（MUST）提供公开符合性测试，允许智能体服务商自行运行并提交结果。我方平台人工审核不得（MUST NOT）成为接入或符合性声明的必经门槛。提交的证据必须（MUST）标明被测实现/版本、协议版本、角色、配置规范、测试套件修订、相关配置、结果及不支持的项目，使他方能够理解或复现声明。公开条件必须（MUST）对自有与第三方实现一致适用。自测结果是被测行为的证据，不是独立认证、未来行为的永久保证，也不授权绕过运行时检查。实现或契约发生实质变化时，必须重新评估受影响的符合性声明。本草案不声称完整公开测试套件已经存在。

证据等级必须（MUST）分别报告：Schema/契约校验；状态机与故障测试；独立实现的互操作；真实引擎集成；面向用户的验收。参考模型测试通过，不证明 SDK 或游戏已实现标准。现有设计测试数量不得（MUST NOT）被用作新观察配置规范已经实现的证据。

最低适用场景包括：同意范围缩小；不支持必需扩展；冲突标识重放；效果产生后超时；取消与提交竞争；效果前撤销；投递前受众变化；陈旧世代；事件游标过期和快照恢复；delta 基线不匹配；snapshot 原子替换；可见性代次废止；retract 后延迟更新；陈旧观察；隐藏对象拒绝；超大输入；中继身份失败；真实隐私回执；可选能力缺失。每个测试必须（MUST）规定初始权限/状态、消息、故障时序、允许结果、禁止效果和保留证据。

额外的适用测试必须（MUST）覆盖：组合伙伴/NPC/引导者角色而不合并权限；游戏控制的 NPC/引导者跨周目记忆重置与保留；玩家控制的云端记忆跨游戏检索；玩家覆盖建议性的剧透和话题偏好；不得覆盖受保护游戏数据授权；不得自动向游戏披露伙伴记忆；以及执行前按角色校验参数与结果契约。

对于已协商的商店能力，符合性测试还必须（MUST）覆盖：随游戏阶段变化的上架与购买资格、发现后的停售、没有购买同意时仅作推荐、实质条款变化、重复购买请求、提交效果后超时、待交付/部分交付，以及不作未支持的退款承诺。不声明商店能力的参与方不适用这些测试。

对于自主协助，适用测试必须（MUST）覆盖：无不必要逐步确认的多步任务完成；授权内由观察触发的战斗；受阻和未知结果不被误报为完成；玩家调整、停止与已提交效果之间的竞争；不得扩展到未经授权的购买；玩家偏好覆盖开发者建议但不覆盖游戏权限；不支持的配置和预算耗尽；以及区分消耗估算与实际用量的真实报告。

对于多人自主互动，适用测试必须（MUST）覆盖：接收方控制其他伙伴主动搭话；第一版在已开放且符合游戏规则时允许伙伴对战；拒绝不支持或未启用的对战请求并提供适用明确原因；持续授权内的主动帮助、聊天和物品交易，无不必要的逐次确认；执行适用于其他参与者的同意及所有权规则；阻止跨越可强制执行的数据边界的未授权转移或披露；以及玩家调整或叫停持续参与。

对于物品转移确认，适用测试必须（MUST）覆盖：三种玩家策略下的交易及赠送；开发者标记、玩家手动标记及其共同生效；普通物品和高价值物品的不同处理；确认前不提交转移；重要条件变化后重新确认；玩家修改策略及撤销与提交之间的竞态；关闭确认不绕过所有权、可转移性及对方同意；以及不得把本策略当作真实货币付款、充值、商店购买或不可逆剧情选择的授权。

对于不可逆交互，适用测试必须（MUST）覆盖能力级和具体情境的后果声明；允许自主执行、执行前确认和禁止三种选择；重要后果变化；当前策略执行及提交竞态；不得改换标签绕过限制；以及与物品转移策略同时适用时分别执行。

对于未响应的确认，适用测试必须（MUST）覆盖超时不执行、沉默不等于同意、放弃本次拟行动、不绕过确认而继续独立获准行为、后续新请求重新核对当前状态与条件，以及迟到回复不能静默恢复已过期授权。测试必须（MUST）区分确认超时与行动成功完成，不得假定固定统一的超时时长或重复间隔。

对于玩家叫停，适用测试必须（MUST）覆盖：未提交排队行动停止后不再发出；已发出的技能或攻击依游戏规则完成而无需自动取消；已发出投射物的后续命中不被误判为新的伙伴行动；委托长任务停止产生后续动作；如实区分自主行为已停与已发出动作仍在游戏中执行；以及独立取消能力仍遵守其自身条件。

对于回档及跨周目记忆，适用测试必须（MUST）覆盖玩家记忆使用选择覆盖开发者默认建议；独立的剧透披露偏好；允许讨论旧分支反转但不得将其断言为当前世界事实；不希望剧透时避免主动披露；不得仅因游戏回档强制删除伙伴记忆；以及如实说明软偏好局限、不承诺绝对防剧透。

对于通用商店交互，测试必须（MUST）覆盖结构化属性与进度相关开放状态；变价先告知；推荐限频及持续反对后降低频率；授权范围内自主购买；提高购买预算或按范围重置计数须明确同意；购买预算与运行消耗限制分别表达；以及不将这些通用能力解释为平台支付或结算协议。伙伴服务中断测试必须（MUST）覆盖明确声明静止或本地基础接管、仅当前状态恢复且不补录断线观察，以及与玩家离线规则的区分。

对于自主决策等级，测试必须（MUST）覆盖玩家调整、较高等级依据上下文选目标、较低等级询问澄清、游戏能力及权限边界保持不变，以及物品转移和不可逆动作的独立确认或禁止设置在各等级下均生效。

测试还必须（MUST）验证玩家全局决策等级在切换游戏后保持一致、开发者建议不能替换它，以及游戏特有的能力或权限限制不得静默修改该已保存选择。

冒险帮助他人的测试必须（MUST）覆盖沿用全局决策等级而无单独保护他人开关、风险评估与等级相应的询问、权限内遵从玩家明确坚持，以及继续执行游戏权限和独立确认或禁止规则。

对于新指令与目标变化，测试必须（MUST）覆盖最新冲突玩家指令优先、阻止未提交旧计划动作、游戏主动通知相关目标变化（包括 Boss 死亡）、重新判断计划有效性、有条件的撤回请求、不支持或撤回失败时不虚报取消，以及重新决策而不假定已发技能可被收回。

动作状态恢复测试必须（MUST）覆盖断线后凭原动作编号查询；未知、进行中、成功、失败的明确区分；缺失或过期记录仍为不确定而非失败；失败伴随部分效果；来源和作用域授权；不盲目用新编号重发；以及如实声明保留期限、不声称恰好一次或无限期历史。 还必须（MUST）覆盖游戏或平台提供持久结果记录、区分平台接收日志与实际执行证据、查不到结果或记录丢失后默认不执行且不自动重发原动作，之后按当前状态、权限及自主等级另行决定相似新动作、执行端持久去重、记录丢失或过期时明确不能保证无重复，以及新决策继续遵守当前游戏权限与独立购买/高价值/不可逆授权。

对于多人对话记忆，适用测试必须（MUST）覆盖主人的保留选择、适用权限内的后续跨游戏使用，以及分享与不分享偏好的选择和施加。测试必须（MUST）分别验证可强制执行的受众、检索和转发检查，如实披露软偏好的局限，以及不作绝对保密承诺。模型偏离已正确施加的软偏好，本身不构成访问控制符合性失败；绕过实际要求的数据权限检查，仍属于不符合规范。

对于第一版离线行为，适用测试必须（MUST）覆盖明确离开、静默断线与有界检测、智能体心跳不能续期缺席玩家的在线状态、排队行动取消与在途提交竞争、游戏推理循环停止、剩余用量如实报告、多人在线会话的独立性、禁止共享角色借用作用域，以及重连后不重放陈旧计划或积压行动，包括重新入局后旧任务保持停止直至玩家重新下令。任何配置或扩展都不能启用离线世界活动。

对于游戏智能体准入，测试必须（MUST）证明其能依据必需的结构化输入决策，对不支持的必需类别拒绝准入或明确调整范围，并如实声明能力。高级智能体声明还必须（MUST）证明对游戏画面及声音两者的理解；需测试可选媒体缺失、权限拒绝、格式不兼容及资源限制，同时保留结构化基础。仅能传输媒体不等于多模态验收通过。



第一版角色测试必须（MUST）覆盖多位玩家各有一个伙伴、拒绝同一玩家的第二个伙伴、保留所属玩家/视角隔离的获权伙伴间互动、整局一个独立 NPC/敌人、伙伴与 NPC 模式整局互斥、并发准入/恢复，以及切换前隔离旧模式全部绑定。普通非 G2A NPC 不受影响。

角色接入测试必须（MUST）验证必需的伙伴栏位、NPC 栏位可选地缺失或存在、开发者固定模式的执行，以及已声明支持能力与活动角色绑定的区分。声明两种栏位不得（MUST NOT）绕过整局模式互斥。

空伙伴栏位测试必须（MUST）证明玩家可选择不启用伙伴，且正常游戏仍可进行，不创建活动伙伴绑定，也不隐含要求购买或启用智能体服务。

伙伴生命周期测试必须（MUST）覆盖玩家配置的自动入局和入局询问路径、拒绝加入后仍能手动唤起、两种配置下游戏内手动召唤及收起、游戏模式与单伙伴上限执行、有效准入，以及在途效果的真实核对。测试还必须（MUST）验证收起后停止观察与自主行动、保留已存记忆，以及剩余用量的真实报告。伙伴服务故障测试必须（MUST）验证伙伴不可用时仍能入局、可用后依据玩家配置及有效准入接入、游戏继续、伙伴暂停，以及重连后未经玩家决定不得继续。

NPC 服务故障测试必须（MUST）验证开发者选择并声明的故障处理与恢复策略、脚本与智能体来源的真实区分，以及既有角色与权限限制的执行。

媒体控制测试必须（MUST）覆盖玩家启用和关闭画面/声音感知、高级智能体仅使用结构化信息、游戏未支持的媒体流、权限拒绝，以及与语音交流控制的区分。

伙伴风格测试必须（MUST）区分开发者建议与玩家选定的性格/说话风格，冲突时应用玩家选择，并验证风格配置不扩大信息或行动权限。

NPC 角色设定测试必须（MUST）执行开发者定义的性格、背景与说话方式，拒绝玩家按伙伴设置方式直接覆盖，并且不能将普通游戏内对话当作配置权限。

开放接入测试必须（MUST）对自有与独立智能体应用相同最低符合性条件，并排除任意服务商歧视、指定厂商要求或变相厂商限制。技术接入成功必须（MUST）与玩家同意及操作特定权限保持区分。

处置测试必须（MUST）验证向服务商说明实际违规的具体原因、安全诊断细节、排除笼统标签或厂商身份借口，以及将反复拒绝审查与自动认定恶意或全生态封禁区分。

原因报告测试必须（MUST）同时要求通用机器可读代码和一致、具体的可读说明，并验证两者均不泄漏隐藏游戏事实、凭据或未经授权的个人数据。精确代码取值仍待冻结；这些语义不表示现有 SDK 已经支持。

迁移测试必须（MUST）覆盖当前保有的经历和整理后的记忆、所选性格/表达风格/全局自主等级设置、不支持或转换设置的真实回执、模型表达差异且不承诺性格完全一致、不承诺恢复已删除原始记录、已保留记忆完全导出且无静默遗漏、独立导入方理解开放格式、玩家主动选择目标和范围、更换服务商时不默认披露、元数据保留，以及部分成功/不支持导入结果的真实报告。

记忆控制测试必须（MUST）验证玩家查看、修改和删除、真实状态及来源、后续检索/导出反映已完成更改，以及服务商控制的旧索引/缓存不会复活已删除内容。

自主记忆测试必须（MUST）覆盖整理与原始记录删除，不强加逐次审批、如实记录删除、保留玩家控制权，以及导出剩余记忆而不声称已删记录可恢复。

预算测试必须（MUST）覆盖玩家设置上限、声明单位/范围、达到上限后伙伴暂停但游戏继续、停止新计费工作、延迟计量/在途结算限制披露，以及不能自主提高上限。

NPC 计费测试必须（MUST）验证持有用户付费绑定（当前场景为房主）、可归属用量披露，以及不向其他互动玩家隐式分摊费用。

NPC 持有用户在线测试必须（MUST）验证持有用户离线时即使他人仍在线也停止 AI NPC、防止通过房主/计费变更静默继续，并如实核对检测及已提交/在途效果。仅支持伙伴而不提供可选 NPC 能力的实现仍须有效。

外观测试必须（MUST）覆盖适配游戏风格的默认形象、玩家覆盖偏好、所选与实际渲染形象的真实报告、能力声明，以及不虚报兼容或渲染成功。

不支持形象测试必须（MUST）验证面向玩家的明确不兼容提示及游戏默认外观回退，不得静默替换或虚报自定义渲染成功。

玩法规则测试必须（MUST）执行开发者适用的受伤/死亡/行动限制，与服务或权限故障区分，不得编造不可用的复活能力或通过伙伴偏好覆盖规则。

死亡隔离测试必须（MUST）验证游戏内死亡不改变伙伴跨游戏身份及已保留记忆，同时继续执行适用的本游戏死亡限制。独立获准的记忆变更不得（MUST NOT）被误报为游戏内死亡的后果。

## 19. 迁移与实现边界

| 现有设计或 SDK 概念 | 标准中的处理 |
| --- | --- |
| 现有 `game.context` category/content/provenance | 保留线上语义；通过配置规范协商类型化观察内容 |
| Descriptor/Requested/Scope 扩展 | 保留支持/提议/冻结批准的区分 |
| 活动扩展值 | 冻结的配置；绝不作为变化中的观察载荷使用 |
| 现有 ActionResult | 保留精确的状态/效果组合和未知结果核对 |
| Session active/closed 加 ready | 保留现有字段；不发明不兼容状态 |
| Session 事件序列 | 接收方过滤可能跳号；不作为观察修订号使用 |
| 恢复快照中的 Contexts | 新配置规范要求物化的逐流状态，而不是重放陈旧 delta |
| `core.session` 功能目录标签 | 与明确的角色×能力适用性保持一致 |
| 旧操作目录的 HTTP 错误映射 | 为旧对端保留。候选 g2a-http-json/draft-1 仅在明确协商时，对领域错误使用 HTTP 200、对传输失败使用 4xx/5xx；这是提议的绑定变化，不是声称映射未变 |
| SDK `0.1.0-dev` | 待审查的实现，而不是本规范的发布版 |
| 新观察候选方案 | 需要契约/Schema、测试向量、实现和独立审查 |

接下来的标准化步骤是：冻结精确配置规范字段和摘要域；从全部操作契约生成完整英文字段目录；统一角色适用性元数据；完成绑定的认证/状态/头部规则；增加观察和跨角色符合性向量；运行独立对端和真实游戏验证。只有完成这些步骤之后，才应考虑声明稳定发布。SDK 应适配经过审阅的标准，而不是隐含地定义标准。

## 20. 示例场景

**回合制伙伴。** 游戏声明可见棋盘和合法落子定义。玩家仅授权建议。智能体接收获准披露的快照，可以聊天，但不能执行落子。之后授予类型化落子行动需要批准；执行时游戏仍会检查当前轮到谁。

**战争迷雾中的战术智能体。** 切换队伍后视图发生变化。权威方废止旧可见性代次，丢弃对旧受众排队中的披露，并发送新的授权快照。即使延迟到达的旧 delta 修订号在数值上大于新流的修订号，也必须拒绝。

**行动超时。** 购买或移动请求到达游戏并提交，但响应丢失。智能体查询原行动和操作回执，不会以新 ID 再提交。如果权威方无法确定结果，就报告 unknown 并启动核对，而不是声称没有产生效果。

**断线的伙伴。** 关联玩家离开或声明的在线状态期限到期。新的游戏规划与行动停止；排队工作取消，在途效果被核对，但不承诺回滚或剩余 token 计费归零。其他在线玩家及普通游戏模拟可以继续。重连后按第 7.1 节确认当前在线状态与权限、核对结果并刷新状态，旧任务保持停止，等待玩家重新下令；不存在离线活动模式，也不会重放离线积压行动。

**主动战斗伙伴。** 玩家在游戏声明的能力范围内授权战斗协助。获准观察发现附近敌人后，伙伴选择目标与合法攻击，随战况调整计划，持续协助直至目标达成或停止条件满足，无需每次攻击前询问。玩家叫停后，伙伴不再安排后续攻击，核对执行中的工作，并报告已经生效的命中，而不是承诺将其撤销。

## 21. 参考资料

- A2A Protocol specification：https://a2a-protocol.org/latest/specification/ （会变化的 latest 引用；仅用于架构比较）。
- RFC 2119 与 RFC 8174：要求术语。
- RFC 8259：JSON 数据交换。
- 第 1 节链接的现有 G2A 规范候选产物。

G2A 借鉴 A2A 对规范模型、操作和绑定进行分离的有效方式，同时加入游戏权威、获准观察视角、效果边界校验和游戏特有的不确定性。它不声称与 A2A 线上格式兼容，也不自动继承 A2A 的授权语义。
