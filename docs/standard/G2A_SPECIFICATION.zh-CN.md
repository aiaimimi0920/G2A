# G2A 协议规范

**Game-to-Agent Interaction Protocol｜游戏与智能体交互协议**

定义游戏与 AI 智能体之间通过**交互源点**、**智能枢纽**与**演算中枢**三层架构实现能力表同步、动态可用方法感知与方法调用队列执行的开放协议标准。

状态：公开审阅工作草案（`standard-review-2026-11-23-r81`）｜修订日期：2026 年 11 月 23 日｜语言版本：[English Specification](G2A_SPECIFICATION.md)

## 架构总览与核心交互案例

### 三层架构总览流程图

G2A 旨在让任何游戏以**极低的开发成本**安全引入 AI 角色（包括陪伴玩家的**伴游 / 玩家伴玩**与可选的**独立 AI NPC**）。入局时同步一次角色通用能力总表（类比 MCP 可用工具表），运行期由**交互源点 SDK** 自动向**智能枢纽**增量同步当前可用方法序号与目标，再由**演算中枢**按需编排**方法调用队列**交由**智能枢纽**逐条安全调度执行：

```text
                        [ 真人玩家 Human Player ]
               ┌────────────────────┴────────────────────┐
       游戏内操控 / 发出任务指令                 授权审批 / 整队确认 / 选配中枢
               ▼                                         ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第一层：交互源点 (Interaction Origin · 随游戏分发的轻量宿主 SDK)     │
│  • 入局同步通用能力总表 (#01 移动 / #02 通用交互 / #03 技能...)      │
│  • 运行期 SDK 自动扫描并增量同步【状态摘要 + 当前可用方法序号/目标】 │
│  • 按指定主体 (actor=伴游/玩家) 直达动作效果层结算，绕过键位动画互斥 │
└───────────────────────────────────▲──────────────────────────────────┘
                                    │ 南向接口（本机回环 / 服务端内网 HTTP）
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第二层：智能枢纽 (Intelligent Hub · 开源安全盾牌与队列调度中枢)      │
│  • 单机电脑单次安装全局共用 / 网络游戏部署于服务端统一同步多端战局   │
│  • 缓存能力表并实时维护可用方法集，向演算中枢按需投影当前活跃方法    │
│  • 集中托管：权限核验、整队确认门禁、防重放去重、队列逐条调度与熔断  │
└───────────────────────────────────▲──────────────────────────────────┘
                                    │ 北向接口（标准 G2A HTTPS / 流式协议）
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第三层：演算中枢 (Computation Core · 云端或本地认知推理引擎)         │
│  • 基于可用方法序号判定任务可行性，抽象编排【方法调用队列】并管记忆  │
└──────────────────────────────────────────────────────────────────────┘
```

### 案例一流程图：用户主动向伴游发出指令 —— “打开右侧的宝箱”

此案例由**玩家明确指令**触发。入局已完成能力总表缓存（`#01 move_to`、`#02 interact`）；玩家下令瞬间，**智能枢纽**无需回头查询游戏，直接将**玩家指令 + 当前活跃可用方法序号及双视角目标信息**一并推给**演算中枢**，单次推理即可生成完整调用队列并逐条落地：

```text

│ [前置状态] 入局已缓存能力总表：#01 move_to(target), #02 interact(t)  │
│ 交互源点 SDK 已向智能枢纽增量同步当前可用方法（rev=18）：            │
│  • #01 move_to ──▶ 可选目标: chest_R (玩家右侧 4m / 距伴游 5m, ready)│
│  • #02 interact ──▶ 可选目标: chest_R (木宝箱·打开, staged: 需先靠近)│
└───────────────────────────────────┬──────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 1. [玩家 ──▶ 交互源点 ──▶ 智能枢纽]                                  │
│    玩家发出语音/文字指令：“打开右侧的宝箱”                           │
│    智能枢纽直接拼装【指令 + 当前活跃可用序号 #01/#02】发往演算中枢   │
└───────────────────────────────────┬──────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 2. [演算中枢：可行性判定与队列编排]                                  │
│    核对可用序号：定位“玩家右侧”目标为 chest_R，判定可执行；          │
│    因 #02 处于 staged（需先靠近），单次推理编排出有序方法调用队列：  │
│    Queue Q-101 = [ Step1: #01(chest_R) ──▶ Step2: #02(chest_R) ]     │
└───────────────────────────────────┬──────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 3. [智能枢纽：防重放去重与逐条受控调度]                              │
│    校验授权与 Q-101 去重账本（网络重发直接拦截，绝不二次执行）：     │
│    • 下发 Step1 ──▶ 交互源点执行 #01(actor=伴游, target=chest_R)     │
│      伴游寻路抵达宝箱前，交互源点增量上报 #02(chest_R) 变为 ready    │
│    • 下发 Step2 ──▶ 交互源点执行 #02(actor=伴游, target=chest_R)     │

└───────────────────────────────────┬──────────────────────────────────┘
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 4. [智能枢纽 ──▶ 演算中枢 ──▶ 玩家]                                  │
│    汇总队列真实执行结果回传演算中枢；伴游向玩家播报开箱收获          │
```

## 1. 引言与核心原则

### 1.1 协议目标与适用边界

G2A（Game-to-Agent Interaction Protocol）是一项面向游戏与 AI 智能体的开放通信协议，通过**能力表注册、动态可用方法同步与方法调用队列编排**，标准化游戏世界与 AI 角色（跨游戏玩家伴游及可选独立 AI NPC）之间的感知、授权与行动交互。

- **适用范围：** 玩家伴游（Player Companion）、独立 AI NPC（如 Boss、战术队友或引导者）、游戏状态与可用方法同步、受约束的方法队列执行及角色对话。
- **非目标边界：** G2A **不是**操作系统级屏幕抓取或模拟物理键鼠输入的外部脚本工具，不规范任意远程代码执行、特定大模型的内部权重，也不干涉商业平台内部分成合同。

### 1.2 五项指导原则

1. **动词通用化与源点零负担：** 游戏无需为每种场景道具编写专有接口，仅复用角色原有的少量通用动作方法；动态空间扫描与增量差分由**交互源点 SDK** 自动托管。
2. **能力受限编排与世界最终权威：** **演算中枢**仅能在当前同步的合法可用方法序号集合内编排调用队列；物理碰撞、距离与胜负规则由**交互源点**最终裁定。
3. **智能枢纽集中托管安全与调度：** 鉴权、整队确认门禁、网络防重放去重、队列逐条调度与异常熔断统一收敛于开源可审计的**智能枢纽**。
4. **支持不等于授权，离线即停：** 一切调用受玩家批准的权限范围约束；一旦关联真人玩家离线，严禁智能体在空游戏世界中后台自动运行。
5. **开放互操作与记忆主权：** 协议中立兼容任意游戏引擎与模型服务；玩家伴游长期记忆独立于单局读档回退，并支持以公开标准格式自由导出。

### 1.3 规范用语约定

本文中加粗的“**必须**（MUST）”“**必需**（REQUIRED）”“**不得**（MUST NOT）”“**应**（SHOULD）”“**不应**（SHOULD NOT）”与“**可以**（MAY）”按 RFC 2119 与 RFC 8174（BCP 14）解释。开篇流程图用于直观阐明协议交互流转，不限定内部实现语言。

## 2. 三层系统架构与零负担接入模型

### 2.1 三大核心层级职责

| 标准层级 | 核心定位 | 权责边界 |
| --- | --- | --- |
| **交互源点**（`Interaction Origin`） | 游戏宿主与随包轻量 SDK | 唯一权威世界状态源与动作执行端。入局输出静态能力总表，运行期由 SDK 自动输出轻量状态摘要与按主体区分的动态可用方法序号，并在指定主体（`actor = companion` 或受权 `player`）上直达动作效果层结算；未揭晓的游戏隐藏秘密**必须**留在内部，绝不外发。 |
| **智能枢纽**（`Intelligent Hub`） | 开源安全盾牌与队列调度中枢 | 连接**交互源点**与**演算中枢**的协议引擎（参考实现源码完整公开）。缓存静态能力总表、维护最新可用方法视图、按需投影活跃方法以节省上下文开销，并统一负责鉴权、防重放去重、整队确认挑战与队列逐条下发熔断。 |
| **演算中枢**（`Computation Core`） | 云端或本地认知推理引擎 | 受权驱动角色槽位的推理与记忆服务。根据玩家指令或定期读取的活跃可用方法，判定任务可行性并输出有序**方法调用队列**，无需适配不同游戏引擎底层。 |

### 2.2 开发者零负担接入与部署拓扑

为避免“高频可变状态难以手写维护”与“区分玩家/伴游需写两遍代码”的开发负担，**交互源点 SDK** 采用**组件挂牌自动路由 + 动作效果直绑 + 底层脏差分**机制：开发者仅需在玩家与（若有局内实体的）伴游预制体上各挂载轻量 `actor` 角色标签，并将现有角色组件方法或允许代按的辅助快捷键效果注册**一次**（无需编写 `if (actor == player)` 分支，老项目亦可直接注册现成玩家单例效果而无需重构）；SDK 在后台低频自动巡检场上 `player` 与 `companion` 实例的组件可用性、相对方位与增量差分（状态无变化时零发包），并在执行时自动路由至对应实例的业务效果函数。

| 部署模式 | 组件运行位置 | 运行与分发特征 |
| --- | --- | --- |
| **单机与客户端宿主模式** | 本地游戏**交互源点** ↔ 玩家电脑**全局共享智能枢纽** ↔ 云端或本地**演算中枢** | 游戏发行时**仅随包分发极小的交互源点 SDK**；玩家整台电脑**单次安装一个智能枢纽供本机所有兼容游戏全局共用**（首次缺失时按需引导下载）。本机回环 HTTP 单跳耗时低于毫秒级。 |
| **服务端权威网络游戏模式** | 游戏服**交互源点** ↔ 服务端集群**智能枢纽** ↔ 云端**演算中枢** | 玩家本地电脑仅运行普通游戏客户端，不接触 AI 接入组件；**交互源点**与**智能枢纽**统一部署于服务端内网，汇总授权视野、协调高并发队列调度，确保组队副本中全队面对一致同步的 AI 反应，同时严格隔离个人伴游与敌对阵营视野。 |
| **NAT 出站连接模式** | 客户端**智能枢纽**（主动出站）↔ 云端中继 / **演算中枢** | 位于家庭防火墙后的客户端**智能枢纽**主动发起出站加密连接，无需在玩家设备上开放任何入站端口。 |

## 3. 通用动作原语、双主体机制与标准接口

### 3.1 通用动作原语、双主体分流与直达效果层准则

为彻底规避“开门、开箱、开电脑各写一个专有接口”的方法爆炸陷阱，同时精准区分“你的装备/你面前的箱子”与“我的装备/我右边的箱子”并消除快捷键动画冲突，**交互源点**遵循三项核心建模准则：

1. **复用角色通用动作，拒绝道具专有方法爆炸：** 静态能力总表定义的是**角色身上的少量通用动作（动词）**——通常直接映射游戏输入动作表（Input Actions）背后的十余个核心逻辑方法加上基础寻路 `move_to(target_id)`（例如用一个通用 `interact(target_id)` 即可复用游戏原有的交互基类，打通全游戏所有的门、宝箱、电脑与机关；用一个 `toggle_flashlight()` 控制手电筒；卡牌游戏仅需一个通用 `play_card(card_id, target_id)`）。仅当某项特殊玩法存在额外结构化参数（如输入密码或按数量合成）时，才按需增设专有方法。
2. **双执行主体分流（`actor = companion | player`）与双视角空间锚点：**
   - **显式区分伴游实体与受权代操玩家：** 可用方法上报与 `origin.execute` 调用**必须**显式携带执行主体 `actor`：
     - `actor = companion`（伴游自身实体）：仅当伴游在局内拥有真实角色实体且挂载对应装备/能力时由 SDK 自动暴露，距离与状态校验以**伴游自身实体**为原点——既确保伴游面前的宝箱即使远离真人玩家也能由伴游成功开启，也确保玩家下令“打开你的手电筒”时精准开启伴游自己的手电筒（若伴游无局内实体或未配备手电筒，则不上报 `actor = companion`，**演算中枢**据此如实告知玩家而绝不误触玩家手电筒）；
     - `actor = player`（受权代操玩家主角）：当游戏规则开放某项玩家辅助快捷键代执行（如开关手电筒、标点、切道具或无肉身伴游/卡牌辅助，默认关闭基础移动与竞技瞄准）且获得玩家授权时暴露，距离与状态校验以**玩家主角实体**为原点，支持玩家在忙碌操作时下令“打开我的手电筒”直接代操作玩家手里的手电筒；
   - **双视角空间参考标签：** 候选 `target_id` 同时标注**相对于执行主体的可执行状态**（如 `ready: 距伴游 1m` 或 `staged: 距伴游 5m，需靠近`）与**相对于真人玩家的方位/视线焦点**（如 `玩家右侧 4m` 或 `玩家当前注视目标`），精准消解“开你面前的箱子”与“开我右边的箱子”。
3. **直达动作效果结算层，绕过键位互斥锁与快捷键表现动画：**
   - **剥离按键前摇与输入互斥：** 游戏内物理快捷键通常包含“① 键位单键互斥锁、长按读条与玩家按键手部动画 → ② 业务规则校验与动作效果结算”两层。G2A 的 `origin.execute` **必须**直接绑定在后者的**动作效果结算层**，伴游只需获得按下后的实际业务效果，**无需**也**不得**走受单键互斥锁或玩家按键动画阻塞的物理按键包装层；
   - **玩家按键与伴游动作并发成立：** 即便真人玩家当前正按住 `E` 键并播放 `E` 键动画，伴游触发 `F` 键背后的开箱或开关手电筒效果（无论 `actor = companion` 还是受权 `actor = player`）**必须**与玩家的 `E` 键操作并行成立、互不阻塞或打断——同时仍正常执行距离、道具持有、冷却与角色存活等真实游戏世界规则校验。

### 3.2 南向极简宿主接口（交互源点 ↔ 智能枢纽）

南向接口仅运行于同机回环或隔离的服务端内网 HTTP 通道，仅包含 4 项原语：

| 南向原语 | 方向 | 职责说明 |
| --- | --- | --- |
| `origin.capabilities` | `交互源点` → `智能枢纽` | 入局（或章节能力变更）时同步静态能力总表：为每个通用或扩展方法分配稳定序号（`#01..#N`）、语义说明、允许的 `actor` 主体范围（`companion` / `player`）、参数结构与风险标记，供**智能枢纽**与**演算中枢**缓存。 |
| `origin.sync` | `交互源点` → `智能枢纽` | 运行期按全量或增量模式定期同步双元快照：(1) **轻量状态摘要**（如血量、阶段、刚发生的事件）与 (2) **当前可用方法序号集**（按 `actor` 主体标注 `ready` / `staged` 状态及携带双视角标签的候选 `target_id`），绑定递增修订号 `rev`。 |
| `origin.player_event` | `交互源点` → `智能枢纽` | 上报已验证玩家席位的实时信号：玩家主动任务指令、上下线状态变更或紧急叫停信号。 |
| `origin.execute` | `智能枢纽` → `交互源点` | 在指定主体（`actor = companion` 或受权 `player`）上绕过键位动画锁、直达动作效果层执行单个已核验的方法序号与目标参数，返回权威执行结果（`succeeded` / `failed` / `cancelled`）与世界效果。 |

### 3.3 北向标准协议接口（智能枢纽 ↔ 演算中枢）

北向接口围绕能力表缓存、活跃方法投影与方法调用队列构建四组标准原语：

| 原语分组 | 核心操作 | 规范语义 |
| --- | --- | --- |
| **会话与能力表** | `session.authorize` | 协商协议版本与权限范围（`Scope`，经 RFC 8785 摘要绑定），在玩家批准后建立会话并同步静态能力总表（或校验能力表缓存摘要免重传）。 |
| | `session.heartbeat` / `resume` / `close` | 续期**演算中枢**控制租约（不延长缺席玩家在线状态）、在短暂闪断窗口内恢复会话快照，或幂等关闭会话并隔离未执行队列。 |
| **活跃方法与观察** | `context.push` / `context.pull` | 向**演算中枢**推送（如玩家下达指令时随同携带）或供**演算中枢**定期拉取当前**轻量状态摘要 + 按需投影的活跃可用方法序号列表**（仅传输当前 `ready`/`staged` 的活跃子集，避免百余项静态总表消耗多余上下文）。画面（`visual`）与环境音频（`audio`）作为可选正交模块由玩家独立开关。 |
| **方法调用队列** | `queue.submit` | 提交带唯一 `queue_id`、绑定状态修订号 `based_on_rev` 与触发类型（玩家指令 / 伴游主动）的有序**方法调用队列**（含单步队列特例）。 |
| | `queue.confirm` | 由玩家认证同意通道对需要确认的整条意图队列记录单次批准凭证。 |
| | `queue.cancel` / `queue.query` | 请求中断尚未执行完毕的队列，或在网络超时后查询 `queue_id` 各步骤的真实结算进度。 |
| **对话交互** | `chat.send` | （可选模块）在授权接收范围与来源标记约束内向玩家或队伍发送文字/语音回复。 |

## 4. 身份、授权与在线生命周期

### 4.1 身份认证、冻结范围与权限撤销

- **传输凭据认证：** 调用方身份**必须**由传输层认证凭据（本机进程核验或 TLS + 加密令牌）确立，严禁采信自称发送方字段。
- **冻结权限范围（`Scope`）：** 会话授权精确绑定玩家、**演算中枢**、游戏实例、受控角色槽位及允许调用的能力序号范围摘要；任何扩权**必须**重新取得玩家批准。玩家或游戏随时撤权时，**智能枢纽**立即终止剩余未下发的队列步骤。

### 4.2 玩家在线即停铁律与双层闪断恢复

- **禁止离线后台运行：** G2A **绝不提供**玩家离线后继续在空游戏世界中自动运行的模式。一旦**交互源点**判定关联玩家退出或离线，**智能枢纽** **必须**立即停止可用方法同步与队列下发、清空未执行的排队步骤，而已在**交互源点**执行中的单步动作按游戏规则自然收尾。下次重进游戏时，旧任务保持停止，等待玩家新指令。
- **游玩期间双层闪断恢复：** 玩家在线期间若**演算中枢**断线，游戏正常继续（伴游保持静止或转为明确标注的本地脚本行为，不补录断线过程）：活动租约内、本地脚本接管前的短暂闪断可通过 `session.resume` **无缝恢复**；长时中断或已触发本地脚本接管后，重连**必须**保持伴游行动暂停直至玩家确认继续。

### 4.3 角色槽位隔离与可配置计费归属

- **声明式角色槽位：** 游戏自主声明开放 `companion`（默认每玩家最多 1 个，允许空槽正常游玩）、`independent_npc` 或两者同局共存，逐角色视野、权限与计费严格隔离。
- **算力上限与 AI NPC 计费模式：** 玩家计费伴游支持消耗上限（触顶仅暂停 AI 而不中断游戏）。独立 AI NPC 支持游戏声明计费模式：**默认采用玩家承担模式（`player_metered`）**（绑定认证房主/持有玩家，禁静默向他人分摊；房主掉线立即停止原房主计费，战局按声明停机、转本地脚本兜底或由在线队友在完全隔离原房主隐私前提下显式接手），同时开放**开发者承担模式（`developer_sponsored`）**（只要局内仍有在线真人玩家即可正常维持）。

## 5. 能力表同步、可用方法演进与调用队列机制

### 5.1 两态可用性标记（`ready` 与 `staged`）与渐进式粒度

为支持单次推理完成多步编排且不增加游戏负担，可用方法同步遵循两态演进与渐进式粒度：

- **`ready`（当前立即可执行）与 `staged`（前置可达）：** 当目标已在视野感知范围内但尚需前置动作（如距离宝箱 5 米需先调用 `#01 move_to`）时，**交互源点 SDK** 将 `#02 interact(chest_R)` 标为 `staged`，使**演算中枢**无需拆分成多次往返即可一次性编排出 `[#01 → #02]` 完整队列。游戏亦可选择直接暴露封装好寻路的高层单步方法（始终标为 `ready`），此时队列自然退化为极简的 1 步调用。
- **代次隔离：** 读档、切换关卡或阵营时推进世界代次（`epoch`）并下发全量同步快照，旧代次的增量包与在途过期队列自动作废。

### 5.2 方法调用队列调度、整队确认门禁与异常熔断

**智能枢纽**对每条提交的方法调用队列（`queue_id`）维护持久化执行账本，按序逐条调度**交互源点**：

1. **前置防重放屏障：** **智能枢纽**按 `(session_id, queue_id)` 幂等去重；网络抖动引起的重复提交直接返回原队列回执，绝不向**交互源点**重复下发动作。
2. **通用三态策略与整队单次确认门禁（`allow` / `confirm` / `prohibit`）：**
   - 凡队列中包含 `prohibit` 步骤，整队直接以 `permission_denied` 拒绝；其中代操作玩家主角本体（`actor = player`）的能力仅在**玩家明确下令**时按授权放行，若由伴游无指令主动发起则默认走 `confirm` 或 `prohibit`，严禁未经许可抢夺玩家控制权；
   - 凡伴游主动发起的队列、高价值转移、不可逆交互或虚拟货币预算超限命中 `confirm` 规则且尚无批准凭证时，**智能枢纽**将整条意图队列合并为**单次玩家确认请求**，返回 `409 confirmation_required`（`outcome: not_accepted`，**不消耗原 `queue_id`**）；超时未答复视为拒绝并在 `cooldown_ms` 冷却期内禁止对同一目标重复弹窗；玩家批准后凭原 `queue_id` 重提即可启动队列调度（涉及真实法币或外部钱包的交易永不允许自动放行，每次必经原生安全界面由真人确认）；
3. **逐步校验与失败自动熔断（`abort`）：** **智能枢纽**每下发队列下一步前，实时核验玩家未叫停且该步方法序号在最新同步视图中已处于 `ready` 状态。一旦任一步骤执行失败、目标失效消失或收到玩家新指令覆盖，**智能枢纽** **立即熔断终止剩余队列步骤**，并将已生效步骤与最新活跃可用方法一并回传**演算中枢**。遇到 `504` / `outcome_unknown` 超时，调用方**必须**先通过 `queue.query` 核对原 `queue_id` 进度，默认严禁盲目重发。

## 6. 数据编码、传输绑定与错误模型

### 6.1 标准 JSON（RFC 8259）与 RFC 8785（JCS）摘要

- **数据交换格式：** 采用国际标准 UTF-8 **JSON（RFC 8259）**，支持标准整数与有限 IEEE-754 浮点数（直接兼容游戏引擎原生数值），拒绝 `NaN`、`Infinity` 与重复键。时间戳与时长建议采用毫秒整数（`_ms`），货币与配额采用最小整数单位或十进制字符串。
- **加密摘要规范化：** 权限范围摘要、静态能力表缓存摘要与队列确认摘要统一采用国际标准 **RFC 8785（JCS）** 生成规范化 UTF-8 字节并计算带域分离的 SHA-256。

### 6.2 标准错误码与 HTTP 状态映射

| 标准错误码 | HTTP 状态 | 受理状态 | 调用方规范恢复行为 |
| --- | --- | --- | --- |
| （成功响应） | `200` | `accepted` | 读取队列或步骤执行结果（如实区分已提交步骤与中途熔断步骤）。 |
| `invalid_request` / `invalid_arguments` | `400` | `not_accepted` | 修正语法、非法方法序号或越界参数，禁止原样重发。 |
| `unsupported_version` / `unsupported_capability` | `400` | `not_accepted` | 切换共同支持的版本/扩展重新协商或断开连接。 |
| `unauthenticated` | `401` | `not_accepted` | 重新获取有效认证凭据后再试。 |
| `permission_denied` / `revoked` | `403` | `not_accepted` | 停止越权或已撤销操作；错误回包严禁泄露未授权隐藏实体。 |
| `not_found` | `404` | `not_accepted` | 在获授权可见范围内核实目标或队列标识符。 |
| `stale_context` | `409` | `not_accepted` | 状态修订号过期或队列目标已不可用，基于随附的最新可用方法重规划。 |
| `conflict` | `409` | `not_accepted` | 核对重复 `queue_id` 内容冲突或终态冲突，严禁换新 ID 绕过。 |
| `confirmation_required` | `409` | `not_accepted` | 等待玩家完成整队 `queue.confirm` 后以原 `queue_id` 重提；被拒则遵守冷却期。 |
| `resource_limit` | `429` | `not_accepted` | 遵守退避等待时间（`Retry-After`）与队列/轮询配额上限。 |
| `unavailable` | `503` | `not_accepted` | 服务暂不可用；只读与带去重键请求可按退避策略安全重试。 |
| `outcome_unknown` | `504` | `unknown` | 提交状态未决；**必须**先调用 `queue.query` 核对进度，严禁盲目重发副作用。 |

## 7. 安全边界、记忆可携与开放生态治理

### 7.1 核心安全与防提示词注入边界

- **数据与控制权绝对隔离：** 游戏对白、目标提示标签、商店文案与召回记忆均属**不可信数据**，绝不能越过当前可用方法集调用未开放能力、修改预算上限或绕过**智能枢纽**确认门禁。
- **传输与防内网探测（SSRF）：** 跨网连接强制启用 TLS，凭据严禁写入 URL 或日志；外部地址与重定向在连接前须校验协议、主机/IP 与端口策略，阻断内网探测与 DNS 重绑定。

### 7.2 伴游记忆归属与开放标准格式可携权

- **记忆归属与玩家管控：** 游戏内部 NPC 状态由**交互源点**管理；个人伴游长期记忆归属玩家（读档回退或开启新周目不得清空伴游记忆）。**演算中枢**服务商**必须**允许玩家查看、编辑、置顶锁定与删除伴游记忆，自主压缩整理不得覆盖玩家编辑或删除置顶记录。
- **通用标准格式导出与迁移保护：** 服务商**必须**允许玩家主动将保留的伴游记忆（含来源与时间元数据）及人设/自主偏好设置，导出为**公开文档化、无私有锁定的通用标准结构化数据格式**。源服务商仅核验玩家本人身份，**不得**审查目标去向；接收端导入须保留来源与保守披露边界（绝不因换平台扩大对外披露范围），并返回真实的本地导入结果回执。

### 7.3 智能枢纽双轨路由与反垄断准入准则

- **智能枢纽推荐商业化与自定义接入双轨制：** **智能枢纽** **可以**提供清晰标示的优选或商业推广**演算中枢**推荐目录以支撑可持续运营，同时**必须**开放无锁定的**玩家自定义接入通道**，允许用户自由连接任意符合 G2A 标准的第三方云端或本地**演算中枢**。
- **合规白名单与公平无歧视对等（FRAND）：** 开发者专为本作剧本创作的专属剧情 AI 角色归属 `independent_npc` 槽位，无需向外部替换开放；一旦开放玩家伴游槽位（`companion`）并因反外挂、主机认证或内容合规设立白名单，自研与第三方**演算中枢** **必须**共用完全一致的可用方法同步与冷却限制，公布客观准入标准并开放申请，严禁排他白名单或商业捆绑锁定。
