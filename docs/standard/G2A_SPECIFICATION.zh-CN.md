# G2A 协议规范

**Game-to-Agent Interaction Protocol｜游戏与智能体交互协议**

定义任意品类游戏与 AI 智能体之间通过**交互源点**、**智能枢纽**与**演算中枢**三层架构实现能力表同步、动态状态与可用方法感知及方法调用队列执行的开放协议标准。

状态：公开审阅工作草案（`standard-review-2026-11-23-r84`）｜修订日期：2026 年 11 月 23 日｜语言版本：[English Specification](G2A_SPECIFICATION.md)

## 架构总览与核心交互案例

### 三层架构总览流程图

G2A 面向**全品类游戏**（涵盖具身动作漫游、策略战棋卡牌、有无化身的模拟经营，以及纯信息演进的互动叙事与推理解谜游戏），以低接入成本引入**玩家伴游**（Companion）与可选**独立 AI NPC**。入局同步一次领域通用能力总表（类比 MCP 工具表），运行期由**交互源点**按信号快照或空间差分同步当前状态与可用方法序号，再由**演算中枢**编排**方法调用队列**交由**智能枢纽**逐条安全调度：

```text
[真人玩家] ─┬─ 游戏内操控 / 下达语音或文字指令
            └─ 权限审批 / 整队确认 / 选配演算中枢
            ▼
┌─ 第一层：交互源点 (Interaction Origin · 轻量宿主 SDK)
│  • 入局同步领域通用能力总表（交互/建造/出牌/合成/查线索）
│  • 按信号快照或空间差分同步【轻量状态摘要 + 可用方法序号】
│  • 在指定主体/席位 (companion/player) 直达效果层结算
└──▲── 源点接口 (Origin Interface · 本机回环 / 内网 HTTP)
   ▼
┌─ 第二层：智能枢纽 (Intelligent Hub · 开源安全与调度中枢)
│  • 单机安装一次多游戏共用 / 网游部署服务端同步多端战局
│  • 缓存能力表并按需投影活跃方法 (ready/staged) 省上下文
│  • 托管鉴权、整队单次确认、防重放去重、逐条调度与熔断
└──▲── 中枢接口 (Core Interface · 标准 G2A HTTPS / 流式)
   ▼
┌─ 第三层：演算中枢 (Computation Core · 认知推理引擎)
│  • 基于可用方法序号判定可行性，编排【方法调用队列】与记忆
└──────────────────────────────
```

### 案例一流程图：玩家主动指令（具身空间游戏示例 —— “打开右侧的宝箱”）

在拥有局内角色与空间位置的动作冒险游戏中，入局已缓存通用能力表（`#01 move_to`、`#02 interact`）。玩家下令瞬间，**智能枢纽**直接将**玩家指令 + 当前活跃可用方法序号及双视角方位标签**一并推给**演算中枢**，单次推理生成完整队列并绕过快捷键动画直接结算：

```text
┌─ [前置状态] 已缓存能力表：#01 move_to(t), #02 interact(t)
│  交互源点 SDK 已向智能枢纽增量同步可用方法 (rev=18)：
│  • #01 move_to  -> chest_R (玩家右侧 4m / 距伴游 5m, ready)
│  • #02 interact -> chest_R (木宝箱·打开, staged: 需先靠近)
└──┬───────────────────────────
   ▼
┌─ 1. [玩家 -> 交互源点 -> 智能枢纽]
│  玩家下达指令：“打开右侧的宝箱”
│  智能枢纽免回查游戏，拼装【指令 + 活跃序号 #01/#02】推中枢
└──┬───────────────────────────
   ▼
┌─ 2. [演算中枢：可行性判定与队列编排]
│  匹配“玩家右侧”为 chest_R；见 #02 为 staged (需先靠近)，
│  单次编排有序队列：Q-101 = [ #01(chest_R) -> #02(chest_R) ]
└──┬───────────────────────────
   ▼
┌─ 3. [智能枢纽：防重放去重与逐条受控调度]
│  校验授权并登记 Q-101 去重账本（网络重发直接拦截）：
│  • Step1：源点执行 #01(actor=companion, chest_R)，寻路到位，
│           SDK 自动增量上报 #02(chest_R) 变为 ready
│  • Step2：源点执行 #02(actor=companion, chest_R)，直达效果层
│           （不占玩家键位锁，与玩家其他按键并行成立），获战利品
└──┬───────────────────────────
   ▼
┌─ 4. [智能枢纽 -> 演算中枢 -> 玩家]
│  回传队列结算结果至演算中枢；伴游向玩家播报开箱收获
└──────────────────────────────
```

### 案例二流程图：伴游定期感知并主动协助（无实体经营/信息游戏示例）

在**无局内角色实体与移动操作**的模拟经营、配方工坊或推理解谜游戏中（具身游戏中伴游走近宝箱主动开箱遵循同一门禁流程），**交互源点**通过业务模块的 `changed` 信号上报账本/线索变化与可用方法；**演算中枢**定期读取后自主发起协助队列，经**智能枢纽**门禁审批后直达业务函数结算：

```text
┌─ 1. [交互源点 -> 智能枢纽]（信号快照驱动，零空间扫描）
│  工坊触发“木料耗尽停工”信号，同步状态与可用方法 (rev=42)：
│  • #05 trade_resource(木料x20, 100金) -> actor=player, ready
│  • #06 resume_line(1号木工台)         -> actor=player, staged
└──┬───────────────────────────
   ▼
┌─ 2. [演算中枢 <- 智能枢纽]（按协商节拍读取活跃状态与方法）
│  演算中枢校验玩家在线，识别停工告警与 #05/#06 前置组合，
│  提请补货复工队列：Q-205 = [ #05(木料x20) -> #06(1号木工台) ]
└──┬───────────────────────────
   ▼
┌─ 3. [智能枢纽：主动行为与玩家席位策略门禁]
│  ├─ 若属伴游非侵入图层操作（如 #02 线索板高亮/蓝图, allow）
│  │   -> 直接进入步骤 4 执行
│  └─ 因 Q-205 主动动用玩家席位资金（命中 confirm 规则）：
│      • 返回 confirmation_required（保留 Q-205 ID）询问一次
│      • 玩家拒绝或超时 -> 放弃队列并进入冷却期（禁重复弹窗）
│      • 玩家点击同意   -> 凭原 Q-205 重提，进入步骤 4
└──┬───────────────────────────
   ▼
┌─ 4. [智能枢纽 -> 交互源点（与案例一同源，零额外业务代码）]
│  执行 #05 购料（#06 变 ready）-> 执行 #06 恢复产线并汇报
└──────────────────────────────
```

## 1. 引言与核心原则

### 1.1 协议目标与适用边界

G2A（Game-to-Agent Interaction Protocol）是一项面向全品类游戏与 AI 智能体的开放通信协议，通过**领域能力表注册、增量状态与可用方法同步及方法调用队列编排**，标准化游戏世界与 AI 角色（跨游戏玩家伴游及可选独立 AI NPC）之间的感知、授权与行动交互。

- **适用范围：** 具身角色漫游、策略战棋与卡牌、模拟经营与建造、互动叙事与推理解谜等品类中的玩家伴游（Player Companion）与独立 AI NPC、状态与可用方法同步、受约束的方法队列执行及角色对话。
- **非目标边界：** G2A **不是**操作系统级屏幕抓取或模拟物理键鼠点击的外部脚本工具，不规范任意远程代码执行、特定模型内部权重，也不介入商业平台内部分成合同。

### 1.2 五项指导原则

1. **领域原语通用化与全品类兼容：** 协议不预设游戏存在物理角色或空间移动；各品类仅注册少量领域通用原语（如交互、出牌、建造调配、配方合成、检视或串联线索），避免为单一场景对象重复定义专有接口。
2. **能力受限编排与源点最终权威：** **演算中枢** **必须**仅在当前同步的可用方法序号集内编排调用队列；世界数值、随机投骰、规则前置条件与胜负状态由**交互源点**最终裁定，未揭晓秘密与谜底**不得**外泄。
3. **智能枢纽集中托管安全与调度：** 鉴权、整队确认门禁、网络防重放去重、队列逐条调度与异常熔断统一收敛于开源可审计的**智能枢纽**。
4. **支持不等于授权，离线即停：** 一切调用受玩家批准的权限范围约束；一旦关联真人玩家离线，智能体**不得**在空游戏世界中后台继续运行。
5. **开放互操作与记忆主权：** 协议中立兼容任意游戏引擎与模型服务；玩家伴游长期记忆独立于单局读档回退，并支持以公开标准格式自由导出。

### 1.3 规范用语约定

本文中加粗的“**必须**（MUST）”“**必需**（REQUIRED）”“**不得**（MUST NOT）”“**应**（SHOULD）”“**不应**（SHOULD NOT）”与“**可以**（MAY）”按 RFC 2119 与 RFC 8174（BCP 14）解释。开篇流程图用于直观阐明协议流转，不限定内部实现语言。

## 2. 三层系统架构与零负担接入模型

### 2.1 三大核心层级职责

| 标准层级 | 核心定位 | 权责边界 |
| --- | --- | --- |
| **交互源点**（`Interaction Origin`） | 游戏宿主与随包轻量 SDK | 唯一权威游戏状态源与动作执行端。入局输出静态能力总表，运行期按信号快照或空间差分输出轻量状态摘要与按主体区分的可用方法序号，并在指定主体/席位（`actor`）上直达业务效果层结算；未揭晓隐藏道具、战争迷雾外敌情、未抽牌序与未解谜底真相**必须**留在内部，**不得**外发。 |
| **智能枢纽**（`Intelligent Hub`） | 开源安全盾牌与队列调度中枢 | 连接**交互源点**与**演算中枢**的协议引擎（参考实现源码完整公开）。缓存静态能力总表、维护最新可用方法视图、按需投影活跃方法以节省上下文开销，并统一负责鉴权、防重放去重、整队确认门禁与队列逐条下发熔断。 |
| **演算中枢**（`Computation Core`） | 云端或本地认知推理引擎 | 受权驱动角色槽位的推理与记忆服务。根据玩家指令或按节拍读取的活跃状态与可用方法，判定任务可行性并输出有序**方法调用队列**，无需适配不同游戏引擎底层。 |

### 2.2 双模式零负担接入与部署拓扑

针对不同品类游戏的代码形态，**交互源点 SDK** 提供两类免样板代码的原生采集与路由模式（混合品类可同时启用），开发者无需手写高频轮询或 `if (actor == player)` 分支：

- **信号与快照驱动模式（面向无角色实体的策略、模拟经营、卡牌、互动叙事与推理解谜游戏）：** 直接对接业务数据模块的状态变更信号与字典快照（例如经济钱包、合成台、日程时钟、任务日志或对话面板触发 `changed` 信号时导出 `snapshot()`），仅在回合推进、账本阈值变化或新线索解锁时增量发包，**零空间坐标、零射线开销**。
- **组件挂牌与空间脏差分模式（面向具身漫游与动作冒险游戏）：** 在玩家与具身伴游预制体上挂载 `actor` 标签并将动作效果函数注册一次，由 SDK 在后台低频自动完成可达性判定、双视角方位计算与脏差分（状态无变化时零发包），执行时自动路由至对应实例。

| 部署模式 | 组件运行位置 | 运行与分发特征 |
| --- | --- | --- |
| **单机与客户端宿主模式** | 本地游戏**交互源点** ↔ 玩家电脑**全局共享智能枢纽** ↔ 云端或本地**演算中枢** | 游戏发行时**仅随包分发极小的交互源点 SDK**；玩家整台电脑**单次安装一个智能枢纽供本机所有兼容游戏全局共用**（首次缺失时按需引导下载）。本机回环 HTTP 单跳耗时低于毫秒级。 |
| **服务端权威网络游戏模式** | 游戏服**交互源点** ↔ 服务端集群**智能枢纽** ↔ 云端**演算中枢** | 玩家电脑仅运行普通游戏客户端；**交互源点**与**智能枢纽**部署于服务端内网，汇总授权视野、协调高并发队列调度，确保组队战局全员面对一致同步的 AI 反应，同时严格隔离个人伴游与敌对阵营视野。 |
| **NAT 出站连接模式** | 客户端**智能枢纽**（主动出站）↔ 云端中继 / **演算中枢** | 位于家庭防火墙后的客户端**智能枢纽**主动发起出站加密连接，无需在玩家设备上开放任何入站端口。 |

## 3. 通用能力原语、全品类适配与标准接口

### 3.1 领域通用原语、双主体/席位分流与直达效果层准则

为规避“每个道具或按钮各写一个专有接口”的方法爆炸，同时覆盖具身与无实体游戏并消除输入表现冲突，**交互源点**遵循三项核心建模准则：

1. **提炼领域通用原语，拒绝专有方法爆炸：** 静态能力总表注册的是各品类**少量的领域通用动词**——具身游戏复用输入映射背后的十余个核心动作（如通用 `interact(target_id)`、`toggle_flashlight()` 与可选寻路 `move_to(target_id)`）；策略与卡牌游戏仅需 `play_card(card_id, target_id)`、`command_unit(...)`、`end_turn()`；模拟经营与配方合成游戏仅需 `place_facility(...)`、`craft(recipe_id)`、`trade_resource(...)`；推理解谜游戏仅需 `inspect_clue(clue_id)`、`mark_board(...)`、`submit_answer(...)`。方法参数除离散 `target_id` 外，原生支持经 JSON Schema 约束的**口令字符串、数值比例、网格坐标与配方数组**（覆盖输入密码、填词数独坐标或微调税率/航点）。
2. **执行主体/席位分流（`actor`）与上下文锚点：**
   - **兼容具身实体与无实体席位的 `actor` 语义：** 可用方法上报与 `origin.execute` 调用**必须**显式指定执行主体 `actor`：
     - `actor = companion`（受控 AI 自有主体 / 非侵入辅助图层；在独立 NPC 槽位下对应其自身 `npc_id`）：在**具身游戏**中绑定 AI 局内角色实体，距离与装备校验以**该实体自身**为原点（确保伴游面前的宝箱远离玩家也能开启、“打开你的手电筒”精准开启伴游手电筒；若伴游无实体或无手电筒则不上报该项，防止误触玩家装备）；在**无角色实体游戏**中代表**伴游专属辅助图层或受托管分管域**（如战棋地图参谋标点、经营沙盘虚影规划蓝图、推理线索板高亮串联），不消耗玩家主席位资金或答题机会；
     - `actor = player`（受权代操作玩家本体 / 玩家主控制席位）：**仅限玩家伴游（`companion`）槽位**在游戏规则开放辅助代操作（具身游戏中如代开关手电筒、切道具，默认关闭基础移动与竞技瞄准；无实体游戏中如代出牌、代调配产线、按提示完成配方递交或代提交玩家确认的谜底）且获玩家授权时暴露，直接作用于**玩家角色或玩家主席位**；独立 AI NPC 槽位**不得**获授 `actor = player` 权限。
   - **双视角、指向焦点锚点与海量对象聚合：** 候选目标元数据在空间与 XR（VR/MR）游戏中同时标注**相对执行主体的可达状态**及**相对玩家的方位、视线焦点或手柄指向射线/鼠标悬停目标**（消解“开你面前的箱子”“开我右边的箱子”与“打开我手指着的抽屉”）；在面板/策略/经营/解谜游戏中则标注**当前选中分区、回合阶段或焦点证词/槽位**（消解“升级这个工坊”“反驳这句证词”）。面对拥有数千建筑或单位的大型模拟经营与策略游戏，`origin.sync` **应**仅投影异常告警对象、玩家当前焦点分区及宏观聚合句柄，**不应**全量枚举静默实体。
3. **直达业务效果结算层，绕过键鼠互斥锁与界面表现动画：**
   - **剥离输入锁与表现前摇：** 物理快捷键或 UI 按钮通常串联“① 单键互斥锁、长按读条、手部按键动画或鼠标拖拽翻页 → ② 业务规则校验与状态结算”两层。G2A 的 `origin.execute` **必须**直接绑定在后者的**业务效果结算层**，智能体只取业务生效结果，**不得**走受键位锁或表现动画阻塞的输入包装层；
   - **并发免打断保证：** 即便真人玩家当前正按住 `E` 键播放动作动画，或正在翻阅其他管理面板，伴游触发 `F` 键背后的开箱/开灯效果或后台产线调配效果**必须**能与玩家当前操作并行成立、互不阻塞打断——同时仍正常接受距离、资金库存、回合阶段、冷却与存活等真实游戏规则裁定。

### 3.2 全品类游戏伴游适配矩阵

下表阐明不同品类游戏的结构特征差异（有什么、没有什么），以及如何在同一套 G2A 协议下原生、一致地实现伴游系统：

| 游戏品类代表 | 品类特征区分（有什么 vs 没有什么） | 状态同步（`origin.sync`）与保密红线 | 通用能力原语、`actor` 与 `ready / staged` 映射 |
| --- | --- | --- | --- |
| **具身空间漫游类**（动作 RPG / 生存冒险 / 载具模拟） | **有**局内角色或载具实体、空间坐标、寻路与随身/车载设备。 | 同步实体状态、路书与双视角周边目标；未探索隐藏区域留在源点内部。 | 原语：`move_to`、`interact`、`toggle_flashlight`、`request_pit_stop`；`actor` 区分伴游实体与玩家主体；远距目标标为 `staged`（需先靠近）。 |
| **策略战棋与卡牌类**（4X / RTS / 塔防 / 卡牌构筑） | **无**具身伴游实体与近身按键交互；**有**阵营席位、回合/阶段锁、费用池与编队/手牌。 | 按回合/出牌信号同步可见战局与手牌；战争迷雾外敌情与未抽牌序**不得**外发。 | 原语：`play_card`、`command_unit`、`deploy_unit`、`end_turn`；`companion` 为战术标点/托管分队，`player` 为受权代出牌；需先回费才够费的卡牌标为 `staged`。 |
| **模拟经营与建造类**（含**无化身全局型**与**带化身混合型**） | **无化身全局型**（城市/产线/体育经理）**无**角色实体与距离限制，**有**全局账本、模拟时钟与供应链；**带化身混合型**（生活/农场模拟）兼具角色走位与经营账本。 | 对接经济/合成/时钟模块的 `changed` 信号与 `snapshot()` 上报账本阈值变化与停工告警（混合型叠加周边交互物）。 | 原语：`place_facility`、`configure_line`、`craft`、`trade_resource`；`companion` 可打虚影规划蓝图，`player` 受权调配产线（大额支出命中整队 `confirm`）；缺料待采购的建造标为 `staged`。 |
| **推理解谜与信息叙事类**（侦探指证 / 海龟汤 / 互动叙事 / 逻辑面板） | **无**物理实体、空间、单位或建筑；全游戏即**已知线索、对话分支与配方/盘面状态的演进**。 | 仅同步已解锁线索、当前台词与阶段变化；**未揭晓谜底与真相不得离开源点**，确保伴游陪玩家推理而不剧透。 | 原语：`inspect_clue`、`mark_board`、`add_ingredient`、`serve`、`submit_answer`；`companion` 在线索板高亮批注（不扣次数），`player` 仅按玩家指令代交答案；前置未完成时后继步骤标为 `staged`。 |
| **实时竞技与高速反应类**（FPS / MOBA / 格斗 / 音游弹幕 / 社交派对） | **无**跨网逐帧微操代打（禁自动瞄准、压枪或逐音符代敲）；**有**合法视野战况、段落遥测、局间配装与低频协同。 | 仅同步玩家本人合法可见战况与结算偏差统计；严防透视敌情或不对称阵营隐藏身份泄露。 | 原语：`ping_map`、`select_loadout`、`adjust_offset`、`trigger_support_skill`（派对合作类含独立伴游实体搬运/制作）；遵循 7.3 节反外挂白名单与对等冷却。 |

### 3.3 源点接口（Origin Interface · 交互源点 ↔ 智能枢纽）

**源点接口**仅运行于同机回环或隔离的服务端内网通道，包含 4 项全品类通用原语：

| 源点原语 | 方向 | 职责说明 |
| --- | --- | --- |
| `origin.capabilities` | 源点 → 枢纽 | 入局（或章节解锁新系统）时同步静态能力总表：分配稳定方法序号（`#01..#N`）、语义说明、支持的 `actor` 范围、JSON Schema 参数结构与风险标记。 |
| `origin.sync` | 源点 → 枢纽 | 运行期按全量或增量模式同步：(1) **轻量状态摘要**（角色状态、经营账本快照或新增线索信息）与 (2) **可用方法序号集**（按 `actor` 标注 `ready` / `staged` 及候选目标锚点），绑定递增修订号 `rev`。 |
| `origin.player_event` | 源点 → 枢纽 | 上报已验证玩家席位的实时信号：玩家主动任务指令、整队审批结果、上下线状态变更或紧急叫停信号。 |
| `origin.execute` | 枢纽 → 源点 | 在指定主体/席位（`actor`）上绕过键鼠动画锁、直达业务效果层执行单个已核验的方法与参数：瞬时动作直接返回终态（`succeeded` / `failed`）；长距寻路、引擎蓄力或持续踩踏机关等耗时动作进入可随时响应取消（收敛为 `cancelled`）的 `executing` 进行中状态，待达成或中断后再收敛为终态并推进队列下一步。 |

### 3.4 中枢接口（Core Interface · 智能枢纽 ↔ 演算中枢）

**中枢接口**围绕能力表缓存、活跃方法投影与方法调用队列构建四组标准原语（玩家确认操作仅允许通过**智能枢纽**本地/受信任玩家交互通道完成，**中枢接口** **不得**开放供**演算中枢**自批确认）：

| 分组 | 核心操作 | 规范语义 |
| --- | --- | --- |
| **会话授权** | `session.authorize` | 协商协议版本与权限范围（`Scope`，经 RFC 8785 摘要绑定），经玩家批准建立会话并同步静态能力总表（或校验缓存摘要免重传）。 |
| | `session.heartbeat` / `resume` / `close` | 续期**演算中枢**控制租约（不延长缺席玩家在线状态）、短暂闪断恢复会话快照，或幂等关闭会话并隔离未执行队列。 |
| **状态感知** | `context.push` / `context.pull` | 随玩家指令推送或供**演算中枢**按协商节拍拉取**轻量状态摘要 + 按需投影的活跃可用方法序号列表**（仅传当前 `ready`/`staged` 子集；面对常驻桌面的放置挂机、电子宠物或慢节奏经营游戏，在局势未跨越显著事件阈值且无玩家输入时**应**自动降频休眠，避免空转消耗算力）。画面（`visual`）与音频（`audio`）作为可选正交模块由玩家独立开关。 |
| **调用队列** | `queue.submit` | 提交带唯一 `queue_id`、绑定修订号 `based_on_rev`、触发类型（玩家指令 / 主动发起）及可选抢占标记 `supersedes` 的有序**方法调用队列**（含单步队列）。 |
| | `queue.cancel` / `queue.query` | 请求中断尚未执行完毕的队列，或在网络超时后查询 `queue_id` 各步骤的权威结算进度与玩家审批状态。 |
| **对话交互** | `chat.send` | （可选模块）在授权接收范围与 AI 来源标记约束内发送文字或语音交流（纯推理解谜伴游亦可仅启用此模块与看板标记能力）。 |

## 4. 身份、授权与在线生命周期

### 4.1 身份认证、冻结范围与权限撤销

- **传输凭据认证：** 调用方身份**必须**由传输层认证凭据（本机进程核验或 TLS 1.3 + 加密令牌）确立，**不得**采信自称发送方字段。
- **冻结权限范围（`Scope`）：** 会话授权精确绑定玩家、**演算中枢**、游戏实例、受控槽位及允许调用的方法序号与 `actor` 范围摘要；任何扩权**必须**重新取得玩家批准。撤权时**智能枢纽** **必须**立即终止剩余未下发的队列步骤并对在途 `executing` 步骤发起取消。

### 4.2 玩家在线即停铁律与双层闪断恢复

- **禁止离线后台运行：** G2A **不得**提供玩家离线后继续在空游戏世界中自动战斗、离线代管经营或推进回合的模式。一旦**交互源点**判定关联玩家退出或离线，**智能枢纽** **必须**立即停止方法同步与队列下发、清空未执行的排队步骤，已在**交互源点**执行中的单步动作按游戏规则自然收尾（游戏自身重开时的常规离线收益结算仍由游戏引擎独立完成）。下次重进游戏时，旧任务保持停止，等待玩家新指令。
- **游玩期间双层闪断恢复：** 玩家在线期间若**演算中枢**断线，游戏正常继续（伴游保持静默或转为明确标注的本地脚本行为，不补录断线过程）：活动租约内、本地脚本接管前的短暂闪断**可以**通过 `session.resume` **无缝恢复**；长时中断或已触发本地脚本接管后，重连**必须**保持伴游行动暂停直至玩家确认继续。

### 4.3 伴游存在形态、槽位隔离与可配置计费

- **具身与无实体双形态统一槽位：** 游戏自主声明开放 `companion`（默认每玩家最多 1 个，允许空槽正常游玩）、`independent_npc` 或两者同局共存（如排位棋牌对局可声明关闭 `companion` 槽位，而教学复盘局开放）。**协议不要求伴游拥有局内角色实体**——具身队友与无实体参谋/经营顾问/解谜助手共用同一套 `companion` 槽位契约，逐槽位视野、权限与计费严格隔离。
- **算力上限与 AI NPC 计费模式：** 玩家计费伴游支持消耗上限（触顶仅暂停 AI 而不中断游戏）。独立 AI NPC（如策略对手指挥官、推理出题主持人或副本 Boss）支持游戏声明计费模式：**默认采用玩家承担模式（`player_metered`）**（绑定认证房主/持有玩家，**不得**静默向他人分摊；房主掉线立即停止原房主计费，战局按声明停机、转本地脚本兜底或由在线队友在隔离原房主隐私前提下显式接手），同时开放**开发者承担模式（`developer_sponsored`）**（只要局内仍有在线真人玩家即可维持）。

## 5. 能力表同步、前置就绪态与调用队列机制

### 5.1 通用前置就绪态（`ready` 与 `staged`）与渐进式粒度

为支持全品类游戏单次推理完成多步编排，可用方法同步采用与空间解耦的**通用规则前置就绪态**：

- **`ready`（规则条件已齐备）与 `staged`（同队列前置可达）：** 当某项方法在当前局势下可见，但需先执行其他合法方法满足前置条件后才能解锁时，**交互源点**将其标为 `staged`——前置条件涵盖**空间距离**（先 `#01 move_to` 靠近再 `#02 interact`）、**策略费用/连携**（先打回费牌再打高费牌）、**经营原料/工序**（先 `#05 采购木料` 再 `#06 恢复产线`、先完成配方递交再接待下一位客人），以及**推理解锁**（先串联矛盾证物再提交指证）。涉及揭晓随机新信息的操作（如抽牌、刷新商店或探索迷雾）结算后经 `origin.sync` 同步新结果，供**演算中枢**衔接下一段编排；游戏亦**可以**直接暴露高层单步方法（如按蓝图建造，始终 `ready`），此时队列自然退化为 1 步调用。
- **代次隔离：** 读档回退、切换关卡、重置回合或切换阵营时推进世界代次（`epoch`）并下发全量同步快照，旧代次的增量包与在途过期队列自动作废。

### 5.2 方法调用队列调度、整队确认门禁与异常熔断

**智能枢纽**对每条提交的方法调用队列（`queue_id`）维护持久化执行账本，同一角色槽位默认串行执行活动队列，按序逐条调度**交互源点**：

1. **前置防重放与新指令抢占：** **智能枢纽**按 `(session_id, queue_id)` 幂等去重，网络抖动重发直接返回原回执；当收到玩家紧急叫停或带 `supersedes` 标记的替代新指令队列时，**智能枢纽**先取消在途旧队列并熔断剩余步骤，再启动新队列调度，杜绝双队列并发竞态。
2. **通用三态策略与整队单次确认门禁（`allow` / `confirm` / `prohibit`）：**
   - 凡队列包含 `prohibit` 步骤，整队直接以 `permission_denied` 拒绝；涉及代操作玩家主席位或本体（`actor = player`）的调用仅在**玩家明确下令**时按授权直接放行，若由伴游无指令主动发起（如主动替玩家支取资金或提交谜底）则默认执行 `confirm` 或 `prohibit`，**不得**未经授权接管玩家控制权或提前泄露答案；
   - 凡命中 `confirm` 规则且尚无批准凭证时，**智能枢纽**将整条意图队列合并为**单次玩家确认请求**（确认凭证绑定 `queue_id` 与步骤参数的 RFC 8785 摘要，防止批准后篡改参数），向**演算中枢**返回 `409 confirmation_required`（未受理，**不消耗原 `queue_id`**）；超时未答复视为拒绝并在 `cooldown_ms` 冷却期内禁止对同一目标或告警重复弹窗；玩家在受信任确认界面批准后，**演算中枢**凭原 `queue_id` 重提即可启动调度（涉及真实法币或外部钱包的交易**不得**自动放行，每次**必须**经原生安全界面由真人确认）；
3. **逐步校验与失败自动熔断（`abort`）：** **智能枢纽**每下发下一步前，实时核验玩家未叫停且该步方法在最新视图中已变为 `ready`。一旦任一步骤执行失败、目标/条件失效或被新指令抢占，**智能枢纽** **必须**立即熔断终止剩余队列步骤，并将已完成步骤与最新活跃可用方法回传**演算中枢**。遇到 `504` / `outcome_unknown` 超时，调用方**必须**先通过 `queue.query` 核对进度，**不得**盲目重发。

## 6. 数据编码、传输绑定与错误模型

### 6.1 标准 JSON（RFC 8259）与 RFC 8785（JCS）摘要

- **数据交换格式：** 采用国际标准 UTF-8 **JSON（RFC 8259）**，支持标准整数与有限 IEEE-754 浮点数（兼容游戏物理与经营账本原生数值），**必须**拒绝 `NaN`、`Infinity` 与重复键。时间戳与时长**应**采用毫秒整数（`_ms`），货币与配额**应**采用最小整数单位或十进制字符串。
- **加密摘要规范化：** 权限范围摘要、静态能力表缓存摘要与整队确认摘要统一采用国际标准 **RFC 8785（JCS）** 生成规范化 UTF-8 字节并计算带域分离的 SHA-256。

### 6.2 传输绑定与消息信封

- **源点接口传输绑定（`交互源点 ↔ 智能枢纽`）：** 单机模式绑定本机回环 HTTP/1.1 或操作系统受保护本地通道（`127.0.0.1` / Unix Domain Socket / Named Pipe）；网络游戏模式绑定隔离内网 HTTP/2 或 mTLS 通道。
- **中枢接口传输绑定（`智能枢纽 ↔ 演算中枢`）：** 请求-响应操作（`session.*`、`queue.*`、`context.pull`、`chat.send`）通过基于 TLS 1.3 的 HTTPS `POST`（`application/json`）承载；服务端实时推送（`context.push`、玩家事件通知及 `executing` 步骤终态回执）通过同一认证会话下的 **Server-Sent Events（SSE，`text/event-stream`）或 WebSocket** 流式承载。
- **最小消息信封：** 所有请求、响应与事件帧顶层统一携带协议版本 `g2a_version`、会话标识 `session_id`（授权建连请求除外）与调用方生成的唯一请求追踪号 `request_id`。

### 6.3 标准错误码与 HTTP 状态映射

响应载荷通过 `acceptance` 字段标识请求受理状态：已受理（`accepted`）、未受理（`not_accepted`）或状态未决（`unknown`）：

| 标准错误码 | HTTP | 受理态 | 调用方规范恢复行为 |
| --- | --- | --- | --- |
| （成功响应） | `200` | 已受理 | 读取队列或单步结算结果（如实区分已完成步骤与中途熔断步骤）。 |
| `invalid_request` / `invalid_arguments` | `400` | 未受理 | 修正语法、未知方法序号或非法参数，**不得**原样重发。 |
| `unsupported_version` / `unsupported_capability` | `400` | 未受理 | 切换共同支持的版本/扩展重新协商或断开连接。 |
| `unauthenticated` | `401` | 未受理 | 重新获取有效认证凭据后再试。 |
| `permission_denied` / `revoked` | `403` | 未受理 | 停止越权或已撤销操作；回包**不得**泄露未授权隐藏信息或谜底。 |
| `not_found` | `404` | 未受理 | 在获授权可见范围内核实目标、槽位或队列标识符。 |
| `stale_context` | `409` | 未受理 | 修订号过期或前置条件已变，基于随附的最新可用方法重规划。 |
| `conflict` | `409` | 未受理 | 核对重复 `queue_id` 内容冲突或终态冲突，**不得**换新 ID 绕过。 |
| `confirmation_required` | `409` | 未受理 | 等待玩家在受信任确认通道批准后凭原 `queue_id` 重提；被拒则遵守冷却期。 |
| `resource_limit` | `429` | 未受理 | 遵守退避等待时间（`Retry-After`）与队列/轮询配额上限。 |
| `unavailable` | `503` | 未受理 | 服务暂不可用；只读与带去重键请求可按退避策略安全重试。 |
| `outcome_unknown` | `504` | 未决 | 提交状态未决；**必须**先调用 `queue.query` 核对进度，**不得**盲目重发副作用。 |

## 7. 安全边界、记忆可携与开放生态治理

### 7.1 核心安全与防提示词注入边界

- **数据与控制权绝对隔离：** 游戏对白、谜面文案、目标提示标签、商店描述与召回记忆均属**不可信数据**，**不得**越过当前可用方法集调用未开放能力、修改预算上限或绕过**智能枢纽**确认门禁。
- **传输与防内网探测（SSRF）：** 跨网连接**必须**启用 TLS 1.3（RFC 8446），凭据**不得**写入 URL 或日志；外部地址与重定向在连接前**必须**校验协议、主机/IP 与端口策略，阻断内网探测与 DNS 重绑定。

### 7.2 伴游记忆归属与开放标准格式可携权

- **记忆归属与玩家管控：** 游戏内部状态与 NPC 进度由**交互源点**管理；个人伴游长期记忆归属玩家（游戏读档回退或开启新周目**不得**清空伴游记忆，但读档前的单局世界事实**不得**在旧档中泄露未解锁谜底）。**演算中枢**服务商**必须**允许玩家查看、编辑、置顶锁定与删除伴游记忆，自主压缩整理**不得**覆盖玩家编辑或删除置顶记录。
- **通用标准格式导出与迁移保护：** 服务商**必须**允许玩家主动将保留的伴游记忆（含来源与时间元数据）及人设/自主偏好设置，导出为**公开文档化、无私有锁定的通用标准结构化数据格式**。源服务商仅核验玩家本人身份，**不得**审查目标去向；接收端导入**必须**保留来源与保守披露边界（**不得**因换平台扩大对外披露范围），并返回真实的本地导入结果回执。

### 7.3 智能枢纽双轨路由与反垄断准入准则

- **智能枢纽推荐商业化与自定义接入双轨制：** **智能枢纽** **可以**提供清晰标示的优选或商业推广**演算中枢**推荐目录以支撑可持续运营，同时**必须**开放无锁定的**玩家自定义接入通道**，允许用户自由连接任意符合 G2A 标准的第三方云端或本地**演算中枢**。
- **合规白名单与公平无歧视对等（FRAND）：** 开发者专为本作创作的专属剧情或裁判 AI 角色归属 `independent_npc` 槽位，无需向外部替换开放；一旦开放玩家伴游槽位（`companion`）并因反外挂、主机认证或内容合规设立白名单，自研与第三方**演算中枢** **必须**共用完全一致的可用方法同步与冷却限制，公布客观准入标准并开放申请，**不得**实施排他白名单或商业捆绑锁定。

## 8. 版本演进、扩展机制与参考标准

### 8.1 语义化版本与模块化扩展

破坏性语义变更通过语义化版本号显式协商，**不得**静默降级。垂直品类增强能力（如多分支叙事时间线防剧透标签、模拟经营批量蓝图描述、游戏内商店商品目录、伴游自定义外观或语音清单等）统一作为带反向域名命名空间的**可选扩展模块**（Extensions）按需协商加载；遇到不支持的必需扩展（`required: true`）时**必须**在授权阶段安全拒绝。
