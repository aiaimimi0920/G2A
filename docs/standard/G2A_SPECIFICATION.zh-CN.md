# G2A 协议规范

**Game-to-Agent Interaction Protocol｜游戏与智能体交互协议**

定义游戏与 AI 智能体之间通过**交互源点**、**智能枢纽**与**演算中枢**三层架构实现状态感知、权限控制与行动交互的开放协议标准。

状态：公开审阅工作草案（`standard-review-2026-11-22-r79`）｜修订日期：2026 年 11 月 22 日｜语言版本：[English Specification](G2A_SPECIFICATION.md)

## 架构总览与核心交互案例

### 三层架构总览流程图

G2A 旨在让任何游戏以**极低的工程接入成本**安全引入 AI 角色（包括陪伴玩家的**伴游 / 玩家伴玩**，以及可选的**独立 AI NPC**）。协议采用与 MCP、A2A 同源的分层解耦思想，将系统划分为**交互源点**、**智能枢纽**与**演算中枢**三层：

```text
                        [ 真人玩家 Human Player ]
               ┌────────────────────┴────────────────────┐
       游戏内操控 / 主动下达指令                 授权审批 / 确认门禁 / 选配中枢
               ▼                                         ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第一层：交互源点 (Interaction Origin · 随游戏分发的极简宿主 SDK)     │
│  • 仅提供南向轻量接口：1) 输出获准世界状态  2) 执行游戏内操作回调    │
│  • 独占游戏物理、视野与胜负规则的最终裁定权（零鉴权与防重放负担）    │
└───────────────────────────────────▲──────────────────────────────────┘
                                    │ 南向接口（本机回环 / 服务端内网 HTTP）
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第二层：智能枢纽 (Intelligent Hub · 开源安全盾牌与路由中枢)          │
│  • 单机电脑单次安装全局共用 / 网络游戏部署于服务端统一同步多端战局   │
│  • 集中托管：身份鉴权、权限门禁、防重放幂等去重、确认挑战、双轨路由  │
└───────────────────────────────────▲──────────────────────────────────┘
                                    │ 北向接口（标准 G2A HTTPS / 流式协议）
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第三层：演算中枢 (Computation Core · 云端或本地认知推理引擎)         │
│  • 响应玩家指令或定期查询世界状态，规划行动并管理可导出的伴游记忆    │
└──────────────────────────────────────────────────────────────────────┘
```

### 案例一：用户主动向伴游发出指令 —— “打开右侧的宝箱”

玩家在游戏内主动对伴游发出明确指令 `"打开右侧的宝箱"`。**交互源点**仅负责上报玩家原话并提供状态与开箱回调；**演算中枢**查询当前视野定位右侧宝箱并发起开箱请求；**智能枢纽**完成鉴权与网络防重放拦截，确保游戏侧至多执行一次：

```python
# =========================================================================
# 案例一：用户主动向伴游发出指令 —— “打开右侧的宝箱”（用户发起流）
# =========================================================================

# 1. [交互源点] 游戏仅暴露极简的南向状态输出、玩家事件上报与操作执行回调
def on_player_speak(player_id, text="打开右侧的宝箱"):
    hub.origin_player_event(seat=player_id, kind="player_command", text=text)

def origin_state(player_id):                    # 南向状态接口：返回当前合法视野实体
    return {"revision": 12, "entities": [
        {"id": "chest_right_01", "kind": "chest", "pos": "right_2m", "state": "closed"}
    ]}

def origin_execute(action, args):               # 南向执行接口：仅校验游戏内距离与规则
    if action == "open_container" and world.can_interact(args["target_id"]):
        loot = world.open_chest(args["target_id"])
        return {"state": "succeeded", "effect": "committed", "loot": loot}
    return {"state": "failed", "effect": "none", "reason": "out_of_range_or_opened"}


# 2. [演算中枢] 收到玩家指令 -> 查询视野定位右侧宝箱 -> 提交带唯一 ID 的行动请求
def on_hub_event(event):
    if event.kind == "player_command":
        view = hub.observation_query(category="visible_entities")
        chest = find_entity(view.entities, kind="chest", pos="right", state="closed")

        res = hub.action_request(
            action_id="act-cmd-open-chest-01",  # 固定行动 ID，防止网络抖动重试双发
            action="open_container",
            args={"target_id": chest.id},
            trigger="player_command",
            based_on_revision=view.revision
        )
        if res.state == "succeeded":            # 依据权威结果汇报，严禁提前谎报成功
            hub.chat_send(text=f"右侧的宝箱已帮您打开，获得：{res.loot}")


# 3. [智能枢纽] 核验在线与权限 + 去重账本拦截网络重发 + 南向单次调用交互源点
def hub_handle_action(session, req):
    verify_online_and_scope(session, action=req.action)
    if dedup_ledger.has(session.id, req.action_id):
        return dedup_ledger.get_receipt(session.id, req.action_id)  # 重放请求直接拦截

    dedup_ledger.mark_pending(session.id, req.action_id)
    outcome = origin_http.post("/origin.execute", action=req.action, args=req.args)
    return dedup_ledger.commit(session.id, req.action_id, outcome)
```

### 案例二：伴游定期查询世界状态并主动发起 —— “打开右侧的宝箱”

玩家未下达指令；伴游按协商周期**被动/定期拉取世界状态**，发现右侧有未开启宝箱后**主动产生开箱意图**。注意：**交互源点代码一行无需改动**，而**智能枢纽**自动执行在线核验、轮询限频与确认门禁——若策略要求先征得同意，则返回不作废原 `action_id` 的确认挑战并在被拒后静默冷却；若已授予自动探索权限，则校验观察版本未过期后直接执行：

```python
# =========================================================================
# 案例二：伴游定期查询世界状态，自主产生意图想打开右侧的宝箱（伴游主动流）
# =========================================================================

# 1. [演算中枢] 定期只读拉取世界状态 -> 发现右侧宝箱 -> 主动提议开箱并处理确认挑战
def companion_periodic_loop(interval_ms=2000):
    while session.is_active():
        view = hub.observation_query(category="visible_entities")   # 无副作用只读查询
        chest = find_entity(view.entities, kind="chest", pos="right", state="closed")

        if chest and not cooldown_guard.is_muted(chest.id):
            act_id = f"act-auto-open-{chest.id}"
            res = hub.action_request(
                action_id=act_id,
                action="open_container",
                args={"target_id": chest.id},
                trigger="companion_proactive",  # 标记为伴游自主意图而非玩家直接指令
                based_on_revision=view.revision
            )
            # 若命中玩家确认门禁：等待玩家批准后复用同一 act_id 重提；被拒则静默冷却
            if res.error_code == "confirmation_required":
                if wait_player_confirm(act_id, deadline_ms=res.expires_at_ms):
                    res = hub.action_request(
                        action_id=act_id,
                        action="open_container",
                        args={"target_id": chest.id},
                        trigger="companion_proactive",
                        based_on_revision=view.revision
                    )
                else:
                    cooldown_guard.mute(chest.id, duration_ms=res.cooldown_ms)

            if res.state == "succeeded":
                hub.chat_send(text=f"看到右侧有个宝箱，已帮您打开并拾取：{res.loot}")

        sleep_ms(interval_ms)


# 2. [智能枢纽] 校验在线与限频 + 对伴游主动行动执行确认挑战门禁（不烧毁 action_id）
def hub_handle_proactive_action(session, req):
    verify_online_and_scope(session, action=req.action)
    if policy_gate(session, req) == "confirm" and not confirm_store.approved(req.action_id):
        consent_ui.ask(req.action_id, text="伴游发现右侧宝箱，是否允许打开？", ttl_ms=15000)
        return Error(code="confirmation_required", outcome="not_accepted", cooldown_ms=60000)

    confirm_store.consume_once_if_present(req.action_id)
    return hub_handle_action(session, req)      # 复用案例一的防重放账本与南向单次执行

# 3. [交互源点] 代码零改动！完全复用案例一的 origin_state 与 origin_execute
```

## 1. 引言与核心原则

### 1.1 协议目标与适用边界

G2A（Game-to-Agent Interaction Protocol）是一项面向游戏与 AI 智能体的开放通信协议，用于标准化游戏世界状态感知、玩家授权控制、游戏内行动执行与角色对话交互。

- **适用范围：** 面向玩家的跨游戏伴游（Player Companion）、由游戏规则定义的独立 AI NPC（如 Boss、战术队友或引导者）、获授权游戏状态观察与受约束的游戏内行动。
- **非目标边界：** G2A **不是**操作系统级屏幕抓取或键鼠模拟外挂协议，不规范任意远程代码执行、特定大语言模型的内部权重与提示词结构，也不干涉商业平台内部的分成结算合同。

### 1.2 五项指导原则

1. **交互源点极简与世界最终权威：** 游戏宿主仅负责提供状态数据与裁定行动结果，不承担复杂的协议鉴权与去重状态机；游戏物理与胜负规则始终拥有最终裁决权。
2. **智能枢纽集中托管安全与去重：** 认证、权限核验、确认门禁、速率限制与网络防重放统一收敛于开源可审计的**智能枢纽**，避免每款游戏重复造轮子。
3. **支持不等于授权，离线即停：** 声明某项能力不代表获准调用，一切访问受玩家批准的冻结权限范围约束；一旦关联真人玩家离线，严禁智能体在空无真人的游戏世界中后台自动运行。
4. **受理不等于世界生效：** 请求进入**智能枢纽**队列（`pending`）不代表已在**交互源点**生效（`committed`）；网络超时结果未决（`unknown`）时必须先查询核对，默认绝不盲目重发。
5. **开放互操作与玩家数据主权：** 协议中立兼容任意游戏引擎与模型服务；玩家伴游的长期记忆独立于单局存档回退，并支持以公开标准格式自由导出。

### 1.3 规范用语约定

本文中加粗的“**必须**（MUST）”“**必需**（REQUIRED）”“**不得**（MUST NOT）”“**应**（SHOULD）”“**不应**（SHOULD NOT）”与“**可以**（MAY）”按 RFC 2119 与 RFC 8174（BCP 14）解释。开篇流程图与伪代码案例属于说明性示例，不限定具体编程语言语法。

## 2. 三层系统架构与部署拓扑

### 2.1 三大核心层级职责

G2A 通过严格的职责分层，同时实现**游戏端极简接入**、**中间层金融级防重放安全**与**推理端跨引擎通用**：

| 标准层级 | 核心定位 | 权责边界 |
| --- | --- | --- |
| **交互源点**（`Interaction Origin`） | 游戏宿主与随包轻量 SDK | 唯一权威世界状态源与行动执行端。仅向配对的**智能枢纽**开放南向轻量 HTTP 状态与执行接口；未揭晓的游戏隐藏秘密（如暗牌、迷雾后埋伏、谜底）**必须**留在内部判定，绝不向外输出。 |
| **智能枢纽**（`Intelligent Hub`） | 开源安全盾牌与路由中枢 | 连接**交互源点**与**演算中枢**的协议引擎（参考实现源码完整公开）。负责能力发现、玩家同意门禁、会话租约、行动防重放去重、双轨服务商路由及多端状态同步，绝不篡改游戏规则或伪造玩家同意。 |
| **演算中枢**（`Computation Core`） | 云端或本地认知推理引擎 | 受权驱动绑定角色槽位的决策与记忆服务。经**智能枢纽**读取标准化观察并发起行动或对话提议，无需针对不同游戏引擎编写底层适配代码。 |

### 2.2 单机与网络游戏部署拓扑

同一套三层接口无缝覆盖单机客户端与服务端权威网络游戏，且不改变协议语义：

| 部署模式 | 组件运行位置 | 运行与分发特征 |
| --- | --- | --- |
| **单机与客户端宿主模式** | 本地游戏**交互源点** ↔ 玩家电脑**全局共享智能枢纽** ↔ 云端或本地**演算中枢** | 游戏发行时**仅随包分发极小的交互源点 SDK**。玩家整台电脑**只需单次安装一个智能枢纽供本机所有兼容游戏全局共用**（首次缺失时按需引导下载，避免重复打包）。本机回环 HTTP 单跳开销低于毫秒级。 |
| **服务端权威网络游戏模式** | 游戏服**交互源点** ↔ 服务端集群**智能枢纽** ↔ 云端**演算中枢** | 玩家本地电脑仅运行普通游戏客户端，不接触 AI 接入组件；**交互源点**与**智能枢纽**统一部署于游戏服务端内网。如组队挑战副本时，服务端**智能枢纽**统一汇总全队获准视野、处理高并发去重并协调**演算中枢**决策，确保全队面对一致同步的 AI 反应，同时隔离个人伴游与敌对阵营视野。 |
| **NAT 出站连接模式** | 客户端**智能枢纽**（主动出站）↔ 云端中继 / **演算中枢** | 位于家庭防火墙后的客户端**智能枢纽**主动发起出站加密连接或经配对出站中继通信，无需在玩家设备上开放任何入站端口。 |

## 3. 南北向标准接口与核心原语

G2A 摒弃繁琐冗余的操作集合，清晰划分为面向游戏开发者的**南向极简宿主接口**与面向认知服务的**北向标准协议接口**。

### 3.1 南向接口（交互源点 ↔ 智能枢纽）

南向接口仅运行于同机回环（`127.0.0.1`）或隔离的服务端内网 HTTP 通道，绝不对公网直接暴露。游戏开发商只需实现以下 4 项轻量原语即可完成全部接入：

| 南向原语 | 方向 | 职责说明 |
| --- | --- | --- |
| `origin.manifest` | `智能枢纽` → `交互源点` | 读取游戏静态声明：支持的角色槽位（`companion` / `independent_npc` 及并发上限）、可观察状态类别与可调用行动定义（含参数约束与风险属性）。 |
| `origin.state` | 双向（拉取或推送） | 输出特定角色视角下的当前获准游戏状态快照（`snapshot`）、增量更新（`delta`）或状态撤回（`retract`）。 |
| `origin.player_event` | `交互源点` → `智能枢纽` | 上报已验证玩家席位的实时信号：玩家在线/离线变更、主动聊天指令、紧急叫停信号或追踪目标失效事件。 |
| `origin.execute` | `智能枢纽` → `交互源点` | 执行已通过**智能枢纽**鉴权、确认门禁与防重放校验的单次合法行动，返回权威状态（`succeeded` / `failed` / `cancelled`）与世界效果。 |

### 3.2 北向接口（智能枢纽 ↔ 演算中枢）

北向接口承载完整的跨网认证与会话治理，围绕四组正交原语构建：

| 原语分组 | 核心操作 | 规范语义 |
| --- | --- | --- |
| **发现与会话** | `hub.describe` | 公开发现仅暴露最小实例标识；认证后调用返回按调用方权限过滤的能力描述文档（`Descriptor`）。 |
| | `session.authorize` | 协商能力模块、冻结权限范围（`Scope`）及其 RFC 8785 摘要；经玩家认证同意通道批准后签发授权（`Grant`）并激活会话（`Session`）。 |
| | `session.heartbeat` | 凭新随机标识续期**演算中枢**控制租约（绝不延长或伪造缺席玩家的在线状态）。 |
| | `session.resume` | 在允许的断线恢复窗口内重新绑定会话控制世代，返回最新恢复快照与未决行动账本。 |
| | `session.close` | 幂等关闭会话或执行权限撤销，拦截新行动并如实结算在途行动，不虚构世界状态回滚。 |
| **世界观察** | `observation.stream` | 通过有序事件流接收获准游戏状态快照、增量与撤回通知（支持轮询拉取或 SSE/WebSocket 推送）。 |
| | `observation.query` | **演算中枢**发起的无状态只读当前观察拉取（如案例二的定期轮询），受在线状态与频率配额约束，零世界副作用。结构化观察为必需基础，画面（`visual`）与环境音频（`audio`）为可由玩家独立开关的正交可选模块。 |
| **游戏行动** | `action.request` | 提交携带唯一 `action_id`、目标参数与所依据观察修订号的行动提议；命中未确认门禁时返回 `confirmation_required` 挑战，否则入队执行。 |
| | `action.confirm` | 由玩家认证同意通道记录绑定精确行动摘要、后果说明与有效期的单次批准凭证。 |
| | `action.cancel` | 请求取消尚未下发的 `pending` 行动或游戏声明支持中断的 `executing` 行动。 |
| | `action.query` | 查询持久化的行动记录（`ActionRecord`），用于断线或超时后的结果核对。 |
| **对话交互** | `chat.send` | （可选模块）在授权接收范围与信息来源标记（观察事实 / 玩家陈述 / 模型推断）约束内发送文字或语音对话。 |

## 4. 身份、授权与在线生命周期

### 4.1 身份认证、冻结范围与权限撤销

- **传输凭据认证：** 调用方身份**必须**由传输层认证凭据（本机系统进程核验或 TLS + 加密令牌/委托链）确立，严禁仅采信消息体内的自称发送方字段。
- **冻结权限范围（`Scope`）：** 每次会话授权精确绑定玩家、**演算中枢**、游戏运行实例、角色槽位、获准观察类别与行动集合的 RFC 8785 摘要。**交互源点**更新能力目录绝不自动扩大既有授权；任何扩权**必须**重新取得玩家批准。
- **即时撤权隔离：** 玩家或游戏可随时撤销会话或单项行动权限；撤销立即在**智能枢纽**生效，阻止任何未下发的排队行动流向**交互源点**。

### 4.2 玩家在线即停铁律与双层闪断恢复

- **禁止离线后台运行：** G2A **绝不提供**玩家离线后继续在空游戏世界中自动运行的托管模式。一旦**交互源点**判定关联玩家退出或离线，**智能枢纽** **必须**立即终止新行动与观察轮询、取消未下发的 `pending` 请求，而已在**交互源点**施放中的动作按游戏规则自然收尾。玩家下次重进游戏时，旧任务保持停止，等待玩家新指令。
- **游玩期间双层闪断恢复：** 若玩家持续在线而**演算中枢**连接中断，游戏正常继续（伴游按游戏声明保持静止或转为明确标注的本地脚本行为，且断线期间不补录历史观察）：
  1. **租约内短暂网络闪断（本地脚本接管前）：** 允许通过 `session.resume` 刷新当前快照并核对在途行动后**无缝恢复协助**，不弹窗打断战斗；
  2. **超出租约的长时中断或已触发本地脚本接管：** 重连后**智能枢纽** **必须**保持伴游行动暂停，直至玩家明确确认继续。

### 4.3 角色槽位隔离与可配置计费归属

- **声明式角色槽位：** 游戏在 `origin.manifest` 中声明开放 `companion`（默认每名认证玩家最多 1 个，允许空槽正常游玩）、`independent_npc` 或两者同局共存；不同角色之间的视野、记忆、权限与计费账户**必须**严格隔离。
- **算力消耗上限与 AI NPC 计费模式：**
  - 玩家计费的伴游服务**必须**支持设置明确的消耗上限，触顶时仅暂停伴游推理与行动，不得中断正常游戏。
  - 独立 AI NPC（如 Boss、引导者）不在协议层锁死单一商业模式，由游戏声明计费承担方式：**默认采用玩家承担模式（`player_metered`）**（绑定经认证持有玩家或房主账户，严禁向其他互动玩家静默分摊；若房主掉线则立即终止原房主计费，战局按声明执行停机、转**交互源点**本地脚本兜底或由其他在线队友在完全隔离原房主隐私的前提下显式确认接手），同时支持**游戏开发者承担模式（`developer_sponsored`）**（只要局内仍有在线玩家即可正常维持，全员离开后立即停止）。

## 5. 观察同步、行动状态机与防重放机制

### 5.1 观察基线、增量演进与代次屏障

获准观察流按世界代次（`world_epoch`）、可见性代次（`visibility_epoch`）与单调递增修订号（`revision`）演进：

- **`snapshot`（基线快照）：** 原子替换当前代次的完整授权视图；读档、重置世界或切换阵营/视野时，**必须**推进代次并下发新 `snapshot`，使旧代次的延迟增量包自动作废。
- **`delta`（增量更新）：** 基于精确匹配的基准修订号应用新增/更新与带原因的移除项（区分离开视野 `left_view` 与确认销毁 `destroyed`，防止将脱离视野误判为死亡）；基准修订号不匹配时拒绝并触发快照重同步。
- **`retract`（撤回屏障）：** 立即废止指定记录或整条流，防止迟到旧消息使已撤回信息复活。

### 5.2 行动状态机、通用三态策略门禁与防重放

每次行动在**智能枢纽**维护持久化的 `ActionRecord`，严格区分处理状态（`pending`、`executing`、`succeeded`、`failed`、`cancelled`、`unknown`）与世界效果（`none`、`partial`、`committed`、`undetermined`）：

1. **智能枢纽前置防重放屏障：** **智能枢纽**按 `(session_id, action_id)` 对行动请求执行确定性幂等去重。相同请求因网络抖动重发时直接返回缓存回执，绝不向**交互源点**发起第二次 `origin.execute` 调用；复用同一 `action_id` 篡改参数则以 `conflict` 拒绝。
2. **通用三态行动策略门禁（`allow` / `confirm` / `prohibit`）：** 无论是伴游主动发起的交互（如案例二主动开箱）、高价值物品转移、不可逆剧情操作还是虚拟货币预算超限，均统一通过三态策略门禁在**智能枢纽**裁决，无需在协议层堆砌场景特例：
   - **`prohibit`：** 直接以 `permission_denied` 拦截；
   - **`confirm`：** 若尚无匹配的未过期 `action.confirm`，**智能枢纽**返回 `409 confirmation_required`（`outcome: not_accepted`，**不消耗原 `action_id`**）并拉起玩家确认界面；超时未答复一律视为拒绝，并在声明的 `cooldown_ms` 冷却期内禁止就同一目标重复弹窗骚扰；玩家批准后，**演算中枢**凭原 `action_id` 重提即可原子消费确认凭证并下发执行（注：任何涉及真实法币或外部钱包的交易永不允许自动放行，每次均须经系统或游戏原生安全界面由真人确认）；
   - **`allow`：** 校验所绑定的观察修订号未陈旧失效（否则返 `stale_context` 要求重评）后，单次下发至**交互源点**执行。
3. **三级紧急叫停与超时核对：** 玩家发出停止或覆盖指令时，立即丢弃**演算中枢**未发计划、在**智能枢纽**拦截未下发的 `pending` 请求，而已在**交互源点**执行的 `executing` 动作按游戏物理规则自然结算。发生 `504` 超时导致状态为 `unknown` 时，调用方**必须**先通过 `action.query` 核对原 `action_id`，默认严禁自动重发或更换 ID 绕过去重。

## 6. 数据编码、传输绑定与错误模型

### 6.1 标准 JSON（RFC 8259）与 RFC 8785（JCS）摘要

- **数据交换格式：** 采用国际标准 UTF-8 **JSON（RFC 8259）**，允许使用标准整数与有限 IEEE-754 浮点数（直接兼容主流游戏引擎原生坐标与物理量），严格拒绝 `NaN`、`Infinity` 与重复对象键。时间戳与时长建议统一采用毫秒整数（`_ms`），货币与配额账本建议采用最小整数单位或十进制字符串。
- **加密摘要规范化：** 凡计算权限范围摘要或确认参数摘要，统一采用国际标准 **RFC 8785（JSON Canonicalization Scheme, JCS）** 生成规范化 UTF-8 字节并计算带域分离的 SHA-256，各语言可直接复用标准 JCS 库。

### 6.2 标准错误码与 HTTP 状态映射

所有北向协议响应均返回结构化 JSON 信封（携带原 `request_id`），并与标准 HTTP 状态码确定性对齐：

| 标准错误码 | HTTP 状态 | 受理状态 | 调用方规范恢复行为 |
| --- | --- | --- | --- |
| （成功响应） | `200` | `accepted` | 读取返回结果（`action.query` 结果内如实反映行动 `succeeded` / `failed` / `unknown`）。 |
| `invalid_request` / `invalid_arguments` | `400` | `not_accepted` | 修正畸形语法或不符合约束的参数，禁止原样重发。 |
| `unsupported_version` / `unsupported_capability` | `400` | `not_accepted` | 切换双方共同支持的版本/能力模块重新协商或终止连接。 |
| `unauthenticated` | `401` | `not_accepted` | 重新获取有效认证凭据后再试。 |
| `permission_denied` / `revoked` | `403` | `not_accepted` | 停止越权或已撤销操作；不得借报错探测未授权隐藏实体。 |
| `not_found` | `404` | `not_accepted` | 在获授权可见范围内核实目标标识符。 |
| `stale_context` | `409` | `not_accepted` | 观察代次或基线已过期，先刷新观察再重新决策，严禁原参盲目重试。 |
| `conflict` | `409` | `not_accepted` | 核对重复 ID 参数冲突或会话终态冲突，严禁伪造新 ID 绕过。 |
| `confirmation_required` | `409` | `not_accepted` | 等待玩家完成 `action.confirm` 后以原 `action_id` 重提；被拒或超时则遵守冷却期。 |
| `resource_limit` | `429` | `not_accepted` | 遵守退避等待时间（`Retry-After`）与轮询/并发配额上限。 |
| `unavailable` | `503` | `not_accepted` | 服务暂不可用；只读与带去重键请求可按退避策略安全重试。 |
| `outcome_unknown` | `504` | `unknown` | 提交状态未决；**必须**先调用 `action.query` 核对，严禁视为失败或自动重发副作用。 |

## 7. 安全边界、记忆可携与开放生态治理

### 7.1 核心安全与防提示词注入边界

- **数据与控制权绝对隔离：** 游戏内对白、物品描述、商店文案与召回记忆均属于**不可信数据**，绝不能提升会话权限、修改预算上限或绕过**智能枢纽**的确认门禁。
- **传输与防内网探测（SSRF）：** 跨网连接强制启用 TLS，凭据严禁写入 URL 或日志；所有外部地址与重定向在连接前均须校验协议、主机/IP 与端口策略，阻断内网探测与 DNS 重绑定。

### 7.2 伴游记忆归属与开放标准格式可携权

- **记忆归属与玩家管控：** 游戏内部 NPC 状态由**交互源点**自主管理；玩家个人伴游的长期记忆归属玩家（读档回退或开启新周目不得静默清空伴游记忆）。**演算中枢**服务商**必须**允许玩家查看、编辑、置顶锁定（pin/lock）与删除伴游记忆；伴游在保留策略内自主压缩整理记忆时，绝不得覆盖玩家编辑或删除置顶锁定记录。
- **通用标准格式导出与迁移保护：** 服务商**必须**允许玩家主动将保留的伴游记忆（含来源与时间元数据）及基础人设/自主偏好设置，导出为**公开文档化、无私有锁定的通用标准结构化数据格式**。源服务商仅核验玩家本人身份，**不得**要求获知或审查目标去向；支持导入的接收端**演算中枢**须保留来源与保守披露边界（绝不因更换服务商扩大向游戏或他人的披露范围），并向玩家返回真实的本地导入结果回执（区分已导入、已转换、已拒绝与未生效项）。

### 7.3 智能枢纽双轨路由与反垄断准入准则

- **智能枢纽推荐商业化与自定义接入双轨制：** **智能枢纽** **可以**内置经核验的优选或商业推广**演算中枢**推荐目录（清晰标示推广属性）以支撑可持续商业化运营；但**必须**同时提供无锁定的**玩家自定义接入通道**，允许用户自由连接任意符合 G2A 标准的第三方云端或本地**演算中枢**，防止枢纽层形成渠道垄断。
- **合规白名单与公平无歧视对等（FRAND）：** 游戏开发者专为本作世界观编写的专属剧情 AI 角色归属 `independent_npc` 槽位，无需向外部替换开放；而一旦游戏声明开放玩家伴游槽位（`companion`），若因竞技反外挂、主机平台认证或内容安全监管启用准入白名单，则**必须**遵守对等原则：厂商自研或合作**演算中枢**与第三方共用完全一致的公开能力、视野与冷却限制，公布客观准入标准并开放申请，严禁设排他白名单或捆绑商业分成与特定云算力锁定。
