## 架构总览与核心交互案例

### 三层架构总览流程图

G2A 旨在让任何游戏以**最低的工程改造成本**安全接入 AI 角色——主要包括陪伴玩家游玩的**玩家伴玩**（即**伴游**，Player Companion）以及可选的**独立 AI NPC**（如 Boss、引导者）。全系统严格解耦为**交互源点**、**智能枢纽**与**演算中枢**三层架构：

```text
                        [ 真人玩家 Human Player ]
               ┌────────────────────┴────────────────────┐
       游戏内操控 / 主动下达指令                 授权审批 / 确认门禁 / 选配中枢
               ▼                                         ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第一层：交互源点 (Interaction Origin · 随游戏分发的极简宿主 SDK)     │
│  • 仅提供两类轻量接口：1) 返回/上报获准世界状态  2) 执行游戏内操作   │
│  • 掌握游戏物理、视野与胜负规则的唯一最终裁定权（零去重与鉴权负担）  │
└───────────────────────────────────▲──────────────────────────────────┘
                                    │ 南向轻量 HTTP（本机回环 / 服务端内网）
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第二层：智能枢纽 (Intelligent Hub · 开源安全盾牌与路由中枢)          │
│  • 单机电脑单次安装全局共用 / 网络游戏部署于服务端统一同步多端战局   │
│  • 集中托管：身份与权限核验、防重放幂等去重、确认挑战门禁、双轨路由  │
└───────────────────────────────────▲──────────────────────────────────┘
                                    │ 北向标准 G2A 协议（HTTPS / 流式通道）
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 第三层：演算中枢 (Computation Core · 云端或本地认知推理引擎)         │
│  • 响应玩家指令或定期查询世界状态，规划游戏行动并管理可导出伴玩记忆  │
└──────────────────────────────────────────────────────────────────────┘
```

三条核心权力边界贯穿所有 G2A 交互：

1. **交互源点掌握世界事实与最终执行权：** 游戏只需提供状态数据与操作回调；底层安全校验、防重放拦截与服务商路由全部由**智能枢纽**承担。
2. **玩家主导授权、策略与中枢选配：** 玩家决定是否启用伴游、连接哪一个**演算中枢**、授予何种权限范围，以及高风险或伴游主动行为是否需要确认。
3. **演算中枢专注认知推理与记忆可携：** 同一套协议同时支撑**玩家指令驱动**与**伴游定期感知主动决策**两种核心交互范式。下面通过两个直观案例展示完整的三层流转逻辑。

### 案例一：用户主动向伴游发出指令 —— “打开右侧的宝箱”

**目标场景：** 玩家在游戏内直接对伴游说 `"打开右侧的宝箱"`。此案例由**玩家的明确实时意图**触发：**交互源点**仅负责上报玩家原话与暴露极简状态/开箱接口；**演算中枢**读取当前视野定位右侧宝箱并发起开箱请求；**智能枢纽**完成权限核验与网络防重放去重，确保宝箱只被安全执行一次，随后由伴游凭真实结果回复玩家。

```python
# =========================================================================
# 案例一：用户主动向伴游发出指令 —— “打开右侧的宝箱”（用户发起流）
# =========================================================================

# 1. [交互源点] 游戏侧仅需暴露极简的南向状态读取与操作回调接口（零安全/去重负担）
def on_player_speak(player_id, text="打开右侧的宝箱"):
    # 将经验证席位的玩家原话上报给智能枢纽（标记真实来源为 player_statement）
    hub_southbound.player_chat_forward(seat=player_id, provenance="player_statement", text=text)

def http_get_visible_state(player_id):
    # 南向状态接口：仅返回该玩家当前合法视野内的实体列表与状态修订号
    return {
        "revision": 12,
        "entities": [
            {"id": "chest_right_01", "kind": "chest", "relative_pos": "right_2m", "state": "closed"}
        ]
    }

def http_execute_action(action, args):
    # 南向操作接口：仅按游戏物理与距离规则裁定开箱结果并返回掉落物
    if action == "open_container" and game_world.can_interact(args["target_id"]):
        loot = game_world.open_chest(args["target_id"])
        return {"state": "succeeded", "effect": "committed", "loot": loot}
    return {"state": "failed", "effect": "none", "reason": "out_of_range_or_already_opened"}


# 2. [演算中枢] 接收玩家指令 -> 查询当前授权视野定位右侧宝箱 -> 提交唯一行动请求
def on_hub_event(event):
    if event.type == "player_chat" and event.provenance == "player_statement":
        # 读取当前获准观察，将自然语言“右侧的宝箱”消解为目标实体 ID
        view = hub_northbound.observation_query(category="visible_entities")
        chest = find_entity(view.entities, kind="chest", direction="right", state="closed")

        res = hub_northbound.action_request(
            action_id="act-cmd-open-chest-01",   # 绑定固定行动 ID，防止网络抖动重试导致双发
            action="open_container",
            args={"target_id": chest.id},
            trigger="explicit_player_command",
            based_on_revision=view.revision
        )
        # 必须依据交互源点确认提交的真实结果汇报，严禁刚入队就提前谎报“已打开”
        if res.state == "succeeded":
            hub_northbound.chat_send(text=f"右侧的宝箱已帮您打开，获得：{res.loot}")


# 3. [智能枢纽] 核验在线与授权 + 拦截网络重复请求 + 南向单次调用交互源点
def hub_on_action_request(session, req):
    verify_player_online_and_scope(session, required_action=req.action)

    # 防重放去重屏障：若演算中枢因断网重试发了两次相同请求，在此直接拦截并返回原回执
    if dedup_ledger.has(session.id, req.action_id):
        return dedup_ledger.get_receipt(session.id, req.action_id)

    dedup_ledger.mark_pending(session.id, req.action_id)
    outcome = origin_http.post("/execute_action", action=req.action, args=req.args)
    return dedup_ledger.commit_outcome(session.id, req.action_id, outcome)
```

### 案例二：伴游定期查询世界状态并主动发起 —— “打开右侧的宝箱”

**目标场景：** 玩家并未下达开箱指令；伴游在玩家在线期间按协商周期**被动/定期拉取世界状态**，发现玩家右侧出现一个未开启的宝箱后，**由伴游自己产生主动意图**想打开右侧宝箱。此案例展示了 G2A 对 AI 自主行为的核心安全治理：**交互源点代码一行不用改**，而**智能枢纽**会自动校验玩家在线状态、轮询频率上限以及玩家的自主确认策略——若策略要求先征得同意（或宝箱带机关风险），则触发**不烧毁行动 ID 的确认挑战握手**与**拒绝后防骚扰冷却**；若玩家已授予自动搜刮权限，则直接校验观察新鲜度后安全执行。

```python
# =========================================================================
# 案例二：伴游定期查询世界状态，自主产生意图想打开右侧的宝箱（伴游主动发起流）
# =========================================================================

# 1. [演算中枢] 定期只读查询世界状态 -> 自主发现右侧宝箱 -> 发起主动行动并处理确认挑战
def companion_periodic_loop(poll_interval_ms=2000):
    while session.is_active():
        # 定期调用无世界副作用的只读观察查询（若玩家离线，智能枢纽会立即拒绝并终止会话）
        view = hub_northbound.observation_query(category="visible_entities")
        chest = find_entity(view.entities, kind="chest", direction="right", state="closed")

        if chest and not cooldown_guard.is_muted(chest.id):
            act_id = f"act-proactive-open-{chest.id}"
            res = hub_northbound.action_request(
                action_id=act_id,
                action="open_container",
                args={"target_id": chest.id},
                trigger="companion_proactive",   # 标明为伴游自主发起而非玩家直接指令
                based_on_revision=view.revision  # 绑定观察版本，若玩家已自己打开则自动失效拒绝
            )

            # 分支 A：若玩家策略要求伴游主动开箱前须确认，智能枢纽返回 confirmation_required
            if res.error_code == "confirmation_required":
                if wait_player_confirm(action_id=act_id, deadline_ms=res.expires_at_ms):
                    # 玩家批准后，复用同一 act_id 原样重提（此前挑战未消耗该去重键）
                    res = hub_northbound.action_request(
                        action_id=act_id,
                        action="open_container",
                        args={"target_id": chest.id},
                        trigger="companion_proactive",
                        based_on_revision=view.revision
                    )
                else:
                    # 玩家拒绝或超时未理：立即放弃并进入冷却期，严禁在同一位置反复弹窗骚扰
                    cooldown_guard.mute(chest.id, duration_ms=res.cooldown_ms)

            # 分支 B（已获自动搜刮授权）或分支 A 确认通过后：凭真实结果主动告知玩家
            if res.state == "succeeded":
                hub_northbound.chat_send(text=f"看到右侧有个未开的宝箱，已帮您打开并拿到：{res.loot}")

        sleep_ms(poll_interval_ms)


# 2. [智能枢纽] 校验在线与轮询限频 + 对伴游主动意图执行确认挑战门禁与冷却控制
def hub_on_proactive_action(session, req):
    verify_player_online_and_scope(session, required_action=req.action)

    # 若当前玩家策略对“伴游主动交互/含风险交互”要求确认，且尚无有效批准凭证：拦截并拉起确认挑战
    if policy_requires_confirm(session, req) and not confirm_store.is_approved(req.action_id):
        player_consent_ui.ask(
            action_id=req.action_id,
            prompt="伴游发现右侧有一个宝箱，是否允许打开？",
            expires_in_ms=15000
        )
        # outcome 为 not_accepted，不锁死 action_id，供玩家同意后原样重提
        return Error(code="confirmation_required", outcome="not_accepted", cooldown_ms=60000)

    confirm_store.consume_once_if_present(req.action_id)
    # 通过门禁后，直接进入与案例一完全相同的防重放账本与南向单次执行链路
    return hub_on_action_request(session, req)


# 3. [交互源点] 代码零改动！完全复用案例一的 http_get_visible_state 与 http_execute_action
```

## 1. 目的与范围

### 1.1 设计目标与四大支柱

G2A 使符合规范的**交互源点**、**智能枢纽**与**演算中枢**能够在本地与云端环境中安全互操作。全规范围绕四大支柱展开：

| 支柱 | 规范内容 |
| --- | --- |
| 准入与控制 | 由**智能枢纽**统一托管的主体身份认证、能力发现、公平准入治理、玩家同意、有界授权、会话租约、控制权交接与分级撤销。 |
| 观察与信息使用 | 源自**交互源点**的获授权游戏状态视图、基线快照与增量更新、信息来源、新鲜度、接收范围边界、多模态输入与记忆治理。 |
| 行动与结果 | 角色能力声明、动态合法行动资格、确认挑战门禁、**智能枢纽**防重放拦截、**交互源点**效果边界裁定、取消语义与未决结果核对。 |
| 互操作与生态治理 | 规范概念模型、抽象操作、标准 JSON/JCS 规范化、南北向 HTTP 接口准则、**智能枢纽**共享分发机制与符合性测试套件。 |

### 1.2 核心架构区分

五项基本区分贯穿三层架构的全部环节：

- **支持不等于授权：** 声明某项能力仅表明技术上支持该功能，发起请求仅表达调用意图；缺少经玩家批准并由**智能枢纽**强制执行的有效授权记录与冻结会话范围时，两者均不赋予读取或执行权。
- **接受不等于效果完成：** **智能枢纽**接收或排入行动请求（`pending`）不代表已在**交互源点**产生世界变化；队列受理、执行领取（`executing`）与世界效果提交（`committed`）**必须**严格区分。
- **获准读取不等于持续有效：** 观察仅反映特定世界代次与修订号下的受限视角，随世界状态或视野变化将过期失效。
- **缺失不等于不存在：** 因战争迷雾、权限过滤或增量压缩而未出现的信息，**不得**被推断为某项事实为假、空世界或实体已销毁。
- **伴玩记忆独立于当前世界状态：** 读档回退、开启新周目或切换剧情分支会改变**交互源点**的权威世界状态，但**不得**静默清空**演算中枢**中由玩家自主管理的伴玩记忆；记住先前周目的经历不代表该事件已在当前世界发生，也不能覆盖游戏的硬性玩法规则。

### 1.3 适用范围与非目标

G2A 严格限定于游戏交互领域：面向玩家的伴玩协助、获授权 AI NPC 交互、游戏状态观察、受约束的游戏内行动及可选的伴玩视觉外观呈现。

G2A **不是**通用操作系统或桌面界面自动化协议。它不将任意远程代码执行、未经声明的屏幕或键鼠抓取、模型权重、提示词模板或商业平台内部收入结算条款纳入标准。G2A 强制执行可观察的数据、接收范围与行动边界，但任何通信协议都无法擦除模型权重中固有的通识先验，也无法阻止端点基于已获披露的事实作内部推断。

## 3. 三层架构、部署拓扑与适用性

### 3.1 三层运行架构与各层标准接口边界

G2A 将游戏玩法宿主、安全路由治理与智能模型推理拆分为命名清晰、边界严格的三层标准架构，并通过南北两道标准化接口衔接：

1. **交互源点与南向源点至枢纽 HTTP 接口：** 游戏开发商（包括各类新引擎与自研引擎团队）只需集成随游戏分发的极轻量**交互源点 SDK**，以本地回环或服务端内网 HTTP 接口形式仅对外提供两项纯粹能力——**获准游戏状态读取/上报接口**与**可执行操作回调及结果返回接口**。开发商只需在对应接口填好状态返回序列与操作执行结果即完成全部接入，无需编写防重放去重、复杂会话握手或外部路由代码。
2. **智能枢纽（开源安全盾牌与路由中枢）：** 架设在**交互源点**与**演算中枢**之间的独立开源枢纽，集中托管全部协议治理逻辑：能力协商、玩家同意门禁、**请求防重放与幂等去重**（例如**演算中枢**因网络中断或抖动连续发出两次相同攻击请求时，**智能枢纽**直接拦截重复请求并返回原回执，绝不穿透至**交互源点**造成二次结算）、会话租约、离线即停隔离与多端路由。**智能枢纽**参考实现**源码完整公开**供全行业审计；由于南向 HTTP 走本机回环或同机房内网，单跳耗时仅亚毫秒至毫秒级，相较于**演算中枢**推理时长完全可忽略。
3. **演算中枢与北向枢纽至中枢标准接口：** 云端或本地部署的**演算中枢**通过标准化的北向 G2A 协议（第 5–18 节）与**智能枢纽**交互，消费统一格式的观察数据并发起行动或对话提议，无需针对不同游戏引擎重复适配。

### 3.2 单机终端与网络游戏双形态部署拓扑

同一套“**交互源点 ↔ 智能枢纽 ↔ 演算中枢**”三层架构无缝适配单机游戏与服务端权威网络游戏：

| 部署形态 | 三层组件运行位置 | 运行流转与分发方式 |
| --- | --- | --- |
| **单机与客户端宿主模式** | 本地游戏内嵌**交互源点** ↔ 玩家电脑**全局共享智能枢纽** ↔ 云端或本地**演算中枢** | 游戏发行时**仅需随包分发极小的交互源点 SDK**；玩家整台电脑**只需安装一次智能枢纽并供本机所有兼容游戏全局共用**（若检测到本机尚未安装**智能枢纽**，由**交互源点 SDK** 按需引导单次下载安装，杜绝每款游戏重复打包安装）。 |
| **服务端权威网络游戏模式** | 游戏服内嵌**交互源点** ↔ 服务端集群**智能枢纽** ↔ 云端**演算中枢** | 玩家个人电脑仅运行常规游戏画面客户端，不在本地运行 AI 也不接触 SDK 接入；**交互源点与智能枢纽统一部署于游戏服务端**。以多人组队打副本为例，服务端**智能枢纽**经内网 HTTP 汇总获准的全队视野与战局状态、管理高并发去重与多端同步，并统一对接**演算中枢**下达战术或 Boss 行动，确保全队玩家面对的智能体反应严格一致且同步（同时对个人伴玩或敌对阵营保持独立权限与视野隔离）。 |
| **NAT 受限出站中继模式** | 客户端/房主侧**智能枢纽**（主动出站）→ **配对出站中继** ← 云端**演算中枢** | 当位于家庭防火墙后的客户端**智能枢纽**需在不开放任何入站端口的前提下与外部端点双向配对时，通过出站中继（第 18.3 节）承载北向协议，保持三层职责边界完全一致。 |

### 3.3 能力模块与适用范围

核心符合性仅要求实现会话管理、事件投递与基础结构化感知；其余能力模块均按游戏设计需求显式协商启用：

| 能力模块标识 | 要求层级 | 核心职责概览 |
| --- | --- | --- |
| `core.session` | 必需核心 | 发现、能力协商、有界准入、会话租约、恢复快照、会话关闭与错误报告。 |
| `core.events` | 必需核心 | 接收方可见的有序事件投递、上下文发布及会话内幂等去重。 |
| `perception.structured` | 必需核心（`演算中枢`） | 理解已协商的结构化游戏状态观察，并在获授权角色边界内决策。 |
| `observation.query` | 可选能力 | **演算中枢**发起的无状态、经授权当前游戏观察读取，不产生世界副作用（第 9.6 节）。 |
| `perception.visual` | 可选能力 | 正交叠加于 `perception.structured` 之上的游戏画面视觉感知（第 9.5 节）。 |
| `perception.audio` | 可选能力 | 正交叠加于 `perception.structured` 之上的游戏环境音频感知，独立于语音对话（第 9.5 节）。 |
| `actions` | 可选能力 | 类型化行动请求、确认挑战门禁、执行领取、效果边界重验、取消与结果查询（第 10 节）。 |
| `chat` | 可选能力 | 绑定信息来源与接收范围的文字或语音对话沟通（第 15 节）。 |
| `team` | 可选能力 | 多人席位映射、成员关系修订号与队伍范围接收控制。 |
| `resume` | 可选能力 | 持久会话账本与活动租约内的无缝重连恢复（第 11、14.2 节）。 |
| `handoff` | 可选能力（依赖 `resume`） | 带控制代次隔离的跨已验证设备或进程会话控制权交接。 |
| `multi-session` | 可选能力 | 同一**演算中枢**身份并发维持多个活动会话，不静默挤占既有会话。 |
| `avatar` / `assets` / `presentation` | 可选能力 | 伴玩外观优先级协商、安全声明式资源解析与设备渲染租约（第 17.2 节）。 |
| `store` | 可选能力 | 结构化游戏内商品目录、限频推荐与权威购买预算账本（第 17.1 节）。 |
| `privacy-request` | 可选能力 | 针对数据保管方的有界数据删除/停用请求与真实处理回执（第 15.4 节）。 |

## 4. 角色、身份与信任

### 4.1 核心信任主体与三层架构角色

G2A 围绕三大标准架构层级、真人玩家以及四类可选支撑角色界定权责边界：

| 角色名称 | 类别 | 权威边界与核心职责 |
| --- | --- | --- |
| **交互源点**（`Origin`） | 核心权威源层 | 游戏宿主及随包轻量 SDK（含内部玩法执行逻辑）。当前游戏状态与行动结果的唯一权威源头；仅向配对的**智能枢纽**开放极简南向 HTTP 状态与行动执行接口。 |
| **智能枢纽**（`Hub`） | 核心安全路由层 | 连接**交互源点**与**演算中枢**的开源协议中枢。负责认证调用方、执行 `Scope` 权限、拦截重放与重复请求、管理会话租约、协调确认门禁并路由至所选**演算中枢**，绝不凌驾于游戏规则之上或伪造玩家同意。 |
| **玩家 / `PlayerConsent`** | 核心主体 | 真人玩家及其经过认证的同意与控制通道，负责批准权限提议、确认高影响行动、配置伴玩策略、选配或自定义**演算中枢**及撤销访问权。 |
| **演算中枢**（`Core`） | 核心认知推理层 | 运行于云端或本地、受权驱动绑定游戏角色（玩家伴玩或独立 AI NPC）的推理与记忆服务；经**智能枢纽**消费获准观察并发起范围内行动或对话提议。 |
| **本地安装与启动器**（Launcher） | 可选支撑角色 | 在玩家电脑尚未安装共享**智能枢纽**时凭明确同意完成单次按需引导安装，或凭显式单次许可唤起本机预登记固定程序，严禁拼接执行不可信命令字符串。 |
| **呈现端点**（Presentation） | 可选支撑角色 | 管理用户设备上的伴玩窗口或覆盖层渲染租约及安全声明式资源缓存。 |
| **数据保管方**（Custodian） | 可选支撑角色 | 任何实际持久化保存玩家或伴玩记录的参与方（**演算中枢**服务商、**交互源点**或平台），负责就其受控数据处理删除请求并签发回执。 |
| **出站中继**（Outbound Relay） | 可选传输角色 | 在客户端**智能枢纽**不开放入站端口时，在已配对端点间转发受允许的北向操作，绝不持有管理权限。 |

关闭单个 G2A 会话仅结束该角色绑定，不会关闭**交互源点**游戏进程、不会退出本机全局共享的**智能枢纽**，也不会解散多人游戏房间。

### 4.2 主体、实例与代次隔离

调用方身份**必须**依据传输层经过认证的凭据确立；消息内的发送方声明仅用于与认证身份作一致性比对，**不得**单独采信。实现**必须**严格区分四类标识概念：

- **主体身份：** 在签发方命名空间内唯一标识玩家、**演算中枢**、游戏或服务。显示昵称不具备任何认证效力，不同签发方下的同名主体**不得**自动合并。
- **设备身份：** 标识持有呈现或会话控制租约的物理或逻辑终端。
- **游戏运行实例：** 标识**交互源点**内具体某局游戏、对局或房间，防止将一局游戏中的授权与凭据跨局重放。
- **代次与控制世代：** 单调递增或严禁复用的阶段标记（实例代次、世界代次、可见性代次与会话控制世代），用于在读档、阵营切换或跨设备交接后立即隔离旧凭据、旧观察基线与已被取代的控制端。

### 4.3 委托链与信任模式

当服务或**智能枢纽**代表玩家操作时，经验证的**委托链** **必须**绑定委托玩家、受托主体、目标游戏实例、获准权限范围及有效期。请求流经任何中间节点绝不会把中间方的自有权限叠加到被代表主体之上。聊天或游戏文本中未经认证的“已获授权”文字声明无效；仅知晓会话、行动或关联标识符也不赋予任何读取或执行权。

部署环境**必须**声明并强制执行兼容的信任模式，严禁静默降级：

- **本机核验模式（`local-verified`）：** 由操作系统进程通信或经核验的本机回环配对绑定同机上的**交互源点**、共享**智能枢纽**与当前登录用户。
- **服务商核验模式（`provider-verified`）：** 通过经认证的 TLS 连接配合加密令牌或委托验证，跨网络绑定玩家、**智能枢纽**、**演算中枢**、目标受众与有效期。
- **测试预登记模式（`test-enrolled`）：** 仅限本地开发调试与符合性测试夹具使用的预登记身份，**不得**宣称为可抵御本机不可信软件的生产安全机制。

实现**必须**如实披露明文可见边界：除非通过专门扩展显式协商端到端加密，**智能枢纽**与所配对的出站中继均可读取途经自身的消息，**不得**虚假宣称仅通信两端可解密。

### 4.4 四维权限分离与源点内部秘密不离场原则

实现**必须**将以下四维权限独立核验，不得相互替代：

1. **接收权：** **演算中枢**获准从**交互源点**或玩家处读取哪些信息；
2. **对玩家披露权：** **演算中枢**可以在面向玩家的对话中说出哪些信息；
3. **对外转发权：** **演算中枢**可以向游戏、队友或外部服务发送哪些信息；
4. **行动权：** **演算中枢**可以在游戏世界中请求执行哪些能力与参数范围。

**未揭晓游戏秘密绝不离场原则：** 现代生成式大模型在同一上下文中统一完成规划推理与对话生成。凡属于游戏规则严格禁止向玩家或其他参与者泄露的隐藏状态（如暗牌、未揭晓谜底、战争迷雾后的敌方埋伏或隐藏陷阱条件），**交互源点** **绝不得**将原始秘密输出给**智能枢纽**或**演算中枢**，而**必须**在**交互源点**内部完成前置条件判定，仅向外暴露获准知晓的结果或当前行动可用状态。

## 5. 规范概念模型

### 5.1 不透明标识、标准 JSON 数值与 RFC 8785 摘要

所有协议标识符（如描述文档、提议、授权、邀请、会话、信息流、请求及行动标识）对消费方均为不透明字符串，消费方**不得**拆解字符串猜测身份、权限或先后顺序。传输请求标识、消息信封标识、关联标识、事件序号与观察修订号分属独立命名空间，**不得**混用。

**标准 JSON 数值表示（RFC 8259）：** 结构化协议数据直接采用国际标准 UTF-8 JSON（RFC 8259），不自造私有编码格式：

- **标准有限数值：** 协议载荷**可以**直接使用标准整数与有限 IEEE-754 浮点数（例如游戏引擎原生的空间坐标、速度、角度或概率），同时严格拒绝非有限数值（`NaN` 与 `Infinity`）。
- **精度约定：** 时间戳与时长**应**统一采用毫秒整数以便跨平台精确比较；涉及货币金额、商店价格与权威额度账本的字段**应**采用最小整数货币单位或显式十进制字符串，避免浮点舍入误差。

**国际标准加密规范化（RFC 8785 JCS）：** 凡**智能枢纽**或各参与方需要对结构化对象计算跨语言一致的加密摘要（如冻结协商后的权限范围摘要或绑定行动确认摘要）时，实现**必须**遵循国际标准 **RFC 8785**（JSON 规范化方案，JCS）生成 UTF-8 规范化字节并计算带域分离的 SHA-256 摘要，使各编程语言实现可直接复用成熟的标准库。

### 5.2 核心协议概念对象

G2A 交互模型围绕以下 14 个核心逻辑概念组织：

| 概念对象 | 规范职责与绑定语义 |
| --- | --- |
| **公开描述文档（`PublicDescriptor`）** | 由**智能枢纽**暴露的未认证最小发现记录，仅公布游戏实例标识、支持的协议版本与认证发现入口，不含任何玩家或会话状态。 |
| **能力描述文档（`Descriptor`）** | 按已认证调用方过滤的能力声明，载明由**交互源点**声明的支持版本、信任模式、角色槽位与并发上限、支持/必需能力模块、观察类别、可调用行动定义及资源限制。 |
| **权限范围（`Scope`）** | 经协商冻结的不可变权限快照，绑定玩家、**演算中枢**、游戏实例、协议版本、角色槽位、启用模块、获批观察类别、获批行动定义、接收范围、生效策略及过期时间。 |
| **准入提议（`Offer`）** | 封装冻结 `Scope` 及其 RFC 8785 摘要的有界准入提议，跟踪审批状态（待决、已批准、已拒绝、已过期或因状态变更失效 `stale`）。 |
| **授权记录（`Grant`）** | 经验证的玩家同意（或匹配的有效预设规则）签发的生效授权记录，绑定获批范围摘要、同意证据、修订号与有效期。 |
| **加入邀请（`Invitation`）** | 绑定已批准 `Grant`、特定**演算中枢**身份、目标游戏实例与接入端点的短期单次加入凭据。 |
| **活动会话（`Session`）** | 托管于**智能枢纽**的活动交互上下文，跟踪存活状态（`active` 或 `closed`）、就绪状态、实例与传输代次、控制世代、**演算中枢**控制租约截止时间、能力与成员修订号及事件流序号。 |
| **消息信封（`Envelope`）** | 数据面消息封装，绑定会话标识、唯一消息标识、消息类型、认证发送方、获准接收受众、期望的能力/成员修订号、业务载荷及可选轻量扩展头。 |
| **行动定义（`ActionDefinition`）** | **交互源点**声明的角色能力规格，指明能力标识、修订号、适用角色、参数与结果约束、确认要求、最长耗时、取消模式、效果可逆性分类及幂等属性。 |
| **行动记录（`ActionRecord`）** | 由**智能枢纽**维护的持久化单次行动账本项，记录生命周期状态（`pending`、`executing`、`succeeded`、`failed`、`cancelled` 或 `unknown`）、世界效果状态（`none`、`partial`、`committed` 或 `undetermined`）、取消标记及**交互源点**返回的最终结果。 |
| **事件项（`Event`）** | 经受众过滤的有序会话事件流条目，配对单调递增序号、消息信封及受理时的冻结接收范围。 |
| **恢复快照（`RecoverySnapshot`）** | 时间点原子状态切面，包含当前会话元数据、事件游标、整理后的当前获准观察状态、未决在途行动及最新能力/成员修订号。 |
| **操作回执（`Receipt`）** | 可复查的操作受理记录，确认操作处于待决、完成或失败状态（并标记被**智能枢纽**拦截的重复重试），本身不赋予额外执行权。 |
| **结构化错误（`Error`）** | 标准化拒绝记录，报告稳定的机器可读错误码、错误类别、重试指引、受理确定性（`not_accepted`、`accepted` 或 `unknown`）及安全的人类可读说明。 |

### 5.3 十条协议核心不变量（`I01`–`I10`）

任何符合规范的**交互源点**、**智能枢纽**与**演算中枢**均**必须**始终满足以下十条核心不变量：

- **`I01`（身份认证前置）：** 未经认证的调用方**不得**产生玩家批准、邀请、有效会话或**交互源点**内的任何游戏世界效果。
- **`I02`（权限交集收敛）：** **智能枢纽**强制执行的实际权限**不得**超出**交互源点**当前能力、有效 `Grant`、冻结会话 `Scope`、当前房间/队伍成员关系与当前玩家策略的交集。
- **`I03`（冻结范围绑定）：** 玩家批准精确绑定 RFC 8785 范围摘要；任何安全相关条件变化均使待决提议或邀请变为 `stale`，要求发起新 `Offer`，严禁原地篡改。
- **`I04`（智能枢纽确定性去重）：** 同一去重键搭配相同规范化内容重试时由**智能枢纽**直接拦截并返回原回执或结果，绝不在**交互源点**重复产生副作用；复用同一键提交不同内容**必须**以 `conflict` 拒绝。
- **`I05`（枢纽回执非世界效果）：** **智能枢纽**队列受理绝不证明**交互源点**世界效果已发生；无法证实结果时**必须**如实报告 `unknown`（`undetermined` 效果），严禁猜测为失败或成功。
- **`I06`（双重接收范围核验）：** 投递受保护消息或事件时，**必须**同时满足受理时记录的冻结受众与投递时刻接收方的当前成员资格及授权。
- **`I07`（旧代次严格隔离）：** 过期、已关闭或已被新代次/新控制世代取代的凭据**不得**恢复写权限或行动权；只读结果查询句柄不含任何会话控制权。
- **`I08`（有界呈现释放）：** 断线、收起或租约到期仅释放本会话持有的呈现租约，**不得**覆盖用户更新的窗口或设备操作意图。
- **`I09`（数据绝不升格为控制权）：** 游戏对白、场景文本、物品或商品描述、资源元数据与召回记忆始终属于不可信数据，**不得**用于提升权限、篡改预算或伪造确认。
- **`I10`（智能枢纽原子受理边界）：** **智能枢纽**的状态变更、去重回执写入与事件入队**必须**共享同一原子提交边界，或在崩溃后明确暴露 `unknown` 待核对状态。

## 6. 抽象操作目录

下表定义围绕**智能枢纽**流转的抽象逻辑操作。游戏工作室集成轻量**交互源点 SDK** 时仅需实现极简的南向状态输出与行动执行回调（第 22 节），全部北向协议状态机均由**智能枢纽**自动承载。出站中继传输操作见第 18.3 节。

| 操作名 | 调用方 → 接收目标 | 所属能力 / 重试族 | 必需的规范语义 |
| --- | --- | --- | --- |
| `describe` | `演算中枢` / 玩家 → `智能枢纽` | `core.session` / `read` | 返回基于**交互源点**声明并按认证调用方过滤后的 `Descriptor`（绝不向未认证公开发现暴露）。 |
| `offer.create` | `演算中枢` / 玩家 → `智能枢纽` | `core.session` / `control` | 基于期望的描述文档修订号协商能力并冻结 `Offer` 与范围摘要（仅在精确命中预设规则且无需启动进程时自动批准）。 |
| `offer.get` | `演算中枢` / 玩家 → `智能枢纽` | `core.session` / `read` | 读取调用主体有权访问的 `Offer` 当前状态。 |
| `offer.decide` | `PlayerConsent` → `智能枢纽` | `core.session` / `control` | 凭经验证的玩家同意证据批准或拒绝精确范围摘要；可按需建立有期限的预设规则或单次启动许可。 |
| `launch.request` | 玩家 / `智能枢纽` → 启动器 | 启动能力 / `control` | 凭显式单次许可触发按需环境引导或唤起本机预登记的固定程序。 |
| `invitation.redeem` | 绑定 `演算中枢` → `智能枢纽` | `core.session` / `control` | 凭已批准 `Offer` 与加入意图兑换绑定**演算中枢**与端点的短期 `Invitation`。 |
| `session.join` | 绑定 `演算中枢` → `智能枢纽` | `core.session` / `control` | 原子消费 `Invitation`，完成必要的呈现/资源准备并激活唯一 `Session`。 |
| `session.heartbeat` | `演算中枢` → `智能枢纽` | `core.session` / `lease` | 凭新随机标识在当前控制世代下续期**演算中枢**控制租约（绝不延长缺席玩家在线状态）。 |
| `session.snapshot` | `演算中枢` → `智能枢纽` | `core.session` / `read` | 按当前读取权限返回原子 `RecoverySnapshot`，不续期控制租约。 |
| `session.events` | `演算中枢` → `智能枢纽` | `core.events` / `lease` | 从有效游标后拉取接收方可见的有序事件（仅在提供新轮询标识时续期控制租约）。 |
| `session.close` | `演算中枢` / 玩家 / `交互源点` → `智能枢纽` | `core.session` / `control` | 幂等关闭会话、拦截新行动、释放呈现租约并如实结算在途行动，不虚构效果回滚。 |
| `session.resume` | `演算中枢` → `智能枢纽` | `resume` / `control` | 在允许的恢复期限内重新绑定持久会话控制权并递增控制世代。 |
| `session.handoff` | `PlayerConsent` → `智能枢纽` | `handoff` / `control` | 隔离旧控制世代写权限并准备向已验证目标端点交接控制权，不暴露凭据秘密。 |
| `session.claim_control` | 目标端 `演算中枢` → `智能枢纽` | `handoff` / `control` | 在已验证目标端点上领取就绪交接的新世代会话控制凭据。 |
| `operation.get` | 原调用方 → `智能枢纽` | `core.session` / `read` | 无副作用核对原始操作回执状态，不重放秘密。 |
| `context.publish` | `交互源点` → `智能枢纽` | `core.events` / `message` | 由**交互源点**提供游戏状态，经**智能枢纽**校验类别、来源与接收受众后写入会话事件流。 |
| `observation.query` | `演算中枢` → `智能枢纽` | `observation.query` / `read` | 无状态拉取当前获授权的最新观察记录，无世界副作用且不续期租约。 |
| `chat.send` | `演算中枢` → `智能枢纽` | `chat` / `message` | 在会话权限范围、信息来源与接收受众约束内发送对话消息。 |
| `player_chat.forward` | `交互源点`（验证席位）→ `智能枢纽` | `chat` / `message` | 准确绑定玩家来源转发来自**交互源点**的认证玩家话语，不续期**演算中枢**租约。 |
| `action.request` | `演算中枢` → `智能枢纽` | `actions` / `message` | 提交类型化行动提议；由**智能枢纽**执行防重放去重，命中未确认策略时返回 `confirmation_required` 挑战，否则入队 `pending`。 |
| `action.confirm` | `PlayerConsent` → `智能枢纽` | `actions` / `control` | 记录单次玩家确认，精确绑定目标行动标识、参数与定义摘要、实质后果及过期时间。 |
| `action.cancel` | `演算中枢` → `智能枢纽` | `actions` / `message` | 请求取消 `pending` 或支持取消的 `executing` 行动，不暗示状态回滚。 |
| `action.query` | `演算中枢` / 结果读取方 → `智能枢纽` | `actions` / `read` | 查询获授权的 `ActionRecord` 当前状态与效果记账（含闭会后保留期）。 |
| `action.claim` | `交互源点` ↔ `智能枢纽` | `actions`（南向） | 再次核验撤权、取消标记与能力修订号后，将单次合法 `pending` 行动下发至**交互源点**并标为 `executing`。 |
| `action.commit_result` | `交互源点` → `智能枢纽` | `actions`（南向） | 将**交互源点**执行完毕返回的权威终态与世界效果记账写入账本。 |
| `capability.replace` | `交互源点` → `智能枢纽` | `actions` / `control` | 同步**交互源点**更新后的能力目录、递增能力修订号，并使不再获准的待处理行动失效。 |
| `membership.replace` | `交互源点` → `智能枢纽` | `team` / `control` | 同步**交互源点**房间或队伍席位变更、递增成员修订号，隔离离队参与者获取新内容。 |
| `permission.revoke` | 玩家 / `交互源点` → `智能枢纽` | `core.session` / `control` | 按指定目标执行分级撤销（`auto_rule`、`grant`、`invitation`、`session`、`capability`、`result_read`、`launch_permission` 或 `relay`）。 |
| `asset.resolve` | 呈现端 / `智能枢纽` → 资源端口 | `assets` / `control` | 按声明式资源清单摘要、大小上限与沙箱策略获取并校验资源。 |
| `presentation.acquire` | `智能枢纽` → 呈现端 | `presentation` / `control` | 申请有界设备呈现模式，并跟踪用户窗口操作意图修订号。 |
| `presentation.renew` | `智能枢纽` → 呈现端 | `presentation` / `lease` | 在匹配的修订号与代次下续期活动呈现租约。 |
| `presentation.release` | `智能枢纽` → 呈现端 | `presentation` / `control` | 幂等释放本会话呈现租约；未被更新的用户手动操作覆盖时恢复原状。 |
| `privacy.request` | 数据主体 → 数据保管方 | `privacy-request` / `control` | 请求保管方对其实际受控数据执行有界删除或停用处理。 |
| `privacy.receipt` | 数据主体 → 数据保管方 | `privacy-request` / `read` | 查询保管方签发的真实处理进度及法定或技术保留例外说明。 |

## 7. 发现、协商与准入

### 7.1 开放生态准入、智能枢纽推荐商业化与反垄断对等原则

G2A 同时兼顾生态可持续运营的三项核心诉求：**支持智能枢纽的合理商业化推荐运营**、**保障游戏厂商的竞技反外挂与监管合规**，以及**捍卫玩家与第三方演算中枢的开放自由选择权**。

**智能枢纽推荐目录与用户自定义接入双轨制（防枢纽垄断）：** **智能枢纽**客户端或托管服务**可以**内置经过质量与安全核验的**推荐演算中枢目录**（含默认合作通道或清晰标示的商业推广推荐位），以支撑**智能枢纽**持续研发与生态运营。但为防止**智能枢纽**自身演变为封闭垄断入口，任何符合规范的**智能枢纽** **必须**同时开放无锁定的**用户自主接入配置通道**，允许玩家自由添加、连接和切换任意符合 G2A 北向标准的第三方云端**演算中枢**或本地自建模型服务。

**允许游戏建立基于客观风险的合规白名单：** 游戏开发者**可以**针对特定游戏模式或运行环境（如竞技排位 PvP、受保护虚拟经济服、主机平台认证环境，或要求生成式内容安全备案的司法辖区）设立准入审核与白名单制度，用于维护反外挂公平性、未成年人与内容合规以及运行稳定。游戏开发者专门为本作固定世界观与剧本创作的专属剧情 AI 角色（如剧情 Boss、任务引导者或定制剧情搭档）归属于由开发者全权设定的 `independent_npc` 槽位（第 13.1 节），无需向第三方玩家伴玩开放替换；反之，只要游戏声明开放的是玩家个人跨游戏伴玩槽位（`companion`），以下四条反垄断规则即完整适用：

1. **严格的技术与权限对等（禁止自有中枢特权后门）：** 若游戏在某一模式中接入了游戏厂商自有、关联企业或独家合作的**演算中枢**，该服务**必须**运行在与合规第三方**演算中枢**完全相同的**交互源点**与**智能枢纽**公开能力边界、观察粒度、战争迷雾限制、动作冷却下限、速率限制与玩家确认门禁之上。游戏**严禁**为自有服务开辟未公开的隐藏状态读取通道、零延迟内部执行快车道或豁免安全确认的特权后门。
2. **公开、客观、可复核的准入标准（公平无歧视准入）：** 一旦某游戏模式启用白名单并允许自有或外部**演算中枢**进入，游戏方**必须**公布清晰、与厂商身份无关的客观技术与合规准入条件（例如：通过公开 G2A 符合性测试套件、具备法定内容安全备案资质、遵守统一的反外挂动作频率上限），并提供对等的第三方申请通道、合理审核周期与具体书面拒绝依据；**严禁**设置“仅限本厂商或关联集团服务接入”的封闭排他白名单。
3. **禁止商业捆绑与底层锁定：** 游戏方**不得**将排他性商业分成协议、强制采购指定云厂商/大模型推理服务，或要求让渡玩家跨游戏伴玩记忆控制权，作为进入技术或安全白名单的前置条件。
4. **按玩法风险最小化限制与数据主权兜底：** 反外挂限制**应**按实际风险能力解耦——例如在竞技排位对局中限制自动战斗代操（`actions`），但不应借反外挂之名在休闲、单机或社交模式中一刀切封杀合规第三方伴玩的低风险对话陪伴（`chat`）；且无论采用何种白名单范围，玩家个人伴玩记忆的通用标准格式导出权（第 15.4 节）始终不可剥夺。

运行时每一次拒绝请求或断开连接，均**必须**返回标准化错误码（第 12.1 节）及指明具体规则依据的安全说明，同时**不得**泄露凭据、他人隐私或隐藏游戏事实。

### 7.2 公开发现与认证后能力披露

**智能枢纽**的发现机制严格区分未认证最小探测与认证后的按权限披露：

1. **未认证公开发现：** 仅返回 `PublicDescriptor`（游戏实例标识、支持的 G2A 版本与认证发现入口），绝不暴露玩家身份、房间成员名单或私有能力。
2. **认证后能力发现（`describe`）：** 要求经过认证的**演算中枢**或玩家身份，返回按该调用主体权限过滤后的 `Descriptor`（含角色槽位、白名单要求、可用模块与传输绑定）。

通信双方选择共同支持的最高协议版本并校验模块依赖；若存在不支持的必需模块或必需扩展，协商**必须**立即失败；未知的可选扩展保持关闭且不得削弱核心安全边界。

### 7.3 端到端准入生命周期

无论是**演算中枢发起**还是**交互源点发起**（如玩家在游戏内点击召唤伴玩），均统一由**智能枢纽**编排收敛为七步授权生命周期：

1. **能力发现（`describe`）：** 从**智能枢纽**获取按调用方过滤的 `Descriptor` 及当前修订号。
2. **提交范围提议（`offer.create`）：** 协商所需能力，生成不可变的 `Scope` 及其 RFC 8785 摘要。
3. **呈现玩家同意请求：** 通过 `PlayerConsent` 向绑定玩家清晰展示权限范围条款（仅在未过期的既有预设规则精确匹配全部安全条件、且无需启动新本地进程时方可免弹窗自动通过）。
4. **记录同意决定（`offer.decide`）：** 记录绑定精确范围摘要的玩家批准或拒绝证据；批准后签发有效 `Grant`。
5. **按需环境引导或本地启动（`launch.request`）：** 若所需本地组件尚未运行且已获显式单次许可，经可信`本地安装与启动器`完成引导或唤起固定程序。
6. **兑换短期邀请（`invitation.redeem`）：** 将已批准 `Grant` 与加入意图绑定为短期 `Invitation`。
7. **激活会话（`session.join`）：** 原子消费 `Invitation`，在**智能枢纽**建立 `Session` 与控制租约，开始流转快照、观察、对话与获准行动。

**准入核心防线：** **演算中枢**绝不得自行批准提议；收窄或修改提议权限须新建具有新摘要的 `Offer` 而非原地修改旧提议；会话加入权限绝不隐含任意启动操作系统进程的权限。

### 7.4 扩展协商与会话冻结边界

可选扩展采用反向域名命名空间标识，并标明版本号及必需或可选属性：

- **会话级冻结：** 支持的扩展选项、请求参数与协商生效的扩展配置均在准入阶段冻结于会话 `Scope` 内，并受范围摘要完整保护。
- **轻量数据面信封：** 会话激活后，已协商扩展配置在**智能枢纽**与会话绑定；逐消息信封仅在扩展规范确有要求时携带轻量逐消息头（默认为空），**不得**在每条实时消息上重复传输庞大的静态配置目录，也不得篡改已冻结的 `Scope` 条款。

## 8. 授权、会话与撤销

### 8.1 授权记录绑定

**智能枢纽**强制执行的每条 `Grant` **必须**绑定签发方、玩家、**演算中枢**、目标游戏实例、允许的操作、冻结的范围摘要、过期时间及撤销修订号。观察授权绑定类别语义、视角、接收受众、频率/大小上限与保留规则；行动授权绑定获批行动定义与参数约束。**交互源点**刷新能力目录（`capability.replace`）绝不自动扩大既有 `Grant`；任何扩权均须重新取得玩家同意。

### 8.2 会话生命周期、控制租约与玩家在线状态

**智能枢纽** **必须**严格区分两项彼此独立的存活机制：

1. **演算中枢控制租约：** 防止崩溃或失联的**演算中枢**无限期占用会话控制权。仅由经认证的 `session.heartbeat` 或带新随机标识的 `session.events` 轮询续期；普通只读查询及**交互源点**调用**不得**续期该租约。
2. **玩家在线状态（第 14.1 节）：** 完全由**交互源点**依据真人玩家在游戏局内的实际参与情况权威上报；**演算中枢**的心跳**绝不得**延长、模拟或伪造缺席玩家的在线状态。

### 8.3 分级权限撤销体系

`permission.revoke` 在**智能枢纽**针对明确的权限层级执行边界清晰的隔离，避免笼统的全局副作用：

| 撤销目标类型 | 立即生效的隔离效果 | 保留的合法状态与核对权 |
| --- | --- | --- |
| `auto_rule` | 阻止该预设规则在后续提议中产生新的自动批准。 | 已签发的 `Grant`、`Invitation` 与活动 `Session` 不受级联关闭（除非另行指定撤销）。 |
| `launch_permission` | 阻止尚未消费的本地应用启动许可。 | 历史启动回执与独立的交互 `Grant` 保持不变。 |
| `invitation` | 使尚未消费的 `Invitation` 立即失效。 | 底层 `Grant` 在未被撤销前仍保持有效。 |
| `grant` | 使该 `Grant` 失效，作废其下所有未消费 `Invitation`，并关闭全部绑定 `Session`。 | 已在**交互源点**提交的世界效果与有效只读结果查询句柄在保留期内仍可核对。 |
| `session` | 关闭指定单个 `Session`，在**智能枢纽**拦截未下发的 `pending` 行动并释放呈现租约。 | 同一授权下的其他并发会话（`multi-session`）与已提交行动记录保持独立。 |
| `capability` | 单向屏障移除特定行动执行权，阻止**智能枢纽**将受影响的 `pending` 请求下发至**交互源点**（`action.claim`）。 | 会话对其余能力仍保持活动，既有 `ActionRecord` 读取权不受影响。 |
| `result_read` | 终止对应只读结果句柄的结果核对读取权限。 | 权威内部审计账本保持不变。 |
| `relay` | 关闭配对的出站中继邮箱并唤醒挂起请求。 | 结果未决的在途行动转为 `unknown` 供后续核对，严禁触发静默重放。 |

### 8.4 逐操作实时权限重验

**智能枢纽**每次处理受保护操作（含快照读取、无状态观察查询、行动结果查询与隐私回执查询）时，均**必须**实时核验：认证调用方及委托链与目标资源、角色、会话及接收受众一致，且 `Grant`、`Session` 控制世代与游戏实例代次均未过期或被撤销。

## 9. 游戏观察规则

### 9.1 观察类别声明与协商

**演算中枢** **可以**在准入阶段声明必需观察类别与可选偏好。若**交互源点**无法提供某项必需类别，协商**必须**明确失败（或仅在双方另行批准收窄范围的新 `Offer` 后继续），严禁伪造空数据流冒充支持。

每个观察类别明确规定其语义版本、单位约定、大小与速率上限、支持的投递方式（主动推送、无状态查询或双支持）、有效新鲜度窗口、获准绑定的视角（`player-self`、`team`、`npc-self` 或 `guide`）以及存储保留限制。

### 9.2 基线快照、增量更新与撤回屏障

在给定的信息流标识、世界代次与可见性代次内，获授权的游戏观察由**交互源点**经**智能枢纽**按三种确定性模式向**演算中枢**演进：

- **基线快照（`snapshot`）：** 原子建立或替换该信息流的完整授权视图（未包含在新快照中的旧记录立即丢弃，不得与旧状态合并），并为当前代次绑定类别版本与语义定义。
- **增量更新（`delta`）：** 在同一代次内基于精确匹配的基准修订号原子应用新增/更新记录及结构化移除项。结构化移除项标明每个被移除实体的转换原因（离开视野 `left_view`、确认销毁 `destroyed` 或未知 `unknown`）。由于基线快照已绑定当前代次的静态类别定义，增量帧省略重复的静态元数据以压缩高频传输开销。
- **撤回屏障（`retract`）：** 在当前代次内立即撤回指定记录子集或整条信息流，并建立单调失效屏障，防止网络延迟或重放的旧更新使已撤回状态死灰复燃。

观察中的实体标识**必须**是当前视角内的局部不透明标识，严禁直接暴露全局递增引擎序号以免泄露隐藏实体总数。流修订号单调递增；采样合并引起的非连续跳号合法，但基准修订号与消费方当前状态不一致的 `delta` **必须**拒绝，并触发新快照重同步。

### 9.3 代次废止、采样合并与可见性转换

世界重置、读档、阵营/队伍切换或权限变更均使受影响观察基线立即失效：**交互源点**与**智能枢纽** **必须**推进世界代次或可见性代次并在继续发送增量前下发全新 `snapshot`；**演算中枢**获知失效后**必须**立即丢弃旧基线。

**智能枢纽** **可以**在保持基准修订号衔接（或改发新 `snapshot`）的前提下合并可替换的中间状态，但具有独立玩法意义的瞬时离散事件**不得**被静默覆盖。实体出现与移除的转换原因**必须**区分进入视野（`entered_view`）、观察到新建（`created`）、离开视野且后续未知（`left_view`）、获准确认销毁（`destroyed`）及不可披露/未知（`unknown`），防止**演算中枢**将脱离视野误判为目标死亡。

### 9.4 新鲜度、时钟边界与恢复快照整理

超出声明有效窗口的观察**必须**视为陈旧不可用。鉴于**交互源点**、**智能枢纽**与远端**演算中枢**可能运行于未同步时钟环境，新鲜度判定依赖声明的生成时间戳与有界时钟偏差假设，而非跨主机墙钟直接相减。

由**智能枢纽**组装的 `RecoverySnapshot`（`session.snapshot`）**必须**返回每条活动授权信息流整理后的当前完整状态，而非重放历史增量日志；未出现在当前恢复快照中的信息流即不再有效。

### 9.5 结构化基础与正交多模态感知

`perception.structured` 是所有游戏类**演算中枢**的必需基础能力；游戏画面感知（`perception.visual`）与游戏环境音频感知（`perception.audio`）是在此之上彼此正交的可选能力：

- **独立协商：** **演算中枢** **可以**仅支持 `perception.structured`，或单独叠加 `perception.visual`、单独叠加 `perception.audio`，或同时支持两者。任何媒体能力均不替代结构化状态理解，也不授予访问操作系统桌面、玩家私人麦克风或隐藏游戏数据的权限。
- **玩家运行期独立开关：** 玩家可在运行期于**智能枢纽**分别开启或关闭画面流与游戏环境音频流（与第 15 节语音对话彼此独立），关闭后对应媒体流的传输与处理**必须**立即停止。

### 9.6 游戏主动推送与无状态观察查询

**交互源点**按类别声明支持会话事件流主动推送、无状态按需拉取（`observation.query`）或两者兼备。`observation.query` 在**智能枢纽**每次调用均核验当前权限与频率上限，且不产生任何世界副作用；凡消耗法力/回合、改变世界状态或揭开战争迷雾的主动侦察技能均属于第 10 节的**行动**（Action），而非观察查询。

## 10. 行动与效果语义

### 10.1 能力粒度与行动声明

游戏开发者自主决定**交互源点**开放行动的粒度——可提供高层语义能力（如攻击目标、合成物品）、底层类型化原语（如向目标坐标移动）或两者组合。即便底层原语也始终是受游戏规则约束的有界游戏内行动，而非操作系统级键鼠注入；组合多个行动既不扩大权限，也不构成跨步原子世界事务。

每项 `ActionDefinition` 明确声明适用角色、参数约束、确认要求、最长执行时长、取消支持模式（不可取消 `none`、领取前可取消 `before_claim` 或步骤间可取消 `between_steps`）、效果可逆性分类（只读 `read_only`、可补偿 `compensatable` 或不可逆 `irreversible`）及幂等属性。副作用与可逆性**必须**显式声明，不得凭名称猜测。

### 10.2 五阶段执行生命周期、枢纽防重放屏障与确认挑战机制

每次行动调用跨越**演算中枢**、**智能枢纽**与**交互源点**严格经历五个阶段：

1. **提议与确认挑战门禁（`演算中枢` → `智能枢纽`）：** **演算中枢**携带稳定的行动标识、期望能力修订号与类型化参数向**智能枢纽**提交 `action.request`。若该行动按静态定义、物品转移策略（第 16.3 节）、不可逆后果策略（第 16.3 节）或购买预算上限（第 17.1 节）需要玩家确认，且**智能枢纽**当前尚无匹配的未过期 `action.confirm`，**智能枢纽** **不得**向**交互源点**下发执行请求，而**必须**返回结构化的 **`confirmation_required` 确认挑战**（受理结果为 `not_accepted`），列明绑定的行动标识、参数与定义摘要、具体后果、过期时间与冷却窗口。由于 `not_accepted` 不会在去重账本中消耗该行动标识，待 `PlayerConsent` 在过期前完成 `action.confirm` 后，**演算中枢**原样重提该 `action.request` 即可顺利进入阶段 2。
2. **智能枢纽防重放门禁与队列受理（`pending`）：** **智能枢纽**校验权限、能力修订号与参数约束，原子消费所需的玩家确认，并同一事务记录 `ActionRecord`（`pending`，效果 `none`）及去重回执。**若因网络中断或抖动导致演算中枢重复发送了同一行动标识（例如同一记攻击请求发了两次），智能枢纽在此直接命中去重账本拦截重放并返回原回执，绝不向交互源点重复转发第二次执行请求。**
3. **南向下发与领取（`executing`）：** **智能枢纽**再次核验会话与授权活性、能力修订号及取消标记（`action.claim`）后，经南向轻量 HTTP 端口将该唯一合法请求下发至**交互源点**，并将状态切换为 `executing`。
4. **交互源点效果边界裁定：** 在实际改变游戏世界状态前，**交互源点**依据当前玩法规则与世界前置条件（如技能冷却、射程或回合归属）完成权威裁定，仅产生合法游戏效果。
5. **结果结算（`action.commit_result`）：** **交互源点**通过南向 HTTP 端口返回执行结果，由**智能枢纽**提交终态与世界效果记账（若因崩溃或超时无法获得**交互源点**权威证实时，如实记录为 `unknown` / `undetermined`）。

### 10.3 行动状态与效果组合矩阵

`ActionRecord` 以配对不变量同步记录处理状态与世界效果：

| 行动状态 | 允许的效果取值 | 规范含义 |
| --- | --- | --- |
| `pending` | `none` | 已在**智能枢纽**受理入队，尚未下发至**交互源点**执行。 |
| `executing` | `none`, `partial`, `committed`, `undetermined` | 已下发至**交互源点**，世界效果可能正在推进。 |
| `succeeded` | `committed` | **交互源点**执行完成且已提交定义的成功世界效果。 |
| `failed` | `none`, `partial` | 按游戏规则执行失败，如实记录是否已产生部分世界效果。 |
| `cancelled` | `none`, `partial` | 在完整完成前取消，如实记录可能已发生的部分效果。 |
| `unknown` | `undetermined` | 超时、断线或故障导致尚未从**交互源点**确立权威结果。 |

已知终态（`succeeded`、`failed`、`cancelled`）**不得**被静默覆写；`unknown` 仅可凭**交互源点**权威执行证据转为终态。`action.cancel` 是尽力停止请求而非回滚保证：若取消请求与执行发生竞争且**交互源点**世界效果已生效，**智能枢纽** **必须**如实报告 `succeeded`（`committed`）。

### 10.4 动态行动资格与静态支持分离

在 `Descriptor` 中声明某项行动仅代表静态能力支持，不代表角色当前时刻合法可执行。**交互源点** **必须**在获授权视图内提供机器可读的当前行动资格信息（如当前回合归属、冷却与资源就绪状态、合法目标范围或离散合法动作掩码），绑定观察修订号且**不得**泄露隐藏目标或秘密前置条件。任何可行性或概率提示均须标明估算属性，绝不替代**交互源点**的权威判定。

### 10.5 观察前置条件与陈旧状态拒绝

依赖环境观察发起的行动请求**应**关联所依据的观察基线（流标识、代次与修订号）及新鲜度上限或目标前置条件。若关联代次已废止、超出新鲜度窗口或在**交互源点**前置条件不成立（例如治疗目标已阵亡或改变阵营），该行动**必须**在产生新效果前被拒绝（返回 `stale_context` 或前置条件不满足），促使**演算中枢**基于最新观察重新评估，严禁原参盲目重试。

## 11. 幂等性、投递与恢复

### 11.1 四类操作重试族与智能枢纽去重保留期

由**智能枢纽**统一强制执行的四类重试族使上层调用能够安全应对网络故障，同时将去重复杂度彻底隔离在**交互源点**之外：

| 重试族 | 代表操作 | 重放与幂等去重规则 |
| --- | --- | --- |
| **`read`** | `describe`, `offer.get`, `session.snapshot`, `observation.query`, `action.query`, `operation.get`, `privacy.receipt` | 每次调用重新核验当前权限；返回最新获授权状态；绝不修改状态或续期租约。 |
| **`lease`** | `session.heartbeat`, `session.events`, `presentation.renew` | 每次续租须使用新随机标识；重放旧请求标识仅返回缓存状态，不延长租约截止时间。 |
| **`control`** | `offer.create`, `offer.decide`, `invitation.redeem`, `session.join`, `session.close`, `session.resume`, `action.confirm`, `permission.revoke` | 在**智能枢纽**回执保留期内按调用主体与操作目标去重；相同规范内容重试返回原回执（`duplicate`），篡改内容则以 `conflict` 拒绝。 |
| **`message`** | `context.publish`, `chat.send`, `player_chat.forward`, `action.request`, `action.cancel` | 在**智能枢纽**按会话、认证发送方与消息标识去重；已受理消息至多下发一次，而受理前的 `confirmation_required` 挑战（`not_accepted`）不消耗该消息标识。 |

去重回执**必须**在**智能枢纽**至少保留至声明的保留期限，且过期的去重记录绝不构成重做非幂等副作用的许可。事件消费方对有序事件至多应用一次，容忍因接收受众过滤产生的序号跳号，并在游标过期时通过 `session.snapshot` 恢复。

### 11.2 行动结果核对与默认不重发规则

每项游戏行动均携带在结果保留期内可跨短暂断线向**智能枢纽**查询的持久行动标识：

- **强制先查与默认不重发：** 发生超时、网关超时（`504`）或连接中断后，**演算中枢**（或遇南向超时的**智能枢纽**）**必须**先查询原行动标识状态。只要结果仍为 `unknown`、缺失或已过期，实现**必须**默认**不自动重发、不再次执行**该行动，严禁通过伪造新行动标识绕过去重屏障。
- **后续独立新决策：** 玩家或**演算中枢**此后**可以**依据刷新后的当前观察、有效权限及确认/预算策略，独立作出新的行动决策；新决策须考虑原未决行动可能已在**交互源点**生效的后果，且不得篡改原 `unknown` 记录。

## 12. 错误模型、时间与资源限制

### 12.1 标准错误码分类注册表

**智能枢纽**返回的协议拒绝**必须**采用稳定的机器可读标准错误码，明确区分受理确定性（`not_accepted` 与 `unknown`）并与第 18.2 节 HTTP 状态码一致映射：

| 标准错误码 | 错误类别 | 受理结果 | 调用方规范恢复行为 | HTTP 状态码 |
| --- | --- | --- | --- | --- |
| `invalid_request` | 语法 / 信封结构 | `not_accepted` | 修正畸形语法或信封格式；不得原样重发。 | `400` |
| `invalid_arguments` | 参数约束 | `not_accepted` | 按声明约束修正操作或行动参数。 | `400` |
| `unsupported_version` | 协商不兼容 | `not_accepted` | 选择双方共同支持的协议版本或终止连接。 | `400` |
| `unsupported_capability` | 协商不兼容 | `not_accepted` | 移除不支持的必需模块/扩展重新协商或终止接入。 | `400` |
| `unauthenticated` | 身份未认证 | `not_accepted` | 获取有效认证凭据后再试；不得探测资源是否存在。 | `401` |
| `permission_denied` | 权限 / 准入拒绝 | `not_accepted` | 申请对应 `Offer` 或尊重游戏/白名单规则拒绝；禁止盲目重试。 | `403` |
| `revoked` | 授权已撤销 | `not_accepted` | 立即停止已撤销范围内的活动。 | `403` |
| `not_found` | 受限范围查找 | `not_accepted` | 在已授权范围内核实标识符（严禁泄露未授权对象是否存在）。 | `404` |
| `stale_context` | 代次 / 基线过期 | `not_accepted` | 先刷新描述文档、恢复快照、能力修订号或观察基线再重新评估。 | `409` |
| `conflict` | 状态 / 去重冲突 | `not_accepted` | 核对原状态或去重冲突；严禁换新标识绕过。 | `409` |
| `confirmation_required` | 玩家策略门禁 | `not_accepted` | 向 `PlayerConsent` 呈现挑战详情；仅在完成 `action.confirm` 后重提原行动。 | `409` |
| `message_too_large` | 资源上限 | `not_accepted` | 在声明限制内缩减载荷或分页大小。 | `413` |
| `resource_limit` | 速率 / 配额限制 | `not_accepted` | 遵守退避等待时间及声明的并发/速率上限。 | `429` |
| `unavailable` | 服务健康状态 | `not_accepted` | 退避等待，仅按第 11.1 节重试族安全规则重试。 | `503` |
| `outcome_unknown` | 超时 / 结果未决 | `unknown` | 调用 `action.query` / `operation.get` 核对；**绝不得**等同于失败或自动重发副作用。 | `504` |

### 12.2 错误披露安全边界

错误响应本身受可见性与隐私边界约束：说明文字与错误详情**不得**暴露**交互源点**内未授权会话或隐藏实体是否存在、泄露其他玩家私有状态，或回显原始凭据与内部堆栈信息。

### 12.3 时钟权威、资源配额与不可丢弃控制信号

**智能枢纽** **必须**对载荷大小、嵌套深度、集合长度、待处理行动数、事件保留量及请求速率实施明确限制，保护**交互源点**免受异常流量冲击且不得产生未报告的部分效果。租约与凭据过期采用单调时钟（monotonic clock）测量耗时，防止系统墙钟跳变静默延长租约。

队列溢出**必须**明确报告缺口、要求快照重同步或返回 `resource_limit` 拒绝。行动结果结算、`permission.revoke` 撤权屏障与 `retract` 撤回通知属于不可丢弃控制信号，**不得**作为普通可替换遥测被丢弃。

<a id="section-13"></a>

## 13. 游戏角色与槽位规则

### 13.1 角色绑定与信息视角分离

**玩家伴玩**（Player Companion）或**独立 AI NPC** 是**交互源点**内受规则约束的角色槽位；**演算中枢**是经**智能枢纽**获准为该槽位感知与决策的认知服务。实现**必须**区分：

- **角色绑定：** **演算中枢**当前驱动**交互源点**中的哪一个具体角色槽位（例如玩家 A 的个人伴玩，或某个独立 AI Boss/引导者）。
- **信息视角：** 该角色获准读取哪一范围的知识视图（`player-self`、`team`、`npc-internal` 或 `guide-progression`）。

同一**演算中枢**服务**可以**支持伴玩、NPC、Boss 与引导者角色，无需拆分为互斥软件。在单角色内组合视角须经游戏显式授权，绝不隐式合并不同槽位的权限，且可见范围变化时立即废止旧观察基线。NPC 可持有开发者赋予的游戏内部背景知识，个人伴玩可持有玩家管理的跨游戏记忆；角色名称本身绝不赋予全知能力或无限制披露权。

### 13.2 声明的角色槽位、共存规则与并发限制

游戏开发者在**交互源点**定义支持的角色槽位、共存规则与活动并发上限（通过 `Descriptor` 对外公布）；**智能枢纽**、**演算中枢**或玩家设置均**不得**覆盖这些由游戏定义的结构边界：

- **支持的角色槽位：** 游戏**可以**提供玩家伴玩槽位、独立 AI NPC/敌人（含 Boss 或引导者）槽位，或同时提供两者。纯 AI NPC 玩法游戏无需虚设伴玩槽位即可合规，专注伴玩体验的游戏也无需实现 AI NPC。
- **伴玩并发与空槽可玩性：** 提供伴玩槽位时，默认上限为每位经认证玩家最多 1 个活动伴玩（多人游戏同样适用，多位玩家的伴玩可在各自授权与游戏规则内共存互动）。玩家**可以**将伴玩槽位留空，游戏**必须**在未启用伴玩时保持正常可玩。
- **模式共存与多 NPC 上限：** **交互源点**显式声明本局是否允许玩家伴玩与独立 AI NPC 同时活动及并发独立 AI NPC 数量上限；未显式声明时**不得**假定允许同局共存或多 NPC 并发。
- **逐角色严格隔离：** **智能枢纽**中的每个活动角色绑定其经认证的责任主体（所属玩家，或第 16.2 节规定的计费承担方）、角色标识、视角、接收受众与 `Scope`。共存角色之间**不得**隐式共享观察、私人记忆、行动授权或计费账户；替换活动绑定前**必须**先隔离旧绑定。游戏原生内置的非 G2A 普通 NPC 不受上述槽位限制。

<a id="section-14"></a>

## 14. 在线状态与角色生命周期

四类不同的生命周期事件跨越三层架构适用清晰的边界规则，严禁将“停止**演算中枢**后续决策”混淆为“回滚**交互源点**已提交的世界状态”：

| 生命周期事件 | 必需的规范处理规则 |
| --- | --- |
| **玩家离线或退出游戏** | 立即停止关联的 G2A 活动；下次重进游戏后，旧任务保持停止，等待玩家新指令（第 14.1 节）。 |
| **玩家在线期间演算中枢服务中断** | **交互源点**游戏继续运行。活动租约内未触发本地接管前的短暂闪断可经 `session.resume` 无缝恢复；长时中断或已触发本地接管后，须由玩家明确决定是否继续（第 14.2 节）。 |
| **玩家主动收起伴玩** | 立即停止转发游戏观察与自主行动，但不得因此删除已保留的伴玩记忆（第 14.2 节）。 |
| **玩家叫停或覆盖当前任务** | 立即丢弃**演算中枢**未发计划，并在**智能枢纽**取消/拦截未下发的 `pending` 行动；已在**交互源点**执行的 `executing` 技能按游戏规则结算（第 16.1 节）。 |

### 14.1 玩家离线强制停止与多人房间 NPC 连续性规则

G2A **绝不提供**在所有关联真人玩家离开或被**交互源点**判定离线后、仍允许**演算中枢**在空无真人的游戏世界中后台自动运行的离线托管模式。

- **离线判定与智能枢纽隔离：** **交互源点**上报显式退出、会话关闭或玩家在线超时后，立即终止发起新自主行动的资格；**智能枢纽** **必须**在有界期限内隔离受影响的控制权，且**演算中枢**心跳**绝不得**延长缺席玩家的在线状态。已在**交互源点**进入 `executing` 的动画或投射物按游戏规则自然结束，停留在**智能枢纽**未下发的 `pending` 行动立即取消或拦截。玩家日后重新进入游戏时，旧任务保持停止，须等待玩家下达新指令。
- **个人伴玩隔离：** 多人游戏中单名玩家掉线或退出时，其个人伴玩会话**必须**立即停止，不影响其他在线玩家的独立会话。
- **多人房间中独立 AI NPC 的连续性处理：** 当房间内有玩家掉线时，独立 AI NPC（如团本 Boss 或公共引导者）的处理方式取决于游戏声明的计费承担模式（第 16.2 节）：
  1. **玩家承担计费模式（默认模式）：** 当承担该 AI NPC 费用的经认证玩家（如房主）离线时，**该玩家的计费授权与控制绑定必须立即终止**——严禁继续扣取掉线房主费用，也严禁静默将账单转嫁给房内其他玩家。对于房间内仍有在线玩家正在进行的多人战局，**交互源点**与**智能枢纽**按事先声明的房间连续性规则执行：(a) 平稳停止该 AI NPC，(b) 切换为**交互源点**本地脚本基础行为接管以保障剩余玩家打完本局，或 (c) 仅在房内其他在线玩家**显式确认**通过新授权绑定接手赞助（或切换为开发者兜底赞助）后继续**演算中枢**驱动，且该接手仅转移后续局内 NPC 算力计费与会话控制关联，**绝不得**暴露原掉线房主的计费凭据、账户信息或个人会话数据。
  2. **开发者承担计费模式：** 当由游戏开发者承担 AI NPC 的**演算中枢**运行费用时，只要战局内仍有至少一名获准真人玩家在线参与，单名玩家离线无需中断该共享 AI NPC 的正常活动；一旦房间内所有真人玩家全部离开，该 AI NPC **必须**立即停止。

### 14.2 召唤、收起与双层服务中断恢复

支持伴玩槽位的**交互源点** **必须**允许玩家在游玩中随时召唤或收起伴玩，遵循入局偏好（凭有效授权自动加入或入局询问），并在启动时**演算中枢**不可达的情况下允许无伴玩正常游玩。

**游玩期间演算中枢中断：** 若玩家仍在游戏中而**演算中枢**断线，**交互源点**正常继续运行，并执行开发者声明的回退表现（伴玩保持静止，或切换为明确标注的本地游戏脚本基础行为）。**交互源点**与**智能枢纽**均**不得**录制断线期间的游戏过程以供重连后补录观察；恢复时仅提供当前获授权快照及此前在途行动的核对结果。

**服务恢复后的双层继续规则：**

1. **活动租约内的短暂传输闪断：** 当已协商 `resume`，且重连**智能枢纽**在未过期的会话租约内、**尚未触发交互源点本地脚本接管前**完成，同时玩家持续在线且未发出停止或收起指令时，**演算中枢** **可以**调用 `session.resume` 重新核验权限与控制世代、刷新快照并核对在途行动后无缝继续，避免秒级网络波动弹窗打断战斗。
2. **超出租约的长时中断或已触发本地接管：** 一旦租约过期或**交互源点**已切换为本地脚本接管，重连后**智能枢纽** **必须**保持伴玩行动暂停，直至取得玩家明确的继续确认；入局自动加入设置不可绕过该中断后确认。

## 15. 对话、信息使用与伴玩记忆

实现**必须**严格区分由**智能枢纽**与**演算中枢**确定性执行的硬性数据权限（存储、检索、接收受众、对外转发）与软性的对话偏好（防剧透、话题倾向、表达风格）。启用可选 `chat` 能力时，消息携带经认证的信息来源分类（`observed_fact`、`player_statement`、`agent_inference` 或 `external_reference`）及显式接收受众，并在投递时核验当前成员资格；文字或语音内容唯有经已认证的玩家控制或 `PlayerConsent` 路径确认方具控制效力。置信度不足的语音转写文本**不得**当作已验证的高影响指令，且语音对话与第 9.5 节的游戏环境音频感知彼此独立。

### 15.1 记忆归属与跨周目边界

**交互源点**自主决定开发者受控 NPC 与引导者的状态在跨周目时保留或重置。相反，托管于**演算中枢**的**玩家自主管理伴玩记忆**归属于玩家的伴玩关系：游戏会话关闭、伴玩在单局内阵亡或在**交互源点**开启新周目，均**不得**静默删除或禁用无关的玩家伴玩记忆；同时，伴玩记忆归属权也绝不授予读取隐藏游戏数据或他人私密通道的权限。

### 15.2 读档回退与可选高级时间线隔离

- **基础读档规则（必选）：** 读档回退、切换剧情分支或开启新周目仅改变**交互源点**的当前世界状态（按第 9.3 节推进世界代次并下发新快照），**不得**清空**演算中枢**内已保留的玩家伴玩记忆。普通游戏**无需**维护复杂的剧情分支树即可完全符合 G2A 规范。在合规的玩家伴玩对话中，玩家**可以**覆盖开发者的默认话题建议（例如讨论前一周目或其他游戏的经历），但不得借此扩大游戏数据读取权限。
- **细粒度存档分支与时间线隔离（可选高级优化）：** 多分支叙事型**交互源点** **可以**按需选配提供周目、剧情分支、时间线进度及单调读档代次标记。仅当**交互源点**与**演算中枢**双方均显式支持并启用该高级优化时，**演算中枢**将记忆绑定时间线来源，并在玩家开启严格防剧透隔离时于构建推理上下文前过滤掉晚于当前存档点或非祖先分支的记忆，或将跨分支召回内容明确标记为先前分支经历而非当前世界事实。

### 15.3 硬性数据权限与软性对话偏好

存储、检索与外发受众等硬性权限**必须**在模型输出之外确定性强制执行，包括由**智能枢纽**执行每位玩家独立控制是否接收他人伴玩主动搭话，以及伴玩主人控制是否保存多人对话记录。防剧透、保密风格以及玩家设定的伴玩性格与说话风格（个人伴玩风格优先于开发者建议，但绝不得篡改游戏开发者设定的独立 AI NPC 人设）属于软性对话偏好，通过**演算中枢**引导执行，并向用户如实说明生成式输出无法在数学上保证零偏差。

### 15.4 玩家记忆控制、自主整理与标准格式导出

- **玩家管控与受保护自主维护：** **演算中枢**服务商**必须**允许玩家查看、编辑、置顶锁定（pin/lock）及删除其保留的伴玩长期记忆，并将已完成的修改与删除同步至受控索引与缓存（法定或技术保留例外通过 `privacy.request` / `privacy.receipt` 如实说明）。在玩家配置的保留策略内，伴玩**可以**自主分类整理记忆并压缩或清理未锁定的原始记录而无需逐条弹窗，但**绝不得**覆盖玩家的显式编辑、删除玩家置顶锁定的记录，或通过陈旧缓存使已删内容复活。
- **来源与时间元数据：** 存储与导出的记录**必须**区分事件发生时间与记录存储时间，并区分直接**交互源点**观察、玩家陈述、模型归纳推断与玩家显式编辑。
- **通用标准数据格式导出与接收端保护：** **演算中枢**服务商**必须**允许玩家主动将其保留的伴玩记忆（含原始经历、归纳摘要及来源元数据）连同玩家选定的伴玩性格、说话风格与自主偏好设置，导出为**公开文档化、无厂商私有锁定的通用标准结构化数据格式**。源服务商仅核验玩家本人身份与所选导出范围——**不得**要求获知、审查或批准玩家后续导入的目标**演算中枢**或本地工具，且导出操作绝不触发向游戏或第三方的自动披露。任何支持导入该标准格式的接收端**演算中枢** **必须**遵守玩家选定的导入范围，保留数据包内标注的来源及访问、保留与披露约束（遇未识别的受限标记时按仅限玩家本人私密使用的保守边界处理），**绝不得**仅因更换服务商而扩大可向**交互源点**或其他参与者披露的信息范围；导入方**必须**返回真实的本地逐记录导入回执（`imported`、`transformed`、`rejected` 或 `unresolved`），保留受支持的伴玩设置，并如实报告不受支持、经过转换或未生效的设置项，不承诺迁移模型权重或保证不同模型的表现完全一致。

## 16. 角色自主性、确认门禁与计费模式

自主性仅决定**演算中枢**在**已获授权**的能力范围内可主动决断的程度，绝不决定其在**智能枢纽**是否拥有某项权限。

### 16.1 自主协助与三级停止机制

在关联玩家保持在线期间（第 14.1 节），持续或任务级授权允许伴玩**演算中枢**主动规划并调用范围内行动而无需逐步确认。多步任务完成**必须**有**交互源点**观察或行动结果证实目标已达成，严禁仅因请求已入队就谎报完成。玩家的自主度偏好可跨会话保持，但绝不突破游戏规则或确认门禁。

当玩家叫停、收窄授权或下达冲突的新指令覆盖当前自主任务时，跨越三层立即执行三级停止规则：

1. **演算中枢未提交的内部计划：** 立即停止该范围内的规划并丢弃所有未提交步骤；
2. **智能枢纽排队中的 `pending` 行动（效果 `none`）：** 在**智能枢纽**立即取消或隔离停止范围内尚未下发的 `pending` 请求，确保其绝不再转发至**交互源点**；
3. **交互源点执行中的 `executing` 行动：** 已下发并在**交互源点**施放的攻击、动画或投射物按游戏规则（或动作级取消支持）自然结算，不虚构回滚，并按第 11.2 节如实核对结果。

### 16.2 运行消耗上限与可配置的 AI NPC 计费模式

**演算中枢**服务商与**智能枢纽** **必须**披露计费依据并区分估算值与实测消耗：

- **伴玩运行消耗上限：** 对于玩家计费的伴玩**演算中枢**，玩家**必须**能够设置清晰的消耗上限（token、算力单位或金额）。触顶时暂停新增计费推理与游戏行动，**交互源点**游戏本体正常继续运行并明确提示暂停原因，严禁谎报任务完成或自行上调上限。
- **可配置的独立 AI NPC 计费模式（默认玩家承担）：** G2A 不在协议层锁死单一商业模式，而是由**交互源点**在能力描述文档中明确声明独立 AI NPC（含 Boss 与引导者）的计费承担模式：
  1. **玩家承担模式（`player_metered`，协议默认模式）：** 若游戏未显式声明其他赞助模式，每个活动独立 AI NPC 的**演算中枢**运行费用默认由经认证的激活/持有玩家（房间制多人场景下为房主）承担。激活前**智能枢纽**与服务**必须**将该 NPC 绑定至该认证玩家的获授权计费账户，清晰披露计费标准与上限控制，并**严格禁止**未经明确同意将费用隐式分摊或静默转嫁给其他互动玩家。
  2. **开发者或平台承担模式（`developer_sponsored` / `platform_sponsored`）：** 游戏开发者**可以**将独立 AI NPC 声明为由开发者、发行商或托管平台承担**演算中枢**运行费用（例如计入买断售价、订阅会员或服务器运营成本），玩家无需绑定外部 AI 算力账单即可直接游玩。
- **回合时序与终止状态区分：** 回合制与同时提交型**交互源点**声明确定性的回合资格与并发裁定规则，不依赖网络先到先得；游戏内正常胜负或角色倒地阵亡（限制本局行动，但不抹除跨游戏伴玩身份与记忆）**必须**与断线或预算触顶暂停等外部服务截断保持区分。

### 16.3 高影响行动确认门禁、冷却限流与目标失效

高影响行动在**智能枢纽**与**交互源点**强制执行玩家受控的策略门禁直至效果提交边界：

- **游戏内物品转移策略：** 玩家**必须**可在**仅高价值转移需确认**（凡开发者标记或玩家在游戏内手动标记为高价值的物品，转移前均须取得列明物品、数量、对象与交换条件的显式 `action.confirm`）、**所有转移均需确认**与**允许范围内自主转移**（遵守物品所有权与对手方同意规则）之间选择。物品转移策略绝不授权真实法币或商店购买（第 17.1 节）。
- **不可逆玩法后果门禁：** **交互源点** **必须**事先声明并暴露具有不可逆世界后果的行动或情境交互（如开启单向章节封印）；玩家独立选择**允许自主执行**、**执行前询问确认**或**禁止执行**（其中**禁止执行**优先阻断任何宽松设置）。
- **确认超时与防打扰冷却：** **智能枢纽**发出的所有确认挑战超时未获肯定答复一律视为拒绝/放弃——沉默绝不等于同意。等待确认或超时被拒后，伴玩可继续独立的低风险常规行为，且实现**必须**执行声明的冷却窗口：在相关游戏状态未发生实质变化且玩家未下达相关新指令前，不得就同一意图重复弹窗打扰。
- **主动目标失效通知：** 当关联目标或任务对象在**交互源点**失效（如目标 Boss 已阵亡）时，**必须**经**智能枢纽**主动将获授权的目标失效事件写入会话事件流（经流式推送、轮询拉取或同步响应提示送达），促使**演算中枢**立即停止发出已失效计划的后续行动。

<a id="section-17"></a>

## 17. 可选能力扩展规范

可选扩展规范**必须**明确所需授权、状态转换、失败模式与符合性检查；遇到未知的必需扩展或未知枚举值时，**智能枢纽** **必须**在触达**交互源点**产生效果前安全拒绝。

### 17.1 游戏内商店与购买预算边界（`store`）

**交互源点** **可以**开放结构化游戏内商店，协议不绑定特定货币体系。商店购买属于受控核验的获授权**行动**（Action），严格遵循第 11.2 节超时结果未决默认不重发规则；超出既有同意的价格或条款变动须重新取得玩家确认。

- **不可信促销文案与限频推荐：** 商店**必须**提供带明确货币单位的结构化价格；商品标题与促销文案属于不可信数据（第 19 节），**不得**篡改玩家预算或确认策略。若启用商品推荐，实现**必须**声明并执行可验证的推荐限频规则，并在玩家持续明确拒绝后降低本局剩余时间内的推荐频率。
- **权威购买预算账本与真实货币隔离：** 玩家**可以**仅针对明确声明的可再生游戏内虚拟货币设定有界自主购买预算（由权威账本独立于第 16.2 节算力上限维护，并在 `unknown` 超时未完成核对前冻结预留额度）。通用自主购买预算**绝不授权**真实法币扣款、外部钱包支付或高价值账户资产不可逆处置——此类交易每次均**必须**通过原生系统或游戏安全界面取得真人玩家直接确认。

### 17.2 伴玩外观优先级与显式降级（`avatar` / `presentation`）

当**交互源点**在其声明的可见范围（仅本地客户端可见或按房间规则多人同步）内启用伴玩视觉外观能力时，形象选择遵循三层优先级：

1. **玩家显式指定覆盖**（玩家主动选择的自定义形象）；
2. **游戏默认伴玩外观**（开发者提供的契合本作美术风格的默认形象）；
3. **伴玩基础外观**（游戏接受外部通用格式但未单独提供专属默认形象时，伴玩自带的基础形象）。

资源解析**必须**强制执行声明式清单摘要、体积上限与严格沙箱隔离（严禁执行代码或抓取未授权内网地址）。遇到格式或渲染能力不兼容时**严禁无提示静默替换**，实现**必须**明确提示玩家，并按约定提示重选或清晰标明已回退至默认外观。

<a id="section-18"></a>

## 18. 传输绑定与规范化准则

### 18.1 南向与北向双段式 HTTP/JSON 接口

G2A 围绕三层架构明确区分南向与北向两道互补的标准化 HTTP/JSON 传输边界：

- **南向源点至枢纽接口（`交互源点` ↔ `智能枢纽`）：** 在单机终端上走本机回环（`127.0.0.1`），在网络游戏上走隔离的服务端内网 HTTP/JSON 通道。仅承载极简的获准状态读取/上报与经核验的单次行动执行回调，绝不对公网或未经校验的外部流量直接裸露。
- **北向枢纽至中枢接口（`智能枢纽` ↔ `演算中枢`）：** 将外部 G2A 操作映射至经认证的 HTTPS 连接（本地**演算中枢**可使用经核验的本机回环），暴露未认证 `PublicDescriptor` 发现入口、经认证的结构化操作请求与响应信封入口（关联请求标识、返回业务结果或结构化 `Error` 并禁用缓存），以及可选的**服务端推送流（SSE / WebSocket）**（每次推送实时核验撤权、受众与玩家在线状态；保持连接本身绝不延长过期权限）。

### 18.2 确定性 HTTP 状态码映射

**智能枢纽**返回的所有北向协议响应均携带结构化 JSON 响应信封并配对确定性的 HTTP 状态码，使标准网关监控、熔断与限流响应头正常工作的同时，彻底消除传输层拒绝与业务层拒绝的二义性：

| HTTP 状态码 | 对应的标准错误码 / 场景 | 响应语义 |
| --- | --- | --- |
| `200 OK` | 操作已受理或完成，无协议级拒绝 | 返回业务结果（注：`action.query` 的业务结果内如实报告游戏执行 `failed` 或 `unknown` 记录）。 |
| `400 Bad Request` | `invalid_request`, `invalid_arguments`, `unsupported_version`, `unsupported_capability` | 结构化错误响应；调用方须修正请求或重新协商。 |
| `401 Unauthorized` | `unauthenticated` | 缺少有效认证凭据或凭据已失效。 |
| `403 Forbidden` | `permission_denied`, `revoked` | 授权或白名单准入不足，或权限已被撤销。 |
| `404 Not Found` | `not_found` | 在调用方获授权可见范围内目标不存在。 |
| `409 Conflict` | `stale_context`, `conflict`, `confirmation_required` | 代次/修订号过期、去重状态冲突，或附带确认挑战详情。 |
| `413 Content Too Large` | `message_too_large` | 载荷超出声明的字节或集合长度上限。 |
| `429 Too Many Requests` | `resource_limit` | 触发速率或并发配额限制（附退避等待指引）。 |
| `503 Service Unavailable` | `unavailable` | 服务暂时不可用；按第 11.1 节重试族规则退避重试。 |
| `504 Gateway Timeout` | `outcome_unknown` | 提交状态未决；按第 11.2 节核对，**严禁**盲目自动重发副作用。 |

### 18.3 出站中继转发准则

当客户端**智能枢纽**位于家庭 NAT 或防火墙后、需在不开放入站端口的前提下与外部端点双向联动时（第 3.2 节），**出站中继**通过五项专用传输操作配对已认证端点：可信邮箱注册（`relay.register`）、**演算中枢**外层认证请求提交（`relay.call`）、**智能枢纽**主动出站拉取（`relay.pull`）、有界响应回传（`relay.reply`）及邮箱即时撤销关闭（`relay.revoke`）。外层中继令牌绝不替代内层会话或授权凭据，且南向**交互源点**执行操作（`action.claim`、`action.commit_result`）在中继通道上**必须**一律拒绝。

### 18.4 传输安全、防服务端请求伪造与 RFC 8785 规范化

**智能枢纽**与远端**演算中枢**之间的连接**必须**启用经认证的 TLS，严禁将凭据写入 URL 或日志，并默认拒绝跨源浏览器请求。所有外部地址与重定向均视为不可信输入，在发起连接前及每次重定向时均须校验目标协议、主机/IP 与端口策略，阻断服务端请求伪造（SSRF）与 DNS 重绑定攻击，同时不得借此歧视合规**演算中枢**服务商。

**标准 JSON 与 RFC 8785（JCS）摘要规则：** 传输载荷采用严格 UTF-8 JSON（RFC 8259），拒绝重复对象键、非法 Unicode 代理项、`NaN` 与 `Infinity`。所有协议加密摘要均对 **RFC 8785**（JSON 规范化方案，JCS）生成的规范化 UTF-8 字节计算带域分离的 SHA-256 哈希。

<a id="section-19"></a>

## 19. 安全与隐私考虑

| 威胁向量 | 必需的规范防护边界 |
| --- | --- |
| 借查询或错误回包探测隐藏游戏事实 | **交互源点**内部秘密闭环判定（第 4.4 节）、**智能枢纽**序列化前可见性裁剪及统一错误脱敏。 |
| 对白、物品描述、商品文案或记忆中的间接提示词注入 | 控制权限与不可信文本严格分离（`I09`）；在**智能枢纽**与**交互源点**独立于模型输出确定性执行权限、确认与预算检查。 |
| 混淆代理与跨层委托越权 | 三层之间每一跳均核验认证主体、目标受众、游戏实例代次与权限范围快照。 |
| 网络抖动与攻击指令重复重放 | **智能枢纽**前置防重放去重账本（直接拦截重复请求，绝不二次穿透至**交互源点**）、`unknown` 状态保留及默认不重发规则。 |
| 撤权与在途执行并发竞争 | **智能枢纽**原子下发门禁（`action.claim`）配合**交互源点**效果边界裁定。 |
| 战争迷雾切换或离队后的数据残留泄露 | 立即废止旧可见性代次、建立 `retract` 撤回屏障并执行冻结加当前双重受众核验。 |
| 恶意资源地址、压缩包路径穿越或 SSRF | 声明式资源清单摘要核验、解压体积与层级上限、禁代码执行及防 DNS 重绑定目标校验。 |
| 伪造自证“干净上下文”声明 | **智能枢纽**与**交互源点**权威账本独立于**演算中枢**单方声明强制执行预算、确认与接收受众边界。 |

单纯读取游戏内文本或商品文案不会废止有效的玩家虚拟货币购买预算，也无需使后续所有常规行动退化为逐次弹窗，前提是权威账本确保不可信文本无法篡改授权、接收方或额度上限。审计日志**应**记录不透明标识与处理结果，最小化私人对话原文留存。

<a id="section-20"></a>

## 20. 版本演进、发布治理与生态中立性

### 20.1 规范版本演进原则

G2A 严格区分公开审阅阶段的编辑修订草案（以 `standard-review-*` 标识）与正式批准冻结的生产协议版本（以明确语义化版本号标识）。凡改变规范状态转换、必选义务、错误恢复规则或规范化摘要输入的变更，均须升级协议版本并在发现阶段显式协商；实现**不得**跨不兼容版本依赖静默降级或宽容解析。

### 20.2 发布冻结与中立生态治理

在正式冻结生产版本前，**必须**通过不可变的**发布清单**（Release Manifest）同步锁定中英文规则规范正文、配套机器可读结构定义、标准测试向量以及开源参考 SDK 与**智能枢纽**符合性套件的加密摘要。

**平台商业治理与协议符合性分离：** 频繁触发有据可查的协议违规可依据标准化错误码与审计日志启动技术核查，但单纯被拒次数本身不等于恶意。各商业目录或**智能枢纽**运营方**可以**在保留用户自定义接入通道的前提下提供透明的优选推荐目录（第 7.1 节），游戏开发者**可以**在第 7.1 节四项反垄断保障下运行合规反外挂/监管白名单，但任何单一平台的商业上下架决定仅作用于该平台自身，**不得**表述为全协议层面的 G2A 符合性封禁。

<a id="section-21"></a>

## 21. 符合性与质量评估

### 21.1 符合性声明与五级证据分层

符合性声明明确标注所实现的正式 G2A 版本、所属标准层级（**交互源点**、**智能枢纽**或**演算中枢**）、传输绑定、已协商能力模块及信任模式。公开符合性测试套件**必须**允许第一方与第三方实现按完全一致的标准自测验证，不设标准作者人工审批门槛；未实现的可选模块如实标为 `not_applicable` 并附说明。验证证据分为五个层级：(1) 标准 JSON 与 RFC 8785 JCS 规范化校验，(2) **智能枢纽**状态机与重放/故障注入测试，(3) 跨层级网络互通，(4) 真实游戏引擎**交互源点**集成验证，以及 (5) 玩家侧策略执行验收。

### 21.2 结构化符合性测试套件矩阵（`CONF-01`–`CONF-14`）

| 套件编号 | 测试域与对应条款 | 适用层级 / 模块 | 必需覆盖的正例、反例与故障验证 |
| --- | --- | --- | --- |
| `CONF-01` | 公平准入、枢纽双轨路由与白名单对等（§§1, 4, 5, 7, 8, 20, 22） | 全部三层 | `PublicDescriptor` 与按主体过滤的 `Descriptor`；RFC 8785 冻结范围摘要与新 `Offer` 收窄；**智能枢纽**双轨路由（商业优选推荐与开放用户自定义**演算中枢**并存）；开发者专属剧情 `independent_npc` 槽位与开放 `companion` 槽位区分；白名单反垄断对等与零秘密泄露的标准化拒绝码。 |
| `CONF-02` | 标准 JSON、RFC 8785 JCS 与南北双段 HTTP（§§3, 5.1, 7.4, 12.1, 18） | 全部三层 | 标准 RFC 8259 有限数值（支持整数与浮点数，拒绝 `NaN`/`Infinity` 与重复键）；跨语言 RFC 8785 JCS 摘要一致性；南向**交互源点** HTTP 端口与公网流量隔离；北向确定性 HTTP `200`/`400`/`401`/`403`/`404`/`409`/`413`/`429`/`503`/`504` 映射；SSRF 与 DNS 重绑定拦截。 |
| `CONF-03` | 角色槽位、共存与生命周期（§§4.1, 13, 14.2） | `交互源点`, `智能枢纽`, `演算中枢` | 声明的角色槽位（`companion`、`independent_npc` 或双支持）；空伴玩槽正常游玩；纯 NPC 游戏无虚设伴玩槽；共存与上限执行及逐角色主体/视角/授权/计费严格隔离；召唤与收起不丢记忆。 |
| `CONF-04` | 离线即停、多人 NPC 连续性与双层恢复（§§8.2, 11, 14） | `交互源点`, `智能枢纽`, `演算中枢` | 禁全员离线后台空跑；**演算中枢**心跳不伪造玩家在线；个人伴玩随主人离线即停；默认玩家计费 NPC 在房主离线时立即终止原房主计费并按声明执行停机/本地脚本接管/显式接手且绝不泄露原房主凭据与私人数据（开发者赞助 NPC 则为剩余在线玩家正常继续）；双层 `session.resume` 与本地接管后强制玩家确认。 |

### 21.3 可复现的质量评估准则

随附于符合性报告的可选质量基准评估**必须**披露**交互源点**游戏构建版本、场景种子、**演算中枢**模型版本、观察与行动速率上限、资源预算及全量试验次数，分别统计协议违规、玩法失败、预算触顶与基础设施故障，禁止选择性挑选样本。质量排行榜分数**绝不得**转化为排斥特定厂商的封闭准入门槛。

## 22. 三层 SDK 架构与智能枢纽分发规范

为彻底消除游戏开发商的接入负担，同时统一保障防重放安全与多服务商灵活路由，G2A 对三大标准层级的软件交付物与分发规则作如下规范：

| 标准层级与交付包 | 接入主体与分发模式 | 标准化接口与职责边界 |
| --- | --- | --- |
| **交互源点**（轻量源点 SDK） | **游戏开发商与引擎团队**；直接随游戏客户端或游戏服务端分发 | 极简南向 HTTP 数据与操作适配器。开发商只需填好状态返回序列与游戏内操作执行回调即宣告接入成功；游戏内**零**去重账本、**零**令牌校验、**零**会话租约与路由代码。 |
| **智能枢纽**（开源枢纽 SDK / 运行时） | **单机电脑整机单次安装全局共用**，或**网络游戏服务端统一部署**；**完整源码公开** | 南向经本机回环或内网高速 HTTP 访问**交互源点**，北向提供完整 G2A 协议对接**演算中枢**。集中完成身份核验、RFC 8785 范围摘要、`Offer`/`Grant` 同意门禁、**行动防重放与重复请求拦截**、会话租约、双轨路由（商业优选推荐目录 + 开放玩家自定义接入）以及网游多端战局同步。若玩家电脑尚未安装**智能枢纽**，由**交互源点 SDK** 触发一次性按需下载安装，整台电脑所有游戏共用同一个**智能枢纽**。 |
| **演算中枢**（中枢服务 SDK） | **云端 AI 服务商与本地/自建模型开发者** | 对接**智能枢纽**北向标准协议，自动拼装观察快照与增量、处理确认挑战重提与 `unknown` 超时结果核对，并支持通用标准格式的伴玩记忆导入导出。 |

将**交互源点**与**智能枢纽**彻底解耦，既把单款游戏的接入工作量与包体增量压缩至最低，又允许游戏厂商直接审查开源**智能枢纽**的全部安全源码，并能以同一套标准从单机伴玩平滑扩展至服务端权威的多人网游。

## 23. 端到端示例场景

- **单机新引擎游戏接入交互源点与整机共享智能枢纽：** 一家新引擎团队仅在单机角色扮演游戏中接入轻量**交互源点 SDK**，通过本机 HTTP 端口填入队伍状态返回序列与“释放技能”操作回调。在玩家电脑上，全局共用的**智能枢纽**（整机仅安装一次，首次缺失时自动引导下载）经 `127.0.0.1` 读取状态并路由至玩家选定的**演算中枢**。当网络波动导致**演算中枢**将同一记攻击请求发了两次时，**智能枢纽**直接命中去重账本拦截第二次请求并返回原回执，确保**交互源点**只执行一次攻击。
- **网络游戏多人副本中的服务端智能枢纽同步：** 在一款服务端权威网游中，玩家电脑仅运行普通游戏客户端，不安装也不接触任何 AI 接入组件；**交互源点 SDK** 与**智能枢纽**统一部署于游戏服务端。四人组队挑战副本时，服务端**智能枢纽**经内网 HTTP 汇总全队获准视野与战局状态、统一处理高并发去重并对接云端**演算中枢**下达战术指令，确保全队队员面对的智能体与 Boss 反应严格一致且实时同步。
- **竞技反外挂白名单与自有演算中枢对等：** 一款战术网游在社交主城开放任意合规 `chat` 陪伴，而在排位副本中仅向通过符合性测试并遵守**智能枢纽**统一反应冷却下限的白名单**演算中枢**开放战斗 `actions`。发行商自研的**演算中枢**与外部第三方共用完全一致的观察视图与冷却下限，并公开标准供第三方申请准入。
- **主动战斗协助与跨三层急停：** 在线战斗协助授权下，伴玩**演算中枢**针对附近敌人排队发起攻击。玩家喊出“停下！”瞬间，**演算中枢**立即丢弃未发计划，**智能枢纽**立即取消并拦截队列中未下发的 `pending` 攻击，而已在**交互源点**离弦飞行的箭矢（`executing`）按游戏物理规则自然结算并如实记账。
- **多人团本 Boss 计费模式与房主断线连续性：** 合作副本同时声明个人伴玩槽位与 1 个独立 AI Boss。若采用开发者赞助计费（`developer_sponsored`），单名队友掉线不影响剩余玩家继续挑战；若采用默认的玩家计费（`player_metered`）绑定房主，当 Boss 残血 5% 房主意外掉线时，原房主计费立即终止，并按声明规则平滑切换为**交互源点**本地脚本行为让队友打完本局（或由其他在线队友显式确认通过新授权接手计费后继续驱动，绝不暴露原房主隐私数据）。
- **超时结果核对与双层闪断恢复：** 网络响应超时返回 `504`（`outcome_unknown`）时，**演算中枢**向**智能枢纽**调用 `action.query` 查询原单，绝不另造新标识重发导致重复扣费。1 秒级网络切换在活动租约内且本地接管触发前恢复，经 `session.resume` 无缝继续战斗；3 分钟长时中断触发**交互源点**本地脚本接管后，重连时保持暂停直至玩家明确确认继续。

**观察流状态转换轨迹示例（世界代次 4 内）：**

| 步骤 | 收到的观察帧 | 消费方规范状态转换（第 9.2–9.4 节） |
| --- | --- | --- |
| 1 | `snapshot`，可见性代次 9，修订号 27 | 原子建立代次 9 基线（修订号 27）并绑定类别定义。 |
| 2 | `delta`，可见性代次 9，基准 27 → 修订号 30 | 原子应用状态更新与带转换原因的移除项；跳号 `27 → 30` 合法，当前修订号升至 30。 |
| 3 | 步骤 2 的完全重复帧 | 幂等忽略，不重复作用，修订号保持 30。 |
| 4 | 整理后的 `snapshot`，可见性代次 9，修订号 30 | 在修订号 30 重新建立等价完整基线，不虚增修订号。 |
| 5 | `delta`，可见性代次 9，基准 28 → 修订号 31 | 拒绝（`stale_context`，因基准 28 与当前 30 不一致）；请求新 `snapshot` 重同步。 |
| 6 | 废止代次 9 → `snapshot`，可见性代次 10，修订号 1 | 立即丢弃代次 9 状态；在可见性代次 10 建立全新基线（修订号 1）。 |
| 7 | 迟到的 `delta`，可见性代次 9，基准 30 → 修订号 99 | 因可见性代次 9 已废止而直接拒绝，不因修订号更大而接受。 |
