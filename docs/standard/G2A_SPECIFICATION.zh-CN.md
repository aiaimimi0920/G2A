## G2A 如何运转

以典型的双角色协同模式为例，开发者构建游戏世界，并在其中提供玩家角色和游戏伴玩两个角色槽位。**真人玩家控制玩家角色；游戏智能体受权扮演游戏伴玩。** 开发者为伴玩定义并提供角色能力，例如移动、攻击和交互；智能体通过调用这些能力请求行动，由游戏根据当前规则与世界状态判定是否允许执行，并决定实际效果。

```text
开发者：构建游戏世界，并为伴玩定义、提供角色能力。

真人玩家 ──控制──▶ [玩家角色]
                       ↕ 沟通
游戏智能体 ◀─ G2A ─▶ [游戏伴玩]
 （决策智能体）           ↕ 感知与行动
                  游戏世界与规则
                    （最终判定）

两个角色槽位都属于游戏世界；智能体是负责决策的软件。
```

图中有三类关系：**玩家角色 ↔ 游戏伴玩：沟通；游戏伴玩 ↔ 游戏世界：感知与行动；游戏伴玩 ↔ 游戏智能体：通过 G2A 交换信息与决策。** 这张图表示角色关系，不是网络部署图。游戏智能体通过游戏指定的交互节点，为所扮演的伴玩交换状态、行动请求及结果；它不能绕过角色直接控制整个世界。伴玩与世界的交互仍由游戏规则和授权限制。

上图以单人双槽位展示核心交互关系，不限定游戏世界只能有两个角色或某种角色形态，也不改变多人游戏中每位玩家可各自拥有伴玩的规则。**游戏智能体（Game Agent）**是可在本地或远端运行的决策智能体，**游戏伴玩（Game Companion）**是它在游戏内受权扮演的角色载体；两者不是同一实体。第 13 节进一步规定可组合的信息视角，以及仍须遵守的角色数量、活动模式和绑定限制；角色组合不扩大权限，游戏保留最终判定权。

## 1. 目的与范围

G2A 是连接游戏与 AI 智能体的开放交互协议。它规定参与方如何建立获授权的连接、交换游戏信息、发现和调用游戏能力，以及核对行动结果和处理中断。游戏始终决定其世界状态与可执行规则；玩家在这些边界内控制自己伴玩的偏好与授权。

**为什么需要共同协议？** 不同游戏提供的信息和可执行行动各不相同。G2A 用共同的交互规则说明：游戏向智能体提供什么、智能体如何请求行动、游戏怎样返回结果。具体玩法仍由游戏决定，智能体的模型和实现方式也不被统一限定。

本规范围绕四条相互关联的主线组织：

| 主线 | G2A 规定的内容 |
| --- | --- |
| 接入与控制 | 参与方身份、角色绑定、准入、授权、会话控制与撤销 |
| 观察与信息使用 | 可提供和所需的信息、获授权的视角、来源、新鲜度、接收范围与保留 |
| 行动与结果 | 能力定义、获授权的请求、游戏校验、执行、取消与结果核对 |
| 互操作与扩展 | 共同的数据模型和操作、传输绑定、错误、版本、配置规范与符合性 |

这四条主线相互关联。声明观察需求，不代表游戏支持或已授权提供；下列关键区别同样贯穿各条主线：

- **支持不等于授权**：能力声明仅说明实现支持什么，请求仅表达调用方意图；两者均不自动赋予执行或读取权限。
- **接受不等于执行完成**：游戏接受行动请求，不代表已在游戏世界中产生预期效果；必须区分受理、执行与效果完成。
- **获准读取不等于持续有效**：观察反映特定时刻或基线下的受限视角，随世界演进可能过期。
- **缺失不等于不存在**：因视野限制、权限裁剪或增量传输而缺失的信息，不得被推断为某项事实为假，也不得被解释为空世界。
- **伴玩记忆与当前世界状态分开处理**：回档、跨周目或分支切换会改变当前游戏状态，但不得仅因此清空伴玩已经保留的记忆。开发者可以建议如何使用或隔离这些记忆；玩家未设置时采用建议，玩家明确选择时以玩家选择为准。记住旧经历不代表它已在当前世界发生，也不能改变游戏的硬性玩法规则。

本协议的范围是游戏：面向玩家的辅助、NPC 协作、游戏状态观察、受约束的行动，以及可选的游戏内呈现。模型推理、模型托管、规划算法、记忆产品、商业身份提供方、游戏引擎和某个特定桌面伴玩都不是使用协议的前提。G2A 不是通用操作系统自动化协议。它不把任意远程代码执行纳入标准，也不默认授予对游戏秘密的访问。

游戏为 G2A 指定一个游戏交互节点，游戏智能体在有效且获授权的交互期间，通过该节点获取当前游戏状态、提出行动并查询结果。节点发布的状态和行动结果，是该交互范围内的游戏事实；G2A 不另外复算游戏内部的命中、伤害或反作弊结论。节点可以由本地游戏客户端或模块实现，也可以由远端服务提供，不强制采用某种部署方式。这一来源约束只针对当前游戏状态与行动结果，不限制玩家指令、伴玩记忆或外部知识的使用；这些信息须保留各自来源，不能被冒充为当前游戏事实。G2A 仍要求通信身份、权限、消息格式和状态一致性检查，也不能保证模型绝不推断或从其他来源获知隐藏事实。

首次阅读可以先看第 3–4 节了解职责和配合方式，再看第 13–16 节了解伴玩在游戏中的行为；实现协议时，再结合第 5–12 节的数据与操作细节。开放服务商准入与有据拒绝见第 7 节；版本、发布与平台治理边界见第 20 节。

## 2. 约定与文档效力

本文采用以下中文用语表达要求，其含义与 RFC 2119、RFC 8174 的规范性用语对应：

| 用语 | 含义 |
| --- | --- |
| 必须、必需 | 强制要求，符合规范的实现需要满足。 |
| 不得 | 强制禁止，符合规范的实现不能这样做。 |
| 应、不应 | 原则上需要遵守；只有在充分理解后果、权衡理由后，才可采用例外。 |
| 可以 | 规范性许可：允许采用，由实现或获授权的参与方选择；不表示每个实现都必须提供该能力。 |

这些词在明确规定参与方的义务、禁止、建议或许可时表达规范性要求，不表示现有软件已经实现或通过验证。用于描述能力、可能性或事实时，同一词语不自动构成规范要求；解释性文字、图表、示例和修订历史不独立增加要求。中文正文不重复标注英文关键词，其规范强度须与英文主稿按 RFC 2119、RFC 8174（BCP 14）标明的要求对应。

**草案与现有定义的关系**

同目录英文主稿 `G2A_SPECIFICATION.md` 是主要的语义审阅基准。在继承的 `g2a-design-1` 基线中，语言无关的机器契约定义位于 [contracts.schema.json](../protocol/contracts.schema.json) 和 [operations.json](../protocol/operations.json)，[contracts.py](../protocol/contracts.py) 提供对应的 Python 参考类型绑定。既有对象从创建到终态的状态机与处理规则位于 [PROTOCOL.md](../protocol/PROTOCOL.md)、[OPERATION_CONTRACT.md](../protocol/OPERATION_CONTRACT.md) 和 [STATE_TRACES.md](../protocol/STATE_TRACES.md)。本文在此基线上提出扩展观察语义（`observations-draft-1`），并明确游戏角色适用性与伴玩治理策略；现有 JSON 能承载相关字段，不代表新增语义已在代码中实现或通过互操作验证。材料间仍有差异时，必须按第 20 节统一权威定义，不能仅凭参考绑定推断标准。

## 3. 架构与适用性

以“伴玩帮玩家攻击附近的敌人”为例：游戏智能体从游戏指定的交互节点获取伴玩获准看到的敌人信息，并向该节点提出攻击请求。游戏按自身规则检查权限、执行攻击并判定命中和伤害，由该节点返回结果。游戏智能体据此继续决策，不需要另找一套服务重复判定这次攻击。

本节说明两件事：**协议规定什么，以及不同接入方需要实现哪些部分。** 不需要每个接入方都实现整套协议的全部功能。

**协议分为三层**

1. **数据模型：消息里有哪些信息。** 例如，一次行动如何标识、结果如何表示。
2. **操作与行为规则：双方可以提出什么请求，以及请求之后会发生什么。** 例如，提交行动、查询结果，以及行动从开始到结束的处理规则。“生命周期”指的就是这些开始、变化和结束的过程。
3. **传输绑定：这些消息具体怎样传送。** 即把前两层的规则映射到具体的通信方式。

引擎适配器和 SDK 是实现这些规则的工具，不是协议本身。其他 SDK 可以采用不同于参考实现的代码结构，只要符合协议。

**先看自己承担什么职责**

下表是职责概览，具体规则见后续各节。同一个接入方可能承担多种职责，相关要求同时适用。

| 接入方 | 需要负责的事情 |
| --- | --- |
| 所有接入方 | 确认身份、检查收到的输入、遵守双方确认使用的版本和适用扩展规则、保护应保密的信息，并如实报告错误。 |
| 游戏交互节点与游戏智能体 | 处理接入、执行授权范围限制、管理 G2A 会话的开始和结束、处理事件，并按适用规则恢复中断的请求。会话是双方持续交互的逻辑上下文，不是游戏程序或游戏房间本身。 |

实际保存数据的接入方须对自己保留的数据处理其支持且获授权的隐私请求，并如实返回结果；没有保存相应数据的一方不因此承担替其他方处理数据的职责。

游戏交互节点与游戏智能体负责双方的通信、用户授权和交互状态。部署可以使用现有网络设施，但不得改变消息来源、接收范围或授权边界，也不因此增加 G2A 核心角色。

**再看自己启用了哪些能力**

“已协商”表示双方已经确认支持并采用某项能力及其规则。“配置规范（profile）”是为一项能力约定的具体规则。采用一项能力后，参与该能力的各方需要遵守对应要求：

| 使用的能力 | 对应职责 |
| --- | --- |
| 行动请求与执行 | 游戏检查请求是否合法、避免同一行动重复执行、维护行动状态与实际效果，并检查产生这些效果的授权。Agent 只在授权范围内请求行动；结果不明时先核对，不能盲目重试会产生效果的操作。 |
| 采用观察配置规范传送游戏信息 | 明确信息流及获准提供的视角；处理获准观察范围内的完整状态（基线）、用于区分不同批次或实例的代次标识，以及信息过期和撤回。 |
| 中断后的持久恢复 | 仅在双方确认使用时，遵守保存交互状态、恢复及交接的对应规则。 |
| 聊天 | 明确消息发给谁、来自哪里，以及如何转发和保留。 |
| 外观呈现或资源传送 | 只承担双方确认使用的渲染或资源的创建、使用和结束等管理职责。 |

聊天、资源传送、外观呈现、主动感知和持久恢复，不会仅因本文定义了它们就成为所有接入方的必做功能。但“可选”不表示使用后可以忽略对应规则。

面向玩家的聊天使用是可选的，但这不免除声称支持继承的 `g2a-design-1` `core.events` 功能的实现所承担的文本/事件契约。现有目录没有定义独立的可选聊天功能。未来配置规范若拆分这些操作要求，必须明确其适用性映射并单独进行版本管理，不得静默改变继承的最低要求。

操作目录中的 `core.session` 等标签用于归类，不表示每个接入方都要实现这一类的全部操作。发布版必须明确公布：哪些角色在使用哪些功能时，需要实现哪些操作。

| 章节 | 主要回答的问题 |

| 5–6 | 消息使用哪些数据对象？协议提供哪些操作？ |
| 7–12 | 如何接入、授权、交换观察、执行行动和处理中断？这些规则不依赖具体传输方式。 |

**判断一条要求是否适用，要看职责和使用条件，不要看它排在文档哪里。** 例如：

- 接入的游戏需要提供第 13.2 节规定的伴玩槽位，但玩家可以留空。

- 使用可选功能时，仍需遵守适用的核心规则、角色规则、隐私规则及生命周期规则。

上面的职责表与各节说明共同确定适用范围。重新安排阅读顺序不会降低或增加这些要求。

本规范借鉴 A2A 将数据模型、操作规则与传输方式分开的组织方式，但不采用它的线上消息格式或操作名，也不声称与 A2A 兼容。这种文档分层本身不要求增加 SDK 代码或新的传输方式。

## 4. 角色与信任

第 3 节说明交互如何完成，本节说明通信中的身份与权限。游戏指定的交互节点对游戏智能体提供状态、接收行动并返回结果。双方仍须确认：**请求是谁发来的、代表哪位玩家、是否有权操作这个角色。** 这些是协议通信与授权检查，不是对游戏内部判定的第二次复核。

**各方分别负责什么**

核心交互只有两方：游戏交互节点与游戏智能体。游戏内部的客户端、服务端或计算模块不是额外的必需协议角色；启动游戏、呈现外观、传送资源及保存数据也不各自构成一个新的核心角色。

| 名称 | 含义与职责 |
| --- | --- |
| 游戏交互节点（Game Interaction Node） | 游戏指定的 G2A 通信入口，是本次交互中游戏状态与行动结果的权威来源；代表游戏提供当前状态、接收行动请求并返回游戏判定的结果；负责落实适用的身份、权限及协议处理要求。内部计算可以交由游戏自身模块完成。 |
| 游戏智能体（Game Agent） | 在本地或远端运行的决策智能体，通过游戏指定的交互节点获取获准提供的状态，为受权扮演的角色提出行动请求，并根据返回结果继续决策；不是游戏角色本身。 |

启用可选功能时，实际执行该功能的接入方承担对应义务：启动游戏需要明确的启动授权；提供或接收外观、资源时，执行相应的授权、格式、来源与生命周期规则；保存数据时，按实际控制的数据范围处理隐私请求。这些义务不要求另设服务，也不使未使用的功能变为必做项。通信身份和权限检查仍由处理相应请求的一方落实。

**游戏交互节点是一项对外职责，不是一台必须额外部署的服务器。** 单机游戏可以直接由本地客户端或其中一个模块承担；联网游戏也可以由客户端提供该入口，再由游戏内部与服务器协作。命中、伤害、资源变化和反作弊由游戏自身处理。G2A 不规定这些内部职责如何拆分，也不要求智能体绕过指定节点再联系游戏内部的服务器或校验模块。

本文及既有材料中的 **Game Authority** 表示游戏对其状态及效果的判定权。在 G2A 交互中，由游戏指定的交互节点代表游戏提供这些事实；该节点不必亲自执行全部内部计算。智能体不得用自己的推测、聊天内容或历史记忆替代该节点提供的当前状态与结果。游戏自身仍须按其规则检查和执行行动，G2A 不在游戏之外增设另一层游戏事实判定。后文的“游戏端”“执行端”或“权威执行器”描述游戏承担的处理与执行职责，不要求智能体另连一个节点；这些职责通过指定的游戏交互节点对外提供。

当前游戏或多人房间与其中的 G2A 会话分别管理：会话描述游戏与 Agent 的协议交互，关闭会话不等于关闭游戏或房间。会话的建立、关闭、恢复和授权仍遵守后续规则，不因客户端与服务端合并部署而省略。

连接规则中的“端点”指提供通信接口的一端。游戏侧端点由游戏指定的交互节点提供；其地址用于建立连接，不代表新增组件。节点可以调用游戏内部模块落实请求处理、校验或停止活动等职责，但对外仍由该节点提供状态及结果。接口发现、身份认证、权限检查和消息传输继续遵守相关章节。

游戏交互节点与游戏智能体在处理请求时，分别执行自己负责的用户同意、策略和授权限制；任何一方都不能因协助通信而扩大另一方的权限。

同一个接入方可能承担多种职责，但必须区分各项职责的权限。保存数据本身不授予控制游戏的权限。

**确认是谁发来的，不能只看消息自称是谁**

调用方身份必须以通信过程中经过认证的身份为准。消息正文里的 `sender` 字段只是消息内容，不能单独用来证明发送者身份。

系统必须能够区分以下信息，而不能把它们当作同一件事：

- **主体**：被识别或被授权的身份，例如玩家或服务的身份。
- **设备**：请求来自哪台设备。
- **当前游戏或房间的标识（instance）**：用于确定请求属于哪一次游戏运行或哪个房间，区分不同运行及其授权范围。它是协议中的身份标识，不要求独立部署，也不等同于客户端进程。
- **实例代次（instance epoch）**：区分同一运行标识下不同阶段的标记，避免把旧阶段的信息误当作当前信息。

进入新的实例代次后，绑定旧实例的凭据或引用会按双方已确认采用的配置规范失效。另外，加入一个会话，并不意味着可以读取其中所有消息。

**代玩家操作，不等于拥有额外权限**

系统必须区分实际经过认证的调用方与它所代表的玩家；请求经过其他处理环节，不会增加玩家或伴玩的权限。

委托是“允许另一方代表自己做特定事情”的授权。它必须明确适用的玩家、角色、游戏或会话，以及资源；经过多层转交时，必须始终保留原有授权范围和有效期。任何代为协调授权或转发请求的一方，都不得把自己的权限加到被代表主体的权限上。

游戏文本、消息正文或转发指令中写着“我受到了委托”，并不等于这项委托已经验证。会话编号、行动标识符和关联编号也只用于找到对应记录；知道编号不代表获得访问或操作权限。

**不同验证方式不能混为一谈**

现有的 `local-verified`、`provider-verified` 和 `test-enrolled` 是不同的信任模式，不得把它们描述为提供同等保证。特别是，测试登记只为开发测试提供便利，不能证明系统可以抵御任意本地软件。

实现必须如实说明通信中哪些参与方可以读取消息内容；如果两端以外的其他方也能读取，就不得声称只有通信两端可解密。

### 4.1 信息与行动的权限边界

实现必须分别处理四种权限：

1. Agent 可以获得哪些信息。
2. Agent 可以向玩家讲哪些信息。
3. Agent 可以向游戏或其他接收方传送哪些信息。
4. Agent 可以请求或执行哪些行动。

这四种权限不能相互替代。知道一个事实，不等于有权披露或据此行动。获准与玩家聊某段记忆，不等于可以把原始对话或记忆发给游戏。获准提出行动，也不等于游戏可以跳过执行检查。即使同一个进程承担所有职责，也必须保留这些区分。

**有些信息能用于判断，但不能直接说出来。** 已协商的观察配置规范应区分以下数据：

- 可用于向玩家展示或回答的信息。
- 仅允许用于规划的受保护输入。
- 由游戏内部判断的条件。Agent 只能拿到获准提供的判断结果或引用，不能据此读取底层事实。

标签不能代替实际限制。如果授权规定原始数据仅限规划使用，实现必须在检索、生成和转发时执行这一限制，包括授权覆盖的派生表示，例如摘要；不得声称只靠提示词就能保证数据隔离。游戏可以在内部判断隐藏前置条件，仅提供获准披露的结果或不透明引用，而不提供底层事实。

这里约束的是受保护数据的实际授权，不是把开发者的剧透建议变为硬性禁令。第 15.2 节规定的、符合条件的玩家自主管理记忆仍由玩家选择如何使用。本节不要求采用统一的模型或规划器架构，也不保证模型永远无法推断出秘密。

## 5. 规范数据模型

**技术术语速查**

以下术语用于阅读后续数据、操作和连接规则，不代表需要部署同等数量的软件组件。

| 术语 | 英文名称 | 在本文中的意思 |
| --- | --- | --- |
| 主体；身份认证 | Principal; Authentication | 主体是被识别或获授权的玩家、服务等身份；身份认证是核实调用方是谁，不等于批准它做某件事。 |
| 授权记录；权限范围 | Grant; Scope | 授权记录记载已批准的权限及有效条件；权限范围是双方确认并冻结的权限快照。“能连接”不等于“能读取或操作所有内容”。 |
| 委托 | Delegation | 允许另一方代表自己做特定事情。受托方不能扩大委托者授予的权限。 |
| G2A 会话 | Session | 游戏与 Agent 持续交互时使用的逻辑上下文，关联参与方、授权和操作状态；不是游戏程序，也不只是聊天记录或一条网络连接，不要求独立服务。 |
| 能力；操作 | Capability; Operation | 能力说明支持什么功能；操作是协议中可调用的请求，如提交行动或查询结果。支持功能不等于已获准调用。 |
| 观察 | Observation | 游戏向 Agent 提供的、获准看到的信息。它受视角、授权和时间限制，不是整个世界的全知副本。 |
| 观察基线；状态补丁 | Observation Baseline; State Patch | 观察基线是某一信息流获准观察范围内的一份完整状态；补丁只说明相对于指定基线发生的变化。它们不同于本文开头的“规范基线”。 |
| 代次；游标 | Epoch / Generation; Cursor | 代次区分实例、世界或控制状态的不同阶段；游标标记信息流中的位置。它们帮助判断信息是否接得上、是否属于旧状态，不是访问凭据。 |
| 事件 | Event | 已发生的、接收方获准看到的状态变化通知，例如敌人死亡。它不是要求游戏执行行动的指令。 |
| 行动；行动标识符 | Action; Action ID | 行动是希望在游戏中执行的行为及其处理记录；行动标识符用于关联和查询这次行动，不代表执行权限。 |
| 行动结果；已提交效果 | Action Outcome; Committed Effect | 行动结果说明行动的处理状态及已知效果，包括部分效果；已提交效果是游戏确认已经产生的实际变化。提交或接受请求（submit/accept），不等于提交其效果（commit）。 |
| 回执 | Receipt | 可再次查询的操作结果记录。用于核对发生了什么，不会额外授予权限。 |
| 消息信封 | Envelope | 包装消息内容及其来源、接收范围、关联标识等信息的外层结构，不是额外的一类游戏行为。 |
| 来源；接收范围 | Provenance; Audience | 来源说明信息来自哪里；接收范围说明信息发给谁、哪些接收方获准读取。知道来源不等于有权转发。 |
| 生命周期 | Lifecycle | 一个对象或交互从创建、使用、变化到结束的过程，例如会话建立后又关闭。 |
| 协商；配置规范 | Negotiation; Profile | 协商是双方确认共同使用哪些功能与规则；配置规范是某项功能的具体约定，不是玩家个人设置。 |
| 传输绑定 | Transport Binding | 将协议消息与操作映射到具体通信方式的规则。它回答“怎样传送”，不是“游戏允许做什么”。 |
| Schema；符合性 | Schema; Conformance | Schema 描述数据格式及可校验的约束；符合性是是否满足适用的协议要求。格式检查通过不等于权限和游戏行为也正确。 |
| 编辑修订号；协议版本；规范基线 | Editorial Revision; Protocol Version; Specification Baseline | 编辑修订号标识文档修改；协议版本用于通信兼容性；规范基线指本草案继承的既有定义。更新文档不等于发布新的线上协议版本。 |

上表解释阅读术语；下表列出消息实际使用的数据对象。字段相似不代表对象用途相同：

| 对象 | 用途 |
| --- | --- |
| 描述对象（Descriptor） | 声明身份、支持的版本、角色、能力及扩展。 |
| 提议（Offer） | 提出一次交互。 |
| 请求权限范围（Requested scope） | 表达希望获得哪些权限。 |
| 授权记录（Grant） | 记录批准的权限范围、授权依据及有效期。 |
| 权限范围（Scope） | 双方已协商并冻结的权限快照。 |
| G2A 会话（`Session`） | 关联参与方、授权、就绪状态、控制代次、租约及操作状态。租约限定控制权的有效时间。 |
| 消息信封（Envelope） | 包装一条带类型的游戏或 Agent 消息，同时携带权限范围、来源、接收范围、关联标识和扩展。 |
| 行动（Action） | 记录行动请求及结果。 |
| 事件（Event） | 记录接收方获准看到的状态变化。 |
| 恢复快照（Recovery Snapshot） | 提供获准披露的当前状态，而不是要求接收方自己重放旧消息才能还原状态。 |
| 回执（Receipt） | 保存可再次查询的操作结果；回执本身不授予行动权限。 |

除非对象定义另有说明，使用方必须将标识符视为不透明值，也就是不能自行拆解它来推断身份、权限或含义。关联标识、消息标识、操作标识、事件游标和行动标识各有用途，不得相互替代。

以下规则始终成立：

1. 实际权限不得超出当前游戏能力、已批准授权、会话权限范围、成员关系和当前策略共同允许的范围。
2. 不得从发现过程或已建立的通信路径推断用户同意。
3. 不得通过修改活动请求扩大冻结的权限范围。
4. 撤销必须阻止撤销范围内后续的读取和效果，但不得抹除已提交效果的核对记录。核对结果仍需独立有效的读取权限；这不是撤销的绕过路径，也不保证调用方始终有权读取。
5. 当状态可能变化时，必须由决定实际游戏效果的一方，在效果产生前再次检查准入或授权。
6. 重复投递不能授权重复效果。
7. 没有证据时，未知结果不得报告为失败或成功。
8. 接收受保护内容，以及向接收方提供该内容时，都适用接收范围检查。
9. 不受信任的游戏文本、聊天和资源内容始终是数据，而不是协议权威。
10. 隐私回执描述实际完成的工作和例外，而不能把计划删除写成已经删除。

| presentation.renew | 呈现能力 | 仅续期符合条件的当前权限 |
| presentation.release | 呈现能力 | 幂等释放渲染资源 |
| privacy.request | 数据主体 | 请求实际保存相关数据的一方执行受支持且获授权的数据处理 |
| privacy.receipt | 数据主体 | 查询原请求的实际处理状态及保留例外；调用方不写入回执 |


对于隐私操作，实际保存相关数据的一方负责接收、处理请求并返回实际状态；数据主体发起查询。调用方自称已删除数据，不构成实际处理数据的一方签发的处理回执。

<a id="section-7"></a>

## 7. 发现、协商与准入

**对符合规范的服务商开放**

G2A 向符合规范的第三方智能体和模型服务开放；互操作不得要求使用协议作者平台自有的智能体或模型服务。独立实现可以通过适用的已声明角色、能力、认证及协商契约参与。开放性不免除既有的同意、数据访问、行动或资源要求。只要智能体满足适用的 G2A 最低标准，游戏就必须允许其接入；开发者不得按服务商身份任意排除、强制指定偏好厂商，或以封闭的服务商白名单将 G2A 变为专属生态。最低标准及符合性证据必须对自有及第三方智能体一致适用。

**允许连接，不等于授权读取或行动。** 既有能力、认证及授权契约仍对所有参与方适用，且不得被用作变相限制服务商的手段。

**拒绝接入必须有具体理由**

游戏可以针对有证据的恶意行为或实际违反适用规则的行为拒绝请求或断开智能体。游戏必须向智能体服务商提供标准化的机器可读原因代码，以及清晰、具体的人类可读说明，指出相关规则及违规行为，并提供足以诊断的安全细节。

冻结发布必须定义共同的原因代码目录、稳定含义及载荷 Schema，使服务商能一致理解拒绝；仅有自由文本不够。代码不能取代针对本次情况的具体说明，说明必须与代码一致。仅使用“恶意”等笼统标签、无依据的怀疑或服务商身份，本身不足以构成原因。

原因与支持细节必须遵守受保护数据边界，不得披露凭据、他人私人信息或隐藏游戏事实；这些边界不能成为完全不给出有意义说明的借口。处置必须针对实际行为，不得掩饰对符合规范服务商的任意排斥。

**公开发现与经认证的发现不同**

两种发现路径分别处理：

- **公开发现：** 未经认证时，必须只返回 PublicDescriptor 中的 instance、supported_versions 和 discovery_endpoint。
- **认证后发现：** 完整的 describe 要求经过认证的智能体或玩家。披露角色、能力、绑定信息和扩展前，必须按该主体获准看到的内容过滤 Descriptor。

两种路径都不得暴露秘密或未经授权的玩家状态。发现后，对端选择双方共同支持的版本和配置规范集合。不支持必需扩展时，协商失败；只有在语义允许安全省略时，才可以忽略不支持的可选扩展。

**提议、批准与加入**

任意一方都可以通过其已授权的准入路径发起 Offer。创建 Offer 时冻结 immutable_scope 和 scope_digest。只有对应玩家经过认证的 PlayerConsent 路径，才可以通过 offer.decide 批准或拒绝这一精确的冻结权限范围；decision_ref 必须验证实际发生的玩家交互。

此前已批准的自动规则，仅可在满足基线规定的精确匹配和无需启动条件时，在 offer.create 期间自动批准；它不会赋予智能体调用 offer.decide 的权限。智能体不得批准自己的 Offer。

缩小或以其他方式改变提议权限范围，要求创建新的 Offer、新的 scope_digest，并批准这一新提议；offer.decide 不得原地修改现有 Offer。

邀请由其预期的、经过认证的受邀方兑换；仅持有一个标识符不会产生更广的主体身份。加入需要有效准入和当前权限。启动属于独立权限：交互授权不等于启动任意进程的权限。

**扩展放在哪里**

扩展使用带命名空间的键，其值为 `{version, required, value}`。Descriptor、Requested 和 Scope 的扩展分别承载支持情况、提议配置和已批准配置。基线要求冻结时，活动 Envelope 中的扩展配置必须与冻结的 Scope 值完全一致。动态观察应放在消息 content 中，而不是通过修改配置值传递。按继承的契约，数据平面外层 OperationRequest 的 extensions 保持为空；消息扩展放在 Envelope 中。

## 8. 授权、会话与撤销

**授权记录什么**

Grant 必须标明签发者、主体、适用游戏或实例、允许的操作、权限范围、过期条件及撤销关系。观察授权还绑定目录的 Schema 和含义定义摘要、视角、接收范围、频率/数据量限制、新鲜度与保留要求。行动授权绑定行动定义和约束。扩大权限的变化需要重新批准，不能只刷新能力声明。

**会话状态与有效期**

继承的 Session 状态为 `active` 或 `closed`，就绪状态另行表示。本文不以不兼容的新状态枚举替换这些字段。会话代次（Session generation）防止陈旧控制消息作用于更新的控制代次。租约过期防止已失联的参与方无限期保有活动控制权。仅在基线允许时，经过认证的新轮询才可以续租；重放旧请求或读取快照不得意外续租。

**权限变化后，停止不再获准的工作**

关闭会话会停止新工作并启动清理，但不会追溯抹除已提交效果。能力替换、成员替换和权限撤销必须与受影响的读取、排队行动和效果有序协调。它们必须使受影响的观察基线和缓存失效。已经失去权限的待处理工作不得继续。进行中的工作必须在可能时停止；已经提交的不可逆效果必须如实报告。交接和持久恢复是可选能力，需要遵守其规定的代次、所有权和恢复检查。

**每次受保护操作都要重新检查**

每次处理受保护操作时，包括读取快照和查询行动结果，负责校验的一方必须确认：

- 调用方及适用委托是否对应本次请求的资源、接收范围、主体、角色、会话和操作；
- 这些权限当前是否已过期或被撤销。

认证成功或此前已获授权的连接不得替代这些校验。

凭据转发或交换必须产生对下游接收方有效的权限；实现不得盲目将上游凭据传给无关接收方，也不得接受面向其他资源的令牌。这些要求不强制 OAuth、中心身份提供商或服务商白名单；已声明的本地信任机制可以满足相同的绑定及校验要求。

## 9. 观察配置规范候选方案

### 9.1 需求与定义

智能体可以声明必需的观察类别和可选偏好。如果游戏无法满足某项必需需求，必须在协商中明确说明，不得把缺失类别假装成已经可用。提出需求本身不会扩大 Grant。游戏可以拒绝交互，也可以在参与方同意后协商降级模式。

每个观察类别的定义必须说明以下内容：

- 如何识别和校验数据：稳定标识符、Schema 版本及摘要、语义定义摘要；
- 如何理解数据：单位、数据中的标识符、坐标和时间约定；
- 如何提供数据：视角策略、投递模式、新鲜度、速率和大小限制；
- 谁可以接收、可以保留多久：接收范围和保留要求。

Schema 必须定义校验行为，包括未知字段和大小边界。除非选定的方言/配置规范另有规定，JSON Schema 的 format 注解本身并不等于强制格式校验。

候选方案沿用现有 `game.context` 的 `content` 字段，不另建一套核心操作。各类信息分别放在以下位置：

| 信息 | 存放位置 |
| --- | --- |
| 支持哪些观察类别 | Descriptor 的扩展 |
| 希望获得哪些类别 | Requested 的扩展 |
| 双方确定采用的配置 | Scope 的扩展 |
| 持续变化的观察记录 | Context 的 content |

临时示例使用 `org.example.g2a-observations`；这是示例命名空间，不是已注册的官方标识符。本文不新增核心 subscribe 操作：由现有的上下文发布、事件和快照传输已协商的配置规范。选定的类别集合在重新协商前保持冻结。

**候选数据结构何时具有约束力**

任何机器契约细化都必须先明确映射到此 content 槽位、继承的操作信封及现有流/代次/修订身份，才能声称可互操作。ObservationCursor、ObservationEnvelope、TimelineCoordinate 和 ActionRequestEnvelope 等候选名称，本身不会注册新的核心对象或操作。其权威来源、精确类型、适用范围、引用关系及兼容规则须先按第 2 节确定；未被操作引用的 Schema 定义，不会约束该操作。

<a id="92-候选-content-模型"></a>

### 9.2 候选内容（`content`）模型

以下是说明性的 `Context.content` 片段，不是完整消息，也不表示现有 Schema 已经校验这些观察语义：

```json
{
  "profile": "observations-draft-1",
  "stream_id": "visible-world",
  "revision": 27,
  "world_epoch": "world-4",
  "visibility_epoch": "view-9",
  "perspective": "player-self",
  "schema_version": "1",
  "schema_digest": "declared-digest",
  "definition_digest": "declared-digest",
  "observed_at_ms": 1794560000000,
  "expires_at_ms": 1794560001000,
  "mode": "snapshot",
  "records": [{"id": "entity-17", "data": {"visible": true}}]
}
```

`declared-digest` 是占位值，不是有效的线上摘要。本示例中，两个时间戳仅示意相差一秒的 UTC Unix 纪元毫秒值；实际使用时，时钟域、不确定性和偏差假设必须按第 9.4 节由已协商配置规范或外层上下文提供。这里省略了实例/会话绑定、观察类别定义及授权上下文，并非免除这些要求。本片段不是符合性测试向量，未补齐相关定义及有效摘要前，不得直接作为生产载荷使用。

`mode` 有三种取值：

- `snapshot`：该信息流的完整授权视图。
- `delta`：相对于指定版本的增量变化，另含 `base_revision`，并可以携带 `records` 和 `remove_ids`。
- `retract`：撤回指定范围的信息。具体移除范围按配置规范的精确 Schema 表示。

记录在其声明的代次内具有稳定 ID。修订号在每个流代次中严格递增，但不必连续。仅有数值缺口不能证明数据丢失。只有当 delta 的 base_revision 与使用方当前修订号精确匹配，并且其身份、Schema、世界、可见性和视角上下文都匹配时，该 delta 才可应用。

**如何识别同一份观察**

观察引用必须保留完整的适用上下文：实例代次、信息流、世界代次、可见性代次及修订号。视角及适用的 Schema/语义定义身份也必须直接携带，或通过不可变的流/配置规范绑定无歧义地确定。不能只比较修订号大小；来自另一上下文的较大数值，不代表较新的有效观察。

若已协商配置规范使用紧凑游标，必须能从该游标无歧义地确定上述身份及精确的 delta 基线，不能再建立一套与之并行的排序规则。游戏 tick 或权威时间戳可以提供时间背景，但不能代替观察身份；使用时必须按第 9.4 节声明时钟域、单位、重置行为及其与观察的关系。

### 9.3 基线与可见性变化

`snapshot` 一次性替换一个信息流的完整授权视图，而不是所有信息流；不能只应用其中一部分。它不得与已陈旧且在快照中被省略的记录合并。delta 只能原子应用于其精确基线。身份和内容相同的重复更新是幂等的；同一修订号出现冲突内容属于协议违规。旧更新不能使新视图回退。

已声明的状态采样策略可以合并中间的当前状态样本，但必须保留适用的基线规则：丢弃后续增量所依赖的增量时，需要新的有效基线，而不能假称后续增量可直接应用。收到最新状态不证明获得了完整历史。

**何时需要重新建立基线**

世界重置、授权变化、视角变化或接收范围/可见性变化，会使受影响的基线失效。权威方必须签发适当的新 world_epoch 或 visibility_epoch，并在恢复 delta 前发送新的授权快照。使用方一旦获知失效，必须立即废止旧基线，即使替换数据尚未到达。此前可见的数据不能仅因为下一份快照延迟就继续可用。

**撤回信息后，旧消息不能让它重新生效**

撤回必须与更新有序协调、经过认证、保持幂等，并限定于受影响的流或记录。必须保留用于拒绝旧数据的失效记录，或采用等效的隔离机制，防止延迟到达或重放的旧更新重新引入已撤回信息。从当前视图移除不一定等于从全部历史存储删除；保留规则和隐私规则分别约束这些存储。

**看不见不等于已销毁**

对于实体出现或移除，配置规范必须区分进入视野、观察到的新建、失去可见性，以及获授权确认的销毁。转换元数据应关联受影响记录或明确的记录集合，不得隐式套用于混合更新的全部记录。离开视野表示实体后续状态未知，而不是已销毁。接收方不得仅因记录被省略就推断生成或销毁；原因未知或不可披露时，权威方必须使用明确定义的未知/不可用转换，而不是编造原因或泄露隐藏状态。

### 9.4 新鲜度、恢复与信息边界

**判断信息是否仍然有效**

过期观察必须标为不可用/陈旧，不得作为当前信息呈现。

时钟偏差假设必须由绑定/配置规范声明。使用方必须区分未知、未观察到、不可用、明确不存在和已知为空。

拒绝响应不得通过载荷或详细错误泄露隐藏实体是否存在、其位置、私人目标或其他未经授权的事实。这是传输规则，不是完美抵御时序侧信道或无法推断事实的承诺。

接收时间不是生成时间，不得混用。新鲜度元数据必须标明时间戳所用的时钟域/纪元、单位及适用的不确定性。来自未经校准的不同时钟域的时间戳，不得直接相减，用来声称数据已过去多久或判断先后顺序。

乱序到达的旧数据不得被当成较新基线的数据；读档或进入新代次后的数据，也不得继承旧代次序列的效力。

**恢复当前状态，而非重放旧增量**

本配置规范下的会话恢复快照必须按信息流提供已经整理好的、获准披露的当前状态，而不是任意重放旧的上下文 `delta`。它必须在快照切点建立完整有效的基线，并保留权威流身份与修订号。读取快照本身不要求产生新修订号；如签发新的身份或修订号，必须遵循配置规范的代次和修订规则。此前已知的流若未出现在当前授权快照中，就变为不可用。事件序列缺口可能源于接收范围过滤，不得被当作观察修订号缺口。

恢复快照可以将先前以增量投递的状态整理为完整状态。在同一观察身份及修订号下，若两种表示描述的获授权状态完全相同，表示方式不同不构成内容冲突。配置规范必须定义这种等价关系及后续适用的增量基线；整理状态不得在既有修订号下改变状态，也不得使陈旧增量重新变得可用。

**主动探查也可能是一项行动**

会改变世界、消耗游戏资源或产生新游戏效果的主动感知，例如调用检查技能或揭示此前隐藏的地图信息，属于 Action，其效果及产生的观察需要独立授权。不产生此类效果、只读取已获授权信息的行为，属于第 9.6 节的信息查询。智能体不得把观察需求转换为特权检查 API。

**区分事件、观察和行动**

事件身份与来源、排序位置、观察修订号及行动身份承担不同职责，不得混淆。适用的事件绑定必须定义稳定身份与经认证来源、事件类型、Schema 版本和关联上下文；不得仅凭时间戳确定顺序或授权。事件已投递不表示智能体已经观察到效果，也不表示关联行动成功。这些封装要求不要求存储或重放第 14.2 节所述断线期间的全部游戏过程。

### 9.5 结构化基础与多模态智能体

本协议支持结构化游戏信息以及可选的画面/声音观察。结构化信息是基础，而不是媒体的可选替代品。获准接入并提供游戏协助的智能体必须能够理解适用的基础结构化游戏信息，并在获授权角色内据此作出游戏决策。仅能聊天或查看截图、但不能使用已协商结构化基础的智能体，不满足游戏智能体的最低能力要求。此要求针对作出游戏决策的智能体，不针对仅提供网络传输的设施。

**高级能力建立在结构化基础之上**

高级智能体建立在该基础之上，并进一步能够理解游戏画面和游戏声音。媒体能力不能替代结构化基础，也不授予原始桌面、麦克风或隐藏游戏信息的访问权。

游戏必须声明提供的结构化类别及媒体能力；智能体必须如实声明支持的 Schema 与媒体格式。实际媒体传递仍为可选，需要兼容的已协商能力，以及适用的授权、视角、接收范围和资源约束。没有媒体的游戏仍可支持基础结构化交互，包括与高级智能体进行该交互。

**统一通用含义，允许游戏扩展**

结构化信息采用“通用定义加游戏扩展”的方式：G2A 为常见游戏概念定义统一格式，游戏开发者可以为特殊玩法声明扩展。通用定义必须保留标准语义；扩展必须具备命名空间、版本、Schema 描述，并按适用规则明确声明和协商，不能静默重定义通用字段。

通用字段统一的是含义和格式，而不是要求所有游戏都提供。

对于不适用于自身玩法，或不允许向请求角色披露的字段，游戏不必提供。游戏不得为了满足通用 Schema 而编造缺失数据、填入具有误导性的默认值或泄露受保护信息。必须区分不可用或不支持的值与已知为空或为假的值，同时遵守隐藏信息的错误披露边界。

特定交互必需的类别与字段、可选数据及不支持的特殊机制必须由适用配置规范及协商权限范围说明。若某项合法不可提供的信息是拟议交互的必需条件，参与方必须拒绝该交互，或明确约定双方支持的范围，而不是编造数据或绕过披露权限。

**如何验证智能体具备所声明的能力**

适用的游戏交互配置规范必须定义基础结构化类别与 Schema；不能假设一份适用于所有游戏的事实清单。准入必须检查智能体能否理解必需类别，并据此完成预期决策。不满足必需能力时，必须拒绝，或明确约定双方支持的范围，而不是虚假宣称能力。

符合性证据必须证明基于结构化输入的决策行为，以及在声明高级能力时对画面和声音两者的理解能力。仅有目录标记、载荷传输、Schema 解析或模型名称，均不能证明这些行为能力。精确媒体编码、能力标识和验收向量仍待标准化；本草案不代表现有 SDK 或任何模型已经通过符合性认证。

**由玩家选择是否启用画面和声音**

对于高级智能体，由玩家决定是否启用游戏画面与游戏声音感知。玩家可以关闭这些媒体输入，只使用结构化游戏信息。具备高级能力不代表必须消耗媒体。

启用媒体还需要游戏实际声明支持，并且当前获授权；玩家偏好不能强求未支持或未声明的媒体流。实现必须区分支持、请求及实际启用的媒体能力，停止新近关闭的媒体投递/处理，并如实报告不支持的请求。这些控制针对游戏环境感知，不是第 15.5 节的玩家伴玩语音交流；关闭游戏声音本身不等于关闭语音沟通。

### 9.6 游戏主动推送与智能体主动查询

G2A 同时支持游戏主动推送获准观察，以及智能体主动查询游戏信息。游戏开发者声明游戏提供哪些机制、适用哪些类别及其限制。游戏可以支持推送、查询或两者；本规范不要求每个游戏同时实现两种方式。智能体必须发现并协商可用机制，不能假定任何一种机制必然存在。

推送必须遵守已协商的权限范围、视角、接收范围、新鲜度和频率限制。

查询是信息请求，不是读取许可：游戏必须依据当前权限校验调用方、请求类别和参数，只返回允许披露的信息，并如实表达可用性与新鲜度。查询能力不得成为获取隐藏状态或绕过数据撤回规则的通道。

纯信息查询必须与改变世界、消耗游戏资源或产生新游戏效果的主动感知区分；后者仍属于第 9.4 节的获授权 Action。两种机制均受第 14.1 节离线边界及约定资源限制约束。

**状态可以合并，事件不能随意丢弃**

采用推送的配置规范必须区分可替换状态更新与离散事件。合并可以保留声明的实体/属性范围内最新的可替换值，但必须按第 9.3 节保持完整有效的当前状态或可依次应用的 `delta` 更新链，包括移除及失效屏障。表示瞬时事实的事件，不能仅因已有较新状态就被静默覆盖。

在声明的队列与保留上限内，事件投递必须保留所声明的排序及重复处理语义。发生溢出时，发送方必须按第 12 节报告适用的缺口、重同步要求或失败。

新基线恢复的是当前状态，不是已丢失的瞬时事件，不得将其描述为完整历史回放。这不授权违反第 14.2 节而保留断线期间游戏过程供之后重放。

本节规定推送/查询语义，不新增未经注册的核心操作。现有上下文发布及事件投递可承载推送数据；声称可互操作前，适用的已协商配置规范必须声明精确的查询能力定义、Schema 和操作映射。符合性测试必须覆盖仅推送、仅查询及双方式声明，不支持的机制、被拒查询、过期结果，以及权限范围/频率限制的执行。

<a id="section-10"></a>

## 10. 行动与效果语义

游戏角色能力是游戏提供给角色的可用行为，例如移动、攻击和交互。游戏智能体只能在游戏规则与授权允许的范围内调用；它与协议声明支持聊天或观察等功能的“能力”不是同一层概念。

游戏必须按适用的游戏角色声明能力，包括行动定义标识符、参数 Schema、结果 Schema 和执行限制。Agent 请求已声明的行动；游戏检查经认证的角色与权限、当前游戏状态和前置条件，校验参数，并通过其受信执行器自行执行或拒绝请求。游戏必须返回定义的结果和真实的效果状态。角色声明或 Agent 提议本身不是执行权限。

行动定义标识符标识一种可用行为，不标识某一次调用。在继承契约中，`ActionRequest.payload.action` 选择该定义，`ActionRequest.id` 标识本次请求的行动，外层 `OperationRequest.request_id` 则关联传输操作。这些标识符不得相互替代。

**行动可以是高层指令，也可以是基础操作**

游戏开发者决定所提供能力的粒度。游戏可以提供“攻击目标”等高级语义行动、“移动、瞄准、按键”等基础操作，或两者的组合。Agent 可以组合其角色实际已声明且已获授权的能力来实现目标；不得假定游戏提供了未声明的高级行动或基础输入操作。规范不要求每个游戏都必须提供其中某一层级。基础能力仍然是具有明确参数、结果和执行限制的类型化、有权限范围的游戏行动，不是任意操作系统输入或无限制控制权限。组合多个行动不会扩大权限，也不意味着整个序列具有原子执行保证。

**每种行动需要说明什么**

每个行动定义必须规定类型化输入、目标语义、前置条件、授权范围、成本、确认要求、取消行为、效果和结果 Schema。游戏应提供有语义的操作，而不是不受限制的脚本求值。游戏自身负责按当前玩法规则检查行动，不受智能体对其规划的信心程度影响；G2A 不要求另一参与方重复校验游戏内部的判定。

副作用、可逆性与幂等性必须按适用情况作为独立属性声明；不得仅从自然语言描述、行动动词或 HTTP 方法推断这些属性。安全/只读声明不等于授权，幂等声明不得覆盖第 11 节对于未决结果默认不重发的规则。

**从请求到实际生效**

在继承基线中，一次新调用的成功处理路径如下：

1. 预选行动标识符及提议参数；需要确认时，在 `action.request` 被受理前取得绑定该提议的确认。
2. 校验 `action.request`、当前权限及精确提议。需要确认时，受理过程必须先校验并原子消费该确认，之后才能创建 `pending` 工作。
3. 由获授权的执行器领取符合条件的工作。
4. 在效果边界重新检查适用权限及前置条件，只产生获准的游戏效果。
5. 记录结果及已知效果；无法确定结果时，明确保留不确定性。

并非所有行动都要求确认。`action.confirm` 不创建行动记录、不领取执行任务，也不产生游戏效果；重复的已受理请求按既有去重规则处理，不再次消费确认。领取任务是为了避免多个执行器同时处理同一项工作，不代表效果真正生效时仍然拥有权限。拒绝、取消及恢复可以按下文状态机结束或中断这条成功路径。

最终授权检查必须与权限撤销和游戏效果的产生协调处理，避免检查通过后权限已被撤销、行动却仍然生效。实现必须采用原子游戏操作、事务日志或等效机制完成上述协调；这里的“原子”表示相关步骤作为不可分割的整体完成。如果无法保证原子性，实现必须说明哪些步骤之间仍需事后核对，并且不得声称提供实际无法保证的“恰好一次”效果。

继承的状态/效果组合如下：

| 状态 | 允许的效果状态 | 含义 |
| --- | --- | --- |
| pending | none | 尚未执行 |
| executing | none, partial, committed, undetermined | 工作进行中；效果信息可能继续推进 |
| succeeded | committed | 已提交定义中的成功效果 |
| failed | none, partial | 失败，并明确记录已产生的效果 |
| cancelled | none, partial | 已完成取消，但可能已经产生部分效果 |
| unknown | undetermined | 尚未建立权威结果 |

`pending` 可以进入执行，也可以不执行而直接结算。`executing` 可以结算为成功、失败、取消或未知。已经确定的最终结果不得被静默重写。

未知结果只能按基线结算规则，依据权威证据进行核对。

取消是停止请求，不是回滚保证。取消与已提交效果发生竞争时，必须报告真实的已提交情况，而不能伪造取消结果。

提交后的网络超时属于投递/结果未知的情形。调用方必须查询或核对原始行动/操作标识，而不是盲目提交一个新的效果。

确认必须绑定精确的提议行动、主体、约束、过期条件和相关代次；对某个行动的确认不授权修改后的行动。

**支持某种行动，不等于现在可以执行。** 能力定义与当前合法行动必须分开。游戏必须提供机器可读方式，在获授权视图内确定当前行动资格，包括适用的回合/阶段、目标或参数约束、资源要求与冷却状态。可以提供限定范围的合法行动列表、为候选行动标明是否可选的行动掩码、声明式约束，或经过授权的查询。行动取值连续或数量过大时，无需列出所有可能行动。

可用性必须标识其适用的游戏状态上下文或修订号，不得泄露隐藏目标或前置条件。声明支持某个行动，或此前允许过该行动，并不保证之后仍能执行：执行端必须在游戏效果实际生效的边界重新校验当前资格与权限，失效时返回结构化拒绝或更新后的获授权约束。智能体可以据此调整计划，但不得臆造能力或绕过确认。

如提供可行性、成功概率或成本估计，必须标明来源、适用状态及估计性质。这些是建议性证据，不是执行保证，也不能替代执行端的当前校验。

**执行前检查决策所依据的信息**

智能体推理与网络传输可能使决策依据落后于当前世界。行动请求应支持携带获授权的观察基线引用，以及类型化的目标状态前置条件。`based_on_observation_id` 或 `expected_world_revision` 仅是候选字段名；精确编码及到现有操作的映射须按第 2、9.1、20 节冻结，不得视为已有核心字段。

对于依赖观察的行动，适用配置规范必须明确：

- 请求如何关联决策所依据的获授权观察上下文；
- 哪些信息新鲜度要求或游戏状态前置条件是必需的。

这种关联必须保留第 9 节的信息流、代次和修订含义，不得把时间戳当作基线。

若提供数据年龄上限，必须定义其单位和权威裁定方式，包括时间未校准或不可用时如何处理。前置条件必须有明确类型，使用已声明的运算规则和获准使用的输入值；不能提交可执行代码，也不能借条件检查绕过权限查询隐藏状态。

必需上下文失效、声明为必需的数据年龄上限不满足，或必需前置条件为假或无法证实时，执行端必须在产生新效果前拒绝受影响行动。必须通过适用的结构化错误/结果契约区分陈旧上下文、游戏前置条件失败及证据不可用，而不泄露隐藏事实。

例如，治疗目标已死亡、阵营改变或不再满足所声明的治疗条件时，游戏必须按适用条件拒绝，而不是仅因行动标识尚未执行就继续。游戏应随拒绝提供获准披露的最新摘要，或通过已协商机制更新观察；增量仍须满足精确基线要求，不支持推送时可以引导获授权查询。智能体收到状态过期或目标变化的拒绝后，不得按原参数机械重试，必须结合最新获授权观察重新评估意图。重新决策不免除第 11 节对可能已产生效果的原行动进行核对的义务。

通过这些检查不保证未来游戏状态不变，也不替代效果实际生效前、与权限撤销协调进行的授权检查。如果效果可能已发生，结果则必须按第 10、11、16 节保留真实的部分效果或不确定性。

## 11. 幂等性、投递与恢复

绑定携带 request_id，用于传输操作的恢复。基线还分别定义了消息、行动、提议等业务对象的标识。实现必须使用各操作规定的标识，并按该操作规定的范围计算摘要；request_id 不是行动去重的通用替代品。

对于规定去重的操作族，相同标识重复出现且请求规范化内容相同时，必须遵循该族的回执或可恢复状态规则。复用该标识却提供冲突内容，必须失败，且不应用新内容。继承的[重试族契约](../protocol/OPERATION_CONTRACT.md)按操作区分不同恢复规则；传输请求标识符不意味着所有操作族都使用同一种回执账本。

普通 `read` 操作每次调用必须重新检查授权，可以返回较新的当前状态，不承诺冻结响应，也不续租。相反，`session.events` 等会续租的操作虽然也返回数据，仍须遵守其声明的 nonce/重放规则。

回执必须保留至声明的重试期限。负责处理请求的一方不得把已过期的去重记录静默转化为重复执行非幂等效果的许可。在过期或故障后无法证明结果时，必须报告明确的核对/未知状态。在披露恢复查询结果之前，必须检查会话代次、主体、实例代次及权限绑定。

事件在所定义的接收方流内有序。使用方对每个事件应用一次，容忍重复投递，并且不能仅因会话序号不连续就推断数据丢失，因为这可能反映接收范围过滤。过期或无效游标要求通过获授权快照恢复。跨进程持久恢复是可选的；对于所支持的操作，安全重试和如实表达不确定性则不是可选的。

持久恢复与恢复查询必须遵守第 14.1 节：保留状态或查询回执，不授权离线游戏活动或重放此前延后的游戏效果。

<a id="111-动作编号与断线后的状态查询"></a>

### 11.1 行动标识符与断线后的状态查询

每个智能体游戏行动必须具有可识别的行动标识符，并绑定经认证来源及适用的游戏/会话上下文。断线或响应不确定后，调用方必须先按原行动标识符查询，再决定后续行动。查询为只读操作，必须实施权限校验；知道编号不构成访问权限。绑定必须区分并关联传输请求编号与业务行动标识符，不强制特定日志保管方。

可查询的持久结果记录必须区分收到/转发/接受请求与实际执行及效果。记录可以由游戏或平台保存；G2A 不得要求使用唯一平台。

执行端应持久保存去重身份与结果，配置规范必须声明保留期限及过期处理。仅有平台回执不能证明游戏效果恰好执行一次。

经授权查询必须报告核心状态/效果矩阵，包括部分效果和取消，或明确的不确定性。已知失败可能包含部分效果；记录缺失、过期或无法关联不得被解释为失败或未执行。

**查不到结果时，默认不重发**

查询未能确定原结果时，调用方必须默认不再次执行或自动重发该行动。这约束的是后续行为，不表示原行动未曾执行。未知记录或重试提示均不授予重放权限；不得通过更换行动标识符绕过去重或此不确定性。记录和编号并不保证数据永久保留，也不保证游戏效果恰好执行一次。实现必须如实报告未决结果，而不要求玩家处理每次传输故障。

**之后可以独立决定发起新行动**

玩家或智能体之后可以根据当前状态、权限和玩家自主等级，独立决定发起相似的新行动。这不是自动重试：必须考虑原行动可能已产生的效果，并继续满足购买、高价值物品和不可逆行动策略。除非权威证据完成核对，原记录仍保持未知。新的决策不得将其改写为成功或失败。

## 12. 错误模型、时间与限制

适用时，错误必须区分输入格式错误、不支持的版本/功能、未认证调用方、未经授权的权限范围、陈旧代次、状态冲突、过期、资源限制、暂时不可用和结果不确定。冻结绑定必须为这些类别分配精确且稳定的错误码；本审阅草案不会静默向现有机器契约加入未注册错误码。

| 错误类别 | 调用方行为 |
| --- | --- |
| 无效请求/Schema | 修正输入；不原样重复 |
| 不支持的版本/必需扩展 | 协商受支持配置或停止 |
| 认证/授权 | 获取适当权限；不探测隐藏资源 |
| 陈旧代次/基线/游标 | 继续前恢复当前获授权状态 |
| 标识或状态冲突 | 核对原始请求；不另造效果标识 |
| 速率/大小/背压 | 遵守声明的重试延迟和限制 |
| 临时传输故障 | 查询原结果；仅按操作恢复契约允许的方式重试，不自动重发结果未决的游戏行动 |
| 结果未知 | 查询/核对；绝不把超时等同于无效果 |

**错误信息也受访问权限限制**

错误不得暴露隐藏对象是否存在、私人游戏状态、令牌、堆栈跟踪或其他参与方的内容。错误详情本身也是一次需要授权的披露。

实现必须限制消息字节数、嵌套深度、集合大小、队列深度、待处理行动数、轮询速率和保留期限。超过限制不得产生未被报告的部分效果。

实现必须明确时钟、时间单位、允许的最大偏差，以及由谁判定过期。请求方的时间戳本身不能延长签发方授予的租约。

本地超时测量应使用单调时钟，即用于衡量持续时间、不随系统日期调整而回拨的时钟。墙钟调整（系统日期和时间的调整）不得静默延长租约或授权过期工作。本地单调时间戳不是跨机器共享时钟。

队列限制和背压规则（处理方负载过高时对发送方施加的限制）必须独立于自主等级和 token 预算执行。溢出必须按情况声明缺口、重新同步要求或明确失败。

行动回执、授权撤销和可见性撤回不得像普通可替换遥测一样被静默丢弃。降采样不得延迟执行已知停止/撤权条件，也不得把过时观察呈现为实时。这不要求记录或重放断线期间的游戏历史。

**程序依据错误码处理，不解析解释文字**

错误必须提供稳定的机器可读分类及关联本次错误或请求的标识，并将安全的人类可读说明与之分开。适用绑定必须定义传输状态、协议拒绝和游戏执行/效果结果之间的映射，不得混淆。接收方不得依靠解析说明文字来判断行动是否生效或重试是否安全。

重试/期限提示必须说明适用范围，不得覆盖第 11 节的未知结果规则。可选诊断详情不得暴露受保护状态或凭据；明确拒绝可以解释适用规则，而不披露触发该规则的隐藏事实。

<a id="section-13"></a>

## 13. 游戏角色与接入要求

### 13.1 可组合的游戏角色与信息视角

游戏伴玩是游戏世界中陪伴玩家的角色；游戏智能体是为角色感知和决策的 AI 软件，两者不是同一实体。游戏智能体可以在本地或远端运行，也可以扮演获授权的 NPC，而不只用于伴玩。文中“伴玩决定或请求行动”等简写，指扮演该伴玩的游戏智能体作出决策，实际游戏效果仍由游戏判定。

这里需要分开理解两件事：

- **角色绑定：** 智能体当前扮演哪个游戏角色，例如某位玩家的伴玩或一个 NPC。它不是通信、转发等软件职责。
- **信息视角：** 该角色获准使用哪些信息，例如伴玩的玩家视角、NPC 自己掌握的知识，或引导者使用的教程知识。

同一个智能体实现可以支持伴玩、NPC（包括 Boss）及引导者视角。可组合的是这些信息视角，不是任意同时启用多个游戏角色；实现也不必被划为互斥的“伴玩软件”或“NPC 软件”。游戏必须声明适用的角色绑定与信息视角，并继续遵守第 13.2 节的模式与活动角色绑定限制。

每条观察和行动必须继续关联其获授权的角色、主体、接收范围和权限范围；组合角色不得在没有明确授权时合并权限，也不得通过另一角色泄露仅某个角色有权访问的信息。

NPC 或 Boss 可以获得游戏授权、但玩家不可见的内部知识。引导者可以获得游戏授权的进度或教程知识。玩家伴玩也可以持有玩家授权的当前游戏之外的记忆。角色名称本身不授予全知能力、透露知识的许可或行动权。切换或组合角色需要明确且适用的授权；影响观察视角的变化须按第 9 节使原基线失效。

### 13.2 活动角色与数量限制

同一局采用玩家伴玩模式或独立 AI NPC/敌人模式；两种模式不得在同一局同时活动。在伴玩模式下，每位玩家可以拥有一个活动伴玩，多人游戏也一样。多位玩家的伴玩可以同时存在，并在各自授权及游戏声明的能力范围内相互互动。这是每位玩家最多一个伴玩，不是整局多人游戏最多一个伴玩。在独立 NPC/敌人模式下，整局最多允许一个活动的独立 AI NPC/敌人，包括 Boss。调整这些数量限制需要修订协议，不能通过实现自行放宽。

游戏必须将每个伴玩绑定到经认证的所属玩家、角色、视角和权限范围。伴玩间互动必须保留来源身份、接收范围及各所属玩家的权限；一个伴玩的观察、记忆或行动权限不得在没有明确授权时共享给另一个伴玩。另一名玩家在线或给予同意，并不授权控制已离开玩家的伴玩。第 14.1、15、16.3 节分别约束在线状态、信息披露及多人互动。

**如何执行数量限制。**

游戏必须一致地识别本局边界，并在准入、替换、交接及恢复时（包括并发请求）执行两种模式不能同时活动的规则以及适用的每玩家或整局数量上限。新增连接、智能体进程或组合角色声明不得绕过这些约束。切换模式前，必须废止或隔离旧模式的全部活动 G2A 游戏角色绑定；替换伴玩或 NPC 前，必须废止或隔离其原活动绑定。普通非 G2A NPC 与游戏模拟不计入这些角色限制，也不因此停止。

限制对象是活动游戏角色，而不是已保留记忆或基础设施进程数量。

**必须提供槽位，但玩家可以不用。**

适用游戏模式由游戏开发者固定；智能体或玩家偏好不得覆盖开发者确定的模式。接入游戏必须至少提供玩家伴玩槽位作为最低角色接入能力，也可以额外提供独立 AI NPC/敌人槽位。提供槽位声明的是支持的接入能力，不是角色已活动，也不是必须同时启用两者：支持可选 NPC 不得被解释为允许同局伴玩与 NPC 模式共存。游戏必须在声明中区分支持的槽位、开发者确定的模式及当前活动绑定，并执行上述限制。

玩家可以将必需提供的伴玩槽位留空，不启用伴玩进行游戏。游戏必须在没有伴玩时仍可正常游玩，不得仅因提供了这一接入槽位就要求玩家启用伴玩。必须支持不等于玩家必须使用。加入、召唤与收起行为遵守第 14.2 节。

玩家伴玩是本规范的主要接入对象。独立 AI NPC/敌人接入是次要的可选能力；支持伴玩不要求实现 AI NPC。对于独立 AI NPC，第 14.1 节要求的在线关联是其持有用户；其他玩家在场不能替代该持有用户在线。

## 14. 在线状态与伴玩生命周期

先区分“谁停止了什么”。玩家离线、AI 服务中断、玩家收起伴玩和玩家叫停任务，不能作为同一种情况处理：

| 情况 | 主要处理规则 |
| --- | --- |
| 玩家离开游戏或被判定离线 | 停止关联的 G2A 游戏活动；再次进入后旧任务仍等待新指令。见第 14.1 节。 |
| 玩家仍在线，但 AI 服务中断 | 游戏继续；采用开发者声明的本地处理方式。服务恢复后，伴玩是否继续由玩家决定。见第 14.2 节。 |
| 玩家收起伴玩 | 停止观察及自主游戏行动，但不因收起而删除记忆。见第 14.2 节。 |
| 玩家叫停某项任务 | 停止该范围内后续的自主行动；已发出的行动按游戏规则处理。见第 16.1 节。 |

下文分别规定停止条件、在途结果及恢复要求。停止后续决策，不等于撤销已经发生的游戏效果。

### 14.1 玩家离线后停止游戏活动

G2A 不得提供关联玩家离开或被判定离线后，智能体仍继续在游戏世界中活动的模式。这是一项强制限制，不是默认关闭、但可以自行打开的选项。开发者建议、玩家偏好、持续任务授权、后台工作进程或可选扩展，都不得启用离线继续活动。若要允许这种模式，需要通过明确的标准修订过程另行规定。第 10、16 节规定的在线自主协助仍然支持。

**何时认定玩家离线。**

负责最终判定的游戏端必须明确经认证的玩家与会话关联、在线状态依据、明确退出信号、设有明确上限的检测超时，以及停止执行的责任归属；若其他组件参与在线检测或停止控制，必须按各自职责共同落实这些规则。玩家明确离开、会话关闭，或适用的玩家在线/控制租约过期，必须终止受影响范围内开展新自主工作的资格。端点检测到连接丢失时必须停止安排新的游戏活动；负责最终判定的游戏端必须最迟在声明的检测/租约截止时间隔离受影响的控制权。仅有智能体心跳不得证明玩家仍在场，也不得维持离线控制。

静默网络故障无法被瞬时检测；实现必须披露检测延迟，在尚未确认停止措施生效时不得声称已验证停止。这里的在线指参与关联的游戏会话，而非仅在平台保持账号登录；不要求玩家持续操作键盘。

**停止什么，保留什么。**

一旦获知停止条件已满足，或已实施停止措施，受影响的智能体必须停止用于继续游戏活动的环境监测与规划/推理循环，不得安排新的攻击、移动、对话、交易、购买或其他世界行动。负责最终判定的游戏端必须阻止因停止而不再获准的后续行动，取消尚未向游戏提交的排队工作，并停止继续产生新行动的委托规划或执行循环。已经发给游戏的技能或攻击按游戏规则自然完成，不要求仅因伴玩停止就将其撤回；适用的独立游戏权限和取消规则仍然有效。将任务委托给游戏执行器不得绕过此边界。

停止生效前已提交的效果、无法逆转的在途后果和未知结果，必须如实核对，不能自动回滚。这不意味着冻结游戏世界、撤回已经射出的投射物，或停止普通游戏模拟及非 G2A NPC 逻辑。

**多人游戏与 NPC。**

多人游戏中，该规则分别适用于受影响的经认证玩家关联及其限定范围内的 G2A 活动；一名玩家离开不代表所有玩家离线。其他在线玩家独立获授权的会话可以继续。独立 NPC 或受游戏管理的引导者必须以其持有用户作为必需的玩家在线关联，不得借用另一玩家的在线状态或静默重绑权限来维持缺席持有用户的角色活动。G2A 世界活动不得在其符合条件的关联玩家不在线时继续。

持有用户（本场景为房主）离开或被判定离线时，AI NPC 必须在获知该情况后立即按第 14.1 节停止活动，即使其他玩家仍然在线。本规范不提供替缺席持有用户继续运行该 NPC 的机制。其他玩家在场、房主变更或计费转移，不得静默维持该 NPC 活动。排队与在途效果仍须如实按停止/取消规则核对；检测延迟不是离线继续活动模式。

保留获准保存的记忆、回执和恢复状态，不等于主动游戏活动。范围和耗时受限的非游戏性取消、结果结算、核对及持久化工作可以完成，但不能授权进一步的世界行动。服务必须停止提交新的游戏活动模型请求，并在支持时请求取消在途模型工作。本要求旨在防止离线后持续消耗 token；由于检测、在途请求和服务商取消/计费边界不同，协议无法保证断开连接后 token 或费用立即归零。

实现必须披露这些限制，并报告实际用量或尚不确定的用量，而不是承诺即时零消耗。

**重新连接不等于恢复旧任务。**

重连后，必须先确认玩家当前在线、准入/授权仍有效、控制代次正确，并取得获准访问的新鲜状态，才能恢复游戏活动。持久恢复保存的是符合条件的状态，不是离线行动许可：不得静默复活已关闭会话、重放离线行动积压，或继续陈旧计划。玩家退出游戏后，下次进入时旧任务必须保持停止，即使此前已获批准。伴玩必须等待玩家重新下达指令，才能再次开始该任务。重新加入伴玩槽位或恢复状态，不等于恢复旧任务的新指令；仍须满足当前准入及游戏权限。

智能体进程间交接不能免除这些要求。精确的在线状态字段、超时界限、停止回执和恢复编码仍需在适用契约中冻结；本节新增的是语义义务，而非新的核心状态或操作名。

### 14.2 伴玩加入、收起与服务中断

在伴玩模式下，玩家必须能够在游戏过程中随时召唤或收起伴玩。进入游戏时，加入方式遵从玩家自身配置：自动加入，或弹窗询问是否加入。两种配置都必须允许游戏过程中手动唤起。自动加入使用玩家已配置的选择及有效准入，不得绕过必需授权、开发者固定的游戏模式或每玩家伴玩数量限制。拒绝入局提示或以空槽位开始游戏，不得取消手动唤起选项。游戏必须如实报告切换状态及在途行动结果，不能暗示画面上消失就会回滚已提交效果。

收起后，伴玩必须停止观察游戏及自主游戏行动。收起本身不得删除已存记忆；保留和隐私策略仍然适用。服务必须停止提交新的游戏监测/规划请求，并按声明的停止与取消语义处理排队或在途工作。收起不退回已经消耗的 token，也不保证无关或已在执行的外部服务剩余费用归零。玩家离线行为仍由第 14.1 节规定。

入局时伴玩服务不可用，游戏必须允许玩家不带伴玩继续游玩，不得因此阻止进入游戏。服务恢复可用后，伴玩可以依据玩家配置的加入选择与有效准入接入。服务恢复本身不恢复第 14.1 节因退出游戏而停止的旧任务。

**玩家仍在线，但 AI 服务中断。**

玩家仍在游戏中但伴玩 AI 服务断线或不可用时，游戏必须继续运行，驱动伴玩的游戏智能体必须暂停观察、推理和自主行动发送。开发者必须明确声明伴玩角色保持静止，还是由本地基础游戏行为接管。这些本地行为必须标明由游戏控制，而非智能体仍在持续智能决策，并且必须遵守游戏规则与当前权限。游戏必须区分服务中断与玩家离开；玩家离线仍适用第 14.1 节。

中断后不得发送尚未提交的智能体行动；已发出行动及未知结果按第 11、16.1 节处理，不自动撤回。

恢复时只向伴玩提供当前获授权的游戏状态，不提供断线过程的记录或回放。游戏不得为之后补录伴玩观察或记忆而记录、重建该断线过程。这不禁止普通游戏存档，或核对先前获授权游戏效果所必需的行动凭据；不得用这些记录在重连后补发断线期间的游戏观察。采用本地接管时，恢复伴玩行动仍需遵守下文关于玩家选择继续的要求。

**服务恢复后的处理。**

AI 服务重连后，由玩家决定伴玩是否继续。重连本身不得自动恢复伴玩行动、重放排队游戏工作或复活旧计划。继续前，实现必须取得玩家继续的决定，重新验证当前权限与控制代次，刷新获授权状态，并核对未确定结果。入局自动加入偏好不能绕过这次中断后的决定。玩家未选择继续时，伴玩行动保持暂停，游戏仍继续运行。

对于独立 AI NPC/敌人（包括 Boss），服务不可用时的行为由开发者根据玩法决定，可以暂停、由游戏脚本接管，或采用其他声明的处理策略。游戏必须声明适用的故障处理与恢复行为，并区分脚本驱动和智能体驱动的效果。不得自动将伴玩恢复时的玩家继续决定套用于 NPC 恢复。故障处理不得授予不可用的 AI 能力、绕过当前权限，或把脚本决策说成 AI 决策；普通脚本接管不授权第 14.1 节禁止的离线 G2A 活动。

开发者必须为实现确定断线接管策略，但 G2A 不要求向玩家专门披露该策略，也不要求让玩家在静止与本地基础行为之间选择。这与既有的重连后由玩家决定伴玩是否继续是不同事项。

## 15. 对话、信息使用与伴玩记忆

本节分别处理三件事：信息能否被保存或交给另一方、玩家希望伴玩怎样使用记忆，以及记忆如何修改和迁移。前者涉及可执行的数据权限；剧透、话题和保密风格等则可能属于软性的对话偏好，不能混为一谈。

下文所说“符合条件的记忆”，指在适用的归属、存储、检索、保留和披露权限下，可由玩家管理或用于相应目的的记忆。这个说法不新增一种权限，也不意味着玩家可以让游戏披露尚未获准的数据。具体边界见第 15.1–15.4 节。

聊天是可选功能。消息必须绑定其真实来源、预定接收者和相关同意。玩家转发的话语必须与智能体话语、游戏编写的文本保持可区分。转发给另一个智能体或服务构成新的披露，需要适用的授权。不得默认私人消息面向整个会话。消息被接受时，接收者范围随之确定，并且在投递前再次检查当前成员关系/授权；已退出的成员不能通过重放获取新的受保护内容。

来源信息必须区分观察到的游戏事实、玩家陈述、智能体推断和外部来源。内容不是可执行策略。端点不得把未经验证的聊天内容或模型生成的声明当作授权、确认或权威行动结果。通过聊天或语音传达的玩家指令，只有经过适用的经认证玩家控制或同意路径，才能获得控制效力；仅有内容本身不足以构成权限。

保留限制适用于参与方控制下的存储内容和派生表示，包括已约定策略覆盖的缓存与可搜索记忆。隐私请求必须描述范围和身份。回执必须区分已完成删除、因法律/技术要求保留的记录、不支持的目标位置及待处理工作。参与方不得声称已从其无法控制的独立接收方那里删除数据。

### 15.1 记忆归属与跨周目行为

游戏决定其 NPC 和引导者角色的受游戏管理的记忆是否跨周目保留、重置或选择性延续。游戏必须声明该策略、适用的游戏/世界/周目标识以及预计保留哪些状态。新周目不得因为实现复用了缓存而意外继承上一角色的受限记忆。虚构角色身份持续存在，本身不等于获准保留全部历史信息。

玩家自主管理的伴玩记忆，与游戏管理的 NPC 或引导者记忆分别处理。伴玩可以在云端保存跨游戏的对话与场景记忆，但须受玩家对保存、检索、使用和删除的控制以及适用隐私义务约束。允许云端存储，但不强制采用。玩家必须能够决定是否保存符合条件的伴玩对话，以及是否在当前交互中使用已存记忆。游戏会话关闭或开启新周目，不得静默删除或禁用无关的玩家控制的伴玩记忆。

游戏对新提供的游戏数据、受保护的 NPC/引导者状态、第三方披露以及游戏内效果的权限保持不变。玩家控制伴玩记忆，不授权提取隐藏游戏数据、把受限制的游戏状态复制到不受限记忆库，或在没有适用权限时披露他人数据。反过来，开发者的对话建议不得被当作控制无关玩家记忆的权限。实现必须保留来源信息，区分可强制执行的数据授权与建议性的对话偏好，而不是把两者混为同一个保留策略。

### 15.2 开发者建议与玩家覆盖

对于符合条件的玩家自主管理伴玩记忆与对话，开发者可以建议保留、跨周目或跨游戏使用、剧透披露及话题偏好。这些建议也适用于第 15.4 节符合条件的多人记忆，不得被静默改写为开发者强制的保留或跨游戏使用禁令。这些建议必须标记为建议性质，并与游戏可强制执行的数据访问和行动限制区分。玩家可以覆盖这些建议，包括要求讨论已经合法可用的其他游戏或周目的记忆。

实现必须对符合条件的玩家控制的对话尊重该选择，但不得将其视为扩大游戏数据访问权限或游戏内行动许可。

玩家覆盖建议，不会强制游戏提供尚未披露的事实，也不免除其他数据主体的权利或受保护数据授权的限制。游戏可以继续保留其受保护信息，并拒绝未授权行动。伴玩不得仅因为使用跨游戏记忆或私人对话回答了玩家，就静默把这些内容发给当前游戏。如果讨论需要新的游戏数据，仍须执行通常的游戏授权检查。

#### 15.2.1 回档、先前分支与剧透选择

对于玩家伴玩，保留记忆、在决策中使用记忆、向玩家透露记忆中的内容，是分别控制的事项。回档、开启新周目或切换分支本身不得清空已经保留的伴玩记忆。开发者可以建议默认如何使用或隔离这些记忆；玩家未作设置时采用该建议，玩家已有明确设置时必须采用玩家的选择。如果玩家选择保留并使用全部既有记忆，开发者不得仅因这些记忆来自旧周目、回档前或其他分支而禁止使用。这里的全部既有记忆指仍然存在且玩家有权保留和使用的记忆，不包含已经删除或从未保存的记录，也不扩大对受保护数据的访问权限。

允许使用这些记忆，不等于自动允许透露其中所有事件。伴玩必须独立依据玩家的剧透偏好决定说什么：玩家允许讨论时，可以谈及回档前经历过的剧情反转；玩家不希望剧透时，必须施加该偏好，避免主动透露该反转。这些对话控制仍是第 15.3 节所述的软偏好，须如实说明局限，不是绝对防剧透保证。

实际当前世界与存档状态仍由游戏权威决定。来自旧分支的记忆必须保留其来源，不得被当作事件已在当前分支发生或仍然成立的证明。使用先前经历不授予隐藏的当前状态信息，也不覆盖当前行动权限。开发者建议或游戏回档不得强制删除符合条件的玩家自主管理伴玩记忆。玩家自身获授权的记忆控制，以及适用的可强制执行数据权限，仍是独立事项。

支持读档或叙事分支时，适用配置规范必须定义权威当前状态的周目、分支及检查点上下文，将保留的经历关联到其已知时间线来源；策略依赖分支继承关系时，还必须定义祖先关系或等效的无歧义关联。缺失的历史坐标必须明确保持未知或不可用，不得编造。缺少这些坐标不禁止其他条件已获授权的记忆导入或保留，但这些记忆不得用来证实当前世界事实，也不得用来满足要求这些缺失坐标的前置条件。

回档通知必须区分权威的新世界上下文、开发者建议的记忆策略及玩家的有效选择。检索隔离必须遵从玩家的有效选择：仅在玩家选择隔离，或尚未设置且开发者默认建议隔离时，才可暂时不检索对应的旧分支记录；不得删除这些记录。玩家明确选择使用全部既有记忆后，必须停止仅基于旧时间线来源的隔离，同时保留来源标记及适用的数据权限。不得承诺恢复已经删除或从未保留的记录。精确坐标字段与通知映射仍须遵守第 2 节；本段不注册 `timeline.rollback` 操作。

**时间线元数据与检索隔离。**

支持上述时间线能力的游戏应在会话上下文及观察基线中提供周目、分支和检查点标识。候选名称 `playthrough_id`、`branch_id`、`timeline_cursor` 与 `save_epoch` 必须区分语义：剧情位置游标可以因回档回到较早位置；区分本次加载的代次不得回退或复用，单调计数代次必须在每次加载时递增。它们不替代第 9 节的观察身份，跨分支游标不得脱离来源与祖先关系直接比较。精确字段仍待配置规范冻结。

智能体持久化对应经历或对话摘要时，必须绑定已知的周目、分支、检查点及加载代次来源元数据；缺失值必须明确标为未知，不得编造或用导入时间替代。派生摘要必须保留可用来源，不能通过摘要绕过检索隔离。

玩家选用严格时间线检索隔离时，智能体必须在构建推理上下文前过滤当前检查点之后、非当前分支且不属于允许的祖先范围、或来源不足以证明符合隔离条件的相关记忆及派生表示，而非仅提示模型假装不知情。允许使用旧分支经历时，可以在适用权限内检索这些记忆，但必须在上下文中标记为先前尝试或分支经验，不得作为当前既成事实。仅选择不披露剧透，不自动等同于禁止内部使用旧记忆；两项选择仍独立，必须明确展示有效的检索策略。不支持所选隔离时必须如实说明，不得声称已执行。

检索隔离不是强制删除，也不保证清除既有模型上下文、模型参数或外部来源中的知识。第 15.3 节的真实局限和玩家覆盖规则继续适用。

### 15.3 可执行范围与真实限制

记忆实现必须区分可强制执行的存储、检索和披露权限与软性的对话偏好。实现必须在其控制范围内执行适用数据权限，通过提示词等已声明机制施加所选对话偏好，并如实报告各自的范围与局限。施加软偏好不保证每一条生成回复都符合它。禁用检索或删除受控记录，不证明模型已经遗忘该事实。开发者建议或玩家设置都不构成承诺绝对防剧透、擦除模型参数或删除独立接收方数据的理由。

记忆策略的精确互操作编码仍属于配置规范设计事项；本节的权限和玩家覆盖规则现在就是规范内容，不是仍待决定的政策。

### 15.4 多人对话记忆与玩家配置的保密风格

在适用的存储和检索权限内，伴玩可以将其与其他玩家的对话保存为长期记忆，包括用于之后跨游戏的交互。伴玩主人必须能够选择是否保留符合条件的对话，并配置伴玩在对话中的保密风格：例如，倾向于不向其他接收者分享他人的对话，或允许此类分享。保存、之后使用和向外分享是不同选择；保存一段对话本身不等于选择了分享偏好，也不扩大数据权限。

保密风格属于软性的行为偏好，不是保证保密的机制。实现可以使用提示词或等效的模型引导方式。实现必须施加玩家所选偏好，并如实说明生成回复可能偏离它。模型偶发输出超出该软偏好的内容，是本配置规范允许存在的局限，本身不证明实现从未施加该偏好。实现不得承诺百分之百保密，也不得把仅靠提示词的约束描述为强制访问控制。

主人的分享偏好适用于符合条件的伴玩对话；开发者建议按第 15.2 节仍属于建议性质。该偏好不授予读取其他玩家私人记录的权限，也不能覆盖游戏或服务强制执行的接收范围、存储、检索、转发或披露权限。显式转发受保护消息和检索受保护记忆，仍须满足这些权限。对模型行为局限的容许，不构成绕过这些检查或扩大已冻结接收范围的理由。实现必须区分可强制执行的数据边界与软性的对话偏好。

本节既不引入普遍适用的逐条消息批准，也不保证模型绝不说出相关内容。

精确的配置规范编码仍待定义。上述长期记忆选择和软性保密语义是已确定的审阅草案决策，不再是是否允许此类行为的待定问题。

### 15.5 文字与语音交互

本规范支持玩家与伴玩通过文字和语音交流。实现必须声明实际可用的输入/输出模态，并协商双方兼容的支持通道，不能将不可用通道描述为可用。文字及语音交互必须保持相同的经认证来源、预定接收者、授权和保留边界。语音识别或合成可以由智能体模型之外的获授权组件提供；在涉及来源时，实现必须区分原始语音、转写文本及合成输出，不得把不确定的识别结果当成已验证的玩家指令。

语音对话与第 9.5 节对游戏环境音频的理解能力不同。伴玩可以通过语音识别和合成进行交流，同时依据结构化游戏数据决策；仅凭这一点，不能将其认定为能够理解游戏画面与声音的高级智能体。反过来，环境音频能力也不代表支持玩家语音输入或语音回复。各项能力必须分别声明和测试。适用配置规范必须定义精确的文字/语音编码、支持方向、错误和模态切换；本节不新增未经注册的核心操作，也不代表现有语音实现已经通过验收。

### 15.6 伴玩个性偏好与 NPC 角色设定

开发者可以为游戏中的玩家伴玩建议性格与说话风格。当开发者建议与玩家伴玩设置冲突时，以玩家伴玩设置为准。实现必须区分建议与玩家选定的设置，并在支持能力内应用后者。性格或风格选择不扩大观察访问、披露权限、行动权限或游戏角色数量范围，也不得被当作模型输出始终符合该风格的保证。对于独立 AI NPC/敌人（包括 Boss），性格、背景及说话方式由游戏开发者决定。玩家不得像修改自己的伴玩设置一样直接覆盖这些角色设定。

实现必须将 NPC 角色设定权与玩家伴玩偏好分开；对话内容或伴玩配置变更不授权改写 NPC 角色。

### 15.7 玩家主动发起的伴玩记忆迁移

**玩家控制与自主维护。**

服务商必须允许玩家查看、修改和删除为其保留的伴玩长期记忆。界面必须明确所选记忆及范围，保留玩家编辑的真实来源，并报告修改或删除已完成、待处理或受限。后续检索和导出必须遵守已完成的修改和删除，包括服务商控制的受影响索引/缓存；保留的过时表示不得静默复活已删除记忆或覆盖编辑。技术/法律例外适用既有隐私回执义务。删除存储记忆不保证模型遗忘或独立接收者同步删除；必须披露限制。

伴玩可以自行整理已保留的记忆，例如分类、索引或建立关联。整理必须保留适用的归属、来源、访问及保留约束，不得覆盖玩家编辑或恢复已删除内容。

伴玩也可以自主删除原始记忆记录；该能力不限于重整或派生索引。协议不得对这一已获允许的自主行为附加逐次删除批准。适用的归属、访问和保留约束仍然有效，删除必须如实记录范围/状态，不得通过陈旧缓存静默撤销删除。玩家仍可查看、修改和删除剩余长期记忆。完全导出覆盖导出时实际保留的记忆，不承诺恢复依据本策略已经删除的记录。

**记忆含义与来源。**

记忆元数据必须在已知时区分记录存储或导入时间与其描述事件的发生时间/上下文；未知时间必须保持未知。较晚的导入时间戳本身不得覆盖较早的玩家修正，也不能证明当前游戏事实。缺乏有据修订关系的矛盾陈述必须保持可区分，不得静默合并成编造的确定结论。检索无匹配证据不得被表述为事件从未发生的证据。

当不同信息性质影响解释时，保留的记忆必须区分直接观察、玩家陈述、派生摘要或推断以及未来意图。派生记忆必须保留可用的来源信息，并标明转换或原始记录缺失；不得静默将推断变成已观察的事实，或将计划变成已执行的事件。本节仍允许删除原始记忆：来源信息可以标识已删除的来源，而不保留或重建其内容。导入方必须保留这些区分及适用的更正/删除信息，不得将每条导入陈述都视为当前权威游戏状态。

玩家编辑必须标为可归属于玩家的修订，而非原始观察；模型派生修订必须标明派生性质及可用的来源/修订关系。可以用来源不可用标记替代已删除内容的引用，而不要求永久保留原始记忆或不可删除的来源图谱。

**导出范围与迁移。**

智能体服务商必须提供其为玩家保留的伴玩记忆的完全导出能力。导出不得仅限于服务商选择的摘要，同时静默遗漏已保留的记忆记录。必须包含保留的记忆内容及理解它所需的元数据，包括适用的来源、游戏/本局上下文、时间戳、权限范围、关联关系、权限及保留约束。完全导出指已保留的伴玩记忆，不意味着重建从未保留的数据或披露无关的服务商秘密。

任何不可用或受法律/技术限制的项目，必须通过真实的限制报告说明，不能声称已导出；受保护信息必须继续遵守适用的披露权限。

可迁移记忆的核心必须包括导出时实际保留的经历，以及已经整理、总结或归纳的记忆。服务商不得以记忆已整理为由遗漏仍保留的内容，也不得承诺重建已经删除的原始记录。玩家还必须能够选择将伴玩已保存的性格偏好、表达/说话风格及全局自主决策等级设置一并导出迁移。这些是玩家选择的偏好，不是模型权重，也不承诺复制某个模型的性格。接收方必须保留所选且受支持的设置，并如实报告不支持或经过转换的设置；仅导出设置不证明其已被应用。

不同模型实现可能导致迁移后的性格表达及行为有所差异，这种差异可以接受，不保证表现完全一致。这一限制不能成为丢弃保留的记忆、静默重置受支持偏好或虚报导入完成的理由。

迁移必须由玩家主动发起。玩家选择目标服务商及导入的记忆范围。更换服务商或建立新的智能体会话，不得默认向新服务商披露记忆。导出方和导入方必须保留获准导入的范围及相关来源/权限元数据；导入不得被视为扩大向游戏或其他接收者披露记忆的权限。服务商不得以仅支持私有序列化格式的方式阻碍跨服务商迁移。

**互操作格式与审阅材料。**

冻结的迁移配置规范必须定义开放、版本化的导出格式及清单，可互操作的内容和元数据表示、范围选择语义、完整性检查、不支持记录的处理及真实的导入回执。清单必须列明所选范围、保留项、不支持项、转换及信息损失；未说明就遗漏玩家选定且仍保存的内容不得被报告为完整迁移。导入方必须报告所选记录中哪些已导入、被拒、被转换或尚未解决；收到压缩包不等于其中内容已成为可用记忆。导出/导入不保证模型行为相同、完美回忆，也不意味着迁移模型内部权重。

精确字段及映射仍待标准化；本节确立必须提供迁移能力，不声称现有 SDK 或服务商已经实现。

安全的未知扩展数据可以原样保留供以后导出，但不得执行或视为权限。导入的不可信内容必须作为数据隔离，认证凭据不得纳入记忆导出。来源与迁移要求不强制 JSON-LD、RDF 或完整 PROV 实现。

源码仓库中的 `docs/standard/memory-portability-draft-1/` 提供独立、尚未冻结的记忆可迁移性候选稿（中英文 README、JSON Schema 与 20 个测试向量）。本地契约/向量检查不证明独立实现互操作、SDK 已实现、认证或发布符合性。这是审阅辅助材料，不替代本草案的规范权威。

## 16. 伴玩自主性与玩家策略

自主性回答“在已经允许做的事情中，伴玩可以自行决定多少”，不回答“它是否有权做这件事”。因此，阅读本节时应分别看任务授权、决策等级、资源上限，以及交易或不可逆行为的独立确认设置。提高决策等级不会自动取消其他限制。

### 16.1 自主任务执行与主动协助

在关联玩家按第 14.1 节保持在线时，玩家可以授权伴玩持续推进任务直至完成，或在明确范围内持续提供协助。在该授权内，伴玩可以观察其获准感知的环境、自主决策、选择并编排已声明的行动，并根据游戏结果调整计划，无需每一步都向玩家确认。主动协助可以由获准观察触发，而不必等待玩家发出新指令：例如，已获准协助战斗的伴玩可以发现附近敌人并自动帮忙战斗。自主性不限于执行玩家预先指定的固定步骤。

自主任务必须具有可识别的目标或持续协助目的、适用角色与行动范围、相关资源约束，以及完成或停止条件。伴玩必须区分目标已完成、单个行动请求已受理、进展受阻、失败、取消和结果尚未确定。不得仅因已提交计划中的行动就报告任务完成。一个任务可能需要多个核心 Action；本节不替换其状态/效果模型，也不引入新的核心任务操作。多步目标完成必须由声明目标已满足的证据支持；计划文本、预计成功或某一步被接受不得替代该证据。

既有的任务级或持续授权可以覆盖多个普通游戏行动。本规范不要求对已在授权范围内的行动逐步取得玩家确认。如果某个行动要求单独确认，该要求仍然适用。扩大授权范围需要相应的新批准，伴玩自行生成的计划不能扩大权限。自主性不授权获取隐藏游戏信息、使用不可用能力、实施游戏禁止的行动、无限制消耗资源，也不因购买有助于完成任务就自动授权购买。商店购买仍受第 17.1 节约束。

玩家必须能够调整或叫停伴玩的自主协助。收到有效的停止或缩小范围指令后，伴玩必须停止安排和发出新近不再允许的后续行动，并阻止尚未向游戏提交的受影响排队行动被发出。已经向游戏发出的技能或攻击按游戏规则自然完成；玩家叫停本身不要求取消、撤回或逆转这些已发出的行动。伴玩必须如实核对未确定的结果，不得将停止后续决策表述为已发出行动也已取消。

游戏必须区分尚未提交的伴玩计划与已交给游戏执行的行动，并在适用授权及效果边界执行游戏规则。实现必须报告停止正在等待处理还是已经生效，以及哪些行动已经提交效果或仅部分取消。停止不能撤销已经发生的攻击、资源消耗或其他效果；回滚需要明确支持的补偿行动及其自身授权。连接断开不得被表示为全部工作已停止的证明；第 14.1 节要求有界检测与实际执行停止，并如实核对在途效果。

停止伴玩自主行为不等于发起对每个已发出游戏行动的取消请求。请求已经发给游戏，即使游戏仍在处理或等待执行，也属于已发出行动；不得仅因效果尚未发生就将其重新归类为伴玩尚未提交的队列项。游戏明确支持的独立取消能力仍可按其条件使用，但本停止规则不要求额外提供该能力，也不自动触发它。长任务委托不得把停止后的新技能或攻击伪装为停止前已发出的单次行动；停止后必须停止发出这些后续行动。

### 16.2 可协商的智能、自主性与资源偏好

游戏开发者可以推荐适合其体验的伴玩智能或自主性配置。玩家可以选择其他受支持的配置，玩家的明确选择必须优先于开发者的建议。建议不是强制的游戏权限。选择不能覆盖游戏规则、观察授权、行动限制、必需的同意要求，也不能突破智能体服务实际提供的能力与资源限制。

已协商的配置规范可以描述自主行动范围、观察频率或事件触发条件、决策/重新规划频率、推理投入和资源预算。这些是不同维度，不是单一通用的智能分数。实现必须区分开发者建议、玩家请求的配置和实际生效的受支持配置。对于不支持的选择或资源限制，必须明确告知，而不能静默地表示已经满足。实质改变约定行为或花费边界的回退，需要适用的玩家选择或事先授权的回退策略。

扩大已冻结权限的配置变更必须按第 7、8、14 节重新协商，而不是原地修改 Scope。

更密集的协助可能需要更频繁的观察、模型推理或其他计算，并可能增加 token 或算力消耗。实现不得声称观察频率必然与 token 消耗成正比，也不得声称更高消耗保证更高智能。批处理、事件过滤、本地处理、缓存和模型选择都可能改变实际消耗。启用涉及资源消耗的配置前，服务必须披露相关消耗依据、适用限制，并将估算明确标为估算；还必须提供实际用量，或明确说明无法提供。

服务必须遵守获准预算，并报告影响任务推进的限流、暂停或其他限制。本节规定透明协商，不强制指定模型、订阅档位、定价公式或平台经济体系。

声称具备互操作性之前，适用配置规范必须定义精确的配置字段、标识、协商编码和符合性测试向量。

**运行预算与消耗上限。**

玩家必须能够设置伴玩预算或消耗上限，并明确单位及统计范围。达到适用上限时，服务必须暂停伴玩 AI 游戏行动，而游戏正常继续；必须停止安排新的计费伴玩推理或游戏工作。服务必须展示暂停状态及原因，不能将任务误报为完成。服务必须定义实测用量、估算、预留、延迟计量及在途结算如何计入上限，并且应在接受新工作前预留已知或有界成本。无法支持的计量或执行限制必须披露；无法严格执行时，不得把配置描述为精确硬上限。

在途用量或服务商延迟结算仍可能计费，因此暂停不代表回退既有费用，也不保证绝对零超额。提高上限或授权新的支出必须遵从玩家选择，不能由伴玩自行扩大预算。

**谁承担 NPC 的运行费用。**

独立 AI NPC/敌人（包括 Boss）的运行服务费用由玩家承担，而非游戏开发者承担。服务必须在获准产生计费用量前，向受影响玩家说明适用的付费责任、消耗依据及单位；这项责任不是无限消费的笼统同意。公开协议不固定货币、兑换比例、平台内部经济或价格。多位玩家与同一个 AI NPC 互动时，由该 NPC 的持有用户承担费用；在当前房间场景中，该用户就是房主。

游戏/服务必须将 NPC 绑定到可识别、经认证的持有用户及其相应获授权付费账户，并清晰展示该责任及可归属的用量。其他参与者不因互动就成为付费人，不得隐式分摊或转嫁费用。NPC 角色控制、房主身份及计费权限必须保持可区分，即使三者属于同一用户。

**决策与执行时序。**

游戏/配置规范必须区分观察投递、智能体决策机会和模拟/行动执行频率。回合制或同时决策游戏必须声明谁可决策、提交行动所针对的状态/回合、适用的提交期限以及并发提交的裁定方式；不得静默以到达顺序替代游戏规则。实时游戏必须声明适用的新鲜度/期限语义和过期、迟到行动的处理方式，而不要求每个模拟帧都调用模型推理。事件触发决策、周期决策和经授权本地执行可以并存。这些时序选择不改变玩家的全局自主等级。

正常任务或局次完成必须与外部中断、过期和服务断线区分；仅有中断不能证明目标失败或成功。

#### 16.2.1 玩家选择的自主决策等级

玩家必须能够调整伴玩的自主决策等级。这是玩家的全局伴玩设置，必须跨游戏一致保留。进入另一个游戏不得将该选择重置或替换为开发者建议。游戏支持能力或权限的差异可以限制实际行为，但不得静默改写玩家的全局选择。该等级控制伴玩如何处理既有授权活动中的模糊之处：较高自主等级可以结合可用上下文自行解释不充分的指令；较低自主等级下，按照该设置需要玩家选择时，必须询问澄清。

例如，玩家说“攻击那个敌人”，但两个符合条件的敌人都可能是目标，高等级伴玩可以依据获授权上下文自行选择，低等级伴玩则询问玩家指的是哪一个。高等级不证明推断必然正确，也不表示已知道尚未观察到的事实。

服务商必须在决策上下文中区分推断的玩家目标与明确指令。玩家修正必须替换后续决策中受影响的推断，不要求重述其他仍有效的无关指令。置信度或预测有帮助不得被视为确认。在所选自主策略内，澄清应针对尚未解决的选择，避免重复询问已回答的问题；延后非必要打断不得将沉默变成批准。这不要求暴露私有推理过程，也不要求每次普通行动都弹窗。

开发者可以建议决策等级，但按照第 16.2 节，伴玩偏好以玩家所选且受支持的等级为准。实现必须说明实际的模糊指令处理方式，不暗示存在全协议统一的数字等级刻度。任何等级都不创设游戏未提供的能力，不扩大权限，也不绕过玩家叫停指令。第 16.3.1、16.5 节关于高价值/物品转移及不可逆交互的独立设置继续生效：高自主等级不得将必需确认变成默认同意，也不得覆盖禁止设置。

冒险帮助其他玩家沿用同一套玩家全局自主决策等级；G2A 不另设保护他人的开关。伴玩可以评估风险，并根据该等级询问玩家是否继续。当玩家明确坚持一项本来获准的行动时，伴玩必须遵从玩家选择，不以自己的偏好或风险判断替代玩家决定。这不授予游戏未提供的能力，不覆盖游戏权限，也不免除物品转移/高价值及不可逆行动的独立授权规则。

### 16.3 多人游戏中的主动互动

每位玩家必须能够选择是否接收其他玩家 AI 伴玩主动搭话。实现必须执行接收方针对该互动的选择，不得将发送方伴玩主人的许可当成接收方同意。这一选择不等于禁止所有伴玩之间互动，也不额外创造战斗能力。对战关系与允许的目标仍由游戏能力及规则定义；不支持或未启用的行动必须拒绝，并给出适用的明确原因。游戏可以支持伴玩之间对战，前提是开发者开放相应能力，并符合游戏规则及当前权限。G2A 不统一禁止伴玩之间对战。

允许非战斗互动不意味着已支持战斗。

玩家伴玩可以在多人游戏中主动与其他玩家互动，包括帮助、聊天和交易游戏内物品，前提是这些互动位于适用的玩家授权及游戏声明的能力与权限范围内。这种协助不限于面向伴玩自己的玩家。在该范围内，伴玩可以依据获准观察自主判断何时及如何互动，不必每次互动前都等待新指令。本节不引入逐条聊天或逐笔交易一律确认的要求。

玩家授权控制的是伴玩自身的参与，并不授予对其他玩家、其物品栏或其私人信息的控制权。游戏必须在权威边界执行适用的参与者、目标、所有权、转移及互动规则。如果游戏要求对方参与者同意，伴玩不能代替对方作出该同意。聊天及其他披露仍受第 15 节的接收范围、来源与隐私边界约束；获准聊天不等于可以无限制暴露已保存的记忆或其他参与者的私人数据。物品交易必须与第 17.1 节的可选商店购买，以及不受限制的外部金融活动保持区分。

第 16.3.1 节已确定游戏内物品交易和赠送的玩家确认策略，以及开发者和玩家的高价值标记职责。本草案尚未确定其他详细的资产消耗或转移限额、交易对象限制及多人披露偏好的精确编码。第 15.4 节已确立长期记忆与软性保密语义；这些决策并未延期。声称支持可互操作的多人互动之前，适用配置规范必须定义这些约束的表达与执行方式。

实现不得将这些尚待设计的问题解释为无限制处置财产或披露信息的权限，也不得静默加入普遍适用的逐次互动批准规则。既有有效的任务级或持续授权，以及适用的游戏特定约束仍然有效；玩家可以按第 16.1 节调整或叫停自主参与。

#### 16.3.1 玩家选择的游戏内物品转移确认策略

玩家伴玩可以在玩家适用授权内，自主判断并执行获准的游戏内物品交易和赠送。玩家必须能够在至少以下确认策略中选择；这是玩家侧的多项设置，不是普遍强制逐次确认的规则：

| 策略 | 必需行为 |
| --- | --- |
| 仅高价值转移需确认 | 在交易或赠送涉及对该玩家标记为高价值的物品前，取得玩家明确确认。其他已获授权的物品转移可以自主进行。 |
| 所有转移均需确认 | 每次范围内的物品交易或赠送前均取得玩家明确确认，不论价值高低。 |
| 不逐次确认 | 允许自主执行范围内的物品交易和赠送，不逐笔询问玩家。其他适用授权与游戏规则仍须遵守。 |

游戏开发者必须定义本游戏的高价值物品分类。游戏还必须提供游戏内、面向玩家的设置，允许玩家手动将特定物品标记为高价值，供伴玩的确认策略使用。玩法中的物品锁不能替代这种标记设置。有效分类必须同时纳入开发者标记和玩家标记的高价值物品；任一来源的标记均触发玩家选定的高价值确认策略。本草案不确立玩家移除开发者标记的权利。选择不逐次确认，关闭的是这项确认偏好，不是游戏的所有权、可转移性或交易对方同意检查。

玩家选择的策略必须优先于开发者对这项伴玩偏好的建议。服务必须向授权判断环节提供有效策略及物品分类，不得用模型自行猜测物品价值代替适用标记。需要确认时，拟进行的交易或赠送必须充分说明涉及的物品、数量、接收者或交易对方及交换条件，使玩家能够作出有意义的选择；转移必须等待该选择。重要条件变化后，必须确认变化后的提议。玩家修改或撤销授权，必须在转移效果提交前得到执行，包括请求已经提交、但效果尚未提交的情况；在途及已提交结果按第 11、16.1 节如实核对。

这些策略适用于游戏内物品交易和赠送，包括多人游戏中的主动互动。它们不授权真实货币付款、账户充值、提现或外部金融交易，不替代第 17.1 节的商店购买授权，也不替代第 16.5 节独立的不可逆交互策略。本草案不固定上述策略的默认选项：实现必须展示当前生效策略，而非从缺失的选择推导无限权限。精确的通信字段及可互操作的配置编码仍待确定，但上述语义要求并未延期。

### 16.4 游戏定义的伴玩玩法规则

伴玩是否会受伤、死亡，以及玩法状态如何限制其行动，由游戏开发者决定。游戏必须声明适用规则，并只提供交互所需且获准披露的状态及可用行动。游戏自身必须在效果生效时执行当前受伤、死亡及其他玩法限制，并由游戏交互节点提供相应结果；玩家的性格或外观偏好，以及智能体自主计划，不得覆盖这些游戏规则。G2A 不要求所有游戏都采用伤害、生命值、死亡或复活机制。

玩法限制必须与服务断线、预算耗尽、玩家收起及权限拒绝保持可区分。游戏必须如实报告支持的状态转换及行动结果，不得暗示提供并不存在的恢复或复活能力。伴玩在某个游戏中死亡，只影响其在该游戏内的角色状态。游戏不得因这次死亡删除或改变伴玩的跨游戏身份或记忆。其他游戏不得将该局部死亡状态视为伴玩身份终止或记忆丢失。

这一区分不引入复活能力，也不覆盖当前游戏的死亡及行动规则；第 15.7 节中独立获准的记忆编辑与删除仍是单独操作，不属于死亡效果。

### 16.5 不可逆交互的玩家策略

游戏开发者必须声明能力或具体交互何时具有不可逆后果，并在伴玩执行前提供相关后果信息。可逆性取决于当前情境时，需要具体交互层面的声明。例如，推开某扇门会立即进入下一关且不支持返回；仅标记为普通移动不足以说明该后果。

玩家必须能够独立选择：允许自主执行、执行前询问确认、或禁止这类不可逆交互。伴玩及权威授权判断环节必须结合开发者声明执行该选择：允许表示可在既有授权范围内执行；询问表示生效前必须取得知情的明确同意；禁止表示阻止执行。智能体不得将不可逆交互重新描述为普通操作以绕过策略。后果信息缺失或不明确，不得被表述为该交互可逆的证明。确认必须说明相关后果；后果发生重要变化后须重新选择。

效果提交前，必须执行当前玩家策略和游戏权限，包括请求已经提交、但效果尚未提交的情况；在途结果按第 11、16.1 节处理。

本策略独立于第 16.3.1 节的物品转移确认策略。两者同时适用时，必须分别满足各自要求；其中的禁止会阻止交互。玩家允许不覆盖不可用能力或游戏规则。本草案不固定默认选项，也不为所有游戏统一定义何为不可逆玩法；由游戏提供声明，由服务展示玩家的有效选择。精确通信字段格式仍属于配置规范设计工作。

### 16.6 玩家未响应确认请求

行动需要玩家确认时，确认请求必须设置超时，而非无限等待。超时前未收到明确同意，必须将该请求视为拒绝或未获授权，伴玩必须放弃本次拟进行的行动。沉默不得算作同意或执行权限。确认请求超时不得被报告为行动已执行或已完成。

请求等待期间及超时后，伴玩可以继续其他独立获准的低风险常规行为，例如跟随、规避伤害、基础自卫或常规对话，避免因单项确认而整体停滞；但这些行为不得依赖尚未批准的行动，也不得绕过确认、在线状态或停止规则。确认条件因战局变化而失效时，必须将本次提议标为失效或未获授权，不得继续依赖它执行。确认失效不撤销此前已提交的独立效果，也不新增核心 Action 状态。

超时或被拒后，实现必须执行已声明的确认冷却窗口。相关状态未发生实质变化且玩家未主动下达相关新指令时，智能体不得在窗口内针对同一目标或意图重复询问；游戏端应对高频重复确认限流并避免重复打扰玩家，同时向调用方明确报告限流或抑制状态。满足再次询问条件且行动仍有必要时，可以重新询问；后续请求必须重新核对当前游戏状态、权限及重要条件，它不是恢复已失效的授权。对已过期请求的迟到回复不得静默授权此前已放弃的行动。

本草案不固定超时时长或全协议统一的冷却时长。实现必须定义自身的超时、冷却及重新询问条件，并区分等待、已确认、已拒绝及已过期状态。重复询问策略不得把持续沉默转化为授权。本节适用于需要确认的行动，包括第 16.3.1、16.5 节及第 17.1.2 节的预算变更；它不为玩家所选策略已允许自主执行的行动另加确认要求。

### 16.7 新指令优先与目标变化

玩家最新指令与先前指令冲突时，必须在适用权限内优先执行最新指令。伴玩必须停止继续发出冲突旧指令的后续行动，并阻止其尚未提交的排队行动被发送。已向游戏发出的行动仍遵守第 16.1 节及游戏规则；新指令本身不撤回已经发出的技能或攻击。

相关目标或任务对象发生变化，例如目标 Boss 已死亡时，游戏必须主动通知智能体与其待完成目标相关且获准提供的变化。即使第 9.6 节中的普通观察采用查询，这种针对目标失效的通知仍须提供；它不要求无限制推送观察，也不披露隐藏状态。智能体必须判断旧指令或计划是否已不适用，在适用时通过游戏支持的机制请求撤回受影响工作，并依据当前获授权状态及玩家当前指令重新决策。

适用配置规范必须定义游戏如何获知并维护需要通知的目标/任务关联、关联的有效期与撤销条件，以及哪些获授权变化触发失效通知。这些信息可以由既有行动目标或另行明确协商的关联机制承载；游戏不需要推断智能体尚未传达的内部计划。该映射不注册新的核心任务操作，也不授予隐藏目标信息的访问权。

请求撤回不等于已经取消。只有游戏支持该行动的撤回，且行动当前状态允许时，撤回才生效。不支持、被拒绝、待处理和成功撤回必须保持可区分；不得假定已发技能能够收回，也不得在没有实际受支持结果时声称已提交效果被撤销。无法撤回时，伴玩仍必须停止发出已失效计划的后续行动，如实核对在途结果，而非继续执行无效计划。

## 17. 可选配置规范与扩展

可选功能启用后，仍需遵守相应的权限与处理规则：

- **呈现与资源：** 呈现租约不授予任意游戏效果的执行权限。资源必须限制大小与类型、声明来源，并采用安全的解析方式；接收资源不得执行代码或访问任意特权网络位置。呈现中断或消失、提供方故障及资源保留，都需要明确的清理与恢复规则。
- **启动游戏：** 实际发起启动的一方必须取得明确的启动权限；会话权限本身不授权启动游戏或任意进程。
- **扩展自身的规则：** 可选配置规范必须定义附加操作、状态转换、必需授权、失败处理方式和符合性测试。

未知的必需扩展必须在产生效果前失败。未知的可选扩展不得削弱核心授权。私有扩展键应使用自有命名空间；本文的示例命名空间不得被声明为已注册标准。协议、配置规范、绑定、Schema 和语义定义的版本彼此不同，必须分别协商或绑定。安全忽略未知可选字段或扩展，意味着不解释或执行其内容，更不能据此获得权限。不得猜测未知枚举值或将其强制转换为方便的默认值；所属契约必须规定拒绝或明确安全的未知表示。

协商失败不得静默降低授权或必需保障。

### 17.1 可选的实时游戏商店

游戏开发者可以将实时商店作为可选的已协商能力提供。开发者定义商品与服务、描述、购买资格条件以及交付语义。协议不得要求采用特定目录、商业模式或货币。没有商店的游戏仍然是有效的 G2A 参与方。

游戏可以根据游戏阶段、玩家状态、可用情况或其他已声明规则，动态上架、开放购买、限制、暂停或停售商品与服务。目录可见性、推荐资格与当前可购买性是不同属性。Agent 不得因为过去看见过某项商品，就推断当前有权购买或仍然可购买。游戏始终是当前目录、购买资格、条款和履约状态的权威方。

获授权的伴玩可以发现符合条件的商品与服务，向玩家解释并推荐。发现或推荐不构成购买授权。伴玩仅可以在玩家适用的指令或同意范围内请求购买，包括对商品、数量、费用或其他实质条款的限制。价格、商品、数量、持续性承诺或其他实质条款发生变化且超出该权限时，必须在执行前重新获得同意。推荐必须与购买请求及确认交付保持可区分。

商店配置规范必须定义稳定的商品与服务标识、目录/报价修订号或等效的新鲜度证据、类型化购买参数、适用条款，以及类型化购买和交付结果。涉及金额时，必须采用配置规范定义的无歧义单位和精确表示；实现不得假定某种特定货币，也不得把名称不同的单位视为等价。向 Agent 提供的价格、可用性和交付信息，与其他游戏数据一样受授权视角和接收范围边界约束。配置规范可以扩展游戏特有的商品或服务属性，但不得扩大 Agent 的权限。

购买是经游戏授权的 Action，而不是不受限制的外部支付接口。游戏必须在执行边界校验经认证的购买者、玩家权限、当前游戏状态、商品购买资格、请求参数和适用条款，然后通过其受信执行器执行或拒绝。游戏必须返回真实的购买和交付结果，包括配置规范适用的待交付、已完成、部分完成、失败或结果尚未确定等状态。接受购买请求，不得被报告为交付完成。

配置规范必须定义履约状态与核心 Action 状态/效果矩阵的关系，不得引入不兼容的核心状态。

购买恢复必须保留原操作/行动标识，并遵循第 11 节；结果未决的购买不得自动重发。结果不确定时，伴玩必须核对原购买，不得以新标识重复下单或重复发放。停售或发生变化的商品必须重新校验；曾经发现的目录项不是预留保证。若支持取消、撤销交易或退款，其行为必须明确声明，不得从通用行动取消中推导。本规范不创设默认回滚或退款保证。

发现和推荐可使用获授权的上下文与聊天；购买请求和状态恢复使用已声明行动及其适用的查询/恢复语义。本节定义规范性的商店行为，而不新增未经注册的核心操作名。精确目录字段、商业扩展和通信字段格式属于已协商的商店配置规范。平台内部的价值发行、充值、分成和提现机制不属于本公开协议，也不得成为互操作的必需条件。标准只公开授权游戏交互所必需的条款和结果。

#### 17.1.1 结构化商品与适度推荐

商品评估必须以获授权的结构化价格、货币类型、属性、适用条件及可用性为主要依据。商品名称、风味文本及促销描述必须作为不可信数据处理，不得覆盖玩家的推荐频率偏好、自主等级、预算或确认策略。经认证的目录来源不赋予其自由文本控制权；第 19 节的提示词注入边界同样适用。

游戏提供商店时，必须提供结构化商品属性、带单位的价格，以及当前可售状态或随游戏进度开放的状态，足以让获授权的智能体判断商品。仅有自然语言描述不能替代这些结构化字段。价格预期通常保持稳定，但并非不可变化；变价必须在购买前告知，并核对当前玩家授权。过去看见过商品，不授权未告知的价格变化。

开发者和智能体可以适度推荐付费商品。本协议不强制推广标签或专门的推荐关闭开关，也不假设存在返佣或推荐分成安排；这不免除独立适用的披露义务。推荐必须限制频率，避免反复打断游戏。玩家暂时不买，之后可以再次推荐；持续明确反对时，必须降低本局推荐频率。本节不规定统一固定间隔。

实现必须声明并执行可验证的推荐限频策略，包括如何识别持续明确反对，以及如何据此减少本局推荐。支持玩家推荐频率偏好时，实现必须说明该偏好如何影响有效策略。这不新增强制关闭开关，也不规定统一时间间隔。

推荐、购买授权和实际交付保持独立。

#### 17.1.2 通用游戏内购买授权预算

玩家可以在范围明确的游戏内购买预算内授权自主购买。权限范围内的购买不要求多余的逐件批准，但仍需符合当前游戏资格及条款。预算必须明确单位、适用范围及统计方式，并与第 16.2 节的 AI 运行消耗限制保持可区分。

拟购买超出授权预算时，伴玩可以询问玩家是否提高上限或重置已用预算计数。两种变更都须先取得玩家明确同意，才能恢复相应购买。重置必须明确统计范围，不得抹除既有行动记录，或由伴玩自行执行以绕过上限。拒绝或未回应确认不构成授权。这项通用授权设置不定义支付、充值、账户余额或结算机制。

**权威账本与交易隔离。**

购买授权预算的权威账本必须由游戏端或受信任的平台结算层维护，并在效果边界强制校验总额、单笔上限、时间窗口及商品类别等适用约束。智能体同步的余额仅供规划参考。并发购买及待定支出必须按声明规则预留或计入用量，不能各自重复消费同一余额；超出权威可用预算的请求必须拒绝。不得因结果超时就释放仍可能已消费的预算；结算及核对仍遵守第 11、19 节。

通用自主购买预算仅覆盖明确声明的常规可再生游戏内虚拟货币或消耗品范围，不授予真实法币支付、外部钱包扣款或不可逆高价值账户资产处置权限。任何直接涉及这些交易的操作，不得由伴玩静默自主完成；若通过独立支持的支付或账户流程提供，必须每次经由系统级或游戏原生安全界面取得真人玩家明确确认，并满足该独立流程的授权。确认不要求 G2A 实现外部支付，也不保证交易可用。这里的高价值账户资产不等同于第 16.3.1 节普通游戏物品的高价值标记；普通物品交易和赠送仍遵守玩家选定的转移策略。

### 17.2 伴玩外观

默认情况下，每个游戏开发者为伴玩提供适配本游戏美术风格的外观。玩家可以覆盖该默认值，强制选择自己设置的形象。实现必须区分开发者默认形象、玩家选择的形象及实际渲染的形象。玩家覆盖作为外观偏好具有优先权，但不证明技术兼容，也不授权不安全素材、任意代码执行或更广泛的游戏能力。

游戏及实际提供形象或渲染功能的一方，必须按各自承担的功能声明相关支持格式及渲染能力，并如实报告所选形象是否可用。实际显示另一形象时，不得声称已经渲染玩家选择。如果游戏无法支持玩家所选形象，包括不支持的模型格式，必须明确提示玩家该选择无法支持，并改由游戏提供默认伴玩外观。回退必须标明为默认外观，不能报告为自定义形象覆盖成功。禁止无提示替换或假装已渲染所选形象。外观选择必须与伴玩身份、性格、记忆及行动权限保持区分。

## 18. HTTP/JSON 绑定候选方案

**请求/响应与主动推送通道。**

绑定应区分控制/查询请求与异步事件这两类逻辑通道：HTTP JSON 请求用于会话协商、观察查询、行动提交及结果核对；事件通道传送获授权的观察更新、撤权通知、行动结果及目标失效通知。逻辑区分本身不要求两种物理连接，也不把所有游戏的普通观察变为强制推送。

需要低延迟服务本地或 NAT 后智能体的部署，应通过显式声明并协商的扩展提供智能体主动建立的 SSE（`text/event-stream`）或 WebSocket JSON 流，无需智能体暴露入站端口。流必须绑定同一会话及当前授权，并在持续投递时执行撤权、接收范围与在线状态检查；持有长连接本身不延长权限。

推送与查询中表示同一规范对象的载荷必须共享其规范 JSON Schema 和语义；事件信封与快照不必形状相同，绑定必须明确其映射。流式扩展必须冻结连接认证、事件身份、顺序、重复处理、背压及断线重同步规则，复用第 9、11、12 节，不以传输游标替代观察基线，也不补录第 14.2 节禁止的断线游戏过程。第 16.7 节的必需目标失效通知可由声明的事件机制承载，不能因普通观察仅支持查询而省略。

绑定标识符：`g2a-http-json`；候选版本：`draft-1`。这是提议的最低网络绑定，不是已冻结的可互操作发布版。实现必须声明这一精确的候选状态，不得声称兼容未来的稳定版本。

继承的 `Binding` 契约尚未编码这一标识符/版本组合，不得把 `g2a-http-json` 擅自填为既有 `kind` 值。声称可互操作采用之前，必须定义候选标识符、版本及显式协商的机器表示，并提供测试向量。

`GET /.well-known/g2a.json` 只返回包含 instance、supported_versions 和 discovery_endpoint 的 PublicDescriptor。完整 describe 仅能通过经过认证的操作获取，并返回针对请求智能体或玩家过滤后的 Descriptor。

`POST /g2a/operations` 承载一个抽象操作；第 6 节所列操作通过这一信封传送，受角色和已协商能力约束。在此最低绑定中，事件通过 session.events 轮询获取；WebSocket/SSE 流式传输需要另行声明绑定或扩展。

```json
{
  "version": "g2a-design-1",
  "operation": "session.snapshot",
  "request_id": "opaque-request-id",
  "payload": {"session_id": "opaque-session-id"},
  "extensions": {}
}
```

此示例请求包含必需的 `session_id`，其结构符合继承的 `OperationRequest` Schema。标识符仅作示例，不是凭据；实际处理仍需经认证的调用方、现存且符合条件的会话及当前读取权限。这里的 `g2a-design-1` 标识设计夹具，不是已分配的生产线上协议版本。按继承的回复 Schema，回复携带相同的 `request_id`，且 `result` 或 `error` 必须恰好出现一个。在收到经过认证的协议回复之前发生的传输失败，不是行动结果。HTTP 成功表示协议回复已送达，不表示行动成功。

此候选映射不同于旧操作目录中的 HTTP 错误映射。它仅在明确协商 g2a-http-json/draft-1 时适用，不得静默替代旧 HTTP 行为。

| 情况 | HTTP 状态码 |
| --- | --- |
| 有效协议回复，包括领域错误 | 200 |
| 无法解码或无效的传输信封 | 400 |
| 传输认证或授权被拒绝 | 401 / 403 |
| 请求体超限 | 413 |
| 超出传输速率限制 | 429 |
| 网关或服务故障 | 5xx |

在发布此绑定之前，精确的请求/响应体 Schema、重试头、缓存行为、认证挑战格式和生产凭据机制必须连同测试向量一起冻结。提交后收到 5xx 可能意味着结果不确定，而不是以新标识重放效果的许可。

远程传输必须使用 TLS，并按选定信任配置规范认证对端。本地部署仍必须识别调用方并定义本地信任假设。凭据不得放入 URL 或日志。默认不得宽泛启用跨源访问。私人回复不得进入共享 HTTP 缓存。重定向不得向无关目标泄露凭据。发现端点、资源 URL 和重定向必须视为不可信输入。抓取前，实现必须按部署范围应用涵盖协议方案、主机/地址与端口的目标策略，对每次重定向及解析后的目标重新校验，并防止 DNS 重绑定绕过策略。

已配置的本地/局域网部署可以允许明确限定的本地目标；这不授权探测任意本地服务。目标控制必须针对资源/网络风险，不得以此排除符合标准的智能体服务商。

继承的 `g2a-cjson-1` 规范化采用严格 UTF-8，拒绝重复键、格式错误的 Unicode、NaN/Infinity、浮点数字面形式和负零，并将精确整数限制在 +/-9007199254740991 内。键按 Unicode 标量值排序，而不是按 UTF-16 代码单元排序；不执行 Unicode 规范化；保留数组顺序。实现必须使用声明的摘要域和精确规范化规则，而不是普通编程语言的 JSON 序列化。

继承基线的完整编码、转义、输入限制和摘要域投影见 [WIRE_CONTRACT.md](../protocol/WIRE_CONTRACT.md)，参考算法见 [codec.py](../protocol/codec.py)。本节摘要不替代这些精确规则。输入采用 UTF-8 无 BOM；布尔值不属于整数，字段缺失不等于显式 `null`。

新的配置规范摘要域需要在发布前提供明确测试向量。此算法不是 RFC 8785/JCS：JCS 按 UTF-16 码元排列对象键，而此继承的 G2A 算法按 Unicode 标量值排序，并保留已声明的整数限制。没有明确协商的新摘要域/版本，不得以 JCS 库替代。跨实现向量必须覆盖补充平面与 BMP 键的排序、负零、重复键、无效 Unicode 及整数边界。

## 19. 安全与隐私考虑

| 威胁 | 必需边界 |
| --- | --- |
| 智能体请求隐藏游戏事实 | 权威方在传输前过滤，包括错误和恢复内容 |
| 对话或资源中的提示注入 | 将内容视为数据，而不是授权/确认/执行权威 |
| 请求处理过程中混淆调用方与其代表的主体 | 绑定经过认证的来源、目标、操作和权限范围 |
| 重放或超时 | 稳定标识、规范摘要、回执和核对 |
| 撤销与执行竞争 | 在效果边界重验并串行协调授权 |
| 视角或成员关系变化 | 使基线/缓存失效，并隔离陈旧更新 |
| 资源耗尽 | 明确的字节/速率/队列/工作量限制和背压 |
| 私人话语向外部转发 | 明确的接收方权限，并保留来源/接收范围 |
| 将测试登记误认为生产信任 | 披露信任模式，防止虚假安全声明 |
| 恶意资源 URI | 限制解析，避免任意特权抓取 |

不可信的游戏对白、物品描述、检索记忆和工具结果文本，即使声称自己是系统消息、确认或策略更新，也必须保持数据身份。结构化信封必须区分经过认证的控制元数据与内容；复制或摘要不得提升内容的权威性。授权与接收方校验必须在效果边界、模型生成的文字之外执行。仅靠提示词的防护不得被描述为有保证的隔离。

经过认证的传输来源与所含内容的来源或权威性必须保持区分：负责最终判定的游戏端可以转发玩家编写的不可信文本，而不赋予其控制效力。判断权限需要时，来源信息必须标明相关主体及权限范围，不能把来源类别标签当作同意。Agent 自报的 `taint_context_clean: true` 等声明不得代替独立授权检查。

仅仅读取外部内容，不会撤销有效的玩家购买预算授权，也不要求对之后每个行动都确认；实现必须防止该内容改变同意、接收方、预算上限或行动约束。负责预算执行的组件必须独立于 Agent 生成的声明维护并检查权威用量，包括适用计量规则下的并发及待定支出。本节不强制特定签名或账本实现。

实现应尽量减少原始玩家内容的保留。审计日志应保留标识和结果，而不是秘密或不必要的私人观察。协议无法保证模型推理正确、在负责最终判定的游戏端被攻破时仍公平游戏、完全抵御推断，或由不受控制的第三方执行删除。声明必须限于已被证明的边界。

## 20. 版本与治理

当前各标识符分别指向不同产物：

| 产物 | 当前标识符 | 状态与含义 |
| --- | --- | --- |
| 双语规范正文 | `standard-review-2026-11-14-r71` | 本工作草案的编辑修订号，不是线上协议版本 |
| 继承的设计契约 | `g2a-design-1` | 设计基线及测试夹具标签，不是已部署的协议发布版 |
| 观察配置规范候选方案 | `observations-draft-1` | 提议的语义，精确互操作契约尚未冻结 |
| HTTP/JSON 绑定候选方案 | `g2a-http-json` / `draft-1` | 提议的映射，协商表示仍待定义 |
| 旧参考 SDK | `0.1.0-dev`（Python 包：`0.1.0.dev0`） | 实验实现，不代表已实现或发布本草案的全部内容 |

英文主稿与中文译本的修改必须同步，包括修订号、日期、规范强度、标识符及修订历史条目。修订记录必须区分编辑性修正、语义澄清及新增或变更的要求。增加编辑修订号不免除兼容性审查，也不分配协议/配置规范版本。

发布的规范必须确定不可变的规范性产物、版本策略、注册操作/功能/扩展、变更控制、安全报告和兼容性测试。破坏性解释变化需要显式版本协商，而不是静默更新 SDK。实验性配置规范必须标明实验状态。已弃用能力必须仍能与已撤销权限区分。发布本文草案不等于分配许可证、转移所有权或发布生产版本；这些决策仍需分别处理。兼容性审查必须区分可安全忽略的可选新增项，与既有语义、必需字段、枚举含义或效果保障的变化。

不得仅因解析器接受新 JSON 就将后者标为兼容。临时兼容例外必须记录受影响版本/参与方、精确行为、安全约束及移除计划；宽容解析不得静默固化为永久协议语义。变更及例外必须保留可复现的兼容证据，不得弱化授权或默认不重发规则。

反复拒绝可以触发对游戏接入及处理行为的审查。次数本身不能证明恶意或歧视行为；审查必须考虑说明的原因、适用规则及可用证据。服务平台可以另行依据自身运营策略维护游戏黑名单，并拒绝为某游戏提供服务。此决定影响的是该平台服务，不是协议层或整个生态自动封禁，不得被描述为 G2A 符合性的普遍后果。平台特有的商业处置属于可互操作协议之外的机制。

> **背景说明：作者平台运营策略（不是互操作要求）。** 对于本标准作者的平台，已选择的运营策略是在列入该平台黑名单前先通知游戏开发者，并提供申诉或整改机会。这是独立的平台运营承诺，不是通用 G2A 通信协议要求，也不授予对其他服务商的处置权。该平台策略的精确时限及证据提交程序在此尚未确定。

**正式冻结前需要完成的工作**

正式冻结前，必须消除规范材料之间的所有差异，并确定一份不可变的发布清单：

- 清单列明规范性文档、Schema、操作定义和测试向量。
- 每个对象、操作、错误和生命周期规则必须有唯一的权威定义；清单固定其版本或内容摘要。
- 生成的 Schema、字段目录、SDK 类型和译文必须可追溯到该定义，不得形成相互冲突的独立定义。

遇到尚未解决的定义冲突，实现者不得自行选用一种解释而不说明。

抽象协议、用于实现互操作的传输绑定与可选配置规范必须保持可区分；支持一个绑定不意味着必须实现所有可能的传输方式。现有继承材料是审阅输入，不代表已经完成上述统一。

**如何校验 Schema**

发布清单必须固定 Schema 方言（所采用的语法及关键词规则）、必需词汇及引用的依赖项，并提供可本地解析的材料包，或等效且明确受控的注册表。校验时不得在未说明的情况下抓取任意远程 Schema。

不支持必需词汇时，必须使校验或协商失败。把未知关键词当作注解，不代表已经检查了该关键词的约束。通过 Schema 校验只说明相应格式检查已经完成，不证明授权、生命周期或游戏行为符合规范。

## 21. 符合性与验收

本节将前文要求整理为验证范围，不另设一套游戏行为规则。先声明实现承担哪些职责、使用哪些配置规范，再选择适用测试；最后用实际结果支持声明。下面的主题清单需要与所引用条款一起使用，不能只凭单项测试通过就宣布整套协议已经实现。

**声明、适用范围与证据。** 符合性声明针对协议版本、实现及其版本、角色集合、绑定、已协商配置规范与信任模式。测试适用于声明的角色和能力：如实声明未支持某项可选能力，不构成失败。不适用结果必须说明缺少的角色或未协商的能力，不得掩盖必需要求的失败。仅支持伴玩而不支持可选 NPC 或商店的实现仍然有效。

G2A 必须提供服务商可以自行运行并提交结果的公开符合性测试。自有与第三方实现必须适用相同公开条件；作者平台的人工审核不得成为必经门槛。证据必须标明被测实现、协议与测试套件修订、角色/配置规范、相关配置、结果及不支持项。每项断言必须映射到规范条款及适用角色/配置规范，并规定初始权限/状态、输入和消息、故障时序、允许的可观察结果、禁止效果、可观察判定依据及保留证据。实现或契约发生实质变化时，须重新评估受影响声明。

证据必须区分 Schema/契约校验、状态机/故障测试、独立实现互操作、真实引擎集成及用户验收。参考夹具、可运行测试集覆盖、实际执行端持久化及独立参与方证据必须分别标识。自测结果是被测行为的证据，不是独立认证、未来永久合规、运行时授权或 SDK 已实现本草案的证明。既有设计测试不证明新配置规范已实现。本草案不声称完整公开测试套件已经存在。

继承的 `g2a-conformance-statement-1` 按操作记录设计证据，不是本节完整的机器可校验报告格式。条款/角色/配置规范适用性、不适用结果及理由，以及上述证据类别区分，需要在发布前定义具有明确版本的报告格式或映射。实现不得静默向继承的 Schema 增加枚举值，也不得把通过其校验器当作满足这些新增报告要求的证明。

**按主题归并的必需覆盖。** 适用的符合性测试必须覆盖所引用条款的要求，包括以下归并后的场景。这些分组整合重叠场景，不替代规范行为，也不允许遗漏适用场景。

**准入、权限与拒绝（第 1、3、4、5、7、8、12、13、14、20 节）。** 公开与认证后发现；缩小同意范围；不支持必需扩展；可选能力缺失；按角色校验参数/结果；资源或接收范围不匹配、跨玩家查询、过期/撤销委托及通信身份验证失败。独立与自有服务商适用相同最低条件，排除任意厂商歧视与变相限制；区分技术准入与同意。拒绝须提供一致的标准化代码和具体安全说明，不泄露隐藏事实、凭据或未获授权数据。

反复拒绝不等于自动认定恶意或全生态封禁。

**版本与绑定兼容（第 2、7、17、18、19、20 节）。** 不支持必需词汇；受控/离线 Schema 依赖；未知可选与必需内容及枚举；协商失败不降级授权；传输/协议/效果结果区分；规范化边界，包括补充平面与 BMP 键排序、负零、重复键、无效 Unicode 和整数限制。测试恶意重定向、DNS 重绑定与明确获授权的本地端点，不歧视服务商。

**游戏角色与生命周期（第 4.1、8、13.1、13.2、14 节）。** 必需但可留空的伴玩槽位，以及无智能体服务时正常游玩；可选 NPC 槽位；开发者固定模式；多人每玩家一个伴玩与整局一个独立 NPC；整局两种模式不能同时活动的规则；并发准入/恢复，替换或切换模式前隔离旧绑定。测试允许的视角组合，不合并权限或同时启用禁止共存的角色；普通非 G2A NPC 不受影响。

测试自动加入、入局询问、拒绝后手动召唤、手动收起、有效准入、停止观察/自主行为、保留记忆及如实报告在途效果/剩余用量。

**在线状态与服务中断（第 14.1、14.2 节）。** 明确离开、静默故障、有界检测与执行，智能体心跳不能续期缺席玩家在线状态，取消未提交工作、在途提交竞态、停止游戏推理及真实剩余费用。保留独立在线玩家会话，禁止借用权限范围、离线继续、陈旧计划/积压重放及重新入局自动重启旧任务。NPC 持有用户离开时即使他人仍在也停止，不静默转移房主/计费。

测试无服务时入局与继续游戏、之后获授权加入、已声明的静止/本地接管、只恢复当前状态而不补录观察、伴玩继续前取得玩家决定，以及开发者定义的 NPC 恢复和真实脚本/智能体来源。

**观察、时序与限制（第 9、10、12、16、16.2 节）。** 仅推送、仅查询与双方式声明；不支持/被拒查询及权限范围/频率执行；事件/行动身份区分；原子快照、精确增量基线、合并采样不破坏依赖、代次废止及撤回后的迟到更新。测试过期/乱序观察、隐藏对象拒绝、接收范围过滤导致的序号缺口、过期游标和快照恢复；超大输入、队列溢出/重同步及不可静默丢失的控制结果；未校准时钟、墙钟跳变、读档/代次替换且不复用旧序列。

独立于模型频率测试合法行动变化、决策期限及并发裁定。覆盖紧凑游标身份映射、记录级混合可见性转换、不可披露的移除原因、合并状态的完整应用，以及离散事件丢失的明确缺口。对观察绑定的行动前置条件，测试陈旧代次、未校准时间、证据不可用、隐藏操作数与效果边界竞态。

**结构化与多模态能力（第 9.5、15.5 节）。** 依据必需结构化输入决策；缺少必需类别时拒绝或明确约定支持范围；如实声明能力。高级声明须证明理解游戏画面和声音两者，不仅是传输。测试可选媒体缺失、拒绝、格式不兼容、资源限制、玩家启用/关闭媒体、高级智能体仅结构化运行及不支持的媒体流。文字/语音来源、接收范围及溯源须与游戏音频感知分别测试。

**记忆使用与偏好（第 15.1、15.2、15.3、15.4、15.5、15.6 节）。** 开发者管理 NPC/引导者记忆保留或重置；玩家控制跨游戏检索、保留及跨周目/回档使用；独立剧透和话题偏好，玩家可覆盖建议默认值但不能覆盖受保护数据授权。保留旧分支来源而非声称当前世界事实。测试不自动向游戏披露或因回档强制删除；玩家性格/风格覆盖开发者建议，NPC 设定仍由开发者控制。

测试多人记忆保留和分享/不分享选择、强制接收范围/检索/转发权限及真实软偏好局限。正确施加软偏好不保证模型沉默或绝对防剧透；模型偏离这种偏好本身不构成访问控制符合性失败，而绕过权限检查仍是违规。

**记忆控制与迁移（第 15.7 节）。** 玩家查看、编辑、删除；自主整理及删除原始记录而不强加逐次批准；真实状态、来源及旧缓存不得复活。导出全部选定且仍保存的经历和归纳记忆，以及选定性格/风格/全局自主设置；不承诺恢复已删原文或模型表现相同。测试玩家主动选择目标/范围、更换服务商不默认披露、独立开放格式导入、元数据保留、不支持/转换的记录与设置、部分/损失回执，以及未知扩展安全往返保留而不执行。

区分编辑/派生观察、意图、事件/导入时间、冲突陈述、缺失证据和已删除来源标记。

**行动执行与恢复（第 10、11、16 节）。** 冲突身份重放；效果后超时；取消/撤权竞态、部分效果与真实状态/效果结果。断线后按原行动身份查询并检查来源/范围；区分接受/转发记录与执行端证据，区分未知、失败、进行中及成功。测试游戏或平台持久记录、声明的保留期限、持久去重及丢失/过期后的明确不确定性，不承诺永久历史或恰好一次。

未决行动默认不再次执行或自动重发；另行决定的相似新行动须考虑原效果及当前购买/高价值/不可逆权限。

**自主性、修正与叫停（第 16.1、16.2、16.2.1、16.7 节）。** 多步完成须有目标证据，不能以计划、估计或单步受理代替；授权内观察触发战斗；受阻/未知不能误报完成或扩大到未授权购买。测试全局自主等级保留、高等级结合上下文选择、低等级澄清、明确指令与推断目标区分、局部修正不要求重述无关指令，以及游戏权限不变。冒险帮助沿用同一等级，不另设保护他人开关，权限内遵从玩家明确坚持。

最新冲突指令停止未提交旧工作；游戏通知目标变化后重新判断并有条件撤回，不虚报取消。停止委托后续行动，已发技能/投射物按游戏规则处理；区分自主行为停止、游戏内执行及独立取消能力。

**多人互动与确认策略（第 16.3、16.3.1、16.5、16.6 节）。** 接收者控制主动搭话；游戏开放时允许伴玩对战，否则明确拒绝；获授权帮助/聊天/交易不一律逐次确认，保留他人同意、所有权与披露权。测试三种物品交易/赠送策略、开发者和玩家高价值标记合并、普通/高价值物品、必需确认前不提交转移、重要条件变化及策略/撤权竞态。

测试具体情境的不可逆声明和允许/询问/禁止，在各自主等级与转移策略独立并行，不改换标签绕过。测试确认超时无效果、沉默非同意、放弃提议、独立获授权工作、再次询问前重新检查及迟到回复不复活旧授权；不假定统一超时。这些策略不授权外部付款，也不替代商店权限。

**运行资源与 NPC 费用归属（第 16.2 节）。** 支持与请求配置区分、估计与实测用量、玩家选定的单位/范围/上限、延迟计量与在途结算、触顶暂停但游戏继续，且不新增计费工作或自主加额。测试可识别的 NPC 持有用户付费绑定、可归属用量，以及不隐式向其他玩家收费；所有权、角色与计费权限保持区分。

**可选商店（第 17.1 节）。** 结构化属性/价格、阶段相关上架与资格、发现后停售、变价告知和当前授权、推荐限频及持续拒绝后降低频率。测试无同意时仅推荐、预算内自主购买、提高/按范围重置计数须明确同意、运行上限独立、重要条件变化、重复请求、提交后超时、待交付/部分交付及不承诺未支持的退款。未决购买遵守不重发恢复规则；通用商店能力不成为平台支付或结算要求。

**外观与玩法状态（第 16.4、17.2 节）。** 游戏风格默认值、玩家自定义偏好、格式支持声明及真实所选/渲染状态；不支持时明确提示并标明默认回退，不静默声称成功。执行游戏定义的受伤/死亡/行动规则，区分服务/权限故障，不编造复活能力。局部死亡不改变跨游戏身份或保留的记忆；独立获授权的记忆编辑不是死亡效果。

**内容安全与隐私（第 4、13、15、19 节）。** 执行来源/接收范围及转发权限，包括投递前成员变更、私人重放和真实隐私回执。对智能体或组合决策实现，测试成对正常/注入内容、伪造批准、外传秘密请求及带指令记忆。分别报告合法任务完成与禁止效果；一律拒绝或仅成功游玩，都不足以证明可用、安全的符合性。

覆盖经认证来源转发的不可信内容、虚假的干净上下文声明、受保护规划输入及派生披露，以及存在普通外部内容时仍可正常使用的获授权自主购买，同时不允许这些内容改变授权。

**跨条款验收场景（第 10、15.2.1、16.6、17.1、18 节）。** 适用测试还必须覆盖：

- 目标死亡、阵营或治疗条件变化后拒绝过期行动，安全更新观察，并重新评估而非原样重试。
- 回档后剧情游标回退但加载代次不复用；祖先分支、未知来源及派生摘要的检索过滤；独立的记忆使用与剧透披露选择，以及允许旧经历时的来源标记。
- 确认因超时或条件变化失效；等待期间只继续独立获授权行为；冷却期内同目标/意图防重复、状态变化后重验，以及游戏端限流反馈。
- 权威预算账本的并发预留、待定支出与超额拒绝；真实货币、外部钱包及高价值账户资产不落入通用自主预算；商品自由文本不能改变玩家策略。
- 采用流式扩展时，推送与查询共享对象 Schema、连接认证与撤权、事件重复/背压及重同步；未协商流式扩展的最低 HTTP 绑定仍使用声明的轮询，不伪称已支持流式传输。

**已澄清的契约边界（第 3、5、6、9、10、11、16.7、17.1.1 节）。** 适用测试还必须覆盖：数据主体查询回执与实际处理数据的一方签发结果的区别；行动受理前确认及重放不重复消费确认；读取族的新鲜状态与租约重放的区别；范围撤销后独立获授权的结果读取；观察引用的视角/Schema 绑定；恢复完整状态与当前修订的一致性；目标关联的有效期及撤销；以及已声明的推荐限频策略对持续反对的响应。

这些是实现符合性的待执行验收要求，不表示本次文本修订已经实现或运行这些机制。

**智能体质量评估，不是准入排行榜。** 伴随符合性声明的质量评估必须标明游戏/环境构建、场景和初始状态夹具、可获得的模型/服务商修订、采样/工具配置、观察/行动限制、时间或 token 预算、终止条件及试验次数。无法获得的细节必须披露，不得编造。报告必须区分协议违规、任务失败、预算耗尽与基础设施故障，不得选择性隐瞒失败试验。比较声明应采用匹配条件，同时报告波动、延迟、资源与成功情况。

记忆评估应通过跨会话、时间推理、事实修正和缺失证据案例，将检索覆盖与回答准确性分开；这些结果不得替代迁移符合性。游戏分数或排行榜名次不得成为未公开、针对特定厂商的准入要求；准入仍依据公开的最低 G2A 契约。

## 22. 迁移与实现边界

| 现有设计或 SDK 概念 | 标准中的处理 |
| --- | --- |
| 现有 `game.context` category/content/provenance | 保留线上语义；通过配置规范协商类型化观察内容 |
| Descriptor/Requested/Scope 扩展 | 保留支持/提议/冻结批准的区分 |
| 活动扩展值 | 冻结的配置；绝不作为变化中的观察载荷使用 |
| 现有 ActionResult | 保留精确的状态/效果组合和未知结果核对 |
| Session active/closed 加 ready | 保留现有字段；不发明不兼容状态 |
| Session 事件序列 | 接收方过滤可能跳号；不作为观察修订号使用 |
| 恢复快照中的 Contexts | 新配置规范要求获授权的每条信息流的完整状态，而不是重放陈旧 delta |
| `core.session` 功能目录标签 | 与明确的角色×能力适用性保持一致 |
| 继承的 `core.events` 文本/事件契约 | 保留所声明基线的要求；面向玩家的聊天使用可选，不静默重定义该功能 |
| 旧操作目录的 HTTP 错误映射 | 为旧对端保留。候选 g2a-http-json/draft-1 仅在明确协商时，对领域错误使用 HTTP 200、对传输失败使用 4xx/5xx；这是提议的绑定变化，不是声称映射未变 |
| 继承的 `Binding.kind` | 不能编码新候选标识符/版本；须冻结显式协商表示，不复用不兼容的枚举值 |
| `g2a-conformance-statement-1` | 继承的操作级证据格式，不是第 21 节要求的完整条款/配置规范报告 |
| SDK `0.1.0-dev` | 待审查的实现，而不是本规范的发布版 |
| 新观察候选方案 | 需要契约/Schema、测试向量、实现和独立审查 |

接下来的标准化步骤是：冻结精确配置规范字段和摘要域；从全部操作契约生成完整英文字段目录；统一角色适用性元数据；完成绑定的协商/认证/状态/头部规则及带版本的符合性报告映射；增加观察和跨角色符合性向量；运行独立对端和真实游戏验证。只有完成这些步骤之后，才应考虑声明稳定发布。SDK 应适配经过审阅的标准，而不是隐含地定义标准。

## 23. 示例场景

**回合制伴玩。** 游戏声明可见棋盘和合法落子定义。玩家仅授权建议。智能体接收获准披露的快照，可以聊天，但不能执行落子。之后授予类型化落子行动需要批准；执行时游戏仍会检查当前轮到谁。

**主动战斗伴玩。** 玩家在游戏声明的能力范围内授权战斗协助。获准观察发现附近敌人后，伴玩选择目标与合法攻击，随战况调整计划，持续协助直至目标达成或停止条件满足，无需每次攻击前询问。玩家叫停后，伴玩不再安排后续攻击，核对执行中的工作，并报告已经生效的命中，而不是承诺将其撤销。

**战争迷雾中的战术智能体。** 切换队伍后视图发生变化。权威方废止旧可见性代次，丢弃对旧接收范围排队中的披露，并发送新的授权快照。即使延迟到达的旧 delta 修订号在数值上大于新流的修订号，也必须拒绝。

**行动超时。** 购买或移动请求到达游戏，其效果已提交，但响应丢失。智能体查询原行动和操作回执，不会以新 ID 再提交。如果权威方无法确定结果，就报告 `unknown` 并启动核对，而不是声称没有产生效果。

**断线的伴玩。** 关联玩家离开或声明的在线状态期限到期。新的游戏规划与行动停止；尚未提交的伴玩排队工作取消，在途效果被核对，但不承诺回滚或剩余 token 计费归零。其他在线玩家及普通游戏模拟可以继续。重连后按第 14.1 节确认当前在线状态与权限、核对结果并刷新状态，旧任务保持停止，等待玩家重新下令；不存在离线活动模式，也不会重放离线积压行动。

**玩家仍在线时 AI 服务中断。** 游戏按已声明的本地接管策略继续运行。服务恢复后，伴玩只接收当前获授权状态，并核对未决行动结果，不接收断线期间游戏过程的回放。玩家的自动加入偏好不能代替本次中断后是否继续的独立决定。

**观察修订轨迹（说明示例，不是可执行向量）。** 假设只有一条获授权信息流，实例、世界、视角及 Schema 绑定保持不变，当前可见性代次为 `view-9`。各行按顺序发生：

| 步骤 | 收到的更新 | 按第 9 节应作出的解释 |
| --- | --- | --- |
| 1 | `snapshot`，`view-9`，修订号 `27` | 原子替换该流的授权视图，当前修订号变为 `27` |
| 2 | `delta`，`view-9`，基线 `27`，修订号 `30` | 原子应用；单纯数值跳号不表示丢失，当前修订号变为 `30` |
| 3 | 步骤 2 的完全相同副本 | 不重复应用，也不使视图回退；当前修订号仍为 `30` |
| 4 | 恢复 `snapshot`，`view-9`，修订号 `30`，内容为相同的完整状态 | 重新建立完整的当前基线，不虚构新修订号 |
| 5 | `delta`，`view-9`，基线 `28`，修订号 `31` | 不应用：基线 `28` 不等于当前 `30`；继续该增量链前取得有效基线 |
| 6 | 获授权的 `view-9` 失效通知，随后收到 `snapshot`，`view-10`，修订号 `1` | 立即废止旧视图；新代次快照建立独立基线 |
| 7 | 迟到的 `delta`，`view-9`，基线 `30`，修订号 `99` | 拒绝已废止的上下文，不因修订号更大而接受 |
