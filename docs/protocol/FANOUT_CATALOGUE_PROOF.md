# 撤权动态目录、目标退休与同 authority 多会话

## 范围与命名

本合同延续 [跨 authority 撤权模型](CROSS_AUTHORITY_REVOKE_PROOF.md)，只增加候选内部
协调器的目录生命周期，不增加公开 G2A 操作或修改 permission.revoke payload。
目录是某个已认证玩家显式登记到该协调器的目标集合，不是发现所有厂商会话的全局目录。
player 来自可信适配器认证；目标仍通过可信端口及各自玩家凭据登记。

目标键继续包含完整 GameInstance、session_id、grant_id、Scope 摘要和玩家。共享 game、
instance 或伙伴 Principal 不合并不同 session 的授权、动作或结果读权。

## 目录版本与冻结选择

`catalogue(player=...)` 只向原 owner 返回活动目标绑定的深拷贝和 revision，不返回端口、
凭据或墓碑。目录 revision 初始为 0；新目标登记和新退休各增加 1。相同端口/凭据的
幂等登记不增加 revision；整数达到安全上限后拒绝需要递增的维护，不回绕。

`begin(..., catalogue_revision=...)` 必须显式提交看到的目录版本及明确目标/CAS 选集。
新操作要求该版本等于当前目录；过时版本返回 generation_conflict，不静默重读或扩大
选择。revision 严格为安全范围内的整数，不能以 bool/float/string 替代。

目录版本只证明在本协调器受理选择时没有遗漏已提交的目录变化，不证明远端权限或
CAS revision 没有变化。每个 authority 仍在接收时执行自身 CAS/权限检查。即使选择当前
目录中的全部目标，也不构成跨 Grant 的未来会话禁令或全局准入屏障。session 等会话局部
对象只影响冻结集合；[共享 Grant 组合](SHARED_GRANT_FANOUT_PROOF.md) 的 grant 选择明确
作用于整个已选授权域，session 只是路由入口，不能误称精确会话清单。

已有 operation_id 的 exact begin 重放先检查冻结目录版本、目标/CAS、对象类型和能力
选择是否一致，再返回原进度，不要求当前目录仍是旧版本。后来登记新目标不扩张旧任务；
改用当前目录版本或增加目标重放同一 operation_id 均为 id_conflict。新目标必须由新意图
明确选中。该候选内部方法签名已收紧；旧调用方不能省略版本自动降级，亦没有生产迁移承诺。

## 退出目录不是远端撤权

`retire_target(key, expected_catalogue_revision=..., player=...)` 表示 owner 明确将目标移出
未来选择。它不发送远端撤权、不关闭活动会话、不取消动作，返回 `state=retired` 而非
`revoked/closed`。想同时撤销远端权限，必须先明确执行相应 permission.revoke；仅从
目录退出不能作为远端权限已撤的证据。无引用的目标可以退出，即使其远端会话仍 active。

退休检查全部协调记录：只要任一记录对该目标仍为 pending 或 unknown，就返回 not_drained，
目录、记录和 checkpoint 均不改变。不能只检查某个操作、只检查已派发项，或以容量压力
为理由遗忘未决工作。接收方 CAS 冲突后仍可能保持 unknown；本配置没有强制遗忘或取消
未决意图的接口，也不保证所有故障必然收敛。

无未决引用后，退休在一个模型提交内保存完整身份墓碑和退休回执、移除活动端口/凭据
引用、增加目录 revision 并更新 checkpoint。接收方本身和全部历史协调记录不删除。
首次退休使用目录 CAS；同一 key 和原 expected_catalogue_revision 重试返回原回执，
不再次推进目录；更改该期待版本重放原退休为 id_conflict。

已确认的历史 begin/view/deliver 在退休后继续可用，不访问已释放端口，不重发远端请求。
完整绑定相同的旧目标不得再次登记，返回 request_gone；真正的新 epoch/session/grant/Scope
形成新 key，必须重新可信登记。旧操作始终指向旧身份，不能重定向到新代同名会话。

## 提交、恢复和容量

目录 revision、活动目标、退休墓碑、原退休回执及协调 records 全部纳入独立可信
checkpoint。退休前旧快照不能撤销退休，新登记前旧快照不能删除新目标；候选快照也
不能更改 revision、删墓碑或把退休目标重新放回活动集合。

退休 before_commit 故障不改变任何本地状态；after_commit 表示墓碑、引用释放和锚点
均已保存。两者均通过当前快照恢复后按原退休参数重试收敛。恢复只为活动目标接回原
可信端口/凭据，不为墓碑恢复端口。旧实例和不健康实例不能读取目录或执行退休。

当前上限为 16 个活动目标、64 个退休墓碑和 64 个协调操作。退休可释放活动槽位，但
不自动清除墓碑或操作记录，不声称无限长期运行。墓碑满额只拒绝新的退休，仍允许
活动目标的撤权、原退休回执重放和恢复；操作记录满额仍允许已受理操作派发/回看/重放、
无未决引用目标的退休和恢复。任一资源耗尽都不允许清空 unknown 来换取容量。

这些提交点仍是可信内存模型假设，不是数据库事务或任意 live-memory 篡改防护；真实
适配器还需独立恢复锚点、原子持久化与崩溃验证。目录维护不创建全局准入/执行屏障。

## 可执行验收

`tests/test_design_fanout_catalogue.py` 的 15 个方法覆盖：

- 迟到目录选择拒绝、新增目标不扩张旧意图、改变冻结版本/选集冲突；
- 无引用退出不产生远端撤权、全部 pending/unknown 引用阻止退出；
- 四类撤权退休后的历史重放不访问端口、新代同名目标与旧身份隔离；
- 两个退休提交故障窗口、旧/篡改快照拒绝、目录副本与 owner 隔离；
- revision 严格类型/耗尽、活动槽位释放、墓碑满额和操作满额时的控制可用性；
- begin/retire 的两种提交顺序、不健康/旧对象拒绝；
- 同 game/instance/epoch、不同 session/Grant 的两个明确 multi-session 会话，保留相同
  action ID 和局部请求 ID，实际经 SessionHarness 字节入口验证动作、结果读权和退休独立。

最后一项明确协商 multi-session 且 session_count=2，是两个已经获准的独立会话端口
组合；没有伪装成实现跨厂商全局 slot 分配，也未验证共享一个 Grant 的实例级广播撤销。

## 独立 JS/Python 链

候选 peer 在两种退休提交故障下各运行一条完整链：同 authority 两个 session → 明确
选中第一侧 → 登记新代同名目标 → 拒绝迟到选择但允许原意图重放 → pending/unknown
分别阻止退休 → 原字节重试确认 → 退休故障与恢复 → 旧快照/旧身份重新登记拒绝 →
退休后历史重放 → 独立撤第二侧结果读权 → 新意图明确撤新代目标。

JS 独立计算目标键、命名空间请求 ID 和规范字节；比对目录版本、远端状态、读权 revision
及全部事件序号，退休和旧回放不得造成额外远端效果。两条链新增 10 次客户端编码请求、
56 次夹具命令。整个候选 fanout 子报告现为 28 次请求、119 次夹具命令，仍与正式
38 操作/503 次 wire 分开计数。门禁要求两种故障、2 次迟到选择拒绝、4 次未决退休拒绝、
2 次退休后重放及明确多会话标记；缺失或旧 passed 总标记不能放行。

本节原链未覆盖多人目录、共享 Grant 广播、未知提交的跨端口独立查证、强制取消、墓碑/
操作账本长期回收及全局准入/执行屏障；这些仍是场景包剩余内容。

后续单 owner 场景已由 [独立候选装配](SHARED_GRANT_PROOF.md) 补齐，并新增
[按 owner 分组的传播与恢复链](SHARED_GRANT_FANOUT_PROOF.md)。原独立 Grant 配置保留，
共享配置另报候选证据；两者都不冒充跨 authority 原子撤销。
