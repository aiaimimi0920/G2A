# 多步执行、竞争和崩溃恢复的协议模型

承接 [单步时序验证](ACTION_ORDER_PROOF.md)。本轮完成上一轮列出的四项问题在
**纯内存设计模型层**的补充，不宣称完成生产实现或全部协议装配。

## 1. 模型和信任假设

[multistep_model.py](multistep_model.py) 使用单动作、1–8 个预定步骤、两个固定执行器。
一个 RLock 代表授权/领取/效果提交共同排序域。它不是数据库锁的替代实现，也不是 SDK。
动作记录与 world 效果事实表分开，防止用动作自身状态伪造外部效果证据。

ticket 绑定动作和执行器。领取竞争只有一个胜者；另一个 worker 即使拿到原 ticket，
也不能使用它执行。固定 worker 名是测试认证夹具，不是可对外使用的凭据。

本模型只处理每一步均为 committed 的成功效果、停止与不确定窗口。业务主动失败、
补偿步骤、复杂步骤依赖仍须额外定义，不推断取消就自动回滚。

## 2. 接受、撤权和领取

accept 与 revoke 在同一排序域中：

- revoke 先发生：accept 拒绝，不产生动作。
- accept 先发生：revoke 将尚未领取的动作置 cancelled/none。
- 授权撤销后不能通过重复 accept 恢复执行权。
- 同一动作重复领取不签发第二份 ticket；无 worker 抢占或自动接管。

已验证两个串行顺序，并以真实 Python 双线程竞争验证 accept/revoke 和两个 worker 的
claim。线程测试证明的是此内存模型的锁边界，不代表跨进程、分布式存储已验证。

## 3. 多步效果与取消

每个新步骤必须依次执行，只有前一步已取得事实才能进入下一步。每一步的 consumed 标记
在效果前记录；已有 journal 的相同步骤返回原事实而不重复执行。

| 世界事实 | 停止/最终汇总 |
| --- | --- |
| 尚未发生步骤，停止且无未决 claim | cancelled/none |
| 部分步骤有可信提交事实，其余未开始 | cancelled/partial |
| 所有计划步骤已成功，随后撤权 | succeeded/committed；撤权不能改写历史 |
| 有 consumed claim 但缺少对应事实 | unknown/undetermined，不允许推断 none |

停止之后，只允许查询/回放原事实和最终对账，不允许新步骤。
终态记录重复汇总得到原结果；恢复查询不能重新开启已终结动作。

## 4. 三个故障切点

| 切点 | 协议记录 | 处理 |
| --- | --- | --- |
| after_claim | 已消费执行资格，无可信效果事实 | unknown；即使测试 world 为空，也不重执行 |
| after_effect | 外部效果已有事实，动作 journal 尚未记入 | unknown；只能查原效果账本后补事实 |
| after_journal | 事实已写入动作 journal，回复丢失 | 重试原步骤，回放已记事实 |

恢复使用 recover_copy 复制假定持久记录并重建锁。它不模拟磁盘，也不包含真实断电。
reconcile 只查询已有 world 事实；查不到不是未执行证明。若未来引擎不能提供可查账本，
after_effect 的 unknown 可以长期无法消除，不能用相同或新请求 ID 重新运行来“修复”。

本模型持锁覆盖一次 step，不模拟一条外部调用仍在运行时撤权同时到达的情况。
实际 adapter 若释放排序锁，必须明确在途步骤的授权线性化点；不能把这里的串行结果
直接搬成跨服务无竞态声明。

## 5. 本轮证据

[test_design_multistep.py](../../tests/test_design_multistep.py) 新增 9 个测试方法：

- accept/revoke 两种顺序及双线程竞争。
- 两个执行器双线程竞争只签发一份 ticket，错误 worker 被拒绝。
- 第一步成功后撤权，第二步拒绝，结果保留 partial。
- 全部效果完成后撤权，可信事实仍能汇总 succeeded。
- 三个崩溃位置的快照恢复、不重复效果、未知结果与对账。
- step1/step2/stop/finish/reconcile 的 120 个有界排列。

累计统一验证为 105 个设计测试方法、42 条原模型重放通过。120 个排列和之前 720 个
单步调度是参数子例，不能和方法数相加成“端到端场景数量”。
回执：linshi/g2a-protocol-design-20261007/multistep-verification.json。

## 6. 剩余交付边界，不把部分闭环说成全部完成

| 范围 | 当前证据 |

| 上一轮四项动作问题 | 本文给出模型实现及本地测试；真实端口仍需兑现 |

| 动作原始字节到实际执行 | 尚未装配，现有模型是可信路由后的调用 |
| 事件消费端乱序/重复/缺口恢复 | 仍缺独立 reducer 的系统化验证 |
| 策略/扩展处理器、来源导入认证 | 仍为显式外部保证，未实现真实适配器 |
| 全操作互通、生产引擎、持久化与发布 | 未验证/未执行，不在本模型成果中结单 |

人工复核重点：取消保留 partial；已成功效果不因随后撤权改写；无可查事实的 unknown
允许长期存在；执行器不能自动接管已消费但不确定的步骤。这些默认值已实现且可测试。
