# 启动终态回执的有界回收与消费屏障

## 维护合同

launch.request 首次受理时冻结内部 gc_after = accepted_at + 协商的
receipt_retention_ms，并检查安全整数溢出。它是允许回收的最早时刻，不是新增
公开字段，也不是自动删除或自动失效期限；未清理的历史终态仍可按当前身份查询。
重试、效果查证和未知收敛不延长此时刻。

compact_launch_receipts 是可信维护入口，不是第 39 个 wire 操作。要求健康 authority
账本、严格整数预算 1..128（默认 64）。只清理达到 gc_after 的 done/failed 回执；
pending/unknown 无论多老都保留，以维持派发未知屏障。历史记录缺少 gc_after 时
不编造期限，不回收；这不是生产旧快照迁移。

每个被回收项必须仍有精确匹配原 request_id 的许可消费记录，缺失时事务拒绝，
不先删一部分再掩盖损坏。维护采用既有 before_commit/after_commit 故障语义，
可信时间维护先独立提交；自然到期关闭会话不是 GC 的删除副作用。

## 删除回执不等于恢复启动权

许可、原 request_id 消费事实、独立 Launcher entries/effects、进程绑定和退出墓碑
均不清理。即使回执已不存在，任何已消费的启动 request_id 都不能重新受理，返回
request_gone；换 payload/许可不恢复该 ID，换 ID 也不能绕过已消费许可或当前授权。
缺失记录的 operation.get 返回 permission_denied，不声明原请求未受理。

本操作不关闭或终止进程、不抹除原效果、不自动重启。会话按自身期限自然关闭后，
原进程仍可运行；回执 GC 后仍能用保留的精确绑定记录退出并执行原监视收敛。
未知启动在保留期后依旧可以通过独立握手查证原效果；只有已确定终态才成为候选。

## 验证与剩余边界

七个测试方法覆盖期限等号、重试不续期、旧 ID 与换 ID 拒绝、unknown 跨期限保留和
后续查证、自然闭会与存活进程分离、失败回执及部分/重复 GC、提交前后故障/假重启、
严格预算、损坏账本/消费屏障拒绝及旧记录无期限保守保留。

这是回执层的有限回收，不解决许可槽、独立效果、退出墓碑和 offer 的长期增长；
这些事实仍保留原容量上限，不能因此宣称支持无限次启动或全账本回收。
没有真实进程/磁盘删除。

## JS/Python 恢复场景

JS 客户端新增 24 次正式 wire 请求，共三条独立启动链。前两条在最早回收时刻之前
重试并查询历史终态，确认不能提前 GC；分别在回收 before_commit/after_commit
注入故障，假重启后核对记录存在与否，再重试维护。最终旧 operation.get 拒绝、
旧 launch.request 为 request_gone，许可消费、端口 entries/effects 和一次启动均保留。

第三条使用 unknown_after_effect：到达回收时刻后维护仍删除零条，查询依旧 pending；
独立握手验证原效果后查询转 done，再允许 GC。最终三条链各清理一条回执、各只启动
一次。报告必须包含两个提交窗口、pending_preserved、三条删除和三次启动的严格类型
子报告；缺失/畸形/计数不足或多启动不能由总 passed 掩盖。维护与握手仍是可信夹具，
不是公开协议授权。正式互通总计 481 次、38 项操作，候选 epoch profile 的 26 次另计。

这没有覆盖任意 GC/查询并发、多 authority、真实数据库恢复或全部未知端口结果。
