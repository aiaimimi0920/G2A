# 关闭会话的有界消息回执清理

本包增加可信内存维护端口 `SessionHarness.compact_closed_receipts`，不是公开 wire 操作，
不是后台服务或真实文件删除。38 个公开入口保持不变，也未实现全账本长期回收。

## 为什么不按 TTL 清理活跃会话

新增反例故意从活跃会话移除聊天去重记录，再提交同一 Envelope：模型实际生成第二条
聊天事件。因此，“没有回执”不能作为“此前未接受”的证据。本轮只允许关闭会话清理，
继续禁止活跃会话淘汰去重记录；满额仍拒绝新请求，不借清理扩大批准的 Scope。

这不是旧代码已提供不安全清理接口的证据：此前根本没有该维护端口。red 日志中的
AttributeError 是新增功能未实现的失败；主动移除内存记录的重复事件才是危险方案的反例。

## 前置条件与批次事务

- 会话必须 closed，Grant 必须 revoked。保留这两个终态作为禁止旧会话写入的依据，
  不能随消息回执一起清空、重新设为 active 或用旧 session_id 创建新实例。
- 使用受信 Nat 时钟；同一维护端口不允许时钟倒退，时间水位与清理同事务提交。
- 只有 `now > accepted_at + receipt_retention_ms` 才可删除；截止点本身仍保留。
- 动作原请求/取消回执还须 `now > read_until`，不能破坏承诺中的 operation.get 读取。
- 有 pending_sync 时拒绝维护，不替代未完成的结果同步；每批最多删除 64 条，按完整键
  确定顺序。当前账本本身有界，该限制是删除条数，不是独立扫描预算或长期公平性保证。
- 复用会话事务同步清理共享消息回执及动作回执副本。键包含会话、主体和业务 ID；游戏
  context 的同名 ID 不得删除 agent 的动作回执。提交前故障全部回滚，提交后丢回包可重试。

此端口不清理控制收据、poll nonce、确认记录、动作/结果、事件、世界效果、成员与权限、
准入记录或会话终态。它不是隐私删除接口，也不声称所有内存已释放。

## 清理后的结果与重试

同业务 ID、同 ID 改正文、新业务 ID 都必须先经过原写权检查；关闭与撤权保持，故不能
因为回执消失而产生第二次效果。即使调用使用旧时间值，已撤销的 Grant 也不恢复。
过期结果读取仍按原权限/保留期规则拒绝；拒绝不表示从未接受，不自动创建新动作或重试。
假账本复制恢复必须保留终态、清理水位及世界效果；不是实际持久数据库 crash-recovery 证明。
