# 现有 Relay 的动态代次轮换与有界旧回执

## 范围

`RotatingRelayHarness` 在显式启用 `g2a-relay-epoch-1` 的现有 Relay 上组合轮换，
沿用 register、call、pull、reply、revoke 五个正式操作及原认证规则。不增加公开
维护操作，不改变默认未启用 profile 的行为，也不把独立候选 binding 模型当成生产实现。

## 三个独立提交点

1. `seal_epoch`：校验当前代次、全部邮箱已关闭及归档容量后封存。新注册停止，
   原请求重试仍可读取其已提交事实。归档容量在游戏端切换之前预检。
2. `advance_game_epoch`：游戏端口独立锁定并前进恰好一个代次；旧命名空间不再
   接受派发。只清执行 journal 和旧关闭标记，不重置游戏业务状态、效果或内层权限。
3. `advance_relay_epoch`：确认游戏端已到目标代次后，把关闭邮箱归档并更新冻结
   扩展，清空当前配对索引，开放新代次注册。

各提交点支持提交前失败及提交后响应丢失。假账本重启可在间隙恢复，目标重试不
重复切换。封存后、Relay 提交前不能注册新邮箱。这是顺序编排，**不是跨 authority
原子事务**。维护入口是可信协调器的模型接口，不允许普通客户端自报代次完成迁移。

## 未知派发不能被清理绕过

游戏端记录派发标记时同时记录 unresolved；只有保存回复与 guard 后才移除。
提交中断、效果后响应未知等情况保留该记录。关闭 journal 退休、GC 及假重启均
不能忘记它；只要存在 unresolved，游戏端轮换返回 `outcome_unknown`。
后续已增加[未调用派发的可信收敛](RELAY_UNSTARTED_SETTLEMENT.md)，仅接受端口仍
持有的未调用见证；可能已进入游戏的未知派发仍持续阻断，不承诺无限可用性。

## 旧回执窗口与新同意

旧邮箱保留原冻结扩展，归档窗口固定为 Relay 切换提交时刻加 60000 ms；最多
8 个归档邮箱，同时当前代次仍最多 8 个邮箱。容量不足时必须等待到期并显式 GC，
不能提前丢弃未知知识换取容量。可信时间单调，窗口不会因重试延长。

旧请求必须重新通过当前有效的 enrolled 身份认证和原主体归属检查，使用原扩展
读取有限的无秘密注册/关闭事实。旧 mailbox token 仍撤销；旧配对证据不能在新
代次注册。新配对必须由可信端登记新同意及当前代次绑定，不从请求自动续权。

归档到期后返回 `request_gone`；有界 GC 后对象不再可授权，返回
`permission_denied`。这不等价于证明历史请求未执行。已排队且未派发的关闭请求
可保留 `not_accepted`，已派发请求仍保守返回 `unknown`，不因轮换杜撰成功结果。
GC 同步清除归档对应的注册回执和撤销凭据，且不恢复任何旧执行权限。

## 验证与局限

七个 Python 场景覆盖新同意、旧回执、已完成派发不重执行、未知派发在 journal GC
后仍阻断、三个提交点前后故障与重启、切换间隙拒绝、归档到期/GC 故障及容量预检。
JS/Python 通过原 canonical 字节入口新增 13 次正式请求，串联切换故障、重启重试、
旧回执、新配对及新代次完整五操作链；互通门禁必须检查 `relay_rotation` 子报告。

本轮不证明真实持久化、防旧快照回滚、进程间并发、真实认证/网络、第三方互通或
任意调度交错。独立候选模型的 checkpoint 假设不能自动转移到此装配。旧归档也不
是所有 operation.get、控制回执及业务结果的统一长期存储；多人公平性仍待验。
