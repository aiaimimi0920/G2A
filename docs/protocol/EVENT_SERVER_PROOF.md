# 事件服务、权限重验与一致快照

后继增量：[统一会话事务](UNIFIED_SESSION_PROOF.md) 已将动作提交接入同一 authority，
补五个控制入口及有限跨语言对照。本文保留当时 169 方法的证据边界，不把历史回执改写
为当前全操作验证；最新剩余项见 [范围表](SESSION_OPERATION_COVERAGE.md)。

接续 [事件消费与恢复](EVENT_RECOVERY_PROOF.md)，本增量将服务端事件账本、当前业务视图、
消息收据、poll nonce 和恢复快照放进同一个单进程内存锁域。它是协议装配模型，不是网络
服务或持久数据库，也不等于所有生产者都已与动作执行模型共享事务。

## 1. 实际装配的入口

[event_server.py](event_server.py) 复用 ChatHarness 及来源/成员检查，支持以下请求字节：

| 入口 | 同事务行为 |
| --- | --- |
| chat.send | 复用原接受链：收据、冻结受众/来源修订、事件 outbox 和新消息续租 |
| context.publish | 核验 GameAuthority、开放类别、共享经历来源；更新当前情境、收据和事件，不续伙伴租约 |
| session.events | 当前控制凭据、cursor、扫描限额、当前投递权限、poll nonce 和新鲜成功轮询续租 |
| session.snapshot | 同一切点读取无秘密会话、cursor、可见情境/动作/定义/成员，不续租 |

另有内部 record_verified_action_result 端口：接受已经验证的动作事实及**动作原先冻结的
origin_members**，在本事件模型事务中一起更新动作可见结果、状态通知和生产去重记录。
它不接受 executor 的线上自报，不验证世界效果，也未与 ActionHarness.commit_result
合为同一存储事务；这条跨模型接缝仍是明确未完成项。

本轮没有新增公开 operation，没有更改旧 SDK；服务端目前产生 chat.message、game.context
和 action.state 三类事件。其余五类核心事件的生产操作尚未接入，不能用上一轮八类消费
通过宣称八类生产事务都已完成。

## 2. 原子提交和快照切点

所有对外入口持有同一个 RLock。事务内对状态副本执行验证和修改，成功回复完成 schema
检查及编码之后才向其他持锁调用暴露；提交前异常还原原状态，提交后丢回复保留原结果。
来源撤销、成员代次变更、结果读权撤销和日志裁剪端口也使用该锁。

snapshot 中的 session.sequence、cursor.sequence 和各业务集合在同一次临界区读取。
测试不只分别断言它们合法，而是实际使用发布/读取两个线程竞争，要求只出现：

```text
cursor=1 + context=old
或者
cursor=2 + context=new
```

禁止 cursor 已越过新事件，情境却仍停在旧值；也禁止相反的混合切点。

这些操作的单进程原子可见性不是磁盘 crash recovery 或多进程事务保证。世界效果仍在
自己的可信端口，不能由复制 Python 字典推导出外部副作用原子性。

## 3. 重复 poll 不缓存重放明文

成功 poll 的 nonce 记录只保存完整请求摘要、原扫描终点、原 high_watermark 和原租约。
再次收到同 nonce：先重新认证，拒绝改 cursor/page_size/extensions 的内容冲突；然后只
在原扫描窗口重新过滤，不混入后来的事件、不再次续租。

每次投递，包括重复 poll 和 snapshot，重新检查：

- 冻结受众与当前成员 incarnation 相同；退出再加入不恢复旧内容资格。
- 来源仍有效、完整声明不变、revision 匹配且未过期；来源包括所有批准的明文观察者。
- 动作结果读权未撤销且 query_until 未到期。

game.context 现在也使用来源权威检查，只允许其显式 provenance 为 shared_experience；
请求方不能凭 provenance 为自己生成来源授权。空 provenance 仍不证明自然语言没有泄密。

动作通知不能按收到通知时的成员表重新冻结。首次结果很晚到达时也必须传入原始受众代次；
后续修订不得换成新代次。即使已没有当前接收者，事实仍可记录，投递结果为空，不能伪造
“记录失败所以世界没有效果”。origin_members 的真实性仍由动作账本端口保证。

## 4. 历史缺口、限额与恢复

扫描预算计入不可见事件，避免大量隐藏事件造成无界扫描。权限过滤的间隔/空页按最后
扫描位置推进 cursor，不按最后可见事件推进；达到可见 page_size 就停止，不跨过漏返项。

日志保留端口 compact_through 只裁剪模型内存事件并推进 event_floor，不删除文件，也不
删除仍需拒重的消息收据。旧 cursor 或重复 poll 的原窗口被裁剪后，返回新鲜、已过滤的
history_gap：快照、next_cursor 和 unresolved_actions 同一切点，错误不续租。
回包实际交给 BusinessConsumer.recover_reply 恢复，不仅检查服务器内部字典。

固定上限：64 条待保留事件，消息收据/poll 记录/结果版本去重各 256 条，扫描预算不超过
256。满额拒绝新写入，不淘汰尚可重试记录；已有消息重试和快照仍可用。当前情境/动作
视图与日志保留分开，仍按当前来源/结果权限过滤；这不是隐私删除或历史全量导出实现。

## 5. 证据和边界

新增 [test_design_event_server.py](../../tests/test_design_event_server.py) 的 18 个方法，覆盖
四个字节入口、生产/读取/消费闭环、提交前后故障、编码失败、重试不续租、重试权限重验、
来源/成员/结果期限、裁剪后恢复、日志背压和原始动作受众。包含两组各 12 次真实双线程
竞争；这些次数不与测试方法数相加，也不是任意调度的穷尽证明。

撤销/poll 竞争允许两种结果：poll 先线性化时可能得到一次旧内容；撤销先线性化则为空。
两者结束后的新请求和重复请求必须为空。**已编码/已发送的旧回复仍可能在撤销后到达**；
本模型不把“之后重新读取不再披露”夸大为可以收回在途或已收到的明文。

统一检查：169 个设计方法通过，0 失败/错误/跳过；42 条原模型重放通过。
回执：`linshi/g2a-protocol-design-20261007/event-server-verification.json`。
