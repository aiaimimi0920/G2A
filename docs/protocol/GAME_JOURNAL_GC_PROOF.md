# 已关闭游戏 journal 的有界槽位回收

## 前置安全条件

独立游戏端口的 `closed_mailboxes` 是永久拒绝屏障：dispatch 和 response_guard
在读取 claim journal 前检查它。只有该屏障已经成功提交的 mailbox，其逐 claim
记录才可删除；Relay 对象关闭本身不足以授权游戏端口回收。

可信维护方法 `compact_retired_journal(maximum=128)` 不增加 wire 操作，不接受
调用者自报的 eligible mailbox 清单，仅按端口自己已提交的屏障选择记录。
maximum 必须是 1..128 的整数，拒绝 bool。端口健康检查和互斥锁仍适用。

每批从最多 1024 条 journal 中选取最多 maximum 条受屏障覆盖的记录，构造新表后
一次替换；闭合 mailbox 屏障、Relay 原请求回执、游戏业务结果与认证表全部保持。
未关闭 mailbox 的 journal 不可被此方法删除，原结果重放与防重执行标记继续有效。

## 故障与重试语义

提交前故障保留原表；提交后丢响应时，调用方可以继续发起下一批维护。这里没有
业务请求 ID 或累计计数回执，因此重试可能清理下一批，并不承诺复现上一批 removed。
`removed` 仅为本次调用实际删除数，`remaining` 仅为此提交点仍可清理数，不包含活动记录。
最终无可回收记录时返回两个零。维护副作用始终限于已被屏障保护的记录。

完整假账本重启同时保留屏障和回收后的表。即使旧 claim 键已经不存在，仍先命中
mailbox 屏障而拒绝，不能按“查不到记录”重新执行。Relay 的 claimed unknown
不因游戏 journal 清空而降级；业务结果仍须在原业务权限下查询。

## 容量收益与限制

回收释放游戏端口 1024 条 journal 容量中的槽位，可供其他未关闭邮箱继续执行。
身份屏障、Relay mailbox 身份及已消费 pairing 标记没有释放；仍不能无限重配对。
这不是基于时间猜测的 TTL 删除，也不是活跃账本回收或永久屏障的回收。
身份代次与持久唯一 ID 方案仍需独立设计，不能把本方法用于删除屏障本身。

## 本地证据

新增七个 Python 场景：删除最后一条后旧 claim 仍拒绝、仅 Relay 关闭时不回收、
活动邮箱原回复仍可重放、有界多批与提交前后故障、输入边界和不健康端口、重启后
unknown 保留，以及 1024 条容量耗尽后释放一条槽位使另一邮箱成功派发。
容量场景明确使用合成占位记录，不宣称执行了 1024 次真实业务。

JS/Python 互通加入清理前后故障与假重启后的空批次检查，随后继续验证原撤销回执、
queued/claimed 知识分类及游戏业务结果读取。不是独立厂商互通或真实数据库证明。
