# 外部协议研究与 G2A 设计决策

研究日期：2026-10-07。使用官方公开规范在线核实，不以 SDK 示例或印象代替标准。
A2A 的 latest 页面是可变来源，本次页面展示 v1.0 导航；不将其标为永久固定版本，
也不声称已经审查全部 A2A 章节。以下区分来源事实、G2A 推导、已实现检查与待证假设。

## 1. 来源与边界

| 来源 | 本次核实的要点 |
| --- | --- |
| [A2A 规范 §3.3、§4.6](https://a2a-protocol.org/latest/specification/) | 发送消息的幂等性是 MAY；必需扩展有明确拒绝语义；不自动退回另一扩展版本 |
| [A2A 扩展设计](https://a2a-protocol.org/latest/topics/extensions/) | 支持声明、请求启用和响应确认不同；扩展定义需描述结构、行为和依赖 |
| [A2A Task 生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/) | Message 与 Task 区分；contextId 聚合交互；input-required/auth-required 是中断状态 |
| [MCP 授权，2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) | 令牌必须面向实际资源服务器，禁止把上游令牌当下游通用授权 |
| [MCP 传输，2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) | 断流不等于取消，恢复流是独立机制；本地 HTTP 也要考虑 Origin 与 DNS rebinding |
| [OAuth RAR，RFC 9396 §7](https://www.rfc-editor.org/rfc/rfc9396.html#section-7) | 实际授权细节与请求分开；某些授权类型允许有定义的补充信息，不能泛化成任意增权 |
| [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#source) | 事件标识以 source 与 id 共同确定；其事件上下文不自动成为 G2A 权限证明 |

本表是有限摘录的中文概括，不复制规范正文。下文是基于 G2A 游戏效果与玩家授权约束的
自主设计分析，不声称外部标准强制 G2A 采用这些选择。

## 2. 协议定位：借鉴机制，不把 G2A 改名为 A2A

G2A 的主问题是玩家授权下，伙伴怎样观察、发言、请求游戏效果，并在撤权、断线、换设备后
仍保持可解释的权限和结果。它不是通用代理委派，也不是一份工具调用清单。

建议分层保持：身份与安全绑定 → 会话与不可变授权 → 消息/动作账本 → 可选资源/呈现。
A2A 可作为未来代理侧互通适配层；MCP 可作为某个已授权执行器的工具适配层。
二者都不能绕过 G2A 的 Grant、WorldGate、控制代次和成员代次。

不立即实现桥接，也不增加第二套核心任务 ID。先要求桥接设计证明以下映射不丢语义：

| 对象/行为 | G2A 的决策 | 若直接照搬的风险 |
| --- | --- | --- |
| 对话 context | 仅关联数据；不凭相同 context 恢复写权 | 将会话关联 ID 当作凭据 |
| 长任务 | action 绑定固定参数、批准定义及执行凭证 | 把一次高层 Task 当作无限次游戏操作授权 |
| 补充输入 | 改变动作参数需新请求和必要的新确认 | 用多轮回复修改已批准动作而保留原摘要 |
| 等待授权 | action.confirm 在执行前独立完成 | LLM 的一句“用户同意”冒充玩家确认 |
| 取消 | 请求停止与已发生效果分别报告 | 将 canceled 映射成 effect=none |
| 结果未知 | 保留 unknown/undetermined；仅根据效果证据收敛 | 将传输失败转换为可安全重做 |
| 增量产物 | 进度、部分内容和最终效果证据分开 | 把一次流结束当作世界操作已完成 |

结论：G2A 不应弱化现有去重保证来追随更通用的协议，也不应为“像 A2A”而给
不可逆游戏动作增加可任意回到工作态的流程。

## 3. 研究促成的已落地选择：扩展必须穿过三道检查

1. **支持**：本地确实实现该 name 与精确 version，不是仅在描述里列出名称。
2. **批准**：来自可信冻结 Scope 的选择，不从消息自报内容生成授权。
3. **本次启用**：请求显式携带配置；通过检查的 activated 集合才交给扩展处理器。

本次增加 `contract_checks.validate_active_request`，装配严格请求校验与活动扩展检查。
当前采用窄规则：扩展 value 是 Scope 冻结配置，必须逐 JSON 类型精确一致，不是任意
逐消息业务参数。若将来需要动态扩展载荷，必须另行定义载荷 schema、权限缩减规则、
摘要位置和失败语义，不能悄悄把 value 改作动态输入。

| 输入情况 | 结果 |
| --- | --- |
| 请求带未批准或本地不支持的 required 扩展 | feature_unsupported |
| 已批准 required 扩展缺失，或本地处理器失去支持 | feature_unsupported |
| 扩展名已批准，但版本/value/required 被改写 | approval_stale，不自动降级 |
| 可选扩展未批准或不支持 | 不启用；原始内容保留并参与请求摘要 |
| 批准、支持、请求三者精确一致 | 返回独立 activated 快照；仍须执行扩展自身验证 |

`true` 与 `1` 不能利用 Python 相等规则蒙混，比较采用规范 JSON 字节。
该函数不是认证入口、不执行插件、不建立事务，也不证明扩展实现遵守语义。
Policy.extensions 与 Scope.extensions 是不同批准位置，不能混合；策略处理器的运行验证
仍待装配，不用本次消息扩展检查冒充策略已经执行。

### 3.1 双层扩展与去重摘要

已确认的结构缺口：数据请求外层与 Envelope 都有 extensions，而 message 摘要只覆盖
Envelope。外层扩展若改变业务，改变它不会改变相同 message ID 的摘要。

本版明确唯一位置：chat.send/action.request/action.cancel/context.publish/player_chat.forward
外层 extensions 必须为 `{}`，扩展只在其 Envelope 中；此限制已进入生成 schema，
包括 RelayInnerRequest。控制请求的外层扩展仍属于 control 摘要。
这是工作草案收紧，不迁移旧 SDK，也不声称与 A2A 的扩展 Header 线格式兼容。

### 3.2 扩展故障不能阻止止损

session.close、permission.revoke、action.cancel、presentation.release、relay.revoke 的
**空扩展核心请求**不要求仍有可用扩展处理器；仍执行原身份、归属、代次及事务检查。
显式携带扩展时不能暗中忽略 required 语义：应正常校验，失败后可选择发送无扩展核心请求。
这不是给未授权主体的后门，而是防止可选组件失效使用户无法撤权。取消也不承诺回滚效果。

## 4. 授权研究：批准对象不是一份能力广告

G2A 保留 requested、approved、current 三个不同视角。可执行集合由冻结批准与当前
能力交集决定；发现描述和缓存命中都不授予执行权。后续 adapter 需固定：

- token 接收者必须绑定实际服务/实例，而非仅检查 issuer/subject；Relay 外层认证
  与内层游戏权限分开，不因内层字段名相同就传递同一令牌。
- 批准后新增技能、修改 ActionDefinition 或放宽资源网络范围，都不能自动增权。
- 自动规则可以重新匹配一个申请，但不能将历史批准的效果范围扩展到新实例或新权限。
- grant 撤销、成员退出、控制代次失效须在效果提交边界重新检查；token 尚未过期不足以放行。

这些原则与现有设计相容；本次没有新增 OAuth 服务器、凭据格式或真实认证测试。
需要补的不是“再写一个 authenticate 函数”，而是认证输出的权威性、受众绑定和
权限缩减能否在同一提交路径中保持。

## 5. 事件、重放和可观测性研究

消息 ID、关联 ID、事件序号、操作结果 ID、传输请求 ID 必须各有职责。
G2A 当前每个会话的序号用于恢复；若导出 CloudEvents，可将实例 epoch 与会话编码成 source，
使用事件序号生成 id，但这是未来适配提案，不是当前 wire 改动。

必须验证的性质：

1. 断流不能产生隐式 cancel；重连不能隐式续权。租约到期仍走原关闭路径。
2. 同一事件重复送达不再次改变模型状态；不同会话相同序号不相互去重。
3. 历史缺口的快照先过滤权限；恢复 cursor 不授权读取过去本无权接收的事件。
4. 投递顺序与业务效果顺序分开；迟到 progress 不得覆盖更高 revision 的最终结果。
5. 不可恢复窗口返回明确 history_gap，而非假装得到完整历史。
6. 重试等待时间只决定何时查证，不证明请求未提交，也不能成为自动重做许可。

以上是 G2A 的验证目标，不因使用 SSE、HTTP 或 CloudEvents 就自然成立。

## 6. 研究后的剩余证据缺口与验收条件

| 优先级 | 问题 | 可接受的下一份证据 |
| --- | --- | --- |
| P0 | 来源声明能否伪造/扩张披露范围 | 权威来源表 + 跨受众负例 + 不存在/已撤销来源拒绝 |
| P0 | 多检查器之间是否遗漏或顺序错误 | 原始 bytes → 路由 → 授权 → 同事务写入 → 响应的假实现闭环 |
| P0 | 扩展处理器返回成功但改变核心效果语义 | 静态处理器 fixture、权限不可扩张断言；动态载荷另立规范 |
| P1 | 事件消费者乱序/重复/缺口收敛 | revision reducer 的有限序列枚举，不仅测生产者分页 |
| P1 | 重复操作与撤权并发 | accept/revoke/claim/effect/commit 的有界交错枚举，给出最短失败轨迹 |
| P1 | A2A 桥接会丢哪些信息 | 显式映射表和不能表达时的拒绝规则，特别是 unknown 与单次确认 |
| P2 | 本地绑定的真实入口安全 | Origin/目标地址/进程身份等适配器证据；不以当前纯内存检查结单 |

来源导入认证、发送前真实预检、其他操作装配及跨进程提交仍待证明，前两项仅部分收敛。

当前停止条件不是“又多了几份协议文档”。本轮闭环是外部依据、确定的双层摘要缺口、
