# 预登记身份的本机跨进程配对

状态：`0.1.0-dev` 实验控制面。复用 `PairingCoordinator` 的授权范围和 `GameHost` 的邀请语义，不另建 Mot 账号中心。这里只处理**已由可信启动器登记的本机游戏与伙伴进程**，不实现陌生软件自动信任、全机广播发现、供应商 OAuth 或云端授权。

## 三个进程及其权限

| 进程 | 持有什么 | 可以做什么 |
| --- | --- | --- |
| 游戏 | GameHost、管理员令牌、LocalPairingService | 开放情境和能力，执行游戏动作，验证邀请/会话 |
| 可信授权控制台 | 单独的 controller_token | 查看申请与完整条件、代表用户批准/拒绝、从游戏入口发起申请 |
| 伙伴 | 固定 agent_id/player_id 的登记令牌 | 获取已登记游戏描述、申请加入、查看自己的申请、批准后领取自己的邀请 |

控制台不能通过配对接口领取邀请，伙伴不能批准自己、查看其他伙伴申请或冒充别的玩家。登记令牌也不能直接用于 `POST /sessions`；游戏邀请和会话令牌仍是独立凭据。游戏管理员令牌不通过启动管道交给另外两个进程。

`LocalPairingService.enroll` 仅是可信启动器/安装器的本地 API，不提供网络注册入口。启动器须先核实它启动的程序及所属身份，再用匿名管道交付角色凭据和当前随机端口；不能只信任应用自报名称。示例固定启动仓库内的程序，不接受网络输入提供可执行文件、参数或 URI handler。

## 两条运行路径

**桌面伙伴已运行**：伙伴通过自己的登记凭据获取该 endpoint 的描述并创建申请；控制台展示固定的游戏描述、玩家/伙伴身份、行动、策略及形象条件。用户允许之后，伙伴领取短期邀请并直接进行原 HTTP join。

**游戏发起、伙伴未运行**：控制台选定已登记伙伴，生成等待批准的申请；批准之前不创建伙伴进程。明确允许后，可信启动器才启动固定程序并交付其登记令牌，伙伴再领取邀请、加入游戏。拒绝时不启动伙伴，也不创建游戏邀请或会话。

这证明了已知程序的真实跨进程启动顺序，不等于任意第三方应用的 OS 注册/唤起协议。当前新示例是交互式控制台，不是 MotGUI 集成，也不是新的桌面窗口视觉验收。

## 本机 HTTP 控制面

参考服务只监听 `127.0.0.1` 随机端口，沿用严格 JSON、禁止浏览器 Origin、单一 Authorization 和原有大小限制。原 `/sessions` 等数据接口保持不变。新权威定义见 schema 的 `pairing_*`；配对是接入控制面，不是 descriptor.bindings 中另一种消息传输。

| 方法/路径 | 角色 | 作用 |
| --- | --- | --- |
| `GET /pairing/discovery` | 已登记伙伴/控制台 | 返回当前预登记游戏描述；不是端口扫描 |
| `GET /pairing/requests` | 已登记伙伴/控制台 | 返回本人/全部申请摘要，不包含邀请 |
| `POST /pairing/requests` | 伙伴 | 以固定登记身份创建桌面申请 |
| `POST /pairing/game-request` | 控制台 | 对已登记伙伴发起游戏入口申请 |
| `GET /pairing/requests/{id}` | 对应伙伴/控制台 | 读取冻结的完整授权快照及当前状态 |
| `POST /pairing/requests/{id}/decision` | 控制台 | 提交 scope、allow、remember；伙伴调用拒绝 |
| `POST /pairing/requests/{id}/redeem` | 对应伙伴 | 提交当前 desktop_visible，批准后返回邀请及加入请求 |
| `POST /pairing/revoke-automatic` | 控制台 | 撤销本进程内自动加入许可，请求体 `{}` |

创建申请请求为 `{"nonce":"唯一ID","request":原join请求}`。同一伙伴、入口和 nonce 在申请有效期内返回原申请；改变内容返回 `id_conflict`，不会悄悄发起第二次授权。申请 ID 和 scope 都不是凭据。

批准请求为 `{"scope":"已展示的范围摘要","allow":true,"remember":false}`。scope 固定实例、endpoint、游戏描述、能力 revision 和加入条件；错误摘要或批准前/领取前条件变化返回 `approval_stale`。即使条件已变化，仍允许用户拒绝旧申请。批准后、正式 join 前的变化继续由绑定授权状态的游戏邀请拦截。

领取请求为 `{"desktop_visible":true}`。响应为 `{"endpoint":"…","invitation":"…","request":原加入请求}`，只给对应已认证伙伴；客户端拒绝把邀请转送到另一个 origin。重取同一申请返回同一邀请；改动已经采样的呈现状态返回 `redemption_conflict`。并发领取不会增加邀请或会话数量。

游戏宿主在邀请中固定完整加入请求，包括已批准的策略、形象、行动和领取时采样的桌面状态。伙伴拿到邀请后若改动任一字段再首次 join，返回 `approval_stale`，不创建会话也不消费邀请；原请求仍可加入和幂等重试。这不改变未指定请求快照的普通宿主邀请语义。

## 有效期与自动加入

- 同时最多 32 个登记伙伴、64 个申请；申请 60 秒后失效。过期申请及 nonce 在后续申请时回收，不淘汰仍有效的申请。
- 邀请最多 30 秒，并且**不能超过原申请的剩余有效期**。在第 59 秒领取，不能获得额外 30 秒加入时间。
- 自动加入许可复用原精确范围。任何条件变化需重新询问；许可只存于本次进程，不跨重启保存。
- 伙伴的已认证调用更新一个 5 秒在线提示。它不是 OS 进程存活证明，不可用来静默启动应用。未运行伙伴的游戏入口仍要求一次明确批准；启动器必须另外确认实际进程状态。
- 用户拒绝、申请过期、身份错误、越权请求不创建邀请。已领取邀请或已加入会话不是可无限撤回的 UI 状态；活动会话仍通过原退出/租约机制终止，不伪造世界回滚。
- 服务重启使用新的角色凭据与实例范围；本次实现没有持久化角色撤销、跨进程恢复或全局应用注册表。

## 运行

安装 Python 包与 JavaScript 依赖后，在仓库根目录执行：

```sh
python examples/process_pairing.py --entry game
python examples/process_pairing.py --entry desktop
python examples/process_pairing.py --entry game --agent python
```

默认伙伴是独立 Node 实现，也提供 Python 实现。控制台展示申请内容，输入“允许”才批准，其余输入均拒绝。`--entry game` 拒绝时不会启动伙伴程序。测试通过明确注入批准/拒绝决定覆盖四条路径，另验证中文交互输入；这不是人工鼠标点击验收。

Python SDK 为 `g2a.pairing_client.PairingClient`，JavaScript 为 `g2a-reference-client/pairing` 的 `PairingClient`。SDK 支持描述获取、创建/查看申请、角色受限的决定和领取；真正游戏会话仍由原 `Client` 处理。

## 安全与未完成边界

此参考不建立对恶意本机进程的强隔离：本机 HTTP 没有 TLS 服务端身份验证，不能抵御凭据读取、端口接管或已失陷启动器。调用方必须使用可信启动通道，进程退出后弃用 endpoint 和凭据；面对不可信本机软件，需要后续 OS 认证 IPC、进程身份校验或双向 TLS，而不是声称随机端口足够安全。

它不是公网服务，尚无生产线程池/速率限制、平台级自动发现、供应商身份认证、通用 OS 唤起、持久化授权或云端控制面。上一阶段 `outbound-poll` 继续独立保留，本机配对尚未被桥接为云端审批通道；不能据此关闭完整 R10–R13 验收。
