# G2A 协议设计完整性梳理

状态：第一轮设计审计，2026-10-07；**不是新版本规范，也不修改现有 wire 契约**。

审计基线：G2A `5290882cf1c6e28e469a3545e83e20e025b15cb5` 的仓库文档和相关 schema 定义。用户已确认当前重心是完整协议的理论研究与设计，不是扩展具体应用实现；必要验证以本地为主，GitHub Actions 不作为当前工作的前置门槛。本轮未重新核验外部标准，既有 A2A 介绍不作为本轮新增决策的依据。

## 1. 结论与使用方法

G2A 已有明确方向、部分实验语义和可用的参考证据，但尚不能称为设计完整。主要缺口不是缺一个 SDK 或演示，而是：最低符合范围、角色与信任模型、跨供应商身份授权、恢复语义、多连接协调、资源契约、兼容演进等仍缺少能让独立实现者得到一致结果的定义。

本文区分四类内容，不能互相替代：

| 类别 | 含义 | 当前效力 |
| --- | --- | --- |
| 已确认原则 | 用户方向和 DESIGN 已明确的协议目标 | 后续方案应遵守；变更需显式讨论 |
| 实验契约 | SPECIFICATION 与 schema 已定义的 `0.1.0-dev` 行为 | 约束当前实验版本，不等于稳定通用要求 |
| 实现限制 | 内存存储、随机回环端口、Tk、容量常量等选择 | 只描述参考实现，不自动升级为协议要求 |
| 待决策建议 | 本文提出的分层、问题拆分和候选方向 | 可用于研究，不得宣称已经采纳或实现 |

本文 D01–D16 是设计审计编号，不是 wire 字段或能力标识。旧 [R01–R17 台账](IMPLEMENTATION_PLAN.md) 保留实施证据，不以历史测试通过关闭设计缺口；也不因本次转向设计而撤销已完成的实现成果。

## 2. 已确认的协议原则

依据：[DESIGN](DESIGN.md) 的“已明确的方向”、[SPECIFICATION](SPECIFICATION.md) 第 1、4–7 节及 [SECURITY](../SECURITY.md)。

1. **独立性**：任何游戏或伙伴均可独立实现，不依赖 Mot 账号、模型、服务器、记忆服务或指定中心目录。
2. **伙伴范围**：面向玩家的固定伙伴，不是任意 NPC 接管协议；会话、玩家、伙伴、游戏身份不能混为一谈。
3. **双向主动性**：游戏可以主动给出情境，伙伴可以主动表达和请求行动，不要求先有用户问题。
4. **世界权威**：游戏决定信息开放和行动能力，协议授权不保证世界当前允许执行；伙伴不能通过形象或策略扩大权限。
5. **用户偏好与权限分离**：用户可覆盖陪伴偏好，但不能突破游戏权限或其他参与者的信息边界。
6. **接入与呈现**：支持伙伴发起与游戏发起入口、本地与云端方向；退出默认恢复接入前的呈现状态，而不抹除共同经历。
7. **形象优先级**：用户强制选择 > 游戏替代形象 > 伙伴默认形象；不兼容时明确反馈，不静默降级。
8. **受众与来源**：私聊和队伍交流保留同一伙伴身份；知道信息不等于可以向所有人披露，外部参考不能伪装为共同经历。
9. **内部实现自由**：不统一伙伴的模型、记忆数据库、人格、规划机制，也不负责每帧渲染。
10. **结果诚实**：取消不等于取消成功，超时不等于执行失败，退出不等于世界回滚，不虚构跨进程恰好一次保证。

这些原则并不自动决定匿名身份是否可用、自动授权保留多久、云端是否必须具备桌面形象或多设备如何协调；这些仍需设计。

## 3. 建议的文档分层与责任边界

以下是组织设计工作的建议，尚未据此迁移现有规范或 schema。

| 层次 | 应回答的问题 | 不应强加的实现 |
| --- | --- | --- |
| 语义核心 | 角色、能力、受众、会话、行动、错误、共同不变量 | HTTP 路径、Python 类、桌面控件 |
| 接入与信任 | 发现、身份验证、同意、授权范围、凭据、撤销、提供者选择 | 唯一账号中心、固定 OAuth 提供商 |
| 能力与可选配置 | 最低接入、呈现、形象资源、多会话、恢复等支持范围 | 每个端点必须实现全部功能 |
| 传输绑定 | 序列化、寻址、认证承载、分页/流、限制映射 | 绑定改变行动或隐私语义 |
| 一致性与演进 | 可观察要求、正反例、版本关系、扩展与弃用 | 必须使用本仓库 SDK 才能符合 |
| 非规范性参考 | SDK、示例、测试说明、部署建议及历史回执 | 把演示成功称为协议完整或第三方认证 |

游戏宿主、玩家、伙伴已在实验规范中定义；授权界面、启动器、提供者、桥接运营者只是现有流程出现的职责。后续需明确它们是独立角色、可合并职责还是绑定特有组件，不能先规定每个参与方都运行六个服务。

## 4. 当前约定不能直接普遍化的地方

| 项目 | 当前依据 | 通用设计要处理的问题 |
| --- | --- | --- |
| `protocol` 精确等于 `0.1.0-dev` | SPECIFICATION §2；schema `$defs.descriptor`、`join` | 版本协商、破坏性变化与安全降级尚未定义 |
| `join` 必填 `default_avatar`、`desktop_visible` | schema `$defs.join.required` | 无桌面/无形象的云端伙伴不能凭“填 false”就表示语义成立 |
| `session` 必填两个桌面可见性字段 | schema `$defs.session` | 呈现状态属于谁、无桌面如何表达、多设备如何恢复仍需定义 |
| `avatar.format` 支持 text/image/model，但只有 id/format/label | SPECIFICATION §4；schema `$defs.avatar` | 这是描述分类，不是已定义模型导入、格式兼容或资源交付 |
| 每伙伴在单宿主最多一个活动会话 | SPECIFICATION §3 | 并非已经决定跨游戏、跨设备、观战或多人场景的并发策略 |
| 只有 `http-poll` / `outbound-poll` | SPECIFICATION §2、§9–10 | 当前绑定集合不等于永久禁止其他传输；也未确定最低必选绑定 |
| 回环 HTTP、拒绝 Origin、禁止重定向/外部 schema 引用 | SPECIFICATION §2、§9 | 是实验绑定的安全措施，不是完整浏览器/公网授权方案 |
| 事件 256、收据 1024、会话 64 等上限 | SPECIFICATION §8 | 需区分协议硬上限、实现可声明限额、保留期及超限协商 |
| 申请 60 秒、邀请至多 30 秒、在线提示 5 秒 | LOCAL_PAIRING“有效期与自动加入” | 常量与不变量分开：邀请不超出批准有效期应与具体秒数分别讨论 |
| 可信启动器预登记、内存许可与令牌 | CONNECTIONS、LOCAL_PAIRING | 不能代替陌生应用认证、跨供应商委托和重启后的授权恢复 |
| 桥接能读取内层凭据和消息 | OUTBOUND“拓扑与信任” | 这种可信终点模型不自动适用于所有中继；E2EE 是另一个待决策范围 |

## 6. 需要优先澄清的规范张力

以下是文档间语义风险，不全部等于已证实的运行时 bug；本轮不修改 schema 或实现。

### F01：云端接入目标与强制桌面字段

DESIGN 明确允许云端伙伴，但 join/session schema 强制表达桌面可见性和形象。`false` 既可能表示有桌面但隐藏，也可能被误用为没有桌面，两者恢复语义不同。应由 D01/D09 决定呈现是不是最低必选能力，以及“不适用”的表达；不能由每个 SDK 私自猜测。

### F02：原则方向和实验成果的状态混用

DESIGN“尚未决定”笼统列出传输、消息格式等；SPEC 已有实验绑定和结构。应解释为“通用/稳定方案未决定，而非没有任何草案”。此外，实施台账的列名是“初始状态”，其后有大量历史检查点，不能把初始状态表直接当作当前完整性评级。

### F03：`unknown` 是知识不足还是不可改变的终态

SPEC §7 使用 `unknown` 表示不确定结果，并允许查询结果，但没有完整说明迟到的可信结果能否将 unknown 更新为 succeeded/failed、谁可以更新、会话关闭后如何认证查询。D05/D06 需区分世界事实与观察者的知识状态；不能简单把 unknown 当作可安全重试的 failed。

### F04：授权撤销有多个对象

CONNECTIONS 撤销自动加入许可、LOCAL_PAIRING 领取邀请、SPEC 撤能力/结束会话、OUTBOUND 撤邮箱是不同操作。尚缺统一撤销对象表：阻止未来加入不等于撤销已签发邀请，不等于终止会话，更不等于撤销已发生的世界效果。D03/D06 应逐项给出范围和生效点。

### F05：接收者可见性不等于路由者不可见

SPEC §6 和 OUTBOUND 已明确宿主/桥接能读取消息，正确保留了实验边界。后续“private”若被理解为连游戏方也不可见，就会与当前信任模型冲突。D07/D11/D12 必须定义隐私承诺的对象，不能把 TLS 或 recipients 字段称为端到端保密。

### F06：恢复原状态不能推广为多会话栈

SPEC §4 的单次恢复原则在一个会话时清楚；两个游戏并存、用户中途主动切换可见性或应用重启时，恢复旧快照可能覆盖更新的用户意图。D09/D10 需决定恢复条件、优先级和责任归属，而非盲目增加“进入时 push、退出时 pop”。

### F07：幂等范围与历史过期没有完整衔接

当前消息去重、cursor 过期、收据容量和内存重启边界分别有说明，但缺少“结果未知且原会话已关闭/宿主已重启”的完整恢复规则。D05/D13 应明确保留期、请求身份和查询权，不能以无限保存去重表作为隐含前提。

## 7. 优先决策队列（建议，未采纳）

每项正式决策记录至少包含问题、场景、候选方案、选择理由、安全/兼容影响、未覆盖范围、可验证例子和状态。下面不冻结任何新的字段名或规范关键字。

| 顺序 | 决策问题与候选方案 | 当前建议及代价 | 依赖与后续 |
| --- | --- | --- | --- |
| Q01 | 最低能力：全部必选；核心 + 可选能力；完全自由组合 | 倾向核心 + 明确可选能力，避免云端被桌面绑定；代价是需要能力依赖与协商失败矩阵 | 先处理 D01，影响所有后续定义 |
| Q02 | 身份信任：单一中心；按部署拓扑声明信任配置；任意自报 ID | 倾向拓扑化信任配置，不强制中心，也不把字符串 ID 当认证；代价是各配置需明确验证与互通范围 | D01 → D02 → D03/D11 |
| Q03 | 授权模型：加入即永久授权；范围绑定且可撤销；逐动作都询问 | 倾向范围绑定授权，必要时由能力要求单独确认；不强制每次行动弹窗，也不自动批准未来新增能力 | D02 → D03 → D06 |
| Q04 | 恢复模型：一律新会话；支持条件明确的恢复；默认跨崩溃恰好一次 | 倾向先定义共同未知结果语义，再声明有限恢复能力；不承诺不可实现的默认恰好一次 | D04/D06 → D05/D13 |
| Q05 | 桌面呈现：核心必填；可选能力；完全移出协议 | 倾向保留用户已确认的呈现协商方向，但能力可选性须由 Q01 明确；无桌面不伪造隐藏桌面 | D01 → D09 → D10 |
| Q06 | 扩展演进：精确版本永远拒绝；可协商版本与显式扩展；忽略全部未知字段 | 倾向后续通用版本采用可协商且可拒绝的扩展策略；当前 `0.1.0-dev` 严格校验保持不变 | D01/D04 → D14/D15 |

当前不要求用户一次性回答整个队列。先形成 Q01 的比较与决策草案，再按依赖顺序讨论。产品范围、稳定兼容承诺、对外信任/隐私承诺、许可和发布事项不能凭本文建议自动视为批准。

## 8. 场景覆盖与失败问题

以下是设计验收用的推演清单，不是本轮已执行测试。每个场景后续需提供角色/初始状态、交互顺序、成功路径、拒绝/超时路径、最终状态、允许的重试和禁止的副作用。

| 场景 | 必须回答的失败或边界问题 | 关联 |
| --- | --- | --- |
| S01 本地伙伴发现游戏并请求加入 | 发现对象伪造、用户拒绝、等待期间能力变化；不因发现而获权 | D02、D03 |
| S02 游戏发起并唤起尚未运行的本地伙伴 | 批准后启动失败、程序身份不匹配、邀请过期；加入许可与启动许可分开 | D02、D03、D05 |
| S03 游戏选择云端伙伴 | 提供者和伙伴身份如何绑定，用户拒绝/授权回调丢失，伙伴没有桌面窗口 | D01–D03、D09、D11 |
| S04 云端伙伴连接只允许出站的游戏 | 桥接失联/被撤销/不可信，控制面同意与传输配对分别由谁保证 | D02、D03、D11、D12 |
| S05 无动作或无形象的最小伙伴 | 是否仍符合核心，如何声明不支持，禁止为了通过校验虚构能力 | D01、D04、D09 |
| S06 动作获接收后发生撤权 | 执行领取前、效果产生前后分别如何判断；取消竞态与部分效果 | D03、D06 |
| S07 世界效果完成但结果回包丢失 | 原 ID 查询、迟到结果、会话关闭后查询、不得另起 ID 重复执行 | D05、D06、D13 |
| S08 宿主/伙伴重启且收到旧请求 | 如何区分实例，旧令牌/收据有效性、恢复或重新授权、未知效果 | D02、D05、D13 |
| S09 断线导致事件 cursor 过期 | 快照能恢复哪些状态、不能恢复哪些历史；隐私过滤、结果账本和去重分开 | D05、D07、D13 |
| S10 伙伴先私聊再队聊，队员中途离开 | 来源记忆不越受众边界；离队者是否接收排队消息、新成员能否读旧消息 | D07、D08、D12 |
| S11 同一伙伴连接两个游戏/设备 | 谁控制呈现，先退出者不能覆盖后进入者或用户后来的选择 | D09、D10 |
| S12 形象格式不兼容或资源不可信 | 保持既定优先级；拒绝/重新选择；外链、脚本、超大资源的信任责任 | D09、D12 |
| S13 旧端点遇到新版本/未知扩展 | 明确拒绝还是受限协商，不能静默忽略改变权限语义的字段 | D01、D04、D15 |
| S14 超限、慢消费者与主动消息突发 | 背压、限额告知、重试时机、失联与租约关系；不凭慢响应重复行动 | D04、D05、D13 |

## 9. 威胁与设计保证的边界

| 威胁/误用 | 已有原则或实验措施 | 待补的协议责任 |
| --- | --- | --- |
| 伪游戏、伪伙伴或混淆提供者身份 | 实验预登记、角色令牌分离 | D02/D03 定义验证根、标识作用域和授权受众 |
| 同意后偷换范围、重放邀请 | 实验快照绑定、短期邀请、幂等 | D03/D05 定义跨重启、轮换、撤销与时钟权威 |
| 玩家文本/游戏描述诱导越权 | SECURITY 区分数据与系统指令；游戏执行权威 | D06/D12 明确协议可执行限制和 Agent 内部遵从边界 |
| 私聊经可信桥接泄露或被伪造 | 当前明示宿主/桥接可读 | D07/D11/D12 决定各部署配置的隐私和端点认证承诺 |
| 恶意资源下载、执行或耗尽 | 当前不下载 avatar URL，有实验大小限制 | D09/D12/D13 定义将来资源能力的获取/完整性/沙箱责任，不由格式名暗示安全 |
| 错把取消、超时、会话关闭当回滚 | 实验已禁止虚构回滚 | D05/D06 定义竞态、持久记录和可验证后续查询 |

游戏拥有世界权威不代表游戏在隐私方面必然可信；来源字段不证明事实真实；传输加密不证明端点诚实。完整研究必须保留这些“不保证什么”，而非承诺防住所有恶意实现。

## 10. 研究顺序与完成标准

### 分阶段交付

1. **设计基线与最低符合性**：D01–D04，首先处理 Q01；输出角色/能力/信任词汇表及最低接入决策草案，不先创建新 SDK。
2. **状态与失败语义**：D05–D08、D13；输出状态转换表、权限检查时点、消息/受众规则、恢复与错误矩阵。
3. **可选能力与部署配置**：D09–D12；输出无桌面/多会话、资源、直连/桥接的边界和威胁模型，不先部署服务。
4. **规范整合与一致性**：D14–D16；输出符合性清单、规范/schema/绑定关系及兼容迁移草案。许可/发布决策单独保留。

安全审查贯穿全部阶段，不等到第 3 阶段才考虑；D12 是汇总审计责任。依赖项可以迭代，但不能先以实现选择代替未决的产品范围。

### 每个设计项的关闭门槛

- 明确属于核心、可选能力、绑定、实现建议还是不在范围内，并说明依赖。
- 给出角色、前置条件、正常/拒绝/超时/重试行为、状态变化和权限检查者。
- 给出至少一个成功例和关键负例；跨进程状态项还需覆盖掉线/重启/迟到结果。
- 对 schema、现有实验语义、相关文档做冲突检查，明确兼容影响。
- 对依赖的外部公开标准使用本轮核实的官方资料和固定版本；没有核验就标作待研究。
- 将未解决问题留在清单中；只有有理由的范围排除可关闭对应范围，不能静默删掉原目标。
- 经设计评审后标记状态；文档存在、本地测试通过、云端绿色或参考实现可运行均不能单独充当设计关闭证据。

### 当前停止边界

本轮完成的是完整性梳理，不是 Q01–Q06 的正式裁决，也不是 G2A 全部理论研究完成。没有修改 wire/schema、业务代码、引擎示例、GitHub Actions 或许可；没有运行完整程序测试、编译、部署、提交或推送。文档本地验证只检查链接、编号、R01–R17 覆盖和编码，不把它称为协议符合性测试。
